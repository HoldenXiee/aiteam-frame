## 0. 裁决

**阶段 1 的产物是一个扎实的「agent 实例管理器」，但还不是一个「集群设计框架」。**

三层结论，按可信度递减：

| 层 | 结论 | 证据强度 |
|---|---|---|
| **机制层** | **可靠。** 钩子、工具通道、事件、`abort`、`dispose`、子进程并发 —— 测下来基本没有坏的 | 强（多轮反复复现） |
| **配置层** | **不可靠而且静默。** 写错一个字符就能把功能关掉、把工具集清空、把审批门废掉，全程零信号 | 强（40+ 组拼写矩阵） |
| **归属层** | **不可靠而且静默。** `RunResult` 不跟调用绑定，重叠投递下会把别人的答案给你 —— **包括主力委派原语 `spawn_agent`** | 强（20/20 确定性 + 真模型复现） |
| **长跑状态层** | **不可靠而且静默。** 上下文超限会让分身**永久静默返回空**；预算对主要成本来源是盲的；回收不还配额 | 中强（真假 provider 双侧一致） |

一句话版本：

> **能搭集群，能跑得很花；但主力委派原语会说错话、配置写错不报错、长跑会静默死掉。**

**最关键的一条**（因为它直接否定「能不能用于真实工作」）：

> 用库**自己文档推荐**的「忙时 `send` 排队、永不抛错」写法，在一个真实的 10 人 4 层任务里，**两个组长的 `spawn_agent` 返回值都变成了另一条澄清消息的答复** —— 顶层主持人的第一轮证据基础整个是错的人的东西，最终交付物里**一个实测数字都没有**。全程零错误、零信号。跑 2 次，2 次都是。（`25-e2e-stress` E2/E4）

## 1. 能力：能做什么

### 1.1 异构配置 —— 13 个字段逐个实测有效

`MemberSpec` 的每个字段都用「假服务实际收到的请求」做 ground truth 验证过：

| 字段 | 实测行为 |
|---|---|
| `model` | 请求里的 model 正确；`provider/id:high` 后缀被正确消费 |
| `thinking` | 请求体里真的出现 `reasoning_effort`；`off` 时该字段消失（**但见 §2.1 的档位失真**） |
| `tools` | 白名单严格生效；`tools: []` → 模型看到 `[]` |
| `excludeTools` | 只给 exclude 不给 tools 时也能剔除 |
| `customTools` | 静态对象与工厂函数都生效 |
| `extensions` | 文件路径与内联工厂两种形式都生效 |
| `skills` | 名字 / 目录 / `SKILL.md` / Skill 对象四种写法都进 system |
| `role` | 走 `appendSystemPrompt`，保留 pi 默认提示词，追加在 `<tools>`（偏移 171）之后（偏移 2610） |
| `cwd` | 工具真的按它解析相对路径（实测读到 A 目录、读不到 B） |
| `agentDir` | 决定读哪份 `models.json` |
| `description` | 只进 `spawn_agent` 的描述，不污染 system |
| `onToolCall` | 返回 `{block:true}` 时工具确实未执行 |

三层优先级（`host.defaults` ← `members[x]` ← 顶层 spec）：未写的继承，写了则**浅合并覆盖**（数组整体替换，不拼接）。

### 1.2 拓扑规模（假 provider，零成本）

| 形状 | 实测 |
|---|---|
| 深链 | **1 → 256 层全部建成，零错误** |
| 宽扇出 | 一个父 200 个子：**260ms** |
| 并存 | **500 个分身 807ms、堆 +15.2MB、RSS 218MB** |
| 建 1 个分身 | 1.3–1.4ms |
| **DAG / 菱形（多父归属）** | **结构上不可能**（`parentId` 单值） |
| 数据流 DAG（一个产出喂多个消费者） | 可以，2 行代码 |

### 1.3 并发与吞吐

```
假 provider：N=1 跑 237ms  N=8 154ms  N=16 145ms  N=32 183ms   ← 库内零闸门，真并发
同一条 assistant 消息里 3 个兄弟工具：342ms ≈ 1 个（默认 executionMode=parallel，可配 sequential）
真模型 cap=2：N=8 → 8/8 零 429；N=16 → 16/16 零 429
单 agent 12 轮接力：12/12 正确，无退化（上下文 3.3k → 42.3k）
```

**真实规模下的并发结构**（`25-e2e-stress` 时间线）：**同刻真正在跑的 provider 请求 ≈ 4**（4 个叶子同时生成）；**父/叔伯层级全程只是 `await`，不是并发源**。

### 1.4 真模型协议遵守（全部大样本实测）

| 项 | 结果 | 95% CI 下界 |
|---|---|---|
| 用 `spawn_agent` 返回的 `agentId` 做后续 `send_message` | **44/44** | 70.1%（单个 9/9 变体） |
| 给一个**不存在的 id** | 9/9 照发→工具拒绝→**如实转述**，从不编造 | — |
| 花名册选人（`description` 区分度高，6 人 / 8 人） | **28/28** | 75.7% / 80.6% |
| 花名册选人（`description` **故意模糊**） | **4/8 严格、6/8 宽松** | 21.5% |
| 「只输出 JSON」（扁平三字段） | **20/20** 可 parse、字段全对、0 围栏 0 解说 | — |
| 被审批门拦下后 | **3/3 如实转述被拦、0/3 编造** | — |
| 护栏拒绝后父 agent | **2/2 如实转达**，明说「我不会替它编造一份」 | — |
| 主动 read 技能正文 | **9/9**（含 3 次描述模糊且任务不提技能） | — |

**给不存在 id 的处理是本框架最好的行为之一**：错误不会静默，模型不会编。

### 1.5 观测与用量

- 7 个归一化事件 + 3 个宿主事件全部可用
- **三方用量对账成立**：`host.usage = Σ agent.usage` 差额 **0**
- 两条恒等式在真模型原始返回上精确成立：`input+output+cacheRead+cacheWrite === totalTokens`、`Σcost 各分量 === cost.total`
- 假 provider 下**逐字节确定**（10/10 sha256 相同）

### 1.6 机制层可靠清单（**别把它当坏的**）

| 项 | 实测 |
|---|---|
| 审批门 | 拦截理由原样进上下文、`isError=true`；真模型 3/3 不编造 |
| 技能机制 | 真模型 9/9 主动读正文并遵守其中的硬性规范 |
| 工具通道 | 3 个模型 3/3 正确调用，入参**一字不差** |
| `abort()` | **不会搞坏 agent**：连续 4 次 abort → 无状态累积、无句柄泄漏、正常轮照跑 |
| `dispose()` | 跑着时调用会先 `abort`、等 settle、再真回收；`host.dispose()` 级联清干净 |
| `waitForIdle()` | 忙时 `send` 排队后**确实等到它跑完**，不提前返回 |
| 失败不连坐 | 3 个并行 spawn，一个炸、两个正常，9.0s 完成 |
| 封装不泄漏 | agent 改不了自己的配置（给 `spawn_agent` 多塞 `tools`/`model`/`cwd` 参数被完全忽略） |

## 2. 极限

### 2.1 结构上做不到

| # | 做不到 | 依据 |
|---|---|---|
| A1 | 分身同时归属两个父（真 DAG） | `parentId` 单值 |
| A2 | agent 工具层的横向/反向投递（兄弟、表兄弟、祖先） | 只准投后代 |
| A3 | **任何带超时的等待** | `waitForIdle()` 无参数；`spawn_agent` 里是无超时 `await child.prompt(task)` —— **与库自己的死锁规则③冲突** |
| A4 | 按成员的采样参数（temperature / top_p / seed） | `MemberSpec` 无此字段（**但 SDK 层可达，见 §6.3**） |
| A5 | 复现产出 | 真模型同输入 10/10 产出不同 |
| A6 | 从 agent 反查它的配置 | `ControlledAgent` 上没有 `spec` |
| A7 | 结构化输出的 schema 强制 | 无 `outputSchema` / `responseFormat` |
| A8 | 按分支/按成员分配预算 | `budgetTokens` 是宿主单一数字 |
| A9 | 运行时给护栏松绑 | `maxAgents` 是闭包常量，只增不减 |

**另有两处「能表达但要设计者自己写」**：拓扑导出（10 行）、子树级联回收（要自己遍历后代）。

### 2.2 静默失败 —— 最危险的一类（合并全部来源，约 40 条）

判据：**设计者的意图与运行结果不一致，而库不发出任何信号**。抛错会被发现；静默失败会在生产里以「行为奇怪」浮现且无法定位。

#### 2.2.1 结果归属层（**最重**）

| # | 现象 | 证据 |
|---|---|---|
| **S-1** | **`RunResult` 不跟调用绑定**。`collectRun()` 排干「共享池里所有未计过的 assistant 消息」并返回**最后一个**的文本 + 用量之和 → 重叠投递时结果**互换/串台** | 20/20 确定性，真模型 2/2 |
| **S-2** | **`spawn_agent` 是主要受害者**：子分身忙时被投一条消息，父拿到的就是那条的答复，原任务答案**整段消失** | 同上；真实 10 人任务里交付物因此**零实测数字** |
| S-3 | 串台时 **per-call `RunResult.usage` 也错**（18→36），而三方累计值仍正确 → **对账查不出** | 主 agent 复核 |
| S-4 | `send()` 排队 + 当前轮 `abort()` → 消息推迟到下一次 prompt，**那次 `prompt()` 返回这条旧消息的答复** | `21` E2-2 |
| S-5 | **空闲 `steer()` / `followUp()` 静默停放**，下次 `prompt()` 才被唤醒并**顶替那次 prompt 的返回** | 三个独立来源一致 |
| S-6 | settle 窗口内 `send` 返回 `{delivered:"queued"}` 但**队列没人排空**，消息不跑 | `20` E1b |
| S-7 | 3 个调用者同时投同一 agent → **全部读到最后一个的答案** | `20` E1f |
| S-8 | 队列积压 11 条 → 只播报 **1 次** `round_completed`（按轮计数少算 10/11） | `20` E3c |

**只有 `prompt`（链内）或 `send`+`waitForIdle` 或**自读 `session.messages`** 才能拿到正确结果。只 `send` 不等 = **0/8**。**

#### 2.2.2 配置层（**写错一个字符就静默失效**）

| # | 触发方式 | 现象 |
|---|---|---|
| S-9 | **`onToolCall` 键名大小写错**（`onToolcall` / `OnToolCall`） | **审批门完全不生效，agent 裸奔**（门被调用 0 次，工具真执行） |
| S-10 | `tools: ['Read']`（大小写）或 `'read'`（字符串） | **工具集塌成 `[]`**，连 system 里的 `<skills>` 段一起消失 |
| S-11 | `excludeTools` 空格 / 大小写写错 | 完全无效（与不写一样） |
| S-12 | `thinking` 非枚举值（`'High'` / `'none'` / `'低'` / `'ultra'`） | **静默回落**，与显式写合法值不可区分 |
| S-13 | 未知 / 拼错键名（`descriptoin` `tool` `excludeTool` `systemPrompt` `Roles`） | **6/6 全部静默忽略** |
| S-14 | `extensions` 路径不存在 / 语法错误 / 内联工厂抛错 | 构造成功，扩展静默不加载。**根因：原因就在 `loader.getExtensions().errors` 里，库只读 `.extensions`** |
| S-15 | `skills` 里写不存在的名字 | 抛错（好行为）；但传**字符串**而非数组 → 逐字符解析，报错说「找不到技能『m』」 |
| S-16 | `cwd` 指向一个普通文件 | 构造与 `prompt` 都成功；用 `bash` 时报 `bash.exe ENOENT`（**误导性根因**，看起来像 shell 没装） |
| S-17 | 两个同名 `customTool` | 后者静默覆盖前者；`customTool` 可冒充内置 `read` 并**真的顶掉它** |
| S-18 | 花名册为空时的 `spawn_agent` | `member` 退化成 `Type.Never` → 调用在**参数校验**阶段失败，`execute()` 里那两句有用的文案成为**死代码** |

**统一结论**：`MemberSpec` 里**只有 `tools` 是白名单**。`extensions`（加载）与 `skills`（注入）都**不受声明控制** —— 想「只暴露这一个」做不到，且零信号。

## 3. 诊断：三条主线

把 40 条静默失败归因，只有三个根因：

### 主线 1：`RunResult` 是一次「排干共享池」的副作用，不是一次调用的结果

`collectRun()` 的语义是「调用那一刻，共享消息池里所有还没被计过的 assistant 消息中**最后一个**的文本 + 它们的用量之和」。**只在同一 agent 上严格串行时才等于「本次运行」。**

后果链：重叠投递 → 归属错位 → `spawn_agent` 报错答案 → 交付物内容错。而且**三方累计用量同步正确**，所以既有的对账手段**永远查不出**。

**这一条是唯一「不补就没法做真实工作」的。**

### 主线 2：配置层没有校验，而且不是白名单

- 40+ 组拼写/类型错误的实测：**未知键 6/6 静默忽略**，`tools` 写错一字符就塌成空，`onToolCall` 写错一字母门就废
- `extensions`（加载）与 `skills`（注入）**不受声明控制**，只有 `tools` 是白名单
- 钥匙孔大小的错误 → 静默的全功能失效。TS 只对对象字面量有效；**成员花名册一旦来自 JSON / 数据库 / 变量，这条防线就不存在** —— 而「从配置生成成员」正是集群变大时最自然的做法

### 主线 3：长跑时的状态没有出口

- 超限 → 分身**永久静默返回空**，没有重置 / 丢历史 / 标废的 API
- 压缩 → 不可配置、不可见、不计入用量
- 预算 → 软约束、可绕过、耗尽后**只能摘掉整个 host**
- 配额 → 终身累计、不回收
- 回收 → 只回收单个分身，留孤儿、断链

三轮交叉验证纠出的错误（**说明「同一件事多测一遍」是必要的**）：

| 5 | 报告 §4.3：预算耗尽后「全宿主冻结」 | **框定不完整**：空闲路径确实被拦，但**忙时 `send`/`steer` 完全绕过** | `04-guards` + 主 agent |

## 5. 真实工作可用性：一个 10 人 4 层任务的实测

`25-e2e-stress` 搭了 10 个真异构成员（6 个不同模型、3 个不同 cwd、7 种不同工具集）、4 层、4 轮、真交付物落盘，用两种写法跑同一件事。

**拓扑**：

```
顶层主持人 host (L0)
  ├─ lead_cap   (L1) ─ sub_cap   (L2) ─┬─ src_reader  (L3, cwd=src/)
  │                                    └─ code_probe  (L3, customTool=probe_metrics)
  ├─ lead_limit (L1) ─ sub_limit (L2) ─┬─ audit_reader (L3)
  │                                    └─ doc_reader   (L3)
  ├─ reviewer   (L1)
  └─ writer     (L1, cwd=输出目录)
```

**A 写法（自然写法）vs B 写法（≈25 行安全纪律）**：

| | A | B |
|---|---|---|
| 轮次中追加澄清 | 直接 `send()` 给正忙的组长（**库文档推荐用法**） | 串行队列 + 先 `waitForIdle()` |
| 读回结果 | `lastResult` / `RunResult.text` | **游标切片**：投递前记 `session.messages.length`，只取新增的 assistant |
| **归属正确** | **0/2** | **2/2** |
| 交付物 | **零实测数字**（自述「未运行任何测试或基准命令」） | 带探针测出的真数字（**864 行 / 6 文件**） |
| 成本 | $0.0247 / 201.8s | $0.0289 / 337.8s（+67% 墙钟、+12.4% token） |

**三个判断题的答案**（附实测依据）：

**① 能支撑什么**：8–10 成员、4 层、4 轮、树形、同步委派，**实测跑通并落盘**；同刻真并发 ≈ 4 个 provider 请求；异构真实生效；一次 $0.025–0.03、3–6 分钟。**前提是必须自己写投递纪律。**

**② 不能支撑什么**：重叠投递下的结果归属 / 预算当闸门 / 回收后的拓扑一致性 / 失败的语义与配额回收 / 慢成员的等待边界 / 多跳信息保真 / 交付物可信性。

**③ 最必须补的三件**：
1. **`RunResult` 与「这一次调用」绑定** —— 唯一一条「不补就没法做真实工作」的
2. **资源层隔离** —— 配额随回收返还、预算变硬天花板且有出口、等待要有超时
3. **失败语义 + 拓扑一致性** —— 返回值带 `code`/`kind` 与稳定 `agentId`；`dispose` 要么是子树、要么留墓碑让 `isDescendant` 能穿透
