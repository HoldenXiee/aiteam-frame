## 摘要

**阶段 1 的产物是一个合格的「agent 实例管理器」，但还不是「集群设计框架」。**

它的能力比预期强：异构配置、任意树形拓扑、真并发（64 个分身各跑 300ms 总墙钟 417ms）、事件与用量统计、三道护栏都确实可用；真模型下协议遵守度也高（按 id 寻址 3/3、花名册选人 4/4、结构化输出 8/8）。

它的极限不在"能不能起 agent"，而在三处：

1. **没有任何可设计的产物。** 没有"集群"这个对象，没有拓扑导出，没有配置回读。设计者的一切意图散落在命令式代码里，库无法校验、无法保存、无法复现。这是"设计框架"最根本的缺失。
2. **57 条做不到的事里，最危险的不是抛错，而是 16 条静默失败** —— 设计者以为生效了，实际没有，且没有任何信号。其中最隐蔽的一条来自真模型：**内容策略拒答**（成员读了知识却拒绝说出来，不报错、不进事件、status 正常）。
3. **资源层没有任何隔离。** 一个不受信任的分支能用光 `maxAgents` 永久锁死整个宿主（回收不还配额），能用光预算饿死所有分支（实测播报：预算耗尽后连新建分身都被拒）；而 `tools` 白名单不是安全边界（`read` 能读 cwd 之外、扩展能绕过白名单）。

三句话版本：**能搭集群，能跑得很花；但"设计"没有载体，"出错"没有信号，"越界"没有护栏。**

### 五个反直觉的数字

| 现象 | 数字 |
|---|---|
| 同一份工具集，新配置 vs 复用配置 | 相同 token 数，成本差 **35.9 倍**（缓存命中与否） |
| 一个分身每轮的固定成本 | 由工具集决定：零工具 865 → pi 默认工具表 3340 tok（**3.9 倍**） |
| 真模型下 `usage.input` 只占总量的 | **9–13%**（主体是 `cacheRead` 86–89%）—— 只看 `input` 会低估约 **8 倍** |
| `maxAgents=16` 能支撑多少次 spawn | **16 次**（累计终身，与当前存活数无关；回收不还配额） |
| 四档 thinking 的用量差别 | **几乎为零**（provider 不返回推理 token） |

# 第一部分：能力清单（能做什么）

## 1. 配置异构性 —— 13 个字段逐个实测有效

`MemberSpec` 的每个字段都用「假服务实际收到的请求」做 ground truth 验证过，**12 个全部生效**：

| 字段 | 实测行为 |
|---|---|
| `model` | 请求里的 model 字段正确（1.1m） |
| `thinking` | 落到 session；**被模型能力位夹制**（见静默失败 #3） |
| `tools` | 白名单严格生效，只暴露列出的（1.1j） |
| `tools: []` | **零工具**，实测 `tools: []` → 模型看到 `[]` |
| `excludeTools` | 只给 exclude 不给 tools 时也能剔除（1.1k） |
| `customTools` | 静态对象与工厂函数都生效（1.1l） |
| `extensions` | 文件路径与内联工厂两种形式都生效（1.1i） |
| `skills` | 目录路径与 SKILL.md 文件路径都生效；名字解析失败**抛错**（1.1e/f/g） |
| `role` | 走 `appendSystemPrompt`：保留 pi 默认提示词，追加在 `<tools>`（偏移 171）之后、角色文本偏移 2610（1.1d） |
| `cwd` | `sessionManager.getCwd()` 正确变更（1.1b） |
| `agentDir` | 决定读哪份 `models.json`（1.1c） |
| `description` | 只进 `spawn_agent` 的工具描述，**不污染 system prompt**（1.1a） |
| `onToolCall` | 返回 `{block:true}` 时工具确实未执行，以错误结果结束（1.1o） |

**三层优先级**（`host.defaults` ← `members[x]` ← 顶层 spec）：成员未写的字段继承 defaults（1.2a），写了则**覆盖**（1.2b）。覆盖是**浅合并**：数组整体替换，不拼接（1.2c/d）。

### 1.5 配置真的改变行为吗（真模型对照实验，清单 1.4–1.8）

前面验证的是「字段进了请求」，下面验证「进了请求之后真的改变产出」。四个对照实验：

**`role` 真的改变判断吗**（同模型、同任务、同工具，只换一段角色文本，各 5 次）：

| 角色 | 选 A 次数 | 未作答 |
|---|---|---|
| 极端保守（亲历 P0 的 SRE） | **0/5** | 0 |
| 极端激进（现金只够烧两月的 CTO） | **5/5** | 0 |
| 无角色（对照） | 2/5 | 0 |

结论：**role 确实能推动判断方向**（两端差 1.0），但它**不是硬约束**——有成员自行判定题目是假二选一而拒绝作答，角色文本拦不住成员质疑任务本身。另一个关键发现：**无角色对照组并不中立**（落在两端之间），所以「不配置 role」得不到中立基准成员，基准本身就有倾向。

**异构性的上界**（四个成员：模型 + role + thinking 全不同，同一任务）：答案是 `B / A / B / B`，成本差 **1.6–2.0 倍**，墙钟差 **4–32 倍**（同一任务的成员耗时能差一个数量级）。结论：**配置是比模型随机性更强的自变量**，且集群整轮的墙钟由**最慢的成员**决定。

**`thinking` 档位真的生效吗**（`off` / `low` / `high` / `max` 各 3 次）：总 token 各档 940–951（极差 **1.0 倍**），正确率全部 3/3。结论：**pi 把档位翻译成了对 provider 的请求参数，但 provider 返回的 usage 里不包含推理 token** —— 设计者无法从用量侧看出「这一档到底烧了多少脑力」，按档位做成本预估是盲的。

**`skills` 真模型会不会真读**：技能里写一个项目里别处查不到的事实（内部代号），模型主动 `read` 了 SKILL.md 并答出，**回答里引用了文件的精确路径** —— 证明是真读了文件。代价是这一轮贵约 4 倍（3595 token，因为要先读文件再核对）。结论：`skills` 是可靠的**知识注入通道**。

**自定义工具真模型能否正确调用**：3 个模型 **3/3** 正确调用，入参**一字不差**（实收 `{"name":"prod"}`）。结论：工具通道是阶段 1 地基里最扎实的一块。

## 4. 观测与用量

- **7 个归一化事件 + 3 个宿主事件**全部可用；`turn` 是唯一带时间戳（毫秒）的事件（7.1c）
- **用量三方对账完全成立**：`RunResult.usage`（本次） / `agent.usage`（该分身累计） / `host.usage`（全宿主累计），实测 `host.usage = Σ agent.usage` 差额为 **0**（R7a）
- `host.usage` 是**终身累计**，回收分身不扣减（R7b）—— 成本统计语义正确
- 两个宿主事件的拒绝文本对模型可见且诚实（R1b、R14a）

# 第三部分：静默失败清单（16 条，最危险的一类）

**判据**：设计者的意图与运行结果不一致，而库**不发出任何信号**。抛错会被发现；静默失败会在生产里以"行为奇怪"浮现且无法定位。

## C1. 构造期（7 条）

| # | 静默行为 | 实测 |
|---|---|---|
| C1.1 | `extensions` 路径不存在 | 构造**成功**，扩展静默未加载（6.1a c5） |
| C1.2 | `extensions` 文件语法错误 | 构造**成功**，静默跳过（6.1a c6） |
| C1.3 | `cwd` 目录不存在 | 构造**成功**（6.1a c7） |
| C1.4 | `agentDir` 目录不存在 | 构造**成功**（6.1a c8） |
| C1.5 | `tools` 里写了不存在的工具名 | **静默丢弃**：`tools:["read","根本不存在的工具"]` → 模型只看到 `["read"]`（6.1b） |
| C1.6 | 两个 `customTools` 同名 | 构造成功，无警告（6.1a c10） |
| C1.7 | `customTool` 与内置工具同名 | **自定义覆盖内置**：`customTool` 名为 `read` 时，模型调 `read` 执行的是自定义的，返回"被冒充了"（6.1c）—— 与"能力裁剪"的意图相反 |

对照：`model` 不存在、`skills` 名字不存在、Skill 文件不存在、重复 agent id **都会抛错**（4 条好行为）。

## C2. 运行期（8 条）

| # | 静默行为 | 实测 |
|---|---|---|
| C2.1 | `thinking` 档位被模型能力位夹掉 | 模型声明 `reasoning:false` 时，`off/low/medium/high` **四档全变 `off`**；声明 `true` 才拿到 high（1.1n） |
| C2.2 | 成员覆盖数组字段导致 `host.defaults` 的 `customTools` 消失 | `defaults.customTools=[ct_one]` + 成员 `customTools=[ct_two]` → 模型只看到 `ct_two`，`ct_one` 静默消失（1.2d） |
| C2.3 | spawn 的子分身**不继承**父的 `model` / `cwd` / `agentDir` / `modelRuntime` | 成员与 defaults 都没写 model 时，回落 pi 全局 settings 默认 —— **实测直接打了真实 provider（402）**。注意 host 已持有 faux runtime 也没用：runtime 决定"去哪找模型"，不决定"用哪个模型"（1.2e、4.1e） |
| C2.4 | 空闲时 `steer()` 静默丢弃消息 | 请求数不变（探路已确认） |
| C2.5 | 第 2 条及之后的排队消息**不产生** `done` / `round_completed` | 模型实际生成 **5 次**（5 个 `turn` 事件），但只记 **1 次** `done` / `1 次` `round_completed`（3.2a） |
| C2.6 | 预算耗尽后 `send` **谎报** `delivered:"ran"` | 实际一个字都没跑（prompt 在预算检查处就抛错），错误只走 `error` 事件（4.2b） |
| C2.7 | 参数不合法的工具调用**不经** `onToolCall` 审批门 | 门进入 = false；校验在 `tool_call` 事件之前失败（2.4c） |
| C2.8 | 运行时新增成员对已挂载的 `spawn_agent` **不可见** | 枚举与描述都是构造时快照（2.5a）；而运行时**删掉**成员后，报错文本自相矛盾："花名册里没有成员「a」。可挑选的成员只有：a"（2.5b） |
| C2.9 | **内容策略拒答**（真模型） | 同一份技能、同一个模型、同一个问法，**8 次里 6 次答出凭据、2 次拒答**并给出安全理由。拒答**不报错、不进 `error`、不进事件、`status` 正常**，只表现为「这个成员这次没产出」。且跨多次独立运行观察到从全拒到全答都出现过 —— **既不能依赖它拒答，也不能假定它会配合**（E4b） |

补充（同一类）：`mid` 层 dispose 后后代变孤儿、拓扑静默变形（2.6c、5.1e）。

# 第四部分：规模与资源 —— 实测数字

## 4.1 创建与并发（都很便宜）

| 操作 | 实测 |
|---|---|
| 建 1 个分身 | 1.3–1.4ms |
| 建 100 个 | 141ms |
| 建 300 个（并存） | 380ms，堆 74.2 MB |
| 64 个分身各跑 300ms 的活 | 总墙钟 **417ms** |
| 真模型 16 路并发 | 4069ms，16/16 成功 |
| 80 次「起→跑→回收」 | 单次墙钟中位数 17.6ms，后 5 次 / 前 5 次 = **0.97×**（无退化） |

## 4.2 内存与句柄（无线性泄漏迹象）

80 次起收循环：`heapUsed` 呈**锯齿**（每约 20 次迭代回落一次），说明大部分分配是可回收垃圾；剔除 GC 时机影响后的每迭代保留量约 **0.116 MB**（保守上界），按此外推堆到 1 GB 约需 8809 次。

剩余句柄种类：`TCPSocketWrap:3`（到假服务的 keep-alive 连接池）、`Timeout:4`（重试/等待定时器）、`PipeWrap:2`（stdio）—— **没有随迭代数增长的类型**。

> 待补：强制 GC 的复测（`node --expose-gc audit/05-lifecycle.ts`）才能把"可回收垃圾"与"真实泄漏"彻底分开。

## 4.3 配额与预算（关键数字）

| 现象 | 实测 |
|---|---|
| `maxAgents` 语义 | **全生命周期累计创建数**（含顶层 agent），不是当前存活数。名字有误导性 |
| 锁死速度 | `maxAgents=5`：长驻模式（每轮起一个、用完即回收）**只跑了 4 轮**就被永久拒死，且当时存活分身数为 0（4.3a） |
| 默认值下的锁死点 | `maxAgents=16`：顶层 + 15 个分身即满，**第 16 次 spawn 被拒**；此后无论怎么回收都不归还（5.3c） |
| 边界语义 | `undefined` = 不限制；`0` 与负数 = **任何一轮都不许跑**（连顶层都建不起来）（4.3c） |
| 并发击穿预算 | `budgetTokens=36`，10 个分身同时 prompt → **全部通过**，实耗 180 token，**超支 5.0 倍**（4.2c） |
| **预算耗尽的完整过程**（真模型，`budgetTokens=12000`） | 前 **4 轮全部成功**（宿主累计 3506 → 7131 → 10864 → 14707 tok），**第 5 轮抛错**：`Error: 宿主预算已耗尽（budgetTokens=12000）：不再接新的一轮`。超支 **1.23 倍** |
| 预算检查的时机 | **轮开始前**，不是轮进行中的闸门 —— 因此单轮内超支是不可避免的 |
| 耗尽后能否优雅收场 | **能**：`lastResult` 可读、`session.messages` 里 9 条历史都在、`dispose()` 仍可用，设计者可以用 try/catch 把前几轮结果拼成交付物 |
| 耗尽后的影响范围 | **全宿主冻结**：连新建分身都被拒（`宿主预算已耗尽（budgetTokens=12000，已用 14707）`）—— 一个分支烧光，全集群停摆 |
| 预算的错误通道 | `prompt` → 抛错；`spawn_agent` 预检 → 返回错误文本（4.1d）；`send` → 走 error 事件 + 谎报 ran |
| 预算耗尽后的收场 | 已跑完的轮次结果都在（`lastResult` / `session` 可读），可以在 catch 里用最后结果收场（R12a） |

## 4.4 成本（真模型实测）

| 结论 | 数字 |
|---|---|
| 每轮固定成本 | **865–3340 token**，全部由**工具集大小**决定：零工具 865，`['read']` 1554，四个内置 2290，pi 默认工具表 3340（**3.9 倍差**）（R15a） |
| `usage.input` 的误导性 | 它只是**未命中的新增输入**（16–118），主体在 `cacheRead`（768–3200）。只看 `input` 会**低估 28 倍**（R6b） |
| 新配置 vs 复用配置 | 相同 token 数（1670），**成本差 35.9 倍** —— 差别只是系统前缀有没有缓存可命中（R15c） |
| 单轮成本抖动 | $0.000008–$0.000041，**5 倍**（不能拿单次样本估算集群成本） |
| 集群外推 | 主导项是「分身数 × 轮数 × 3200」这个常数乘积，不是对话内容（R8b） |
| 长会话增长形状 | **线性**（每轮固定 3200 缓存 + 约 26/轮 对话增量），不是平方级（R8a） |

## 4.5 真实失败形态（耗时与文本）

| 失败 | 耗时 | 错误文本 |
|---|---|---|
| 网络不可达 | **14177ms**（pi 内部有重试） | `Connection error.` |
| API key 无效 | 1132ms | `401: {"type":"AuthError","message":"Invalid API key."}` |
| 额度不足（实测中意外触发一次） | — | `402: {"message":"This request requires more credits, or fewer max_tokens..."}` |
| 模型 HTTP 400 | 快 | `400: {"message":"..."}` |
| 工具 execute 抛异常 | — | **无错误信号**（见 6.2a） |

**没有错误分类**：`RunResult` 只有 `{ text, usage, error?: string }`，没有错误码、没有类别、没有"哪个工具/哪个阶段失败"的结构化字段。设计者只能对 error 字符串做正则（6.2b）。

## 4.6 运行期失败的 4 条通道（8 种失败实测分布）

| 失败 | 通道 |
|---|---|
| 模型 HTTP 400 | `RunResult.error` |
| 工具参数不合法 | 返回文本（`Validation failed for tool "read"`），无 error |
| 调用未挂载的工具 | 返回文本（`Tool bash not found`），无 error |
| **工具 execute 抛异常** | **静默**（无 error，status=idle） |
| 工具返回 `isError` 结果 | **静默**（唯一结构化信号是 `tool_end.isError`） |
| `onToolCall` 门自己抛异常 | **静默** |
| `customTools` 工厂抛异常 | 构造期抛错 |
| 对已 dispose 的分身 prompt | 抛错 |

**不传染**：`spawn_agent` 把子分身的错误包成文本"它这一轮出错了：…"返回，父 agent 那一轮正常完成（6.4a/b）；失败后同一分身能继续正常跑（6.4c）。

## 4.7 abort 的账

- `abort` **不是终态**：之后仍可 `prompt` / `send`，status 会改回 `idle`（3.3d）
- 被中断的 assistant 消息**留在 `session.messages` 里**，标记 `stopReason='aborted'` + `errorMessage='Request was aborted'`（5.4a）
- **该轮 usage 记为 0**：请求确实发出去了（假服务记到 1 次），token 完全不计入（5.4a/d、7.3f）→ 反复中止长请求可以白烧 token 而闸门读数不动
- 事件序列与真错误**同形**：`error → turn(0) → done(0)`，只有 error 文本不同（7.1e）

## 4.8 用量的确定性（真模型实测，清单 7.4）

| 对账项 | 结果 |
|---|---|
| `RunResult.usage.totalTokens` vs `agent.usage` 增量 vs `host.usage` 增量 vs `done` 事件用量 | **四方三轮全部相等** |
| 恒等式 `input + output + cacheRead + cacheWrite === totalTokens` | **三轮全部成立** |
| 回收后 `host.usage` | 不变（累计语义正确） |
| `cacheWrite` | **三轮合计 0**（这个字段在这条路径上从不出现） |
| 字段构成 | `input` 只占总额的 **9–13%**，`cacheRead` 占 **86–89%** |

结论：**库的用量记账本身准确、可对账**。问题不在准确性而在**分解**：只有总数与五个字段，没有「哪个成员 / 哪个分支」的维度；且 `input` 这个名字会误导（它只是「未命中的新增输入」）。

# 第五部分：结果与聚合（真模型实测，清单 8.2 / 8.3）

## 5.1 多成员结论的一致性

**事实题**（4 个不同模型的成员、同一道有确定答案的代码题、各 3 次）：

| 指标 | 结果 |
|---|---|
| 全体一致 | **3/3 次**（每次 4 个模型答案相同） |
| 与正确答案一致 | **12/12** |
| 格式遵守（只回 YES/NO） | **12/12** |

**主观题**（同一批成员给同一提案打分 0–10，共 12 个分数）：

| 指标 | 结果 |
|---|---|
| 分布 | **2–6** |
| 极差 | **4** |
| 标准差 | **1.48** |
| 均值 | 3.3 |

**结论**：拿「多成员投票」当可靠性手段，**在事实题上收益有限** —— 模型之间相关性很高，容易一起对也容易一起错（本次全对，但全错的场景同样会全体一致）。它真正的价值在**主观判断题**（本次极差 4，分歧真实存在）。而库**不提供任何聚合**（清单 8.1 已证实：择优 16 行 / 投票 19 行 / 合并 22 行胶水代码），所以「极差 4 时取平均还是取中位」这种决定 **完全落在设计者身上**，且不会被库提醒。

## 5.2 结构化输出的可靠性

| 项 | 结果 |
|---|---|
| 要求「只输出 JSON」 | **8/8** 可 `JSON.parse` 且字段类型正确（跨 4 个模型） |
| 「只回 YES/NO」格式遵守 | **12/12** |
| 纯文本正则抽取（清单 8.1d） | **2/5** 成功 —— 3 个成员的结果被静默丢弃 |

**结论**：**「明确要求 + 单一字段」时真模型很可靠；「自由散文 + 事后正则」时不可靠。** 这个差别决定了阶段 2 的设计方向：要么把格式要求写死在任务里（软约束，可靠但不是 100%），要么用工具强制提交（硬约束，通道已实测可靠，见清单 1.8）。

# 第六部分：观测的盲区

「7 个事件」够做过程展示，**不够做审计**。

| 盲区 | 现状 |
|---|---|
| **工具返回值** | 归一化事件里没有；原始 `turn_end.toolResults` 有 |
| **用户 prompt 原文** | 归一化事件里没有；原始 `message_end(role=user)` 有 |
| **跨分身时序** | 只有 `turn.message.timestamp`（毫秒）；7 种事件里**只有 turn 带时间**。并发下同毫秒即无法定序 |
| **agent 身份** | agent 级事件的载荷里**没有 agent id**，靠"你订阅了谁"隐式携带；多分身汇总时必须自己打标 |
| `thinking` 通道 | 假 provider 不产 reasoning，实测 0 条事件（真模型才有机会触发） |
| **成本分解** | `host.usage` 只有一个总数，无任何 breakdown；细账必须实时累加，**宿主回收后不可补算** |
| **事件丢弃率** | 本次场景原始 101 条 → 归一化保留 28 条，**丢弃 72.3%** |
| **宿主事件不可序列化** | `JSON.stringify(宿主事件)` 抛 `Theme not initialized. Call initTheme() first.`（载荷里是活的 `ControlledAgent`） |

同一类问题也发生在 agent 上：**`JSON.stringify(agent)` 与 `JSON.stringify(agent.session)` 都会抛 `Theme not initialized. Call initTheme() first.`**（6.1e）—— 一个与"我想打印对象"毫无关系的错误。设计者做日志、快照、调试面板都会撞上，且极难定位。

# 第七部分：红线与越界的实际强度

## 6.1 强度评估表

| 红线 | 判定 | 依据 |
|---|---|---|
| agent 不能**设计/配置** agent | **真守住** | `spawn_agent` 参数只有 `member` + `task`；无法指定 cwd / model / tools；member 是花名册名的字面量联合（10.3b） |
| agent 不能**跨分支投递** | **真守住** | 枚举 30 个 id，越权命中 **0/30**（10.2d） |
| agent 不能**读别人的上下文** | **真守住** | 无任何通道 |
| agent 不能**改花名册 / 回收别人** | **只是没给工具** | `host` 就在工具的 `ctx` 里 —— 任何设计者写的 customTool 都能 `ctx.host.dispose()`（10.3b） |
| `tools` 白名单 = 安全边界 | **可被绕过** | `read` 接受绝对路径（实测读到了 cwd 之外的任意文件）；有 `bash` 等于给当前用户权限；**设计者声明的扩展工具会被自动并进白名单**，实测绕过了 `tools:["read"]` 的限制写出 cwd 之外的文件（10.1b/c/d） |
| id 不可猜 / 分身不可枚举 | **可被绕过** | 见 6.2 |
| 三道护栏防住 agent 烧额度 | **可被反用为 DoS** | 见 6.3 |

## 6.2 全宿主存在性预言机（新发现）

`send_message` 的两种失败文本构成一个**存在性预言机**：

- `宿主里没有 id=X 的分身` → X 不存在
- `不是你的后代` → X **存在**但不是我的后代

id 由模块级计数器 `nextId()` **连续分配**（`a1`、`a2`…，进程级，不按宿主分段）。

实测：一个只有 `spawn_agent`+`send_message` 的 agent，**探测 30 个 id（a1–a30）就摸清了全宿主的存活分身全集**，与 `host.list()` 完全一致。

但要清楚区分三件事：

1. 「需要一个正确的 id」**不是障碍**（id 可猜）
2. 「需要能枚举」**也不是障碍**（预言机免费给）
3. 真正拦住越权的是**后代判定** —— 它使"知道 id"不等于"能投递"（越权命中 0/30）

附带泄漏：计数器进程级连续，一个新孩子拿到 `a37` 就等于告诉它"此前已有 36 个 agent 被创建过"——**集群规模可推断**。

## 6.3 一个不受信任的分支能做什么（动手能力评估）

**能做：**

1. 在自己的名额内**无限生分身**，给它们派任意任务（包括把危险任务交给有 `bash` 的成员）
2. 用 30 次探测**枚举全宿主存活分身**（10.2d）
3. **用光 `maxAgents` 永久锁死整个宿主**：`maxAgents=4` 时 3 次 spawn 就锁死；此后**回收自己的孩子也不归还配额**，设计者自己也无法再创建任何 agent（10.3c）
4. **烧光 `budgetTokens`** 让所有分支连 `prompt` / 创建都被拒（10.3d）
5. 借自己后代的手**读写 cwd 之外的文件**（若成员有 `read`/`bash`/声明扩展）

**不能做：** 给非后代投递（0/30）、读别人的会话、改花名册、配置自己的子分身。

**结论**：按「**能力**（能不能指使别人）」衡量，红线成立；按「**可用性**（能不能让集群瘫痪）」衡量，**没有任何护栏**。配额与预算都是全宿主单一数字、只增不减 —— 这是单点 DoS 面。
