# 本地 pi 的定制记录

> **本地 pi 在哪**：`dev/pi/`（上游 `earendil-works/pi` 源码的一份拷贝）
> **基线版本**：`1.2.0`（2026-10-12 发布）
> **怎么接管**：`package.json` 里 `file:dev/pi/packages/coding-agent`（软链接到 `node_modules`）
> **为什么要它**：研究工具需要绝对的操控能力。撞到 pi 的墙时，能直接改底座，而不是绕。
>
> ⚠️ **每次改 pi 都要在这里记一条**：改了什么、为什么、有什么后果。
> 因为研究结论必须能回答「用的是哪版 pi + 我改了什么」。

---

## 原则（研究员定的）

> 「反正都是本地的了，那就应该是为我的这个项目而服务啊……对于高版本的 pi，
> 应对策略应该是**提取好的功能**，如果对我们项目有启发，就改本地 pi 库的具体地方。」

所以：
- **本地 pi 是 aiteam 的底座，不是"跟着上游升级的对象"**
- 上游有好处就**取**（参考、移植），但**以本项目需要为准**
- 改 pi 的门槛是「aiteam 需要这个能力」，不是「上游这么做了」

## 已做的改动

### P1 · 运行期可增删的工具白名单（2026-10-15）

**背景（撞到的墙）**：

pi 0.99.1（项目原来用的版本）把白名单做成**私有 Set**：

```ts
private _allowedToolNames?: Set<string>;      // 0.99.1
private _excludedToolNames?: Set<string>;
```

aiteam 的 `permissions.only/allow/deny` 与 `tools.add/remove` 需要在运行期改它，
而 pi 没有公开 API ⇒ 库**只能 cast 私有字段**（记在 `docs/FACTS.md` #11）。

升到 1.2.0 后这堵墙**变硬了**：

```ts
private _allowedTools?: ToolNameMatcher;      // 1.2.0，不可变匹配器
private _excludedTools?: ToolNameMatcher;
```

- 从「可增删的 Set」变成「**不可变的匹配器函数**」（为了支持 `mcp__*` 这类模式）
- 而且 `reload()` **不重建**它（白名单只在构造期设一次）
- ⇒ cast 私有字段这条路**彻底断了**

**改了什么**：

| 文件 | 改动 |
|---|---|
| `src/core/mcp-servers.ts` | `createToolNameMatcher` 返回值从裸函数变成 `ToolNameMatcher` 接口，多了 `add` / `remove` / `names` —— **保留模式匹配能力**，同时可变 |
| `src/core/agent-session.ts` | 给 `AgentSession` 加 4 个公开方法：`setAllowedToolNames(mode, entries)`（`add`/`remove`/`replace`）、`setExcludedToolNames(mode, entries)`、`hasAllowedToolNames()`、`isExcludedToolName(name)` |
| `src/core/resource-loader.ts` | 给 `DefaultResourceLoader` 加 `mutateExtensionFactories(mode, factory)` 与 `listExtensionFactories()` —— 同一个问题（`extensionFactories` 私有且被 `filter()` 拷贝） |

**aiteam 侧的影响**：

- `src/surfaces/tools.ts` 的 `toolFilters()`（cast 私有字段的访问器）**删掉了**
- `src/surfaces/resources.ts` 的 `factoryList()`（同上）**删掉了**
- ⇒ **库现在零私有字段依赖**（`grep "as unknown as {"` 为空）

**验证**：`npm test` **156/156 全过**（跑在本地 1.2.0 上）。

**顺带修掉的天花板**（`docs/FACTS.md`）：
- #11「`_allowedToolNames` 是私有字段，pi 无公开增删 API」
- #16「`setActiveToolsByName` 只在注册表里找名字」
- #17「`extensionFactories` 被 `filter()` 拷成新数组，推自己的没用」

## 怎么重建（改了 pi 源码之后必做）

```bash
cd dev/pi
npx tsc -p packages/coding-agent/tsconfig.build.json
```

**注意**：不能跑官方的 `npm run build` —— 它包含 `check:model-data`，要联网核对模型数据（本机不通）。
按依赖顺序批量构建时用：

```bash
cd dev/pi
for p in telemetry chord tui codemode mcp ai agent coding-agent; do
  npx tsc -p packages/$p/tsconfig.build.json
done
```

**依赖顺序**是有讲究的：`telemetry` 必须最先（`ai` 依赖它的类型声明）。

## 待办：上游值得取的（codemode）

**上游 1.2.0 的 `codemode`（`@earendil-works/pi-codemode`）已被 aiteam 用上** —— 见
`src/surfaces/sandbox.ts` 与 `dev/test/sandbox.test.ts`。

**我们复用了什么**：`InlineCodemodeSandbox` + `CodemodeTool` 接口。**没有改 pi** ——
沙箱的接缝（「给一组工具，脚本里 `tools.x()` 调到」）本来就够用。

**我们加了什么（aiteam 侧，不在 pi 里）**：
- 能力白名单（设计者声明沙箱里能碰哪些面；未声明的连存在都看不见）
- 把它包成**一个普通 AgentTool**（`agent.tools.add()`），不新增机制
- **限一层**：沙箱里 spawn 的子 agent 不继承沙箱

**这一处值得记的设计**：pi 的 codemode 是把 **pi 自己的工具**暴露给脚本；
aiteam 是把 **aiteam 的面**暴露给脚本 —— 也就是模型能通过脚本去动 agent 本身。
这是 `examples/11-redline.ts` 那条「可被推翻的假设」的正面实现。
