# aiteam 研究问题清单

- 日期：2026-10-01
- 性质：**活文档**。列出手头值得研究的问题，随研究进展增删、更新空白度。
- 定位：本文只列**问题**，不列计划、不排优先级的时间表。

---

## 0. 判据

一条问题值钱，要同时满足 5 条：

1. **可回答** —— 有判定标准，不是意见
2. **可测量** —— 能用现有基建（零成本假 provider / 真模型 / `audit/` 的探测手法）或明确的设计测出来
3. **非显然** —— 结论不是常识
4. **有区分度** —— **正反两种结果都有价值**（只能得一种结果的是宣传，不是研究）
5. **有人会引用或复用**

## 1. 标记

- **●** 完全空白 —— 检索中没有找到任何人在做
- **◐** 有人提过，没人测
- **○** 已有部分结论，缺另一半

「空白度」的依据见 [附录 A：外部对照](#附录-a外部对照)。

## 家族 1：范式成立的前提

最该先做，其他家族都建在它上面。

| # | 问题 | 值钱在 | 空白 |
|---|---|---|---|
| 1 | **如果底下的模型是概率系统，「用代码定义规则」到底继承了多少确定性？** 同一集群代码跑 N 次，产出的方差有多大？规则能压住多少？ | 这是整个范式的**成立前提**。实测已知真模型同输入 10/10 产出不同；如果集群产出也不可复现，「代码规范逻辑」就名不副实。**没人在测方差，大家都在谈拓扑** | ● |
| 2 | **自由发挥 vs 固定流程的边界在哪？** 哪些任务形状下前者真的赢，哪些必输？ | 全场共识是「workflow ≠ agent」，**但没人刻画边界**。公开证据的主流结论是静态流程通常赢——那这条边界就是全部价值所在 | ◐ |
| 3 | **规模律**：agent 数量 / 委派深度 → 产出质量的曲线，拐点在哪？协调开销什么时候吃掉收益？ | 所有框架都在卖「起更多 agent」。现有实测只有「500 个分身建成 807ms」这种**建成成本**，没有**产出曲线** | ◐ |
| 4 | **上下文隔离 vs 共享的边界**：每个 agent 独立上下文 vs 共享黑板（同一 `cwd` / 文件），分别在什么条件下更优？ | 本库刻意只做隔离（把共享 session 视为反模式）。**这个取舍只有论点没有数据**，而它正是「控制上下文」这条主线的核心 | ● |
| 5 | **委派多跳的信息保真衰减**：深度 1→2→3→4，一条信息传到底还剩多少？ | 审计自己列为「未覆盖」。这直接决定 `maxDepth` 该设几 | ● |

## 家族 2：规则的可迭代性

对应「改的是集群的代码，不是它写出来的代码」。**几乎完全空白。**

| # | 问题 | 值钱在 | 空白 |
|---|---|---|---|
| 6 | **改一轮集群规则，产出提升多少？收敛还是震荡？** 迭代几轮后收益消失？ | 「改集群代码而不是改产出」是这个范式的核心闭环。**没有任何项目把它当作可测量的东西**。「Loop engineering」「LLM-as-Code」都把话说了，没人给数 | ● |
| 7 | **规则过拟合**：为任务 A 调出来的规则，在任务 B 上掉多少？ | 这是该范式最大的风险。如果规则高度任务特定，「可迭代的集群」就退化成「一堆一次性脚本」。**没人测过** | ● |
| 8 | **规则的最小充分集**：几条规则能表达多少种集群形态？给出「原语集 → 可表达拓扑」的刻画 | 把「表达力」从形容词变成定理。现在的 10 形态清单是案例，不是刻画 | ● |
| 9 | **人 vs agent 的规则分工边界**：哪些规则必须人写、哪些交给 agent 在运行时自己决定更好？ | 这是「人写集群、AI 自由发挥」的**分界线本身**。混合策略（人给骨架、agent 填肉）几乎无人系统研究 | ● |

## 家族 3：红线的代价与强度

**本项目的独有资产：检索中零先例。**

| # | 问题 | 值钱在 | 空白 |
|---|---|---|---|
| 10 | **「agent 不能配置 agent」的代价是多少？** 表达力损失多大？ | 检索一圈：主流框架（ovo-runtime 的 `SpawnOpts`、agent_works 的 `spawn_child`）**都允许 spawn 时传 model / tools / permission**。没人测过「不给这个自由会损失什么」 | ● |
| 11 | **红线在对抗条件下的强度**：prompt injection 能否让子 agent 越权（加载代码、换贵模型、扩工具）？ | 本库明确不承诺安全边界——但「红线实际能挡多少」是**可测事实**。库不承诺安全 ≠ 不需要知道抗性。**这个对抗方向没人做** | ● |
| 12 | **「连收窄工具集都不给」这一条的净成本**：它挡住的合法用法多不多？ | 红线里最激进的一条。它是设计选择、不是事实——**需要数据来辩护或推翻** | ● |

## 家族 4：低层操控面的工程极限

来自那轮能力与极限审计，方法学上的强项。

| # | 问题 | 值钱在 | 空白 |
|---|---|---|---|
| 13 | **把 `RunResult` 绑到调用，代价多大、收益多大？** 游标切片 / 队列 / 事件关联三种方案的对比 | 审计的第一号结论。已知「不补就没法做真实工作」，**但补法的成本收益没比过** | ○ 已有诊断 |
| 14 | **配置层的静默失败能否被系统性消除？** 校验覆盖到哪一层就够？ | 40+ 组拼写矩阵已证明「错一个字符就全功能失效」。**能不能设计出「静默失败率 ≈ 0」的配置层**，是个可测的工程问题 | ○ 已有诊断 |
| 15 | **长跑状态出口的设计空间**：上下文超限 / 压缩 / 预算，恢复机制有几种，各自代价？ | 现在超限 = **永久静默返回空**，除 `dispose` 无解。这是设计问题，不是 bug | ○ |
| 16 | **预算是硬天花板还是软约束，agent 的策略会不同吗？** | 审计证明预算能击穿 5.0×。**但「给了硬天花板之后 agent 会不会更省」没人测**——有可能反而更贵 | ● |
| 17 | **失败语义化的覆盖率与实用性**：失败分类学能做到多细？分细之后有人用吗？ | 约 40 条静默失败全挤在「一个字符串」上 | ◐ |
| 18 | **护栏强度 vs 资源利用率**：终身配额（回收不还）导致 `maxAgents=5` 的长驻模式只跑 4 轮就锁死——配额返还的设计空间有多大？ | 所有长驻集群都会撞这面墙 | ○ |
| 19 | **超时的引入会解锁哪些拓扑？** | 无超时等待与本库自己的死锁规则相矛盾。形态 11（长跑监督）现在表达不了。**「哪些形态是被缺超时挡住的」没人列过** | ● |

## 家族 6：方法学

**可引用价值最高的一族。** 600 条假 provider 实测 + 约 400 次真模型调用的双轨数据，是本项目的稀缺资产。

| # | 问题 | 值钱在 | 空白 |
|---|---|---|---|
| 23 | **假 provider 的结论能外推到真模型吗？** 哪些结论可外推、哪些不可？ | 那轮审计全程两者并用。**这是整个领域都没解决的方法学问题**——绝大多数论文只用真模型、样本极小 | ● |
| 24 | **测「涌现」必须用真模型吗？** 假 provider 的确定性脚本能否测自组织？ | 如果能，涌现研究就能摆脱「跑 100 次才有一点信号」的困境 | ● |

## 依赖顺序

不是时间表，只是「谁挡着谁」：

- **26（基准）与 25（方法）挡着 1、2、3** —— 没有可比任务集和可复用测量套件，家族 1 的结论站不住。
- **1（可复现性）挡着 6、7** —— 规则迭代的可测量性建立在「同一份代码能重跑」之上。
- **13、14 与家族 3 无关，可并行** —— 它们是库自己那一侧的工程结论。
- **家族 5、6 与其余全部正交** —— 随时能做，且引用价值最高。

**若只挑三个先做：`26 → 1 → 6`。** 26 让后面可比，1 让范式站得住，6 是「迭代集群代码」这条主线上唯一没有任何数据的部分。

## 附录 A：外部对照

### A.1 检索范围与方法

一轮多角度网络检索（2026-10-01）。**注意局限**：搜索 API 中途限流，约一半查询失败；未配置备用搜索 provider。绝大多数项目**只读到 README / 文档级，未深读源码**。这个领域的仓库噪音极大——相当一批项目（Symbio、Avernet、A3S、EvoX、YGN-SAGE 之类）从命名与 README 风格看像批量生成，已按「有实体代码 / 官方背书 / 有源码级细节」筛过一轮。

| 来源 | 关键表述 |
|---|---|

### A.3 结论（这份清单「空白度」的来源）

1. **「低层操控库」这一侧不独特。** conjure 的三原语、ovo-runtime 的 `spawn_agent + 深度 + 预算 + 并发` 三元护栏、tangle 的预算池 + 组合子，切得比 aiteam 还细。
2. **但「agent 不能配置 agent」这条红线没有先例。** 主流框架**都允许** spawn 时传 model / tools / permission（ovo 的 `SpawnOpts` 里有 `model` / `agent_type` / `output_schema`；agent_works 的 `spawn_child` 有 `full_permission`）。**「连收窄工具集都不给」是差异点**（置信度中高，未深读全部源码）。
3. **「自组织 / 涌现」这一侧有明确同类**，且 Agent Society 与灵台都是中文项目、方向高度重合。**但它们不是库——「做成一个底层库而不是一个系统」这一格没被占。**
4. **「迭代集群的代码而不是产出」有提法、没项目。** Loop engineering 与 LLM-as-Code 都把话说出来了，都是文章 / 方法论，没有对应的成熟库或测量。
5. **「拒绝预置流程」几乎无人当作立身原则。** 大家都承认 workflow ≠ agent（Anthropic 官方文档、ADK 自己的文档都承认），但**同时又都提供 workflow 那一半**。

### A.4 环境备注

- 搜索 provider：仅 exa 已配置，且中途触发免费额度限流；Brave / Tavily / Firecrawl 无 API key。
- 因此**覆盖不完整**，尤其 PyPI / npm 上小而新的库很可能漏了一批。附录 A 的所有「空白」结论都受此限制。
