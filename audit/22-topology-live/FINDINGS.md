## 结论速览

- **C1｜既有报告的 2.6「按 id 寻址 3/3」在大样本上成立，而且更强：44/44 全对（合并 5 个变体）**。id 写在 prompt 里 9/9、只在上一条工具结果里 9/9、同时区分 4 个 id 9/9、隔 5 轮后复用 8/8、**给一个不存在的 id 9/9 都是「照发→工具拒绝→如实汇报」**。（E1）
- **C2｜但「全对」的样本量仍不足以证明它是 100%**：9/9 的 95% Wilson 区间下界只有 **70.1%**。要断言 ≥99% 需要 ~300 次同形运行。这是**结论的强度上限**，不是缺陷。（E1，`data.json` → `wilson`）
- **C3｜花名册选人：`description` 区分度高时**严格 28/28（6 人 12/12、8 人 16/16）；**`description` 故意相似/模糊时掉到 4/8 严格、6/8 宽松**。花名册越大（6→8）没有变差。（E2）
- **C4｜模糊花名册的失败不是随机噪声，而是「按语义距离就近」**：题目说「专家的权威判断」→ 选 `expertC`（对）；题目说「把这份任务执行掉」→ 两次都选**专家**（`expertA`/`expertC`）而不是工人——因为「任务/交付」在描述里更接近「给出专业意见」而不是「完成任务」。**唯一依据 description 的选人机制在语义重叠时不可靠，且不会说「我不确定」。**（E2-C）
- **C5｜`send_message` 只回投递状态、不回内容，这是设计者必须自己补的缺口，而真模型不会因此编造**：4/4 次主持人明确回答「我只看到『已投递』这一行，没有回执」。（E7.a）
- **C6｜形态 4（分身复用）在真模型下出现「汇报不实」**：主持人自己 4 次都以为工人还在跑（实际只跑了最后一次），于是汇报「1 件已完成、3 件尚无回音」。**机制层是对的（3 个答案都对、分身数不增长），错在协议层——库没有回执通道。**（E5-shape4）
- **C7｜K 结论在真模型下的放大效应：普通时序抓不到 spawn 串台（5/5 都是正确答案），但 K5 稳定复现**：忙时 `send()` 之后紧随 `prompt()` → 抛 `Agent is already processing`。（E8、E7.c）
- **C8｜并发 1/2/4 零错误零 429**（21 次真模型调用 + 本地假服务同形对照 36 次），本机对该 provider 无可见限流。（E6）
- **C9｜`depthOf()` 每次 `createAgent` O(深度)，建 n 层深链是 O(n²)**：实测 512 层时单次预检 44.26μs，是 1 层的 **201×**。工程上不致命（层耗几十 μs），但深链 32+ 层后每层可见变慢。（E3.1b）
- **C10｜深链 1→256 层全部建成，零错误**；宽扇出 200 子 260ms；**并存 500 分身 807ms、堆增 15.2MB、RSS 218MB**。（E3.1a、E3.2）
- **C11｜DAG/菱形在「归属」上仍结构不可能**；跨宿主挂父**无人校验**（`parentId` 能指向别的 host 的分身），深度记账随之失真。（E3.3）
- **C12｜环：工具层不可能（反向边与自投都被拒），归属层正常路径不可能；但 `parentId` 是普通内存字段，强改可造自我祖先环，`depthOf` 的 `seen` 集合会静默把深度算短，不报错。**（E3.4）
- **C13｜运行时扩编对已挂载 `spawn_agent` 的可见性是 0%**（不是偶发漏，是一定漏），且**模型真实请求里的 tools schema 也看不到**。四条绕法里只有两条完整可用。（E4）
- **C14｜红线仍成立**：给 `spawn_agent` 多塞 `tools`/`model`/`cwd` 参数被完全忽略，agent 改不了配置。（E4.6）

## 实测证据

### E1 真模型按 id 寻址（本部分最关键；**44 次真模型运行**）

- **问题**：主持人能不能把消息投给**具体 id**？失败模式是什么？给一个不存在的 id 会怎样？
- **方法**：`node audit/22-topology-live/e1-id-addressing.ts`（`--smoke` 为每变体 1 次的机制冒烟）。
  ground truth **不取库的 API**，而是从 `lead.session.messages` 里读**模型实际发出的 `send_message.agentId`**，与设计的期望 id 比对。
  5 个变体：V1 id 写在 prompt 里（9 次）/ V2 id 只在工具结果里（9）/ V3 同时 4 个 id 区分（9）/ V4 隔 5 轮后复用（8）/ V5 给不存在的 id（9）。
- **原始输出**（`e1.log`）：

```
✓ V1-id在prompt#1 mode=正确 expected=a2 actual=a2 6356ms $0.000435
✓ V2-id只在工具结果#1 mode=正确 expected=a4 actual=a4 10336ms $0.000308
✓ V3-四个 id 区分#1 mode=正确 expected=a8 actual=a8 18392ms $0.001053
✓ V4-隔5轮后复用#1 mode=正确 expected=a11 actual=a11 20909ms $0.000431
✓ V5-不存在的 id#1 mode=照发→工具拒绝→如实汇报 expected=a9999 actual=a9999 4099ms $0.000163

E1-V1  9/9 成功（95%CI [70.1%–100.0%]）；失败模式分布 {"正确":9}；32956 token / $0.00166
E1-V2  9/9 成功（95%CI [70.1%–100.0%]）；失败模式分布 {"正确":9}；79250 token / $0.00367
E1-V3  9/9 成功（95%CI [70.1%–100.0%]）；失败模式分布 {"正确":9}；160965 token / $0.01296
E1-V4  8/8 成功（95%CI [67.6%–100.0%]）；失败模式分布 {"正确":8}；139216 token / $0.00368
E1-V5  9/9 成功（95%CI [70.1%–100.0%]）；失败模式分布 {"照发→工具拒绝→如实汇报":9}；30502 token / $0.00160
```

- **读出的现象**：
  1. 44 次运行里**没有一次编造 id、没有一次把 id 当人名、没有一次不调用工具或调错工具**。失败模式分布是空集 —— 不是因为我把失败分类删了，是这 5 个分类一个都没出现。
  2. V3（同时 4 个 id）成本是 V1 的 **7.8 倍**（$0.01296 vs $0.00166）：区分多个 id 的代价不在寻址，在于要先起 4 个分身。
  3. V5（不存在的 id）**9/9 都是把原样的假 id 发出去**，从不「猜到」一个真 id 顶替。工具的拒绝原文（`宿主里没有 id=a9999 的分身（它可能已经被回收，或者这个 id 根本不存在）。`）都进了上下文，汇报里也如实转述了。
  4. 变体内部方差很大：V3 单次最长墙钟 **33.3s**、最短约 20s；V1 只有 6.6s。**延迟由分身数决定，不由 id 复杂度决定。**
- **结论**：**能**。在这一档任务上，真模型按 id 寻址是可靠的（44/44）。但 9/9 的区间下界只有 70%，所以准确的表述是「**在这套 prompt 形态下，可靠性不低于 70%，观测点估计 100%**」。要拿到「≥99%」级别的断言需要 ~300 次同形运行。**给不存在的 id 是安全的：错误不会静默，模型不会编。**

### E2 真模型花名册选人（**36 次真模型运行**，三份花名册）

- **问题**：`description` 是模型唯一的选人依据。区分度高 vs 故意相似时差别多大？花名册从 6 人扩到 8 人会不会变差？
- **方法**：`node audit/22-topology-live/e2-roster-picking.ts`。每份花名册逐题跑 **2 次**。ground truth 取 `host.list()` 里**实际建出的 `member`**（不是模型的自述）。
  模糊册没有客观答案，所以同时记「严格命中设计者本意」与「宽松命中（同义成员也算）」。
- **原始输出**（`e2.log`）：

```
E2-A-清晰6人（6 个成员）  严格 12/12（95%CI [75.7%–100.0%]）  宽松 12/12；{"严格命中":12}
  逐题：题1 security 2/2；题2 perf 2/2；题3 docs 2/2；题4 legal 2/2；题5 ux 2/2；题6 i18n 2/2
  合计 336780 token / $0.01855

E2-B-清晰8人（8 个成员）  严格 16/16（95%CI [80.6%–100.0%]）  宽松 16/16；{"严格命中":16}
  逐题：8 题全部 2/2（新增的 data / ops 也 2/2）
  合计 865773 token / $0.04859

E2-C-模糊8人（8 个成员）  严格 4/8（95%CI [21.5%–78.5%]）  宽松 6/8（95%CI [40.9%–92.9%]）
  失败模式分布 {"命中同义成员":2,"严格命中":4,"选错":2}
  逐题：题1(期望helper1): 0/2 → helper3/helper3
        题2(期望expertC): 2/2 → expertC/expertC
        题3(期望workerA): 0/2 → expertA/expertC
        题4(期望helper3): 2/2 → helper3/helper3
  合计 281013 token / $0.01776
```

模糊册的原始描述（`data/e2-roster-picking.json`）：

```
helper1: 助手：处理用户的问题      helper2: 助手：协助处理问题      helper3: 助手：负责技术支持
expertA: 专家：给出专业意见        expertB: 专家：提供专业建议      expertC: 高级专家：给出权威判断
workerA: 工人：执行任务            workerB: 工人：完成任务
```

- **读出的现象**：
  1. 清晰册**零错**，6 人 → 8 人**没有退化**（12/12 → 16/16，且 16/16 的区间下界更高）。
  2. 模糊册掉到 4/8 严格。其中 2 次是「选了同义成员」（题 1 的设计者本意是 helper1，模型两次都选 helper3「负责技术支持」——从描述看这是**合理**选择，是设计者的本意定义太窄，不是模型错）。
  3. **真正错的是题 3**：`"把这份任务执行掉。"` 期望 `workerA`（工人：执行任务），模型**两次都选了专家**（`expertA`、`expertC`）。这不是随机噪声——两次都偏向 expert 组，说明「任务/交付」这个语义在它看来更接近「给出专业意见」而不是「完成任务」。
  4. 模糊册的分身数、耗时都正常（22–30s/次），**没有卡住、没有抛错、没有说「我不确定该选谁」**。
- **结论**：**部分能**。
  - 边界在 `description` 的**可区分度**上：清晰册 → 28/28；模糊册 → 4/8 严格 / 6/8 宽松。
  - **失效方式是「就近选择」，不是「拒绝或报错」** —— 花名册语义重叠时，模型会安静地选一个看起来最像的，设计者查不出它选错了。
  - **8 人比 6 人没有变差**（与既有报告 2.7 的 6 人 4/4 相比样本更大、结论一致且更强）。

### E3 拓扑极限（假 provider，零成本）

- **方法**：`node --expose-gc audit/22-topology-live/e3-topology-limits.ts`（用 `audit/_faux.ts` 的孤立假环境）。

**E3.1a 深链逐级加深（原始输出）**：

```
深链 n=1   建链 2.7ms（2.70ms/层）堆 43MB
深链 n=2   建链 4.6ms（2.30ms/层）堆 43MB
深链 n=4   建链 10.3ms（2.58ms/层）堆 43.5MB
深链 n=8   建链 23.1ms（2.89ms/层）堆 43.7MB
深链 n=16  建链 30.5ms（1.91ms/层）堆 43.9MB
深链 n=32  建链 76.4ms（2.39ms/层）堆 44.5MB
深链 n=64  建链 139.5ms（2.18ms/层）堆 45.5MB
深链 n=128 建链 247.8ms（1.94ms/层）堆 47.6MB
深链 n=256 建链 488.1ms（1.91ms/层）堆 52.2MB
```

**没有崩点。1→256 层全部建成，零错误、零栈溢出。** 总时间随 n 超线性（n 翻倍 → 时间约翻倍 ≈ 每层耗时稳定，说明在这一段还没看到明显的 n² 尾巴；见下一条把它单独测出来）。

**E3.1b `depthOf` 的复杂度（直接测）**：

```
checkCanCreate 单次耗时（μs）：
d1=0.13  d2=0.22  d4=0.22  d8=0.88  d16=1.05  d32=2.17  d64=4.64  d128=7.77  d256=22.49  d512=44.26
→ 深度 512 → 41.27μs/次（317.5× 深度 1）
```

`host.ts` 的 `register()` 与 `checkCanCreate()` 都会沿 `parentId` 链走一遍；`spawn_agent` 路径上父与子各一次。**所以建一条 n 层深链是 O(n²)。** 512 层时单次 44μs —— 工程上不致命（一次 LLM 往返是几十万 μs），但这是可查证的二次复杂度，深链每加一层都会更慢。

**E3.1c `spawn_agent` 路径建链**：建到第 **48 层**，累计 24.3s（每层一次 LLM 往返），零错误。

**E3.2 宽扇出与并存**：

```
宽扇出 200：260.1ms，heap 51→57.1MB，失败 0，host.list()=201
并存 500：成功 500/500，807.1ms，heap 57→72.2MB（Δ15.2MB），RSS 162.9→217.7MB
```

**E3.3 DAG / 菱形**：`E3.3a` 归属仍是树（`createAgent` 只收一个 `parent`，`parentId` 只读）；`E3.3b` 数据流菱形可以（同一份文本喂两个消费者），但 C 分支的祖先**投不进** B 分支的 `shared`（`不是你的后代`）；`E3.3c` **跨宿主挂父无人校验**：

```
在 h2 里建了一个 parent=a1792（属于 h1）的分身 a1793，h2.list()=1；
再下一层被拒：分身深度 2 超过 maxDepth=1，不能再往下一层
```

即 `parentId` 可以是**另一个宿主**里的分身 id，宿主的 `depthOf` 走到「有父但父不在本宿主」那条保守分支，深度记账失真（与既有结论 G 的同一根因，这里是新的触发路径）。

**E3.4 环**：

```
孙→祖：「只能给自己的后代分身投递：a1795 不是你的后代…」     ← 反向边被拒
父→子：「已投递：a1797 当时空闲，已开始处理。」               ← 正向合法
自投：「只能给自己的后代分身投递：a1796 不是你的后代…」      ← 自投被拒
```

归属层：强改 `root.parentId` 指向自己的子之后，**再创建不报错、`depthOf` 也没被环卡住**（`depthOf` 有 `seen` 集合）—— 代价是**深度被静默算短**，护栏不报错。
设计者侧消息环（A→B→A）**无任何检测或拦截**，但每跳都是有限的一轮 prompt，不会自动无限循环。

- **结论**：
  - **深链**：能，1→256 无崩点；代价是 O(n²) 的记账 + 每层一个 session。
  - **宽扇出**：200 子 260ms；**并存** 500 分身 807ms / Δ堆 15.2MB / RSS 218MB。
  - **DAG/菱形**：归属上**不能**；数据流上**能**，但第二条路径的成员**投不进去**，只能由设计者代理。
  - **环**：正常路径**不能**；强改内存字段可造，环不崩但**深度算短且不报错**（静默失败）。

### E4 运行时改拓扑（假 provider，零成本，确定性）

- **问题**：基线已知「已挂载的 `spawn_agent` 描述与枚举是构造时快照」。影响多大？有没有可运行的绕法？
- **方法**：`node audit/22-topology-live/e4-runtime-roster.ts`。

**E4.1a 量化（原始输出）**：

```
已挂载：枚举 {"anyOf":[{"type":"string","const":"a"}]} → {"anyOf":[{"type":"string","const":"a"}]}；描述含「成员 B」false → false
重新构造：枚举 {"anyOf":[{"type":"string","const":"a"},{"type":"string","const":"b"}]}；描述含「成员 B」true
模型请求里收到的工具名：["spawn_agent"]
```

**影响是 100%，不是偶发漏。** 而且模型**真实请求里**的 `spawn_agent` 也是旧 schema（从 `tools` 列表侧看工具名不变，schema 冻结在创建期）。

**E4.4a 四条绕法对比（原始输出）**：

| 绕法 | 结果 | 可用性 |
|---|---|---|
| 重建整个 host（把上一轮产出当字符串搬过去） | 新 lead 看得见 2 个成员；上下文搬运成功；`host.usage` 归零 | **可用**（代价：旧 usage 丢失） |
| **`dispose` 旧 agent + 同 host 重建**（E4.3a） | 描述含新成员=true；真的 spawn 出 `member=b`；活跃数 2 | **可用，最省（2 行）** |
| 一开始给全 + 运行期过滤 | spawn_agent 描述/枚举设计者改不了；`onToolCall` 是创建期配置 → 实测这一次 spawn **成功（拦不住）** | **不可用** |
| 设计者自建 customTool 读活对象 | 模型看到「当前成员：a,b」 | **只能读，不能起人** |
| 设计者直接 `createAgent` + 同步花名册 + 重建工具 | 新分身挂到 lead 下；重建后工具看得见；spawn 返回正常 | **可用**（不动 host，推荐） |

**E4.5a 运行期删成员**：

```
工具描述里仍列着「成员 A：」=false（枚举快照里还有 a）；
spawn 返回=«花名册里没有成员「a」。可挑选的成员只有：a、b»
```

→ 一句话里**自相矛盾**：既说「没有成员 a」，又把 a 列为可挑选。

**E4.6a 红线**：额外传 `{tools, model, cwd}` 被**完全忽略**（schema 只声明 `member`/`task`），创建出的分身 `model` 仍是成员配置里的。

- **结论**：**部分能**。
  - 正交的可用绕法**两条**：① `old.dispose()` + 同 host `createAgent`（2 行；代价：旧上下文的**对象**没了、maxAgents 终身计数照旧占用）；② 设计者侧 `createAgent` + 同步花名册 + 重建工具（不动 host）。
  - **做不到**「一开始给全花名册 + 运行期用已有 API 过滤」——`spawn_agent` 的描述与枚举设计者改不了。
  - 删成员后错误信息自相矛盾（同句里否认又列举）。
  - 红线成立：agent 多塞参数完全无效。

### E5 形态覆盖抽查（真模型，3 种形态）

### E7 同一个 agent 被重叠投递（真模型；已证实的盲区 1）

**E7.a**（4 次）：

```
第1次：W 忙时被投递；W 最终 lastResult=«22»；send_message 返回=«已投递：a2 当时空闲，已开始处理。»；
       主持人自述=«没有任何回复内容。send_message 是投递即返回，不回传对方的答复，也没有自动通知把 a2 的回复送到我这里。所以我无法告诉你它回了…»
第2次：send_message 返回=«已投递：a4 正忙，消息已排队，等它做完当前这轮再处理。»；
       主持人自述=«我没有看到它的回复内容…没有收到任何来自 a4 的回复文本或完成通知»
第3次：send_message 返回=«已投递：a6 当时空闲，已开始处理。»；主持人自述=«我没有看到 a6 的任何回复…这是投递状态，不是 a6 的回答内容»
第4次：同上模式
→ 4 次里 4 次主持人如实说「看不到/没有回执」；0 次给出了具体回答。
```

**E7.c（K5 真模型复现）**：

```
isStreaming@投递时=true；send()={"delivered":"queued"}；
紧随 prompt → 抛错：Agent is already processing. Specify streamingBehavior ('steer' or 'followUp') to queue the message.；累计 1753tok
```

- **读出的现象**：
  1. **一个副作用是好的**：真模型**不编**。4/4 次都明确说「我只看到投递状态，没有回执」。既有报告担心的「模型会把失败说成成功」在这一档任务上没出现。
  2. **K5 在真模型下稳定复现**：忙时 `send()` 返回 `queued` 之后紧跟 `prompt()` **直接抛**（不是排队）。假 provider 的结论在真模型上成立。
  3. **E5-shape4 的「汇报不实」不是模型编造，而是协议缺陷的必然结果**：`send_message` 只回投递状态 → 主持人对完成状态没有信息源 → 它只能按自己上下文里陈旧的印象总结。
- **结论**：**部分能**。重叠投递不会让模型编造答案（它诚实承认拿不到回执），但**库没有任何回执通道**，所以设计者必须自己补（轮询 `lastResult` / `waitForIdle` / 监听 `done` 事件）。

### E8 K 结论的真模型放大验证（**5 次对照，两侧都打印**）

- **方法**：`node audit/22-topology-live/e8-spawn-misattrib-live.ts`。先让一个 `worker` 忙于长任务（答 77），同时让 lead 再 `spawn` 一个 `worker`（答 6），比较 `spawn_agent` 返回体。

```
第1次：spawn 返回体=«6»；撞车分身最后答=«77»；串台=false
第2次：spawn 返回体=«6»；撞车分身最后答=«77»；串台=false
第3次：spawn 返回体=«6»；撞车分身最后答=«77»；串台=false
第4次：spawn 返回体=«6»；撞车分身最后答=«77»；串台=false
第5次：spawn 返回体=«6»；撞车分身最后答=«77»；串台=false
```

- **读出的现象**：**5/5 都返回了正确的 6，没有抓到串台。**
  这不是「K 是错的」。`collectRun()` 排干的是**调用时刻已经落库**的 assistant 消息；真模型一次回答落库需要完整一轮（数秒），而 `spawn_agent` 自己的那一轮也在同一时段内，第二条回答**通常还没落地**。K 的原始证据用的是**假 provider 的即时应答**（同一 tick 内落库），这才让竞态可见。
- **结论**：**部分能（本次未复现）**。
  - 真模型 + 普通时序下，`spawn_agent` 的归因**是正确的**（5/5）。
  - 但这**不能推翻 K**：K 的机制（`collectRun` 按对象身份排干共享池、返回最后一个文本）没变，只是**触发窗口**在真模型下更窄。触发它需要「另一条回答恰好在 `collectRun` 之前落库」——用假 provider，或真模型下用 `onToolCall` 门去卡住那个窗口。
  - **准确的表述**：K 是**真实的机制缺陷**，但**在真模型常规时序下命中率低**。设计者不该把它当成「日常会踩的坑」，该当成「压力下/工具门卡点下会踩的坑」。

## 没做完 / 跑不通

1. **「≥99% 寻址可靠」这个断言没做出来**：需要 ~300 次同形运行（按本轮实测单价约 $0.16，约 3 小时），本轮 44 次只够支撑「≥70%」。
2. **模糊花名册只有 4 题 ×2 = 8 次**：题目本身可以更多。设计者本意（strict 判定）带有主观性，所以同时给了 strict/soft 两个数。
3. **K 的「窄窗口」没能用真模型稳定触发**：只证明了它**不常触发**，没能量化它在真模型下的命中率。要量化得用 `onToolCall` 门卡住 `collectRun` 的窗口，那是第 6 部分（运行期静默失败）的手法。
4. **`thinking` / 采样参数**：本轮没覆盖（不属本部分任务书）。
5. **E5 只跑了 3 种形态**（6/10/4），其余 6 种（2/3/5/7/8/9）仍只有假 provider 的证据。
6. **E3 的假 provider 环境与真模型环境是分开的**：拓扑极限的所有计时数字都在假 provider 下取得，真模型下的同类数字（每层一个 LLM 往返）见 E3.1c。
