## 0. 这一轮要回答的问题

不是探某个点的边界，而是：**「如果我用这个框架跑一个真实的 8–10 人团队任务，实际会发生什么？最先崩的是哪里？」**

做法：搭一个**真的 10 成员、真异构、真 4 层、真 4 轮**的集群，跑一个**真的交付物落盘**的任务，然后用**两种写法跑同一件事**对照（A 自然写法 / B 按基线 K 自己推的安全纪律），再做 3 个故障注入 + 1 次紧预算。

### 被跑的任务（A/B 完全相同）

产出 `report.md`，必须含 4 个二级标题：`## 能力证据` / `## 风险证据` / `## 实测输出` / `## 审查意见处理`。

拓扑（**4 层**，`maxDepth: 3`、`maxAgents: 20`）：

```
顶层主持人 host (L0)
  ├─ lead_cap   (L1) ─ sub_cap   (L2) ─┬─ src_reader  (L3, cwd=src/)
  │                                    └─ code_probe  (L3, customTool=probe_metrics)
  ├─ lead_limit (L1) ─ sub_limit (L2) ─┬─ audit_reader (L3)
  │                                    └─ doc_reader   (L3)
  ├─ reviewer   (L1)
  └─ writer     (L1, cwd=输出目录)
```

10 个花名册成员，**6 个不同模型**、**3 个不同 cwd**、**7 种不同工具集**（`[]`/`[read]`/`[read,bash]+customTool`/`[read,write]`/`[spawn_agent,send_message]`/`+read`）：

| 成员 | 层 | 模型 | tools | cwd |
|---|---|---|---|---|
| lead_cap | 1 | deepseek-v4.1-flash | spawn_agent, send_message, read | 仓库 |
| lead_limit | 1 | qwen3.8-flash | spawn_agent, send_message, read | 仓库 |
| sub_cap | 2 | mimo-v2.6-flash | spawn_agent, read | 仓库 |
| sub_limit | 2 | glm-5.3-flash | spawn_agent, read | 仓库 |
| src_reader | 3 | qwen3.8-flash | read | `src/` |
| code_probe | 3 | **deepseek-v4-pro** | read, bash + customTool `probe_metrics` | 仓库 |
| audit_reader | 3 | mimo-v2.6-flash | read | 仓库 |
| doc_reader | 3 | glm-5.3-flash | read | 仓库 |
| reviewer | 1 | deepseek-v4.1-flash | read | 仓库 |
| writer | 1 | deepseek-v4.1-flash | read, write | 输出目录 |

4 轮协作：**R1** 顶层一条消息并行派两个组长（组长各自再往下派两层）→ **R2** 派审查员挑错 → **R3** 顶层把审查意见回灌给两个组长收修订 → **R4** 派写手落盘。

### A / B 两种写法的唯一区别 = 怎么投递

| | A 写法（自然写法） | B 写法（按基线 K 推的安全纪律） |
|---|---|---|
| 轮次进行中追加澄清 | 直接 `send()` 给正忙的组长（**库文档明说忙时排队、永不抛错，这就是库设计的使用方式**） | 串行队列 + 先 `waitForIdle()` 再投 |
| 投递审查意见后 | `send(critique)` 之后**紧跟** `prompt(修订)` | 统一走 `SafeMember.ask()` |
| 读回结果 | `agent.lastResult` / `RunResult.text` | 「投递前 `session.messages.length` 游标 → 新增 assistant 消息」切片 |

B 的纪律就四条（`safe.ts`，注释加代码 62 行，**去掉注释与类型约 25 行**）：
D1 同一个 agent 上永不重叠（本地 Promise 链做互斥）；D2 投递前判别 `status/isStreaming`，忙则 `waitForIdle`（因为 `spawn_agent` 也会起这个 agent 的一轮，本地链看不见它）；D3 不采信 `lastResult`/`RunResult`，用游标切片；D4 不混用 `send`/`prompt`。

## 结论速览

1. **A 写法在真实规模下 2/2 串台，且是库自己推荐的使用方式造成的** —— 两个组长的 `spawn_agent` 返回值都变成了「澄清回复」，顶层主持人的第一轮证据基础整个是错的人的东西。（E2）
2. **B 写法 2/2 归属正确、交付物完整落盘** —— 安全纪律确实存在且可行，但**库不提供它**，设计者要自己写约 25 行。（E3、E4）
3. **代价可量化**：B 比 A 墙钟 +67%、token +12.4%（A $0.024697/201.8s → B $0.028858/337.8s）。（E4）
4. **`send()` 在预算耗尽时返回 `{delivered:"ran"}` 而一个字都没跑**，同时 `lastResult` 里躺着上一轮的完整结论、`status` 是 `idle` —— 三个信号一致指向「成功」。（E8）
5. **预算在真实规模下是废纸**：`budgetTokens=130000`（完整跑的 60%），R1 一轮就烧掉 117245（0.90×），R2 结束 143960 = **1.11× 击穿**，「派写手落盘」那一步直接被拒 → **交付物为零**。（E8）
6. **一个成员必然失败时，兄弟不受影响、父没瞎编，但失败成员的配额与花名册登记都留着**，且失败只以「一条普通工具结果文本」呈现，形状与成功结果不同（没有 `已让成员…` 头，因此没有 agentId）。（E5）
7. **一个成员极慢时，兄弟分支不被拖住，但顶层那一轮被最慢分支锁死**：3 快 20.4s → 加 1 慢 36.3s，快的三句话早就返回了却没人能处理。（E6）
8. **中途 kill 中间层后，祖先对真正的后代投递被拒，且理由是事实错误**（「a4 不是你的后代」，而 a4 确实是它的后代）；同时产生一个跑到完成、结果没人收的孤儿。（E7）
9. **4 层转述会把「实测输出」丢掉一半**：B 的交付物里带着探针测出的真数字（864 行 / 6 文件），A 的交付物里一个数字都没有。（E4）
10. **同刻真正在跑的 provider 请求 ≈ 4**（4 个 L3 叶子同时生成）；父/叔伯层级都只是 await，不是并发源。（E6、E9）

- **读出的现象**：两侧的交付物都在，格式都合格（4 个二级标题）。但 A 的「能力证据」「风险证据」两节的**头一条**是**澄清回复**（`## 能力证据` 下第 1 条 = lead_cap 的澄清回复原文，`## 风险证据` 下第 1 条 = lead_limit 的澄清回复原文），真正的组小结要到第 2 条才以「修订版」的形式出现，且已被审查意见改写；A 的探针实测数字在 4 层转述里彻底丢失，B 的留下来了。
- **结论**：**诚实标注两点** ——
  1. A/B 不是逐字可比的对照（真实模型有随机性：B 这一跑里子代自己多派了 2 个 `src_reader` 做交叉核对，A 没有）。所以**墙钟 +67% / token +12.4% 只能当量级参考**，不能说「安全纪律的精确开销就是这些」。

### E5 故障注入 F1：一个成员必然失败

- **问题**：一个成员必然失败（模型不可达 / 子分身首轮就炸），它的父、它的兄弟、整条链会怎样？父 agent 会不会瞎编？
- **方法**：`node audit/25-e2e-stress/faults.ts f1`。同一条消息里并行派 3 个：`ok_worker`（正常）、`bad_model`（`model: "opencode-go/no-such-model-xyz"`，构造期就该炸）、`bad_auth`（`agentDir` 指向一个空临时目录，构造能过、首轮 `prompt` 炸）。
- **原始输出**：

```
  R1 墙钟 9045ms；驱动层抛错=无
  R1 顶层文本：第 1 轮三次 spawn 的返回文本，原样如下：
    **ok_worker**    已让成员「ok_worker」处理，它的分身 id 是 a2。 1+1 等于 2。
    **bad_model**    模型「opencode-go/no-such-model-xyz」解析有警告：Model "no-such-model-xyz" not found
                     for provider "opencode-go". Using custom model id.
    **bad_auth**     No API key found for opencode-go. Use /login to log into a provider via OAuth or API key.
  error 事件：[]
  是否把失败成员编出内容（未提到失败/未取得）= false
  存活分身：["host","ok_worker","bad_auth"]  用量 7151 tok  $0.000836
```

- **读出的现象**（四条，都重要）：
  1. **兄弟完全不受影响**：同一条消息里的 3 个 `spawn_agent` 各自独立，一个抛错不影响另外两个，`ok_worker` 正常返回。R1 只花了 9.0s。
  2. **失败以「一条普通工具结果文本」呈现**，与成功结果的形状**不同**：成功的以 `已让成员「X」处理，它的分身 id 是 aN。` 开头（又带 agentId），失败的**只有一句错误文本**，没有 agentId、没有 `details`、没有 `error` 字段。设计者想按前缀解析 agentId，在失败分支上会拿到空。
  3. **`bad_auth` 被登记进了宿主且留着**：`存活分身=["host","ok_worker","bad_auth"]` —— `createAgent` 在离线状态下成功（基线 I4），`child.prompt` 才炸；它**已经消耗了 `created` 计数（maxAgents 终身配额）**并留在 `host.list()` 里。`bad_model` 则因为构造期抛错没登记（干净）。
  4. **父没瞎编**，但代价是提示词里必须写一句「如果某个成员没给出结论，必须写「未取得结论」并说明原因，不许替他编」。去掉这句话会不会瞎编，本轮**未测**。
- **结论**：部分能。**孤立性合格**（兄弟不连坐、无 error 事件泄漏爆炸），**但失败语义不合格**：错误没有类型、没有 agentId、与成功结果的形状不一致；**失败的成员不回滚配额**（基线 4.3 的同一根因在故障路径上复现）。
- **设计者要多少额外代码才能优雅处理**：约 **15–25 行**。必须在每个 `spawn_agent` 之后自己扫 `pre` 前缀 + 自己维护 `spawned → member` 映射 + 自己判「这条返回是错误还是结论」（无 `error` 字段可用）+ 失败后自己 `dispose()` 把配额还回去（框架不会自动还）。

### E6 故障注入 F2：一个成员极慢

- **问题**：一个成员极慢，其余分支会不会被拖住？整体墙钟由谁决定？
- **方法**：`node audit/25-e2e-stress/faults.ts f2`。`slow_worker` 挂一个 `customTool slow_probe`（服务端 `sleep(25000)`），先跑基线（只派 3 个快工人），再在同一条消息里派 4 个（3 快 + 1 慢）。
- **原始输出**：

```
  [基线] 3 个快工人：顶层墙钟 20375ms；各轮 fast3=4797ms fast1=5433ms fast2=11054ms
  slow_worker 实际调用的工具：["slow_probe"]
  [混跑] 顶层墙钟 36317ms；slow_worker 轮长 30627ms；
         fast 结束时刻 fast3@10827 fast1@11463 fast2@17084 … slow 结束 @53686
```

- **读出的现象**：
  1. **快分支没被拖住**：3 个快工人在 10.8 / 11.5 / 17.1s 就结束了（慢的那个要到 53.7s）。
  2. **但顶层那一轮被最慢分支锁死**：顶层墙钟从 20.4s（基线）变成 36.3s ≈ 慢分支的 30.6s + 开销。在一条消息里派出去的工具调用是并发执行的，但 `prompt()` 要等**全部**工具返回，所以**先到的结果无法先处理**，「谁最后完成谁决定这一轮的墙钟」。
  3. 跨分支不互相拖累（不同父的子代互不干扰）。
- **结论**：部分能。**并发本身是对的**（4 个 provider 请求真并发，这一条也是本轮实测的并发峰值 ≈ 4）；**但没有任何「先到先处理 / 部分结果可用 / 超时放弃」的机制** —— 一个慢成员会把整轮变成「等最慢的人」，且没有超时（README 自己的死锁规则要求"任何无超时等待都不允许"，而 `spawn_agent` 的 `await child.prompt(task)` 就是无限等待）。
- **设计者要多少额外代码**：约 **20–30 行**。要么自己 `Promise.race` 一个超时然后 `abort()` 那个分身（还要自己判断 abort 后有没有孤儿）；要么放弃 `spawn_agent`、自己用 `createAgent` + 直接控制并发与超时。

### E7 故障注入 F3：中途 kill 一个中间层

- **问题**：在真实任务里 `dispose` 一个正在跑 `spawn_agent` 的中间层，实际后果是什么？后续轮次会不会失败？报错是不是「不是你的后代」？
- **方法**：`node audit/25-e2e-stress/faults.ts f3`。拓扑 `host → lead → sub → leaf`；在 `leaf.status === "running"` 时对 `sub` 调 `dispose()`；然后 R2 让顶层对 **leaf（真正的后代）** 投递；R3 让它如实报告断点。
- **原始输出**：

```
  kill 时刻：{"mid":"a3","leaf":"a4","leafParent":"a3","midStatus":"running",
              "listAfter":["host","lead","leaf"],"midInList":false}
  R1 驱动层抛错=无；顶层文本=已让成员「lead」处理，它的分身 id 是 a2。 小组已组建：sub（a5）→ leaf（a6），
                          任务「查框架 maxDepth 默认值」处理中，待结论回传后我再补一句最终小结。
  kill 后：lead=a2 leaf=a4（parent=a3）leaf 仍在 list=true

  R2 send_message 返回：["只能给自己的后代分身投递：a4 不是你的后代（它可能是祖先、兄弟或不相干的分身）。"]

  R3 顶层收场：## 任务结果报告（如实）
              **结论：任务未完成，且中间链路存在断点。**
              … 1. **a2 的「最终小结」从未到达我。** … 按我目前的工具集（只有 spawn_agent / send_message，
              没有取结果的工具），我**无法主动拉取** a2、a5、a6 的任何输出，只能等，而它没有来。

  listAtEnd = ["host(a1)<--","lead(a2)<-a1","leaf(a4)<-a3","sub(a5)<-a2","leaf(a6)<-a5"]
  rounds = [{leaf 3195ms}, {sub 6140ms error:"This operation was aborted"}, {leaf 5593ms},
            {sub 48993ms}, {lead 69701ms}, {host 75374ms}, …]
  花费 $0.002896
```

- **读出的现象**（五条）：
  1. **被 kill 的中间层确实报错，而且是 in-band**：`sub(a3)` 那一轮的 `error = "This operation was aborted"`，并通过 `spawn_agent` 的 `run.error` 通道以「它这一轮出错了：…」的形式传给了 `lead`。**所以模型自己重试了**：它随后又派了 `sub(a5) → leaf(a6)`，任务实际完成了 —— 但这是**模型的功劳，不是框架的能力**。
  2. **产生孤儿且孤儿跑到完成**：`leaf(a4)` 在父被回收后继续跑完（5593ms、无错），留在 `host.list()`，`parentId=a3` 悬空，产出无人收取，token 照样计进 `host.usage`。
  3. **祖先对真后代的投递被拒，且理由是事实错误**：顶层对 `a4` 的投递返回「**a4 不是你的后代**」—— 而 `a1→a2→a3→a4` 是不折不扣的后代链。失败原因是 `isDescendant()` 沿 `parentId` 上溯时在已回收的 `a3` 处 `host.get()` 返回 `undefined` 就停了。设计者最可能的误诊是「我 id 记错了」。
  4. **顶层「如实报告」的质量出乎意料地高**：它明确写了「任务未完成，且中间链路存在断点」「我无法主动拉取」「这条补充消息没有出现」。**但这是靠一句提示词换来的**（我要求它「如果有分身被回收导致链路断了，必须明确指出断在哪里、谁收不到消息；不要假装任务成功」）。
  5. 顶层在同一段报告里把 id 说成 `a2/a5/a6` 混着用（它的上下文里同时有 `spawn_agent` 的返回文本和它自己的推断），说明**没有 agent-id 的一致性视图**这条缺口在真实文本里就表现为「说不清谁是谁」。
- **结论**：**不能**。`dispose` 是「单位是分身不是子树」，中间层回收会（a）留下孤儿、（b）永久截断祖先的投递能力、（c）以事实错误的文案报错。**框架没有拓扑修复、没有孤儿回收、没有 re-parent**。
- **设计者要多少额外代码**：约 **30–60 行**。要自己维护 `parentId` 图 + 自己判「父已回收 = 断链」+ 自己收拢孤儿（`host.list()` 里 `parentId` 指向不存在 id 的都要捞出来）+ 自己重派。库对外只有 `list()`/`get()`，`list()` 里 `parentId` 悬空这件事没有任何标注。

### E8 紧预算：`budgetTokens` = 完整跑的 60%，跑到耗尽

- **问题**：预算设成任务用量的 60%，跑到耗尽 —— **已经跑完的部分能不能交付？** 设计者要多少代码才能优雅收场？基线 J1 说预算会被忙碌路径击穿，真实规模下击穿多少？
- **方法**：`node audit/25-e2e-stress/run-budget.ts`，`budgetTokens = 130,000`（= 完整 A 跑 217,777 的 **59.7%**）。A 写法（自然写法），跑到耗尽后再试三种落盘方式。
- **原始输出**：

```
budgetTokens=130000（完整 A 跑实测 217,777 tok 的 59.7%）
  R1 墙钟 151371ms ｜ 驱动层抛错=无 ｜ busy 通道投递=[{"delivered":"queued"},{"delivered":"queued"}]
  [R1 结束] host.usage=117245 / 130000  超支 0.90×
  [R2 结束] host.usage=143960 / 130000  超支 1.11×

  send 返回：[{"delivered":"ran"},{"delivered":"ran"}]
  send 路径上的 error 事件：["宿主预算已耗尽（budgetTokens=130000）：不再接新的一轮",
                            "宿主预算已耗尽（budgetTokens=130000）：不再接新的一轮"]
  紧随其后的 prompt 抛错：宿主预算已耗尽（budgetTokens=130000）：不再接新的一轮
  lead_cap.lastResult 文本： 【澄清回复】 已按补充要求补一句，并采信 `src/agent/events.ts` 的源码原文（48 行）…   ← 上一轮的陈旧结论

  R4 顶层 prompt 抛错：宿主预算已耗尽（budgetTokens=130000）：不再接新的一轮
  R4 结束时交付物状态：report.md exists=false bytes=0            ← 交付物为零
  R5 耗尽后 send → {"delivered":"ran"}；error 事件=["宿主预算已耗尽（budgetTokens=130000）：不再接新的一轮"]
      usage 143960→143960（一个字都没跑）；lastResult 仍读到上一轮的【澄清回复】

  [兜底1 同宿主直接 createAgent] createAgent 抛错：宿主预算已耗尽（budgetTokens=130000，已用 143960）
  [兜底2 摘掉 host] 成功 text=已写入 `report.md`。 # 预算耗尽后的最小交付 花费 $0.000641

  预算耗尽时：overshoot=1.11×  存活分身=15 个（含 host）
  实测：预算 130000 ｜ 实花 143960 tok ｜ $0.016843 ｜ 墙钟 207611ms
```

- **读出的现象**（五条）：
  1. **击穿幅度 1.11×**：检查只在 `prompt()` 开头与 `spawn_agent` 预检做；R2 在 117,245（<130k）时被放行，一轮跑完到 143,960。**单轮不封顶**——在真实规模下 R1 一轮就吃掉 117k（预算的 90%）。
  2. **忙碌路径：`send()` 返回 `{delivered:"ran"}` 但两轮都没跑**，只有两条 `error` 事件；`host.usage` 一动不动。**三信号一致误导**：`delivered:"ran"` + `status:"idle"` + `lastResult` 里躺着上一轮的完整结论。轮询式设计者（`send → waitForIdle → 读 lastResult`）会静默拿到上一轮的答案并当作本轮结果。**两条对照都打印了**：R5 的 `send` 返回 `ran`（谎报）与 `usage 143960→143960`（确实没跑）并列在同一段输出里。
  3. **交付物为零**：耗尽发生在「派写手落盘」之前，`top.prompt` 一抛错，整条链没有产出任何文件。已经跑完的 R1/R2 成果躺在各分身的 `session.messages` 与 `lastResult` 里，**没有任何框架级出口**。
  4. **耗尽后无法在同宿主上做任何事**：`createAgent(..., {host})` 直接抛「宿主预算已耗尽」。
  5. **唯一的兜底是摘掉 host**：`createAgent` 不带 `host` 就绕过了预算检查，花费 $0.000641，**且这笔钱不进 `host.usage`**（`usage 143960 → 143960` 不变）—— 预算是「宿主的记账闸门」，不是「钱包的天花板」。
- **结论**：**不能交付**。60% 预算下（即「按完整用量打 6 折拨款」）实际后果是：跑完研究、跑完审查，然后卡在落盘那一步，产出零文件，超支 11%，且设计者看到的成功信号是假的。
- **设计者要多少额外代码优雅收场**：约 **20–30 行**，而且必须包含一个「**摘掉 host 才能继续**」的逃生阀（见兜底 2）：自己预估每轮开销（框架不给预估）、自己在每个投递点前判预算（框架只在 `prompt` 开头判）、自己缓存已完成轮的产出、耗尽了就换个不挂 host 的分身落盘（花费还不在总账里）。

### E9 规模与成本的实测上限（谁在等谁）

**同刻真正在生成 token 的分身数 ≈ 4**。近似按轮次区间重叠算出来的「9」是把「阻塞中的祖先」也算进去了 —— `spawn_agent` 是同步的，父/叔伯在自己那一轮里全程 `await`，它们不产生并发请求。

一次完整 4 层跑的等待链（B 跑）：

```

t=  3571→ 48597ms  lead_cap(a2)  ← 组长在第一轮里等 sub_cap
t=  6495→ 44256ms  sub_cap(a4)   ← 副组长在等两个叶子
t=  9837→ 22846ms  code_probe(a7)   ┐ 这 4 个才是真并发的 provider 请求
t=  9837→ 30577ms  src_reader(a6)   │
t= 14577→ 30068ms  doc_reader(a9)   │
t= 14577→ 43927ms  audit_reader(a8) ┘
```

规模实测（同一任务，两种写法）：

| | A | B |
|---|---|---|
| 花名册成员 | 10 | 10 |
| 树层数 | 4（L0–L3） | 4 |
| 协作轮次 | 4（R1–R4，另有追加澄清轮） | 4（+追加澄清轮） |
| 创建的分身 | 11 | 13 |

| 端到端交付 | 文件落盘但内容错 | 文件落盘且内容对 |

### E10 三个判断题（每条附本次实测依据）

#### ① 这个框架现在**能**支撑什么规模的集群？

- **成员 8–10 个、4 层（L0 主持人 → L1 组长 → L2 副组长 → L3 组员）、4 轮协作、树形拓扑、同步委派** —— 实测完整跑通并落盘（E3、E4）。
- **同刻并发 provider 请求 ≈ 4**（E6 混跑：3 快 + 1 慢同时真并发；E9 时间线：4 个 L3 叶子同窗口生成）。超过这个数的"并发"要靠「一条 assistant 消息里多个工具调用」触发，而父级全在 `await`。
- **异构是真的**：6 个不同模型、3 个不同 cwd、7 种不同工具集，全员按各自的 `role` 干出了符合角色的事（E2/E3 各成员轮次输出）。
- **成本可控**：一次 $0.025–0.03、墙钟 3–6 分钟。
- **前提**：必须自己写投递纪律（B）。不写就是 E2。

#### ② **不能**支撑什么？

1. **重叠投递下的结果归属**（E2）：库自己推荐的「忙时 `send` 排队」会静默污染 `spawn_agent` 的返回值。2/2 命中。
2. **预算当闸门**（E8）：软约束、单轮不封顶（1.11× 击穿）、忙碌路径直通、耗尽后只能摘掉 host 才能交付（且脱账）。
3. **回收后的拓扑一致性**（E7）：中间层 `dispose` 永久截断祖先→后代的投递能力，报错还是事实错误；孤儿跑到完成、产出去无踪影。
4. **失败的语义与配额回收**（E5）：失败只以「一条与成功形状不同的文本」出现，无类型、无 agentId；失败的成员留在花名册里、**不还 `maxAgents` 终身配额**。
5. **慢成员的等待边界**（E6）：`spawn_agent` 是无限 `await`，一轮被最慢分支锁死，无超时、无部分结果。
6. **多跳信息保真**（E4）：4 层转述下，A 的交付物丢掉了探针的实测数字，B 的保住了 —— 但那是模型自觉，不是机制。
7. **交付物可信性**：B 的交付物里有一条被本轮实测证伪的结论（「串台在正常工具链上不成立」），而框架没有任何机制能发现它（E4）。

#### ③ 如果现在就要用它做真实工作，最必须补的三个东西是什么？

**1）`RunResult` 与「这一次调用」绑定（对应 E2、E3、E4）**
最小形态：给每次 `prompt()` 分配 run id，`collectRun` 只排干属于本次 run 的消息（或者直接返回「本次新增 assistant 消息数组」而不是「最后一个 + 总和」）。**这是唯一一条「不补就没法做真实工作」的**：它让主力委派原语说错话。现成的替代品在 25 行里可复现（B 的游标切片），但没有库提供 → 每个设计者都会重犯。附带把 K5（`send` 后紧跟 `prompt` 必抛）收敛成交互契约。

**2）资源层隔离（对应 E5、E6、E8）**
- **配额随回收返还**：`maxAgents` 卡 `created` 终身计数，回收不还，失败成员也不还 —— 长驻集群会在几十次派活后死锁。
- **预算变硬天花板**：轮前判不够，要在「单轮内累计」与「忙碌通道（`followUp`/`steer`/`send`）」上都设闸；耗尽后要有**出口**（可交付的收尾通道），而不是「只能摘掉 host」。
- **等待要有超时**：`spawn_agent` 里那条无超时的 `await child.prompt(task)` 与库自己的死锁规则相冲突（E6 实测一轮被 25s 慢分支锁死）。

**3）失败语义 + 拓扑一致性（对应 E5、E7）**
- 返回值带 `code`/`kind`（`spawn_failed` / `child_run_error` / `guard_rejected` / `aborted`）与稳定的 `agentId`，形状与成功结果一致；失败自动回收配额。
- `dispose` 要么是子树、要么在 `parentId` 上留墓碑并让 `isDescendant` 能穿透墓碑（现在是**对真后代说「不是你的后代」**，属于事实错误的报错）；`list()` 要能标出孤儿与断链。

## 没做完 / 跑不通的

1. **A/B 不是逐字对照**：真实模型有随机性（B 那一跑子代自己多派了 2 个 `src_reader`）。所以 +67% 墙钟 / +12.4% token 只能当量级参考，不能说这是安全纪律的精确开销。
2. **「父会不会瞎编」只测了「提示词里明令禁止编造」的情况**。去掉那句约束后会不会瞎编，本轮**未测**（F1 里 `hallucinated=false`，但这是被提示词兜住的）。
3. **429 / 限流未触发**，因此**限流下的行为完全未覆盖**（任务书要求记录 429；本轮一次都没出现）。
4. **`maxAgents` / `maxDepth` 护栏在真实规模下未被撞到**（用了 20/3，实际创建 13，最深 3 层）。E5 的「失败成员不还配额」是从 `存活分身` 与 `created` 语义推出的，**没有跑到「配额被失败成员吃满」那一步**。
5. **`thinking` 档位、内容拒答**本轮完全没碰（沿用基线，未重测）。
6. **3 次 A 跑中的前两次因我方脚本 bug 作废**（writer 的 `cwd` 未接线/模型自己写绝对路径到仓库根），产出目录 `audit/25-e2e-stress/out/a-20260930155859/` 为空目录保留作痕迹；这两次的钱（$0.048079）已计入总账。
7. **F3 的 kill 命中不是「确定性」的**：探针循环 120ms 一次、命中条件是 `leaf.status==="running"`，本轮命中的是第一次的 `sub(a3)`；不同时序下可能命中别处。
