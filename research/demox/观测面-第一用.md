## 2. ★★★ 第一次用：`tail` vs `onResult` 的机制之谜解开了

### `tail`（挂消息尾部）—— **不是"埋得深"，是"压根没挂上"**

```
第 1 轮: ★含账本=true      ← 挂在 user 消息上（消息还少）
第 2 轮: ★含账本=false     ← ★ 账本不见了
第 3 轮: ★含账本=false
```

**原因**（现在直接看得见）：
`context.override` 每轮都拿**当前那批消息**重算，
而第 2 轮是**新的一批**（历史 + 工具结果）——
**上一轮挂上去的账本，不在这一批里。**

> ★★ **所以「挂消息尾部」的本质是**只对当轮有效**，而注入时机还错了（账本尚未累加）。**
> **我原来猜的机制（"埋在历史末尾看不见"）是**错的** —— 它是**没挂上**。**

### `onResult`（挂工具返回值）—— **进到了内容里，而且一直在**

```
第 3 轮: ★含账本=true    ← 工具返回值里的账本 → 成为 toolResult 消息
第 4 轮: ★含账本=true    ← ★ 而且**持续存在**
```

---

## 3. ★★ 由此得出的通用机制

| 注入手段 | 改的是什么 | 是否持久 |
|---|---|---|
| `context.override` | 只改**这一轮**发给模型的那一份（pi 从原始历史重建下一轮） | ❌ **当轮有效** |
| `tools.onResult` | 改**工具返回值**，它会**成为一条 toolResult 消息**进历史 | ✅ **持续存在** |
| `context.replace/erase` | 追改历史 entry（append-only） | ✅ 持续 |
| `context.compact` | 压缩历史 | ✅ 持续 |

> ★★ **判据：「改的是**即将发出的那一次**，还是**会存进历史的东西**？」**
> **前者只活一轮，后者才累积。**

★ **这一条直接补上了 [`未解决问题清单.md`](未解决问题清单.md) 里 A2 的机制**，
并且**改写了 P11 的做法 5**（原文说"必须挂工具返回值"，现在**知道为什么**了）。

## 4. ★ 观测面带来的第二个能力：**干预生效性**

```json
{"context.override":{"calls":3,"changed":3,"lastArgs":"{\"messages\":10}","lastReturn":"{\"messages\":10}"}}
```

**以前**：override 生效没有？→ **跑完看效果，靠猜**（A1 就栽在这里：判据写错、**生效 0 次都不知道**）。
**现在**：`calls` / `changed` / `lastArgs` / `lastReturn` **直接可读**。

★ **它已经抓到一个真事故**：测试时用 `msgs.slice(-2)` 做 override，
观测面显示**第 3 轮的 wire 里 assistant 消息不见了**（3 条：system + toolResult×2）
—— **我的干预悄悄破坏了上下文，而这件事以前看不见。**

---

## 5. 【做法】

| # | 做法 |
|---|---|
| 1 | ★★ **要"持续存在"就用 `onResult` / `replace`；要"只影响这一轮"才用 `override`** |
| 2 | ★★ **注入之后要看 `observe.wire` 确认它真的进了模型看到的内容** —— 别靠行为推断 |
| 3 | ★ **区分「它没听」和「它没收到」** —— 这就是观测面存在的理由 |
| 4 | ★ **干预点自带计数** —— 四次静默失败里有三次是"没生效但没报错" |
