# G1-1 · 反馈延迟相图结果

> 选题出处：[`研究规划.md`](研究规划.md) §2 的 G1-1（控制论 · 反馈延迟与稳定性）。
> 脚本 [`bench/scan.ts`](bench/scan.ts)（`flat-guarded` 系统）· 数据 `runs/G1-phase-A.jsonl`、`runs/G1-phase-B.jsonl`
> 成本：免费档，cost 恒为 0。

---

## 0. 一句话

**存在一个稳定岛，而且它的边界由「死区」而不是「采样率」决定。**

| | grace=0（不给余地） | grace=30（给余地） |
|---|---|---|
| **pollEvery=1**（检查及时） | **2/4** —— 产物被自己打死（产物为空 2 次） | **2/2** ✅ |
| **pollEvery=20**（检查迟滞） | 3/4，代价中位 29k | 1/1，但代价中位 **170k** |

> **控制器本身没问题，缺的是「让被控对象有时间响应」的那段余地。**
> 这正是 `demom` §10.5 坑 2 的干净复现 —— 而这次是在**受控扫描**下得到的，
> 所以它从"一次踩坑的经验"升级成了**一条可复现的规律**。

## 1. 实验设置

| 项 | 值 |
|---|---|
| 系统 | `flat-guarded`：单 agent + 实时护栏（`tool_call` 计数 → `steer`/`abort`） |
| 任务 | T-A，`corpusPairs=8`（18 份语料，8 个重复组）—— G0-3 测出的工作点 |
| 上限 | `callCap=20`（G0-3 实测：正常轮 20–40 次调用，失控轮 73 次） |
| 自变量 | `pollEvery ∈ {1, 5, 20}`（采样率）× `grace ∈ {0, 30}`（死区） |
| 控制方式 | `steer`（比例控制，不打断在飞那轮） |
| 重复 | 2 次/格 |

**为什么反馈信号是 `tool_call` 计数，不是 `agent.usage`**（`demom` §4.2 的库层缺口）：
`agent.usage` 在 **prompt 结算之后**才累加，跑的过程中是陈的 ——
拿它做实时闸会**静默不生效**。单轮内失控对它完全不可见。

## 3. 三条结论

### 3.1 死区（grace）决定成败：0 → 2/4，30 → 2/2

看 `pollEvery=1` 这一行，**唯一变的就是 grace**：

```
poll=1 grace=0    → 2/4   产物为空 2 次（被打死）
poll=1 grace=30   → 2/2   产物为空 0 次
```

逐轮读数（`grace=0` 那 4 轮）：

```
steered=[{calls:20, reason:"超过上限 20", grace:0}]   ← 第 20 次就拉
guarded=[{calls:21, cap:20, action:"拉过没用，abort"}]  ← 第 21 次就打死
序列长度 = 21，write 在第 21 次 / 或压根没写
产物 = 无
```

**模型在第 20 次被叫停，第 21 次就被打死 —— 它只获得了 1 次调用的收尾时间。**
而它正常需要几十次才能把产物写完。

> ★ **这就是控制论里「延迟使负反馈回路失稳」的实例**：
> 控制器的采样周期（1）比被控对象的响应时间（几十次调用）**小了 1–2 个数量级**，
> 于是控制器把系统打死了。**不是阈值设错了，是"拉回来"和"允许反应"之间没有留时间。**
>
> 修法不是降低采样率（那会让它发现得更晚），而是**加死区**：
> 发现越限 → 拉 → **允许超调 30 次调用** → 还不行才 abort。

### 3.2 采样率不影响成功率，只影响**代价**

对比 `grace=0` 那一列：

| pollEvery | ok | token 中位 |
|---|---|---|
| 1 | 2/4 | **11,231** |
| 5 | 2/2 | 24,498 |
| 20 | 3/4 | **29,026** |

**采样越密，代价越低**（11k vs 29k，2.6×）——它更早发现越限、更早开始收尾。
但**成功率反而更低**（2/4 vs 3/4）：因为发现得早 = 打得更早 = 更容易在产物写完前打死。

> **这是一个真实的权衡（trade-off），不是"调好参数就能两头兼顾"**：
> - 采样密 → **省 token，但更容易误杀**
> - 采样疏 → **不容易误杀，但代价高**
>
> 而**死区（grace）才是打破这个权衡的那一维** —— 它把「发现得早」和「允许收尾」解耦了。

### 3.3 代价的尾部依然在：170k 那一格

`poll=20 grace=30` 只有 1 轮，无法作结论，但它**通过了却烧了 170k token**（中位数的 6 倍）。
与 G0-3 的发现一致：**护栏控制的是上界，不是方差。**
一个对的护栏仍然可能允许一次很贵的运行。

## 4. 与 `demom` 的对接

| demom 的发现 | 本次 |
|---|---|
| §10.5 坑 1：「连续 20 次调用没 note/write」当触发条件 → **0/2**。因为「读材料」本来就是正常工作 | 本次触发条件换成了**纯粹的调用计数**，避免了把正常工作当异常 |
| §10.5 坑 2：「拉完不给余地」→ 2/3；加 `GRACE=30` → **3/3** | ✅ **完整复现**：`grace=0` 2/4 → `grace=30` 2/2 |
| §10.5 结论：「steer 之后必须抬高上限」 | ✅ 且本次量化了：**固定的 `grace=0` 是最差的配置** |
| 「阈值必须从实测分布里取，不能拍脑袋」 | ✅ G0-3 给出了分布（正常 20–40，失控 73），本例取 cap=20 正是落在这个区间下沿 |

**新增的一条（demom 没有的）**：采样率与死区**不是同一件事**。
`demom` 只发现了「要给余地」，本次发现**采样率是独立的一维**，且它与成功率是**反向**的
（密采样省钱但易误杀）。要两个都要，只能靠死区。

## 5. 局限（必须一起看）

1. **n 极小**：`grace=30` 两格只有 2 和 1 轮。`2/4 → 2/2` 的对比**在噪声内**。
   本节的价值在于**机制被看见且方向一致**（每轮都有 steer/abort 记录可查），不在数字精度。
2. **只有一个 cap 值（20）**。cap 与 grace 是耦合的 —— 换 cap 后稳定岛的位置会移动。
3. **`pollEvery=20` 的"迟滞"是采样意义上的**，不是真正的滞回（连续 k 次异常才动）。
   真滞回（G1-3）还没做。
4. **单 agent、无委派**。带委派时控制器要管多个对象，"被打死的代价"会不同。
5. **`abort` 用的是 `io.interrupt`（截断输入）**，它会把当前轮打断 ——
   所以"产物为空"里有一部分是**打断本身**造成的，不全是模型没来得及写。
   这也解释了为什么 `grace=30` 能救：它让 abort 不发生。

## 6. 建基建时修掉的两个真 bug

1. **异步 `steer` 在 agent dispose 后执行 → 抛错打死整个扫描。**
   ```js
   void agent.io.steer(...)  // 发后不管，但 agent 可能已经被 dispose
   → Error: agent ... 已 dispose（disposed），不能再操作
   ```
   第一次跑相图时，**这一个异常让整个进程挂掉**，后面所有轮次都跑不了。
   → 已修：加 `finished` 旗 + `safeSteer`/`safeInterrupt` 包装（不抛、不阻塞、结算后不发）。

2. **单轮异常会打死整批扫描。**
   → 已修：`runWithRetry` 用 try/catch 把系统抛的异常包成一条可归档记录，
   单轮坏掉不弄脏后面几十轮。**一个 bug 吃掉一整批数据**是最亏的失效模式。
