## 一、分析：把 22 条做法 + 8 条分析 + 2 条特性，逐条过一遍它对这个集群说什么

### 1.1 ★★★ 最重要的一条：`P10` 我读错了，而正确读法改变了整个拓扑

**`P10` 的实测**：

| 形态 | 通过 | token | |
|---|---|---|---|
| `carry` **完整交接** | 3/4 | ★ **66,609** | ★★ **比 flat 便宜 2.1 倍** |
| `flat` 单 agent | 4/4 | 139,860 | |
| `redundant` 冗余 | **1/3** | 165,792 | ★ 最差 |
| `pipeline` 流水线 | 3/4 | 212,121 | |
| `star` 星形 | 4/4 | 233,987 | |

★ 原结论写的是"四种多 agent 没有一个在质量×成本上胜过单 agent"。
★★★ **但设计者指出这个读法不对，我复核后同意 —— 请看 P10 自己写的失败机制：**

| 形态 | P10 自己写的失败原因 | 这是"多 agent 必然"吗 |
|---|---|---|
| `pipeline` | 上游读过的下游**要重读**（28.3% 跨 agent 重复读） | ✗ **交接设计问题**（P9 说完整交接能治） |
| `star` | scout 产出**要回 coordinator 再过一遍** | ✗ **拓扑绕路** |
| `redundant` | 3 倍读入 + **交集投掉少数派**（P7） | ✗ **合并规则问题** |
| ★ **`carry`** | ✅ **完整交接 → 便宜 2.1 倍** | ★★ **设计对了的多 agent** |

★★★ **正确结论**：
> **不是「多 agent 不如单 agent」，而是「当时那几个多 agent 设计得不好」。**
> ★ **`carry` 是唯一设计对了的，它直接便宜 2.1 倍（66k vs 140k）。**

### 1.2 ★★ 而且 `P10` 的实验条件是最不利于多 agent 的

```
任务 T-A：读 26 份文件 → 分成 12 对
★ 一个 agent 一次就能做完（B6 上下文够），且能肉眼验证最优解
★ 线性任务，没有需要并行的部分；scouts 同质（不是不同视角）
```

★★ **多 agent 该赢的场合，`P10` 一个都没测**：

| 多 agent 该赢的场合 | P10 测了吗 |
|---|---|
| ★ **上下文装不下**（B6 硬边界） | ✗ 26 份装得下 |
| ★★ **要不同视角 / 不同知识** | ✗ scouts 是同质的 |
| ★★ **要独立校验**（故意不共享上下文） | ✗ redundant 是"同样做法做 3 遍" |
| ★★ **要并行探索多条路** | ✗ 线性任务 |
| ★★★ **要长期沉浸 + 有人管全局** | ✗ 单轮任务 |

★★★ **而"研究员集群"恰恰全中**：
```
上下文装不下   ← ★ B6：430 轮历史 + 全库材料，一个 agent 装不下
要不同视角     ← ★ C2：系统科学 / 信息论
要独立校验     ← ★ C5：review 要干净上下文
要并行探索     ← ★ 多条候选方向
要全局         ← ★ C2 途径 1：复审目标需要全局视野
```

★★★ **⇒ 设计律 1：多 agent 该赢在「单 agent 结构上做不到的地方」。**
★ 错的是 `P10` 的**形态是预先设计的、且不是为这些场合设计的** —— **不是"多 agent"本身。**

### 1.3 ★★★ 设计律 2：必须给"路"，不能只给"禁令"（`P12`，硬证据）

## 二、★★★ 从七条律推出的**拓扑**（不是预先摆座位）

### 2.1 第 2 稿的病（对照 `P10`）

★ 我第 2 稿摆了六个常驻角色 + 一张固定拓扑图 ——
★★ **那正是 `P10` 的病：形态是预先设计的，不是从需要里长出来的。**
★★ **而且 `P13` 说：它不会主动用你给的通道** —— 我摆了座位，但**没人来坐**。

### 2.2 新形态：**一个"根" + 按情况长出来的"分支"**

```
                    ┌──────────────────────────────────┐
                    │  researcher（★ 唯一的常驻）        │
                    │  沉浸在研究对象里：                │
                    │  找问题 → 设计实验 → 跑 → 分析      │
                    │  → 复审目标 → 再找问题              │
                    └──────────────┬───────────────────┘
                                   │ ★ 代码监听它的"情况"
        ┌──────────────┬───────────┼───────────┬──────────────┐
        │              │           │           │              │
   【写出成果】   【撞到"库做不到"】 【上下文快满】 【要跨学科】  【长时无产出】
        ↓              ↓           ↓           ↓              ↓
   inspector      libsmith    archivist    inspirer       watchdog
   鼓励+纠正      改 lib/      复审目标      借学科视角      区分探索/卡住
   +判停 ★        （★ 给路）                     │
        │              │                        │
        └──────────────┴────────────────────────┘
                       │ 它们的产出回到 researcher
                       ↓
                  （★ 是新探索，不是"下一轮"）
```

★★★ **与第 2 稿的关键差别**：

| | 第 2 稿 | 第 3 稿 |
|---|---|---|
| 角色 | ★ **六个常驻** | ★★ **一个常驻，其余按情况长出来** |
| 触发 | 我写触发规则 | ★★ **代码监听"情况"，长出来的角色是"路"** |
| 依据 | 我的直觉 | ★★ **`P10`（形态要从需要长）+ `P13`（它不会主动用通道）** |

### 2.3 ★★ 五个"情况"分别是什么（这是拓扑的真正内容）

| 情况 | 怎么判定（**代码，不是提示**） | 长出什么 | 依据 |
|---|---|---|---|
| ★ **写出成果** | `outbox/` 有新 `.md` | `inspector`（干净上下文，只读） | `C5` + `P24` |
| ★★ **撞到"库做不到"** | 它连续撞同一堵墙 / 它写了能力缺口文档 | `libsmith`（**有 `lib/` 可写**） | ★★ **`P12`：给路不给禁令** |
| ★ **上下文快满** | `observe` 面的 token 曲线 | `archivist`（复审目标，全局视野） | `B6` + `C2途径1` |
| ★ **要跨学科** | 它自己的探索卡在一个"概念"上 | `inspirer`（借系统科学/信息论） | `C2途径2` |
| ★ **长时无产出** | 工具调用在转圈（同一文件反复读/同样命令重复） | `watchdog`（区分探索/卡住） | `P16`（成本在定位）+ `P23` |

★★★ **注意"上下文快满"这一条** —— 它是 `B6` 的直接后果，**而第 2 稿完全没有它。**
★ 这是"从特性推拓扑"的一个真例子：**B6 ⇒ 需要有人管全局；而研究员沉浸在局部，装不下全局。**

### ① `researcher` · 研究员（**唯一常驻**）
