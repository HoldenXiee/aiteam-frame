# 真实工作形态调研（任务设计的依据）

> 2026-10-15 · 委托调研，非本项目实验。
> **用途**：`demox` 的任务要从**真实劳动**里提取，不从理论里造（清单 §0.3）。
> 本文就是那份"真实劳动"的底稿。每条都尽量带出处；推断会标出来。

---

## 0. 一句话

**真实工作里「能不能并行」几乎不由任务决定，而由「是否写共享状态」决定。**

这比任何从理论造出来的任务形状都更适合当实验骨架 —— 因为它是**可操作的结构判据**：
一个活能不能并行，问一句「它有没有隐含决策要落到共享状态上」就够了。

---

## 1. 六类活的系统形状

### 1.1 软件工程（素材最富）

| 子类 | 形状 | 校验位置 | 能否回滚 |
|---|---|---|---|
| 改 bug（SWE-bench 型） | **串行深链**：读 issue → 定位 → 改 → 跑测试 | **最后一次性**（测试） | 可重跑 |
| 加新功能 | 串行深链，**交接面宽**（架构决策） | 最后 | 合并前可 |
| 大规模重构/迁移 | **笛卡尔积**：N 文件 × M 模式 | 每处可局部验，**边界交互只有最后能验** | 需分批提交 |
| 代码审查 | **并行扇出**：1 协调者 + 最多 7 专家 | 完成后集中（协调者去重） | 天然幂等 |
| 写测试 | 并行（每模块独立） | **立即**（测试自己就是判据） | 幂等 |

**真实数据点（Cloudflare）**：每次 MR 起最多 **7 个专门 reviewer**（安全/性能/质量/文档/发布/合规），
由一个**协调者**去重、判级、合并成一条评论；按风险分层 ——
typo 走 2 agent（**$0.20**），大改动走 7+ agent（**$1.68**）；中位时延 3 分 39 秒，P99 **$4.45**。
协调者独占最强模型（Opus 4.7 / GPT-5.4），子 reviewer 用中档，文档 reviewer 用免费模型。
<https://blog.cloudflare.com/ai-code-review/>

★ **关键结构**：它不是"一个 agent 干七件事"，而是**共享上下文写盘**、
7 个子 reviewer **各自读、且只读自己的 diff 分片** ——
因为"把 MR 上下文复制七份会让 token 成本乘 7"。
**这是一条真实的「交接面窄化」证据。**

### 1.2 研究与写作（唯一被证实适合并行的领域）

**Anthropic Research 的形状**：orchestrator-worker ——
Lead agent 分解 → 起 **3–5 个子 agent 并行** → 各自多轮搜索 → 回传结论给 lead →
lead 综合、判断是否再起一轮 → 最后交给 **CitationAgent** 单独做引用归属。

三个硬数据：
- 多 agent vs 单 agent Opus 4：快 **90.2%**（内部评测）
- **token 用量解释 BrowseComp 80% 的性能方差**
- 多 agent 比 chat 多烧 **15× token**

**且 Anthropic 自己划了红线**：
> "大部分 coding 任务的真正可并行部分比研究少，LLM 还不擅长实时协调与委派"

他们明确说多 agent 只适合「**重并行、信息超单上下文、工具复杂**」的活。
<https://www.anthropic.com/engineering/multi-agent-research-system>

**另一个真实形状**：文献综述 = **串行流水线 + 双向校验**，"每一句话都要对回原文"。
⚠ 这是 **O(n)** 而不是 O(n²)，因为校的是**断言↔出处**的一对一映射。
<https://luneresearch.com/blog/literature-review-with-claude-code>

### 1.3 运营与客服（升级机制是核心形状）

**形状 = 分流 + 升级**：AI 解决 **65%**，剩余走人；
**升级判定本身是独立的一项任务**（Fin 专门为"该不该升级"训了一个多任务模型）。
ElevenLabs 月处理 **22,000 张工单**、65% 端到端解决、平均首响 60 秒。
<https://fin.ai/research/to-escalate-or-not-to-escalate-that-is-the-question/>
<https://elevenlabs.io/blog/how-we-solve-22000-support-tickets-every-month-with-elevenagents>

★ **系统科学意义**：这是**唯一天然含「判断/执行分离」和「负反馈控制器」的领域** ——
**升级率是显式控制变量**，调高调低都有明确代价（漏接 vs 淹没人工）。
这是测**反馈延迟与稳定性**（G1）最好的素材。

### 1.4 数据与文档处理

**形状**：提取 → 规则校验 → 异常路由 → 人工队列 → 审计留痕。**纯并行、每单元独立**。
Vendr 处理 10 万+ 文档，用「聚类 + 定向人工复核」**降低校验面**；
多家合规流水线共同的时间数字：审查时间降 **78%**、人工省 **80%**。
<https://www.zenml.io/llmops-database/scaling-document-processing-with-llms-and-human-review>

⚠ **注意**：这类活的"并行"是**假的** —— 吞吐可并行，
但**准确率不可并行**，因为抽样复核的统计功效要求独立同分布。

### 1.5 创意与设计

形状最模糊。有真实用途（Neon 用 Devin 批量改文档/changelog/regex 清理；
Nubank 用 Devin 重构 600 万行 ETL），但**判据缺失**。
<https://neon.com/blog/ai-workflows-for-docs-devin>

### 1.6 其它真实形态：Agent 造 Agent（自反系统）

Cognition 一周合并 **659 个 Devin PR** 进自己的代码库。
这是**自反系统** —— 扰动能闭环回到系统自身，**非常适合测级联**。
<https://cognition.com/blog/how-cognition-uses-devin-to-build-devin>

## 2. 五个关键问题的回答

### Q1 哪些活"看起来能并行、实际必须串行"？

> **答案：所有会写共享状态的活。**

**机理（Cognition）**：并行 agent 会对**风格、边界情况、代码模式**做出**隐式决策**，
这些决策彼此冲突，产生脆弱的系统。两条原则：
> "Share context, and share full agent traces, not just individual messages"
> "Actions carry implicit decisions, and conflicting decisions carry bad results"
<https://cognition.com/blog/dont-build-multi-agents>

**量化证据**（Google 180 组受控实验）：
- **顺序约束满足**类任务上，**所有**多 agent 变体性能下降 **39%–70%**
- 可并行任务（金融推理）：**中央协调 +80.8%**
- 动态网页导航：**分散协调 +9.2%**
<https://arxiv.org/html/2512.08296v2>

**真实例子**：7 个并行 reviewer 各自"改代码"会互相覆盖；
但它们只**读**、只**报**，所以能并行。
→ 这解释了为什么 Anthropic 说多 agent 适合「**读多写少**」。

### Q2 哪些活的校验成本会爆炸？

| 复杂度 | 形态 | 实例 |
|---|---|---|
| **O(n²)** | 任何「N 个产出必须**两两一致**」的活 | 合并 N 个并行分支；N 个并行架构决策要协调；N 份文档交叉引用一致 |
| **O(n)** | 断言↔出处**逐条**核对 | 文献综述；逐单元提取校验 |
| **O(1)** | 有**可执行判据**的 | 跑测试、跑 lint |

★ **Cloudflare 的解法**：让协调者做**单点**去重与仲裁 —— **把 O(n²) 降回 O(n)**。

**真实成本曲线**：Cloudflare trivial 档 2 agent / **$0.20**，full 档 7+ / **$1.68** ——
**成本随 agent 数超线性**，P99 由大改动触发的全档编排决定。

> ⚠ **这一条直接命中 `demox` 的 G3-3b**：我们观测到的「`verify=2` 崩溃」
> 正是**把校验面从 O(n) 打开成 O(n²)** 的结果。调研给出了它的工业界解法：**单点仲裁**。

### Q3 哪些错误会静默传播？（MAST 1642 条真实轨迹）

| 模式 | 占比 | 静默性 |
|---|---|---|
| FM-1.3 步骤重复 | **15.7%** | 中（浪费但可检测） |
| FM-2.6 推理与行动不一致 | **13.2%** | **高** —— 说一套做一套 |
| FM-1.5 未识别任务已完成 | 12.4% | 高（多余工作） |
| FM-1.1 不遵守任务要求 | 11.8% | 高 |
| FM-2.3 任务脱轨 | 7.4% | **最高** —— 悄无声息跑偏 |
| FM-2.2 用错误假设继续而不澄清 | 6.8% | **最高** |
| FM-2.4 信息扣留 | **0.85%** | 最低频但**最毒** |

MAST 的例子：Phone Agent 没告诉 Supervisor「用户名格式要求」，Supervisor 也没问，
导致反复登录失败 —— **双方都以为对方知道**。
<https://arxiv.org/abs/2503.13657>

★ **决定静默性的结构变量是拓扑**（Google 实验）：
- **独立式（Independent）拓扑把错误放大 17.2×**
- **中央协调压到 4.4×**

**因为协调层就是验证瓶颈，能在错误进入聚合前截住它。**
→ 这是测「错误传播」最干净的对照组，也是 `demox` G3-3 该用的对照。

### Q4 ★ 加人什么时候有用、什么时候更糟？（最想要的一条）

四条可操作判据：

1. **能力饱和点**：单 agent 准确率**超过约 45%** 后，加 agent 出现**负回报**
   （β = **−0.404**, p<0.001）。协调成本超过了剩余改进空间。
2. **工具协调权衡**：**工具密集**任务（如 16 工具的软件工程）在固定预算下被多 agent 开销
   不成比例地拖累（β = **−0.267**）—— 因为多 agent 把每个 agent 的 token 预算切碎，
   留给复杂工具调用的容量不够。
3. **拓扑必须匹配任务**：顺序任务上**任何**多 agent 都是负的（−39% ~ −70%）；
   可并行任务上中央协调 **+80.8%**；高熵搜索空间（网页导航）上**分散**协调更好（+9.2%）。
4. **协调开销随通信链接数增长，不随 agent 能力增长** —— 加模型智能救不了拓扑错误。

外部佐证：METR 的 RCT ——
**有经验的开发者在自己的成熟项目里用 AI 反而慢 19%**（16 人、246 任务、平均 5 年项目经验）。
<https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/>

> ★ **一句话的实验假设**：
> **加人有用 ⟺ 任务可分解 ∧ 单 agent 基线 < 45% ∧ 拓扑匹配 ∧ 协调层是验证瓶颈而非传声筒。**

## 3. 两条必须直说的

### ① 创意与设计**不适合**做系统科学实验

没有廉价判据 ⇒ 无法区分「系统变差」和「评审者口味变了」。噪声会淹没要测的效应。
若一定要做，必须先把判据**外部化**（如"改动后必须通过 X 条既有规则"），
**那就退化成第 4 类了**。

### ② 「多 agent 更好」这个前提在真实数据里是假的

MAST 在 7 个 SOTA 开源多 agent 系统上实测失败率 **41%–86.7%**。

> **所以实验设计不该以「证明多 agent 有用」为靶，
> 而应以「找出拓扑—任务匹配的边界」为靶** ——
> 这个边界已经有定量预测器（Google 的模型在留出集上 **87%** 猜对最优架构）。

### ③ 方法论建议

**别自己造任务。** MAST-Data 的 1642 条轨迹和 Cloudflare 的成本分布表
已经把"真实形状"数字化了，**直接拿来当任务发生器**，比任何合成流水线都有判别力。

## 5. 已知风险（调研者自己标的）

- Google 那篇的 β 系数来自**四个基准**，是否能外推到本库环境**需先跑一次基线复现**。
- 与 Nature MI 那篇的差异**未逐条比对**。
- 创意/设计领域**跳过了原始出处检索**（判断它不适合后不再花预算）。
- 部分出处是**厂商自报**（Anthropic/Cloudflare/Cognition 的博客），未经第三方复现 ——
  这一点与 `demom/研究记录.md` §5 的处理一致。
