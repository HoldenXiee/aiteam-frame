# ★★ 任务设计重做：从「编程题」到「人的意图落地」

> 2026-10-17 · 研究员指出：
> ① 「实验的任务会不会太简略了，没有设计过，应该要经过设计才对」
> ② ★★ 「**我们这个项目不只是可以用于编程方面，而是服务于整个人类的劳动。让人的意图/想法落地**」

---

## 0. ★ 我的两个立场错误

### 错误一：任务来源倒置

| | 我做的 | ★ DESIGN 的立场 |
|---|---|---|
| 任务从哪来 | ★ **从"能造出什么考题"倒推** | ★★ **从"人真在做什么劳动"正推** |
| 任务服务于谁 | 服务于"能测出差异" | ★★ **服务于"这是人真要做的事"** |
| 判据 | 我造的 JSON 比对数 | ★★ **产出的东西人能不能用** |

### 错误二：把「劳动」窄化成「编程」

**DESIGN 第 60 行原文**：
> 「人是以新的工具去"**劳动**"……人的价值就在于去使用知识、工具来**改造现实世界**……
>  **让人更好的利用这个工具**，让人们能**更大程度去实现自己的价值**。」

★ **"劳动"与"改造现实世界"都不是编程的同义词。**
**我把全部实验都做成了"改这个仓库的代码"——那只是劳动里极小的一块，而且是我最顺手的一块。**

## 1. ★ 诊断：此前任务的三个缺陷（已确认）

| # | 缺陷 | 实测 |
|---|---|---|
| ① | **工具单调** | 全部任务只有 `["read","write","ls"]` —— **从没用过 `edit`/`bash`/`grep`/`find`** |
| ② | **形状单调** | 一步到底（读 N 份 → 写 JSON）—— **无中间产物、无返工、无依赖** |
| ③ | **性质单调** | 全是**判断类**（"这些材料重复吗"）—— **没有改造类** |
| ④ | ★★ **领域单调** | ★ **全是"读文档找重复"一种活** —— 而真实劳动有六类（见 §2） |

## 2. ★★ 真实劳动的六类形状（`真实工作形态调研.md` 已有，我只用了最窄的一类）

| 类 | 形状 | 校验位置 | 我做过吗 |
|---|---|---|---|
| **1.1 软件工程** | 串行深链（读→定位→改→跑测试） | 最后一次性 | ★ **只做了这个** |
| **1.2 研究/写作** | orchestrator-worker（3–5 子 agent） | 集中校验 | ⚠ 沾边 |
| ★★ **1.3 运营/客服** | ★ **分流 + 升级**（**升级率是显式控制变量**） | 逐单 | ❌ **零** |
| ★★ **1.4 数据/文档处理** | ★ **提取 → 校验 → 异常路由 → 人工队列 → 审计留痕** | 抽样复核 | ❌ **零** |
| 1.5 创意与设计 | 判据缺失 | — | ❌ 零 |
| **1.6 Agent 造 Agent** | 自反系统 | 闭环 | ❌ 零 |

> ★★★ **1.3 与 1.4 恰恰是 DESIGN 说的地方**：
> 「升级机制」里**人是显式的**（AI 解决 65%，剩下走人）；
> 「审计留痕」里**人也是显式的**（人工队列）。
> **而这两类我一次都没碰。**
>
> ★ 调研里还有一句关键：**1.4 的"并行"是假的** ——
> **吞吐可并行，准确率不可并行**（抽样复核要求独立同分布）。

## 3. ★ 任务设计的四条判据（写进纪律）

一个任务要能进实验，必须同时在**四个维度**上有设计的痕迹：

| # | 维度 | 判据 | 反例（我此前的） |
|---|---|---|---|
| **1** | ★ **来源** | **这条活真有人在干**（有出处 / 是这个仓库真做过的） | ❌ "造个 JSON 比对数" |
| **2** | ★ **形状** | **多步、有中间产物、有返工点** | ❌ 一步到底 |
| **3** | ★ **工具** | **至少用到 edit / bash / grep 里的两个** | ❌ 只有 read/write |
| **4** | ★★ **人的位置** | **能说清"人在这条活的哪一步介入、介入什么"** | ❌ 人只在最后看判据 |

> ★★ **第 4 条是最要紧的** —— 因为 DESIGN 的整个目标是「**让人更好地利用这个工具**」。
> **一条活里如果没有人，它就不是这门学科要研究的活。**

## 4. ★★ 两条任务族（按 DESIGN 第 60 行设计，不限于编程）

### 族 A · **数据/文档处理流水线**（1.4 类）—— ★ 人是"异常处理者"

**真实出处**：Vendr 处理 10 万+ 文档；合规流水线审查时间降 78%。
真实形状：**提取 → 规则校验 → 异常路由 → 人工队列 → 审计留痕**。

**设计**（跨领域：发票 / 合同 / 病历 / 申请表 —— **都不是代码**）

| 步 | 谁做 | 产物 |
|---|---|---|
| 提取 | agent | 结构化字段（真 JSON schema） |
| 规则校验 | ★ **代码**（不是模型）| 哪些字段违反规则 |
| **异常路由** | ★ **模型判断"这该不该给人"** | ★ **路由决策 + 理由**（这就是"人的位置"） |
| **人工队列** | ★ **人**（实验中由我扮演 / 一个独立的裁决 agent） | 接受 / 驳回 / 改 |
| 审计留痕 | 代码 | 每个决定带得出依据 |

★ **三个可测的量**：
- **路由准确率**（该给人却自己处理了 / 不该给人却推给人）
- ★ **人工队列的长度**（人的工作量 —— **这就是"人花了多少劳动"的可测化**）
- **审计可追溯率**（每个决定能不能追到依据）

> ★★ **这条族的革命性**：**它是第一条"人真的在里面干活"的任务。**
> 而且**代价函数里含人的时间** —— 这正是 DESIGN 说的"最大化利用这个工具"。

---

### 族 B · **研究/写作**（1.2 类）—— ★ 人是"意图的持有者"

**真实出处**：Anthropic 的 orchestrator-worker（3–5 子 agent）；
文献综述 = 串行流水线 + 双向校验，**"每一句话都要对回原文"**（O(n)，不是 O(n²)）。

**设计**：给**一个模糊的意图**（不是明确的题），让它落地成**一篇有引用归属的短文**。

| 步 | 判据 |
|---|---|
| 分解 | 拆出的子问题**覆盖**了意图吗 |
| 检索 | 每条断言**带得了出处**吗（可验证） |
| 综合 | ★ **有没有编造**（断言 ↔ 出处一对一） |
| ★ **人的位置** | ★ **人给的是"意图"，不是"题目"** —— 意图模糊、题目明确，**这个落差就是人的价值** |

★ **这条族测的是 DESIGN 那句「让人的意图/想法落地」** ——
**人只出一句话（意图），产物是完整的、可核对的、能用的东西。**

---

### 族 C · **修 bug 让测试过**（1.1 类，已开工）

**它不是"又一个编程题"** —— ★ **它是 1.1 类里判据最硬的那个**（真跑测试，不可伪造）。
**保留它当对照**（改造型 vs 判断型的差别），**但不再把它当唯一**。

## 6. ★ 纪律（写进研究规划）

| # | 纪律 |
|---|---|
| ★★ | **任务从真实劳动正推，不从"能造什么考题"倒推** |
| ★★ | **领域要跨出编程** —— 劳动不只是写代码 |
| ★★ | **每条活要说清"人在哪一步介入"** —— 说不出人的位置，就不是这门学科的活 |
| ★ | **判据要含"人的工作量"**（人工队列长度 / 复核条数）—— 不只是"对不对" |
| ★ | **四维检查**：来源 / 形状 / 工具 / 人的位置 |
