## 二、集群是什么（重写）

### 2.1 三层位置（不变）

```
设计者（人）
   │  定 DESIGN 目标、审成果、决定什么进仓库
   ↓
研究助手（我）      ★ 只管研究员集群，让它能达到理想目标
   │                  ★ 它的提案（改库 / 跨仓库）由我分析、我来做
   ↓
研究员集群          ★ 沉浸在研究里：找问题 → 设计实验 → 跑 → 分析 → 得做法 → 复审目标 → 再找问题
   │
   ↓ 用库搭装置
研究对象            ★ DESIGN 的目标本身：这门新生产方式
```

### 2.2 ★★★ 它的定义（按 C8、C9 重写）

**它不是执行者，也不是"给我干活的下手"。**

> ★ 它是：**一个沉浸在研究对象里的探索者** ——
> 用**探索的眼光**和**批判性的思维**，**不断更新对研究对象的理解**。

**它的价值就是"研究"本身**（C9 逐字）：

| 算成果 | 不算 |
|---|---|
| ★ 发现一个底层库的缺陷 | ✗ 只写综述、没有新东西 |
| ★ 提出一个没做过的问题 | |
| ★ 造出一个新装置 | |
| ★ 推翻一条已有结论 | |
| ★ **把研究方向往无人区推了一步** | |

★★★ **"不强制要求必须做出成绩"** —— 这一条我原来完全理解反了：
我写"没有新实验证据的综述不算成果"，**那是在逼它交成绩。**
★ **正确的表述是**：**只要它在真研究，就是在产出。** 哪怕这一轮结论是"我试了，没发现"。

### 2.3 ★★★ 任务书（BRIEF）要被替换成什么（C8）

**不是"任务书"，是"教它怎么研究 + 研究方向"。**

| 该有 | 不该有 |
|---|---|
| ★ **怎么研究**：什么是好的研究（对照、单变量、跑前冻结、可离线重判） | ✗ 每轮该干什么 |
| ★ **研究方向是什么**：DESIGN 的目标 | ✗ 选题清单 |
| ★ **哪些材料存在**（路径） | ✗ 已有成果的清单 |
| ★ **它有什么工具**（库的 API / 面） | ✗ 固定的工作步骤 |
| ★ **怎么找灵感**（C2 的两条途径） | ✗ 产出格式的硬规定 |
| ★ **它的权限与边界** | ✗ "你必须交一份成果" |

★ 名字也该改：**`BRIEF.md` → `研究手册.md`**（或 `如何研究.md`）。
★★ **"任务书"这个词本身就是错的** —— 它暗示有一个"任务"在等它完成。

## 三、★★ 找灵感的两条途径（C2 落实）

### 途径 1 · 阶段性复审目标

```
探索过的东西（实验、现象、特性）
        ↓ 用探索后的眼界重看
    DESIGN 的目标
        ↓
   新发现（原来没看见的问题）
```

★ **机制**：它 `work/` 里有全部探索痕迹（设计、数据、JOURNAL）。
**"复审"不是新工作，是把已有材料和新长出来的眼界对齐。**

★★ **我原设计缺的**：我从没给它任何"复审"的触发点（见 §五 触发式拓扑）。

## 五、★★★ 拓扑：从"流程"改成"触发"（C6 落实）

### 5.1 我原来的错（C6）

```ts
// ✗ 这是一个流程 —— 而且我把"流程"写进了角色定义里
for (let r = 1; r <= maxRounds; r++) {
  const prompt = `# 第 ${r} 轮\n\n## 这一轮\n\n★ 怎么做由你定…`;
}
```

★★★ **"由你定"和"第 N 轮"是矛盾的：框架还是流程，只是格子变空了。**
★ **而且我在角色里写「你不是执行者，你是研究者」，装置却在按轮次驱动它。**

### 5.2 ★★ 正确的形态：**触发式**（conditions，不是 schedule）

| 触发条件（**什么情况**） | 该发生什么 | 为什么这样设计 |
|---|---|---|
| ★ **它写出了一份成果 / 一份提案** | 起审查员（干净上下文）审它 | ★ 产物驱动的 review |
| ★ **它连续跑了很久没产出** | 起一个"看门狗"看它在干什么 | ★ 区分"在探索"与"卡住" |
| ★ **它复审目标后说"有新问题"** | 让它开那条线（**它自己决定，不用问我**） | ★ 探索的本能 |
| ★ **它想改底层库** | ★ **直接让它改自己那份库**（C1） | ★ 不再设"申请通道" |
| ★ **它宣布"够了"** | ★ **交给审查员判**（C7），不用数字 | ★ 见 §六 |
| ★ **它写的成果与已有成果冲突** | 起一个"对照审查"专门看这个冲突 | ★ 冲突是高价值信号 |
| ★ **它连续撞同一个墙** | 起一个 agent 专门去看那个墙 | ★ 墙 = 值得研究的现象 |
| ★ **它在同一件事上转了 N 次** | ★ 触发"复审目标"（C2 途径 1） | ★ 用**情况**触发，不用轮次 |

★★ **关键区别**：

```
流程：  第1轮 → 第2轮 → 第3轮 → …           ← 它被时间驱动
触发：  <情况A> → 发生X；<情况B> → 发生Y     ← 它被状态驱动
```

★★★ **"复杂的拓扑依赖关系"**：不是一个主循环，而是**多个角色按事件互相触发**。
见 §十一 的具体拓扑图。

## 七、★★★ 停止：交给审查员（C7）

### 7.1 我原来的错

```ts
if (quiet >= quietNeed) break;   // ✗ 这是个数字
```

### 7.2 新设计

★ **停止不是一个数字，是审查员的一个判断。**

```
它说"我觉得够了"（writer 的直觉）
        ↓
审查员判：它是真的探索完了，还是想收工 / 累了 / 卡住了？
        ↓
审查员说"停" → 停；说"继续，因为 X" → 继续
```

★ **交给审查员更贴合实际，因为**：
- 审查员**干净上下文**，没有它自己的疲劳和沉没成本
- 审查员**能看到它的全部产物**，能做全局判断
- ★★ **数字判据是"我"在替它做判断** —— 而判断该由**了解那个研究对象的人**做

★★ **审查员判"停"要给出理由**，并且**理由要可被我审**（这是我保留的部分）。
