## 一、它是什么：我对「研究员集群」的完整定义

### 1.1 三层位置

```
设计者（人）
   │  定 DESIGN 目标、审成果、决定什么进仓库
   ↓
研究助手（我）          ★ 只管研究员集群：让它能达到理想目标
   │                     ★ 它的提案（改库 / 跨仓库）由我分析、我来做
   ↓
研究员集群              ★ 自己做研究：找问题 → 设计实验 → 跑 → 分析 → 得做法
   │
   ↓ 用库搭出实验装置
研究对象                ★ DESIGN 的目标本身：这门新生产方式
```

★ **我理解的设计者裁定（逐字）**：
> 「你只管研究员集群，让它能够达到理想目标，然后它的提案你要自己分析（如要改库、要跨仓库），
>  相当于**研究员集群是你的下手**」

> 「**第二层集群就是 design 中的目标**：研究这个新生产范式，怎么使用好、有什么特性、怎么分析等等」

### 1.2 它的职责判定表（我写的，**请审这一条对不对**）

| 是研究员的活（它干） | 不是研究员的活（别让它干） |
|---|---|
| 自己找问题、自己判定哪个值得做 | 照别人给的选题清单做 |
| 设计实验（自变量 / 对照 / 判据 / 跑前冻结） | 执行别人给好的步骤 |
| 跑、读数据、分析、得做法 | 写文献综述、概念梳理、理解性总结 |
| 判断「够了没有」（收敛由它声明） | 等别人数轮子决定停不停 |

★★ **我不确定的地方**：
- "写综述不算成果"—— **这是我的判断，不是设计者说的**。它可能过强？（见 §十 问题 3）
- 「找灵感」算不算它的活？我在文档里写了"规划/实验/找灵感/重审视/记录"，但**"找灵感"我从没给过它任何入口**。

### 2.2 权限：用代码立规矩（这是我目前**最有把握**的设计）

```ts
// ★ 受保护路径：src/ dev/ bench/ 成果/ —— 只能读
const PROTECTED = [...];
function protectedHits(text)   // ★ 带路径边界（不是裸子串）
function stripReadOnlyRedirects(cmd)  // ★ 白名单 2>/dev/null、2>&1
function looksLikeWrite(cmd)   // ★ 只认真写：>/>>/tee/sed -i/rm/mv/cp/touch/mkdir

agent.permissions.gate(async (call) => {   // ★ 形状 dump 过，不猜
  if (call.name === "bash" && looksLikeWrite(cmd) && protectedHits(cmd).length) {
    return { block: true, reason: "受保护路径只读。要改就复制到你的 work/ 里。" };
  }
});
```

★★ **为什么用 gate 而不是提示**：本项目实测过 ——
**用提示规范"该怎么做"是弱干预**（P13：给通道 0/3 vs 强制落盘 6/6；P17：`bash`/`grep` 是 `read` 的完整旁路）。
**能用代码立规矩的，就用代码。**

### 2.3 ★★ 这里有一段我**吃过亏**的历史（请重点审）

守卫第一版用**裸子串** `includes("dev")` + 正则 `/(>|>>|sed -i|rm\s...)/`：

```ts
// ✗ 第一版（错）
"2>/dev/null"   // ← 同时含 "dev" 和 ">" → 任何含它的命令无条件被拦
```

★ **后果**：`ls foo 2>/dev/null` 也被拦。集群跑了 45 分钟撞墙多次。
★★ **这个缺陷是集群自己抓出来的**（`outbox/装置缺陷-受保护路径守卫误伤只读命令.md`）。
★★★ **更狠的是**：它建议的修法（边界正则）**仍然 MATCH `/dev/null`** ——
这一点是**独立审查员**离线重跑判据后证伪的，**我复核确认**，而且比它说的更严重：
那条"修法"会**把真写全部放行**（`sed -i` 都放行）—— **把"修补"变成了"拆掉守卫"**。

★ **我的教训**：**拦截规则和"看起来像写"是两件事，不能用一个正则表达。**

### 2.4 审查员（⑤ AUDIT）—— 目前最成功的部件

```ts
const auditor = await lab.createAgent({
  role: "你是一个独立审查员。★ 你没有看过任何推导过程 —— 你只看产物本身。…" +
        "★ 输出（严格按这个结构，我要机器解析）：…② 每条**必须**以 `DEFECT: ` 开头…",
  permissions: { only: ["bash","read","grep","find","ls"] },  // ★ 只读，审查员不该改东西
});
```

★★ **"上下文干净"是用库的 `context` 面直接实现的** —— 审查员 `context` 里不含被审者的推理过程，
**它无法被"推导过程"说服**。这是设计者提示的机制（逐字：
「在设计研究员集群时，可以用上下文干净的 agent 来审查或监督」）。

### 2.5 停止条件（⑥ STOP）—— **从没跑通过，而且我自己搞错过一次**

我的设计（三条同时成立）：

```ts
if (declared && fresh.length === 0) {
  quiet++;
  if (quiet >= quietNeed) { convergedThisRound = "..."; break; }
} else {
  if (fresh.length > 0) quiet = 0;   // 有新缺陷 → 之前"静默"作废
  if (!declared) quiet = 0;          // 没声明收敛 → 也算断
}
```

★★ **一个我搞错过的地方**：我一度以为"声明→有新缺陷→声明→声明"会**过早收敛**，
★ 实测（离线模拟）**逻辑是对的**（中间那次复位生效了，第 4 轮才收敛）—— **是我的测试脚本显示错了。**
★★ **但我还是不确定这套判据对不对**（见 §十 问题 1）。
