## 【现象】

**质量分同为 1.00（全对）的 177 个 run，token 最大/最小 = 316.7 倍。**

| 尺度 | 倍数 |
|---|---|
| 全库（n=177） | ★ **316.7×** |
| 按实验看，中位 | **7.3×** |
| 按实验看，平均 | **21.5×** |
| 极端（G0-3-difficulty2） | **179.9×** |

---

## 【归因】

**判据只约束「对不对」，完全不管「花了多少」。**
一个 2,694,162 token 的正确答案和一个 14,972 的，判据给同样的分。

⇒ ★ **成本是一个**自由变量** —— 没有任何机制在管它。**

**这解释了 P8 为什么有效**：往返回值里注入一行代价+阈值，token 就降到 1/5。
★ **那块地从来没人耕种过。**

## ★★ 2026-10-16 补：**形状**已知（用新增的 `agent.observe.turns`）

**原来只有结论**（差 316.7 倍），**现在能看到它长什么样**。

### 机制：**相变点 = 它从「批量读」改成「逐份读」的那一刻**

```
单 agent:     1608 → 2381 → 2840 → 3724 → 3888           总 14,441
三棒管线 S1:  1603 → 2300 → 2774 → 3289 → 3673
                 ★ → 10025 → 13290 → 14002 → 15472 → 15786   总 82,214
    消息数:   2 → 5 → 11 → 17 → 21 ★→ 26 → 47 → 52 → 60 → 62
                                    ↑ 相变点：此后每轮重发全部已读内容
```

### ★★ 而且相变点是**随机的**

**同一份代码跑 4 次**：轮数 5/5/8/5，**峰值 4.4k / 11.0k / 13.0k / 5.7k（3 倍差）**。

> ★★★ **这就是 316 倍的微观形态** ——
> **不是"设计好坏"，是**采样随机**（B4）撞上**结构性放大**（每轮重发全部历史）。**

### ★ 干预有效：把 `read` 返回值缩成一行

| | 峰值 |
|---|---|
| `keep`（原样） | 4.4k / 11.0k / 13.0k / 5.7k |
| **`shrink`（缩一行）** | ★ **4.3k / 4.4k / 4.7k** / 9.6k |

★ **前三轮次的峰值被压平了** —— 机制确认。

### ★ 新做法

| # | 做法 |
|---|---|
| 1 | ★★ **算"读一份"的代价要乘上"还剩几轮"** —— 上下文累积重发，近似**平方** |
| 2 | ★★ **要治成本就治相变点**（什么时候开始逐份读），不是治"每轮效率" |
| 3 | ★ **把已读原文从源头减**（`onResult` 改写 / `context.erase`）—— 不是压缩 |
| 4 | ★ **用 `observe.turns` 看成本形状**：单调上升 vs 相变，是两种病 |
| 5 | ⚠ **凡压缩都有反作用**：`drop` 档（说"已读过"）反而让它改成逐份读，成本 3.75 倍 |
