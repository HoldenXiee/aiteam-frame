---

## 【现象】

**拦截 `read` 的返回值，干预 0 次生效** —— 因为下游用的是 `bash cat`。

**逐个工具对照**（文件里埋 marker，看能不能拿到）：

| 只给 | 能拿到内容吗 |
|---|---|
| `read` | ✓ |
| ★ `bash` | ★★ **✓（而且只有这一档成功把内容写进产物）** |
| ★ `grep` | ★★ **✓** |
| `find` | ✗ |

---

## 【做法】

### ① 裁剪要按**能力**声明

```ts
// ✗ 按工具名裁 —— 有 bash 就漏
permissions: { only: ["write"] }

// ✓ 按能力裁 —— 想清楚"读内容"有哪些入口
const READ_CONTENT = ["read", "bash", "grep"];
const WRITE_FILE   = ["write", "edit", "bash"];
```

### ② 拦截前先看**在飞的真实工具分布**

★★ **这是 O7 的教训**：我以为它在 `read`，实际它在 `bash cat`。
**`Meter` 里已经有 `callsDetailed`（工具+实参）—— 用它，别猜。**

### ③ 拦不住时，第一个怀疑对象是「换了入口」

**不是"干预没生效"** —— 先问「它是不是从别的门进的」。

### ④ 真正要封死时，`bash` 得单独处理

**`bash` 是万能的**：`cat` 读、`sed -i` 写、`curl` 外联。
**要真封，要么不给 `bash`，要么在 `onResult` 里对 `bash` 的**实参**做检查**（比拦工具名复杂得多）。
