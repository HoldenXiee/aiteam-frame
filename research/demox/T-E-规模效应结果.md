# T-E 规模效应 · 「多大才逼出分工」

> 承接 [`T-E-代码审查结果.md`](T-E-代码审查结果.md) §5 第 1 条。
> 数据 `runs/TE-fanout.jsonl`(12, 7 文件) · `runs/TE-big-smoke.jsonl`(2, 35 文件) · `runs/TE-big.jsonl`(3, 部分)
> 成本：免费档

---

## 0. 一句话

**7 个文件时，模型 12 轮 0 委派；32–35 个文件时，委派立刻出现（deleg=2, agents=3）。**

> **所以「集群」有一个规模阈值。** 低于它，模型（正确地）选择自己干；
> 高于它，才出现分工。而 `demom` 早就撞过这面墙 —— 它的语料从 14 份扩到 44 份，
> 否则「自由集群」压根不出现（`delegations=0`）。

---

## 1. 两次规模对比

| 规模 | 文件数 | 轮数 | **委派** | 单 agent 工具调用 | 结果 |
|---|---|---|---|---|---|
| 小（首扫） | **7** | 12 | **0 / 12 轮** | 8–9 次 | 11/12 通过 |
| 大（本次） | **35** | 3+ | **1 / 3 轮有委派（deleg=2, agents=3）** | **37 次** | 见下 |

**小规模那 12 轮**：`shards ∈ {1,2,4}` × `coordinator ∈ {0,1}` 全扫了，
**每一轮都是 `agents=1`、`delegations=0`**。系统提示里明说了分片可用，role 里也写了"你可以派"。

**大规模这一轮**（`shards=2 coordinator=1`）：
```
agents=3 deleg=2 tok=87,780 412s  ✗ 失败：漏掉的缺陷所在文件：src/retry.js
```

**它派了 2 个只读分片。** 而且**漏掉了一个静默型缺陷**（`src/retry.js` = D9：
重试耗尽后隐式返回 `undefined`）。

## 2. 三条读数

### 2.1 规模阈值：分工是被"读不完"逼出来的，不是被"允许"催出来的

`demom` 的原话（§10.1）：
> **能力给了，模型不会自己用。** 给它挂上 `peers`/`ask`，**一次都没被调用过**。

T-E 把它推进一步，给出了**条件**：

| 条件 | 委派 |
|---|---|
| 7 文件 + 明说可派（含分片清单） | **0/12** |
| 35 文件 + 同样明说 | **有**（3 agents，2 委派） |

★ **所以"不给就不用"的根因不是"模型不会"，而是"不划算"。**
7 个文件自己读 8 次调用就完了；派一个 reviewer 要付一次完整的
agent 启动 + 提示 + 回传 —— **模型（可能）算对了这笔账。**

**这对 `demox` 的直接含义**：任何想研究"集群 vs 单点"的实验，
**必须先确认任务规模超过了单 agent 的舒适区**，否则整个实验在测一个不存在的现象。
`demom` 用 14→44 份做过这件事，`demox` 用 7→35 份复现了它。

### 2.2 大规模下失败的是**静默型**缺陷

大规模那轮唯一漏掉的是 `src/retry.js`（D9）：
```js
export async function retry(fn) {
  for (let i = 0; i < 3; i++) { try { return await fn(); } catch {} }
}   // 重试耗尽后隐式返回 undefined
```
**它不崩、不报错、不看代码注释根本看不出来。**

而缺陷库里**静默型占 8/20**（`crash` 3 · `wrong-value` 6 · **`silent-leak` 8** · `inconsistent` 3）。

> 与调研 Q3 对上：MAST 的 1642 条轨迹里，
> **FM-2.3 任务脱轨 / FM-2.2 用错误假设继续 / FM-2.4 信息扣留** 是**静默性最高**的那几类。
> T-E 给出了一个可量化的版本：**静默型缺陷的漏检率 > 崩溃型**。
> ⚠ 但本次只有 1 个漏检点，**只能算线索**。

### 2.3 大规模下代价跳到 5–10 分钟一轮

| 规模 | 秒 | token |
|---|---|---|
| 7 文件 | 43–445 | 7.7k–24k |
| 35 文件 | **246–1924** | **4.2k–87.8k** |

其中一轮（`shards=2 coordinator=1 rep1`）跑了 **1924 秒（32 分钟）**却**只烧了 4,214 token**、
`calls=4`、产物为空 —— **它卡住了，不是烧钱**。

> 这与 T-A 的失控形状不同（T-A 是烧很多 token）；这里更像**长时间空转**。
> 两种都是"无界"，但机制不同 —— `demox` 的护栏（G1）需要区分这两类。

## 3. 建基建时抓到的两个**静默失效**（都比 bug 本身值得记）

这两条是同一族问题：**参数/配置没有生效，而数据里看不出来**。

### 3.1 `fillerCount` 没传进任务 → "规模扫描"扫了个寂寞

第一次跑 `fillerCount=20` 时，`buildTaskFor` **忘了把它传给 `buildReviewTask`**，
于是语料一直只有 15 个文件，而记录里 `params` 明明写着 `fillerCount: 20`。

**修法（比修 bug 重要）**：在 `scan.ts` 里加 `assertParamsTookEffect()` ——
**在跑之前**检查任务层的可观测旋钮是否真的随参数变化，不通过就抛错。

### 3.2 填充文件没进"干净文件清单" → 误报判据对它们失效

`judgeReview` 收到的是 `cleanFiles.map(...)`（只有 2 个内置的），
而 20 个填充文件**不在**干净清单里。
于是「报了填充文件」**不会被算成误报** —— 判据静默地少了一块。

**修法**：干净清单改为用**最终的那份** `cleanList`（内置 + 填充），
并加一条回归测试：「报填充文件 → 误报数 = 1」。

> ★ **这两条与 `demom` §3 的"判据错了六次"是同一族**：
> **先怀疑测量，再怀疑模型。**
> 而且它们的共同症状是**数据看起来正常** —— 这比"跑崩了"危险得多。

## 4. 局限

1. **大规模数据只有 3–4 条**（扫描超时被打断），且 `shards × coordinator` 的对照**没跑完**。
   §2 的所有结论都是**方向性的**。
2. **规模阈值未定位**：只测了 7 和 35 两个点。真正的阈值在中间某处
   （`demom` 的两个点是 14 和 44）。**要扫 `fillerCount = 0,5,10,20,40` 才能定位。**
3. **静默型 vs 崩溃型的漏检率对比**里，每类样本都太小。
   要测这条，应当**固定总缺陷数、只改种类的配比**（例如 12 个缺陷里静默型占 2/6/10）。
4. **一轮 32 分钟的空转**说明这批实验的**单轮时间上界**没控制好 ——
   下一批要加 `--timeout` 或按轮 abort。

## 5. 下一步

1. **定位规模阈值**：扫 `fillerCount = 0,5,10,20,40`，找"委派开始出现"的点。
   ★ 这是 `demox` 后面所有"集群 vs 单点"实验的**前置条件**。
2. **跑完 `shards × coordinator` 的对照**（本次被打断），
   才能回答 Cloudflare 那条「协调者单点仲裁把 O(n²) 降回 O(n)」。
3. **测"错误可见性"这一轴**：固定缺陷总数，只改 `crash / silent-leak / inconsistent` 的配比。
