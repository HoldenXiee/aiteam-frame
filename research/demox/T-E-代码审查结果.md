# T-E · 只读代码审查（真实形状任务）

> 任务出处：[`真实工作形态调研.md`](真实工作形态调研.md) §1.1（Cloudflare 的 7 reviewer + 协调者）。
> 代码 [`bench/tasks-review.ts`](bench/tasks-review.ts) · 系统 `review`（在 [`bench/scan.ts`](bench/scan.ts)）
> 数据 `runs/TE-smoke.jsonl`(1) + `runs/TE-fanout.jsonl`(12) · 成本：免费档

---

## 0. 一句话

**T-E 与 T-A 是同一批系统参数下的两个极端：T-E 便宜、准、稳；T-A 贵、飘、会失控。
差别不在模型、不在拓扑 —— 在「校验复杂度」。**

| | **T-A**（找重复组） | **T-E**（代码审查） |
|---|---|---|
| 模拟的真实活 | 文献综述的去重 | 代码审查 |
| 校验复杂度 | **O(n²)**（每对都要核） | **O(1)**（跑测试 / 看代码就能定） |
| 单 agent 基线 | 20–40 次调用 | **8–9 次调用** |
| token | 13.9k – **2,694k**（极差 **40×**~100×） | 7.7k – 24k（极差 **3.1×**） |
| 通过率 | 88%（pairs=8） | **11/12** |

> **这是 G3-3b 那个 O(n²) 假设的第一个直接对照。**
> 同一套基础设施、同一个模型，**只把任务的校验复杂度从 O(n²) 换成 O(1)**，
> 代价的极差从 40× 掉到 3.1×，失控完全消失。

---

## 1. 任务设计（按真实形状，不按理论）

**模拟的活**：Cloudflare 每次 MR 起最多 7 个专门 reviewer，由一个协调者去重、判级、合并；
子 reviewer **只读、且只读自己的分片**（"把上下文复制七份会让 token 成本乘 7"）。

**语料**：7 份"源文件"，其中 4 份各含一个真实缺陷、2 份完全干净：

| 缺陷 | 文件 | 类别 | **错误可见性** |
|---|---|---|---|
| D1 | `src/stats.js` | 循环越界 `i <= arr.length` | **一跑就崩** |
| D2 | `src/money.js` | 浮点用 `===` 比较 | 值错，不崩 |
| D3 | `src/reader.js` | `openSync` 没 `closeSync` | **静默泄漏**（压测才炸） |
| D4 | `src/api.js` | 调 `/api/v1/` 但 `routes.js` 只有 `/api/v2/` | **跨文件不一致**（只看一份发现不了） |

**判据是机械的**（8/8 离线自检通过）：
- `foundAll` —— 4 个缺陷文件全找到
- `noFalsePositives` —— 没报干净文件（防"到处报 bug 就能得分"）
- `describedAll` —— 每条用**关键词正则**判"说清了是什么问题"（不用 LLM 判）
- 另记 `precision`、`described` 等连续读数

★ **不用 LLM 当判官** —— 这是 `demom` `judgeText` 的同一个哲学：判据必须是纯函数、可重判。

## 2. 结果

### 2.1 单 agent 在 T-E 上**又便宜又准**

12 轮里 **11 轮全过**（4/4 缺陷、0 误报、说清 4 条）。
工具调用 **8–9 次**（一次 read 一个文件 + 一次 write），token **7.7k–24k**。

对比 T-A 在同模型下的读数（G0-3）：
- 工具调用 20–40 次（pairs=8），失控时 **73 次**
- token 13.9k–135.9k（pairs=8），失控时 **2,694k**

> **T-E 的成本极差只有 3.11×**（7.7k–24k），而 T-A 是 **40×** 起。
> **失控在 T-E 上完全不出现。**

### 2.2 ★ 意外发现：**12 轮里委派 0 次**

`shards ∈ {1,2,4}`、`coordinator ∈ {0,1}` 全都扫了，**每一轮的 `agents=1`、`delegations=0`** ——
模型**从不派分片**，永远自己把 7 个文件全读一遍，然后写产物。

```
轮次  shards coord ok  agents deleg calls tok
1     1      0     ✓  1      0     8     8,508
1     1      1     ✓  1      0     9     13,719
1     2      0     ✗  1      0     8     7,723     ← shards=2，但没派
2     2      1     ✓  1      0     9     24,027
1     4      0     ✓  1      0     8     11,093    ← shards=4，也没派
2     4      1     ✓  1      0     8     15,079
```

> ★ **这是 `demom` §10.1「能力给了，模型不会自己用」的第三次复现。**
> 第一二次是 `demom` 的 `spawn` 与 `peers`/`ask`，这次是 `spawn_reviewer`。
>
> **而这次给了它更强的理由**：系统提示里**明说了分片可用**
> （`当前可用分片：#1(...) #2(...)`），role 里也写了"你可以派" ——
> **它仍然不派。**

**为什么？** 从数据看答案很清楚：**派分片在这个任务上是不划算的。**
7 个文件、8 次调用就能读完，派一个 reviewer 要付一次完整的 agent 启动 + 提示 + 回传。
**模型（可能）算对了这笔账 —— 它选择自己干。**

这与 `demom` §10.3 的发现是同一件事的另一面：
> `demom`：A 的最优形状是「1 个 agent」（root 自己读完 45 份材料时胜率最高）
> `demox` T-E：**即使明说可以分片，模型也收敛到 1 个 agent**

★ **所以「集群」不是免费的**：它要有一个**足够大的规模**才划算。
T-E（7 文件）太小；T-A（44 份材料）才逼出委派。

### 2.3 唯一的失败轮：**它什么都没报**

```
shards=2 coordinator=0 rep=1  ✗  失败：漏掉的缺陷所在文件：src/stats.js、src/money.js、src/reader.js、src/api.js
tok=7,723（最低）  calls=8
```

**不是报错了，是一条都没报** —— 7.7k token 是全场最低，说明它**读完就交了个空**。
这与 T-A 的失败形状一致（G0-3：失败轮更便宜，因为它"没读够就交了"），
但**方向相反**：T-A 的失败是"漏了几组"，T-E 这次是"一条没报"。

## 3. 这条数据对 demox 的意义

### 3.1 它给了 G3-3b 的 O(n²) 假设一个**直接对照**

| | T-A（O(n²) 校验） | T-E（O(1) 校验） |
|---|---|---|
| 代价极差 | **40×** | **3.11×** |
| 是否出现失控（>100k token） | ✅ 出现（393k、2,694k） | ❌ 从未 |
| 失败形状 | 漏项 / 产物为空 | 一条不报 |
| 委派 | 会派（T-A 里 root 会 spawn scout） | **从不派** |

**同一套 scan 基建、同一个模型、同一类 agent 配置。**
**唯一的大差别是「校验/搜索的复杂度」。**

→ §G3-3b 的解释（"校验有效当且仅当它要检查的东西是 O(n)；一旦 O(n²)，校验自己会失控"）
**得到了一个跨任务的支持证据**。

### 3.2 但它也暴露了一个**设计问题**：T-E 太小，测不出拓扑

`shards` 参数完全没生效（12 轮 0 委派）。
所以 **T-E 目前不能用来测「只读扇出 vs 写共享」** —— 那个对照需要模型**真的去派**。

**两个可选修法**（都需要再跑）：
1. **把 T-E 做大**：文件数从 7 提到 30–50，让它超过单 agent 的舒适区（对应 `demom` 把 14 份扩到 44 份）。
2. **给委派一个硬理由**（像 `demom` 的 A 变体做的那样）：
   role 里加一句"你一个人读不完这么多文件"。
   ⚠ 但 `demom` 已经认账过这是个**未控制的变量**，用之前要记清楚。

## 4. 局限

1. **n=12，且 11 过 1 败** —— 分辨率低，`3.11×` 这个极差是 12 个点的读数。
2. **T-E 的难度对小模型也偏低**：4/4 缺陷全被找到，包括最难的跨文件不一致（D4）。
   要测"基线能力 vs 加 agent"（调研 Q4 的 45% 饱和点），**需要把缺陷藏得更深**。
3. **判据的 `describedAll` 用关键词正则**，比 LLM 判官硬，但也**更宽松**
   （只要提到"越界/<=/undefined"任意一个就算说清）。换任务要重新审视关键词表。
4. **委派为 0 让 `shards`/`coordinator` 两个自变量完全失效** —— 本次数据**不能**回答
   "协调者单点仲裁能不能把 O(n²) 降回 O(n)"（Cloudflare 那个结论）。
   这是下一步最该补的。
5. **成本恒为 0**，token 数不等于钱。

## 5. 下一步

1. **把 T-E 做大到单 agent 会吃力**（文件数 30–50），再扫 `shards × coordinator`。
   这才能测 §3.2 的对照。
2. **用它测「错误可见性」这一轴**：把 D3（静默泄漏）/ D4（跨文件）的比例调高，
   看静默型缺陷的漏报率是否显著高于崩溃型。**这是调研 Q3 的直接检验。**
3. **与 T-A 配对报结论**：凡是"校验复杂度"相关的结论，都要同时给出 T-A 与 T-E 的读数。
