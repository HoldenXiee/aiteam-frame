# O3 补完：那 316 倍的成本差，**形状**是什么

> 2026-10-16 深夜 · 探针 `bench/o3shape2.ts` · 用新增的 `agent.observe.turns`（按轮 token）
> 承接 [`标准读数集结果.md`](标准读数集结果.md) 的 O3 结论

---

## 0. 一句话

**成本差**不是「每轮都贵一点」** —— 是越过一个**相变点**之后，
**每一轮都在重发它自己已经读过的全部历史。**

---

## 1. O3 原来只有结论，没有形状

> 「质量分 1.00 的 177 个 run，token 最大/最小 = **316.7 倍**」

**当时只有全生命周期累计** —— 知道差了 316 倍，**不知道差在哪**。

---

## 2. ★★ 现在有了按轮 token，形状一清二楚

**同一任务（10 份材料）**：

```
单 agent:      1608 → 2381 → 2840 → 3724 → 3888            总 14,441  (5 轮)
三棒管线 S1:   1603 → 2300 → 2774 → 3289 → 3673
                  ★ → 10025 → 13290 → 14002 → 15472 → 15786   总 82,214  (10 轮)
                        ↑ 第 6 轮突然跳 2.7 倍，此后稳定在 ~15k
        消息数:  2 → 5 → 11 → 17 → 21 ★→ 26 → 47 → 52 → 60 → 62
                                        ↑ 同一位置翻倍

S2: 1601 → 1827 → 3129 → 3794 → 4197 → 6251 → 6729          27,528
S3: 1629 → 2203 → 2639 → 4810 → 5258 → 5578                  22,117
                                                        ───────────
                                                总计   ★ 131,859 = 单 agent 的 **9.1 倍**
```

## 3. ★★★ 机制：**相变点是「它从批量读改成逐份读」的那一刻**

| 轮 | 它做了什么 | 每轮 token |
|---|---|---|
| 1–4 | **批量**（一轮里塞多个 read） | 1.6k → 3.7k |
| **5** | 消息数 21（到此为止还正常） | 3,673 |
| **★ 6** | ★ **改成逐份 read** → 每轮多一条**全文 toolResult** | ★ **10,025（跳 2.7 倍）** |
| 7–10 | 已读内容越积越多，**每轮重发全部** | 13.3k → **15.8k** |

> ★★★ **每轮 15k 里，绝大部分是**它自己已经读过的原文** ——
> 因为上下文在累积，而**每一轮请求都要把全部历史重发一遍**。
>
> **这就是 316 倍差的来源：不是效率低，是**结构性的重发**。**

---

## 4. ★★ 这直接连上三条已有结论

| 已有结论 | 现在能看到什么 |
|---|---|
| **P9（交接待判断）** | 下游若自己重读 → **每轮重发**；若拿上游结论 → **不重发** |
| **P11（账本是方向盘）** | "已用 N" → 少读 → 少重发；"还剩 N 必须读完" → 读满 → **多 2 倍** |
| **A1（override 抽掉原文）** | 抽掉原文 → **每轮不重发原文** → token 降到 1/4（**机制现在说得通了**） |
| **N1（跨 agent 重复读 28.3%）** | 每次重复读 = **往后的每一轮都多背一份** |

> ★★ **所以「读一份」的真实代价**不是那一次 read 的钱，
> **是**此后每一轮都要重发它**的钱 —— **平方级的。**

---

## 5. 【做法】

| # | 做法 |
|---|---|
| 1 | ★★ **算"读一份"的代价要乘上"还剩几轮"** —— 上下文是累积重发的，近似平方 |
| 2 | ★★ **要治成本就治"什么时候开始逐份读"** —— 那是相变点 |
| 3 | ★ **读过的原文该被替换/删掉**（`onResult` 改写 或 `context.erase`）—— 不是压缩，是**从源头减** |
| 4 | ★ **用 `observe.turns` 看成本形状** —— 单调上升 vs 相变，是两种病，治法不同 |
| 5 | ★ **单 agent 在"批量读"上天然占优** —— 多 agent 逼出逐份读（N1 的后果） |

## 6.5 ★★★ 预测检验：**机制成立，但相变点是随机的**

**预测**：如果机制是「每轮重发已读原文」，那把 `read` 的返回值缩成一行 → **每轮不该再累积**。

**做法**：同任务各跑 4 次，比较 `keep`（原样）vs `shrink`（返回值缩成一行）。

| | 轮数 | 总 token | ★ **峰值** |
|---|---|---|---|
| **keep** | 5 / 5 / **8** / 5 | 15.7k / **29.8k** / **49.5k** / 18.6k | 4.4k / **11.0k** / **13.0k** / 5.7k |
| **shrink** | 5 / 5 / 4 / **9** | 15.1k / 15.0k / 13.0k / 45.4k | ★ **4.3k / 4.4k / 4.7k** / 9.6k |

### ★★★ 两个结论

**① 预测成立**：`shrink` 档**前三次峰值全部压在 4.3–4.7k**（keep 峰值最高到 13.0k）
—— **把返回值缩成一行，真的阻止了累积。**

**② 但相变点是**随机的**（`keep` 四次：5/5/8/5 轮，峰值 3 倍差）**

> ★★★ **同一份代码四次跑出 3 倍的成本差 —— 这就是 O3「316 倍」的**微观形态**。**
> **它不是"设计好坏"，是**采样随机**（B4）撞上**结构性放大**（每轮重发）。**

**③ `shrink` 第四次（9 轮）还是进了逐份模式** ——
★ **因为"缩成一行"也让它觉得"没读全"而重读**（凡压缩都有这个反作用）。

### ★ 一个失败的档

`drop`（第一次读留全文、之后只给 `[已读过 M7]`）：**11 轮、60,500 token，3.75 倍** ——
★ **告诉它"已读过"反而让它改成逐份读**（P11 的"方向盘"效应又一次出现）。
