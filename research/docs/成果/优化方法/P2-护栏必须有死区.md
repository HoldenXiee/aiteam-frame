# P2 · 护栏必须有**死区** —— 控制器不能当场打死被控对象

| | |
|---|---|
| **归因到** | **LLM 没有「分阶段」的概念，只有「下一步」** |
| **强度** | 中（1 个任务，样本小但机制清楚） |
| **出处** | `../G1-1-反馈延迟相图结果.md` |
| **与 `DESIGN.md` 的对应** | 「系统设计」—— 反馈控制的基本设计问题 |

---

## 【现象】

实时护栏（数工具调用，越限就 `steer` 甚至 `abort`）扫「死区 grace」：

| 死区 grace | 结果 | 怎么坏的 |
|---|---|---|
| **0**（一越限就拉） | **2/4** | 2 次产物为空 —— **被护栏自己打死** |
| **30**（留 30 次调用的收尾余地） | **2/2** ✅ | — |

逐轮读数（`grace=0` 那 4 轮）：

```
steered=[{calls:20, reason:"超过上限 20", grace:0}]     ← 第 20 次就拉
guarded=[{calls:21, cap:20, action:"拉过没用，abort"}]   ← 第 21 次就打死
序列长度 = 21，write 在第 21 次 / 或压根没写
产物 = 无
```

**模型在第 20 次被叫停，第 21 次就被打死 —— 它只有 1 次调用的收尾时间。**

### 同时发现的第二维：采样率

| pollEvery | ok | token 中位 |
|---|---|---|
| 1（密） | 2/4 | **11,231** |
| 5 | 2/2 | 24,498 |
| 20（疏） | 3/4 | **29,026** |

**采样越密，代价越低（11k vs 29k）—— 但成功率反而更低（2/4 vs 3/4）。**
因为发现得早 = 打得更早 = 更容易在产物写完前打死。

> ★ **这是一个真实的 trade-off，不是"调好参数就能两头兼顾"**：
> - 采样密 → 省 token，但更容易误杀
> - 采样疏 → 不容易误杀，但代价高
>
> **而「死区」是打破这个权衡的那一维** —— 它把「发现得早」和「允许收尾」**解耦**了。

---

## 【归因】

**LLM 没有「分阶段」的概念，只有「下一步」。**

所以「越限就打断」在它那里不是「提醒它收敛」，而是**把一个正在成形的产物砍断**。

它不像人 —— 人在被喊停时会「把手上这句写完」，模型不会。
**它的产物是一次性长出来的，中途砍掉就什么都没有。**

---

## 【做法】

### ❌ 别这么做

- 一越限就 `abort`（→ 产物为空）
- 靠「提高采样率」两头兼顾（采样率影响的是代价，不解决误杀）

### ✅ 该这么做

1. **护栏要有死区**：越限后先给「收尾窗口」（如再允许 N 次调用把当前产物写完），
   窗口内不管，窗口外才硬停。
2. **护栏信号用结构事件**（`tool_call` 计数），**不用资源用量**
   （`agent.usage` 结算后才累加，实时是陈的 —— 这是实测踩的坑，也是 P1 的推论）。
3. **「停」和「改向」是两回事**：
   - `steer`（改向，不打断）**先用** —— 大多数情况够了
   - `abort`（硬停）是最后手段，因为它会留下空产物

---

## 【验证】

- `grace=0` → 2/4，`grace=30` → 2/2
- 与 `demom` §10.5 坑 2 独立复现（那边：拉完不给余地 → 2/3；加 `GRACE=30` → 3/3）
- ⚠️ 只有 1 个任务（T-A）、n 小（grace=30 那格只有 2 和 1 轮）→ **待跨任务验证**

## ⚠️ 引用时的注意

| 污染口径 | 影响 |
|---|---|
| **缺枚举手段** | ⚠️ **可能有影响** —— `flat-guarded` 是单 agent，猜错率 4–11%（低），所以影响小 |
| **端点退化** | ⚠️ 「产物为空」有**两种成因**：被 abort 打死 / 端点挂死。当时只有一种记录方式 |
