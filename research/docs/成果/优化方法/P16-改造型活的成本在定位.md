# P16 · 改造型活的成本在**定位**，不在修改

| | |
|---|---|
| **类型** | ⑤ 优化 / ④ 分析 |
| **归因到** | ★ **"找在哪"与"改什么"是两笔成本，前者占 90%** |
| **强度** | **强**（三个 bug、8 轮一致） |
| **来源** | `runs/repair-*.jsonl` · [`../../族C-修bug结果.md`](../../族C-修bug结果.md) |
| **日期** | 2026-10-17 · `deepseek-v4.1-flash` |

---

## 【现象】

**修 bug 的工具分布**（8 轮）：

| 工具 | 次数 | 占比 |
|---|---|---|
| `bash`（跑测试、缩小范围） | **14–41** | ★ **~70%** |
| `read`（看代码上下文） | 1–10 | ~20% |
| ★ **`edit`（真动手改）** | ★ **1–2** | ★ **~5%** |

**修一个 bug 要 20–99 万 token，而其中真正"改"的部分只值几次调用。**

---

## 【归因】

### 活的形状是「**长定位 + 极短修改**」

```
跑测试看失败 → grep/read 缩小范围 → 再跑 → 再缩 → ★ 找到那一行 → edit 一次 → 跑测试确认
└────────────────────── 定位（90%）──────────────────────┘   └─ 改(5%) ─┘  └─ 验(5%)─┘
```

> ★★★ **而"判断类"任务**根本没有定位阶段** —— 它一步就到结论。**
> **所以我们此前十几轮的结论，都缺了"定位"这一整块劳动。**

### ★ 难度差异也落在定位上

| bug | 结果 | bash 次数 |
|---|---|---|
| `tools-noreload` | ✓✓ | 17–25 |
| ★ **`ctx-refresh`（最难）** | ★ **✓✗** | ★ **15–41** |
| `obs-syscount` | ✓✓ | 14–27 |

★ **失败那轮 bash 41 次（全场最多）** —— 它**反复跑、反复缩，但没找到那处 `refreshContext`**。
**难的 bug 不是"难改"，是"难找"。**

### ★★ 量级差 20 倍

| 任务 | token |
|---|---|
| 族 B 整个"意图落地"（写一份可核对报告） | ★ **15,600** |
| 族 C 修一个 bug | ★ **200,000–990,000** |

> ★★ **「改造型」与「判断型」是两种完全不同量级的劳动** ——
> **混在一个实验体系里比"效率"会得出荒谬结论。**

---

## 【做法】

| # | 做法 |
|---|---|
| 1 | ★★ **优化改造型活，要往"更快缩小范围"上使** —— 不是让它"改得更快" |
| 2 | ★★ **给更好的定位手段**（grep/find/测试输出结构）比给更好的改法有用得多 |
| 3 | ★★ **"改动行数"不是难度指标** —— 我注入的都是一行级改动，但成本差 5 倍 |
| 4 | ★ **成本预算要按定位算**：修一个 bug 的量级是几十万 token |
| 5 | ★ **别拿判断类任务的成本标准去预估改造类**（差 20 倍） |

---

## 【验证】

| 证据 | 强度 |
|---|---|
| ★★ `edit` 1–2 次 vs `bash` 14–41 次（8 轮） | **强** |
| ★ 最难 bug 的 bash 次数最高（41）且唯一失败 | ★ **强**（定位难度→成本 的因果） |
| ★ 与族 B（15.6k）对比得 20 倍量级差 | **强** |
| ⚠ 只 3 个 bug | 中 |
