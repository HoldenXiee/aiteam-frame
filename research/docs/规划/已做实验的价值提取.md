## P1 「代价不能当验收信号，管控要挂在结构边界上」

### 【现象】

同一份系统代码、同一个任务、同一个模型，跑 6 次（G0-3-flat）：

| 量 | 读数 |
|---|---|
| 产物 | **6/6 逐字节相同** |
| 代价 | 9.7k → **393k token，极差 40.6×**，CV 1.903 |
| 更大的规模（pairs=16） | **2,694k token / 43 分钟 — 而产物是对的** |

跨 49 轮的特征分析（G0-1）：**总 token 与成功率无关（AUC = 0.498，等于掷硬币）。**

### 【归因】

**LLM 的本性：看不见自己的代价，也不知道「够了」。**

它不觉得「已经读了 300k token 该停了」，因为它根本没有这个感知。
所以：
- 同一件活，它可以花 9.7k 做完，也可以花 393k 做完 —— **结果一样**
- 花多少**不由任务难度决定**，由它这一路的路径决定
- 于是**代价方差远大于效果方差**（结构方差为 0，代价方差 40×）

### 【做法】

❌ **别这么做**：
- 用 token 预算当护栏信号（方差太大，9.7k–393k 都正常，卡在哪都会误伤或失效）
- 用「花了多少」判断「做得好不好」（AUC 0.498，等于掷硬币）
- 靠模型自己觉察"差不多了"（它没这个感知）

✅ **该这么做**：
1. **管控挂在结构边界上，不挂在资源消耗上。**
   阶段边界（pipeline 的 S1→S2→S3）、结算点（`agent_settled`）、
   工具调用计数 —— 这些是**确定的、可复现的**。资源是**随机的**。
2. **不要试图省 token，要试图限定路径。**
   给代码定死「只准读这几个文件」，比「控制读了 20k token 就停」可靠得多。
3. **冗余是理性的**（★ 零成本前提）：
   既然同一件活花 9.7k 或 393k 都做对，而成本是 0，
   **跑 3 遍取交集** 比 **精心设计一遍** 更划算 —— 而且能顺带抵消采样随机性。

### 【验证】

- 配置 1（`pairs=4`）：产物相似度 1.000、代价极差 **40×**
- 配置 2（`pairs=8`）：产物相似度 0.984、代价极差 **9.78×**
- 两个配置上都成立 → **结论变硬**
- ⚠ 未在**形状不同**的任务（如 T-E）上验证 → **待补**

## P2 「护栏必须有死区：控制器不能当场打死被控对象」

### 【现象】

实时护栏（数工具调用，越限就 steer 甚至 abort）扫「死区 grace」（G1-1）：

| 死区 grace | 结果 | 怎么坏的 |
|---|---|---|
| **0**（一越限就拉） | **2/4** | 2 次产物为空 —— **被护栏自己打死** |
| **30**（留 30 次调用的收尾余地） | **2/2** ✅ | — |

同组数据里还有：**采样越密越省 token，但越容易误杀**（11k vs 29k，2/4 vs 3/4）。

### 【归因】

**LLM 的本性：它没有「分阶段」的概念，只有「下一步」。**

所以「越限就打断」在它那里不是「提醒它收敛」，而是**把一个正在成形的产物砍断**。
它不像人 —— 人在被喊停时会「把手上这句写完」，模型不会。
它的产物是**一次性长出来的**，中途砍掉就什么都没有。

### 【做法】

❌ 别这么做：
- 一越限就 abort（→ 产物为空）
- 靠「提高采样率」两头兼顾（采样率影响的是代价，不解决误杀）

✅ 该这么做：
1. **护栏要有死区**：越限后先给「收尾窗口」（如再允许 N 次调用把当前产物写完），
   窗口内不管，窗口外才硬停。
2. **护栏信号用结构事件**（`tool_call` 计数），不用资源用量
   （`agent.usage` 结算后才累加，实时是陈的 —— 这是实测踩的坑）。
3. **"停"和"改向"是两回事**：
   - `steer`（改向，不打断）先用 —— 大多数情况够了
   - `abort`（硬停）是最后手段，因为它会留下空产物

### 【验证】

- G1-1（反馈延迟相图）：grace=0 → 2/4，grace=30 → 2/2
- ⚠ 只有 1 个任务（T-A）、样本小 → **待跨任务验证**

## P3 「不要指望模型自己分工 —— 分工要由代码写死」

### 【现象】

T-E（只读代码审查）扫 `shards × coordinator`，**36 轮**：

| 文件数 | 轮数 | **有委派的轮** | 委派边 |
|---|---|---|---|
| 7 | 14 | **0** | 0 |
| 11 / 21 / 26 | 5 | **0** | 0 |
| 35 | 7 | 2 | 4 |
| 36 | 10 | 3 | 9 |

**总计：36 轮只有 5 轮出现委派（14%）。**
系统提示里**明说了分片可用**，role 里也写了「你可以派」。

且委派出现后：**10 轮里 5 轮超时，卡在「reviewer-3 prompt 中」** ——
派出去的子 agent 不返回。

### 【归因】

**LLM 的本性：不会主动分工（这是 `demom` 第三次复现同一个现象）。**

三个来源：
1. `demom` §10.1：给它挂 `peers`/`ask`，**一次都没被调用过**
2. `demox` T-E：36 轮只 5 轮派
3. `demox` 更早（`demom` 语料从 14 → 44 份）：14 份时 `delegations=0`

而且**它不算错**：7 个文件自己读 8 次就完了，派一个 reviewer 要付完整个启动+提示+回传。
**所以「不派」往往是它的正确判断，不是缺陷。**

### 【做法】

★ **这是本次提取里最值钱的一条。**

❌ 别这么做：
- **给 agent 挂 spawn 工具，然后假定它形成了集群**
  （实测：14% 的概率才是集群，剩下的轮次是单干 —— 而**数据里看不出来**）
- 把「集群 vs 单点」当对照实验，而不检查实际委派数

✅ 该这么做：
1. **分工要由代码写死**（pipeline / 显式 fan-out），
   不要靠「给它工具让它自己决定」—— 那是把控制权交给一个**不会主动用**的东西。
2. **如果一定要用模型自主分工**：
   - 必须**检查 `delegations` 是否为 0**，为 0 的轮次**不能当集群实验用**
     （已在 `bench/scan.ts` 里加了「规模自检」强制这一步）
   - 规模要足够大（实测阈值在 26–35 文件之间）
3. **规模阈值本身是个参数**：低于它「集群」根本不存在，你测的是个不存在的现象。

### 【验证】

- 3 个不同规模（7 / 21–26 / 35–36 文件）× 36 轮，方向一致 → **强**
- 且与 `demom` 的独立观察一致（不同代码、不同任务）→ **跨项目复现**
- ⚠ 阈值区间仍宽（26→35 未细采）→ 待补

## P5 「要给枚举手段：只给 read 它会盲猜文件名」

### 【现象】

`pipeline` 系统（S1-摸底 → S2-去重 → S3-成文），工具集 `only: ["read","write"]`。
扫 `verify × corpusPairs`（27 轮）：

| verify | 卡死率 | 平均工具调用数 |
|---|---|---|
| 0（无校验） | 1/9 | ~110 |
| 1（泛泛核对） | 3/9 | ~175 |
| 2（明说错误类型） | **7/9** | ~140 |

**失控轮的特征**：100+ 次 read，**0 次命中真实文件**。把路径打出来看：

```
corpus/C1.md   corpus/1.md   corpus/材料1.md   corpus/doc1.md
corpus/01.md   work/spec.md  corpus/index.json  ...
```

而现场只有 `M1.md` … `M18.md`。**它在盲猜文件名** —— 猜不中就换个拼法再猜。

**全库扫描**（39 个 run、8,307 次 read）：**66.9% 读的不是语料文件**。

| 系统 | 猜错率 | 为什么 |
|---|---|---|
| `flat` | **4–11%** | 一个 agent 从头读到尾，**自己数着** |
| `pipeline` | **62–88%** | 下游 S2/S3 是**全新 agent** |
| `review` | **94–100%** | 同上（reviewer 是全新的） |

### 【归因】

**两个本性叠加，主因是能力缺口：**

1. **它不会「先看看有什么」**（B2 的近亲）—— 任务说「列出 corpus/ 里的材料」，
   它就直接开始 read，**不先枚举**。而它**做不到枚举**：没有 `ls`。
2. **看不见自己的代价**（B1）—— 猜错 10 次、50 次、100 次，它**没有「我已经浪费很多了」的感知**，
   于是猜不中就一直猜。

`verify` 指令的作用是**把「必须读到原文」变成硬要求**，于是放弃阈值被抬高：
卡死率 1/9 → 3/9 → 7/9。

★ **模型自己知道缺什么**。实测里它明说：
> 「我没法完成这份清单 —— **环境里没有能列目录的工具**。」

所以它不是笨，是**在残缺工具集下的唯一手段**。

### 【做法】

✅ **凡是让 agent 自己去某个目录取东西的活，必须给它枚举的手段。**

| 做法 | 效果（实测） |
|---|---|
| `["read","write"]` | ✗ **90 秒卡死** |
| `+ ls` | ✓ 36 秒完成 |
| `+ ls/find/grep` | ✓ **16 秒**完成，read 调用 54 → 31 → **19** |

1. **`permissions.only` 收窄时要想清楚**：你砍掉的每一项，它都得用「猜」来替代。
2. 若确实不能给枚举工具，就**在提示里显式给出确切文件名** —— 把枚举这一步**由代码替它做掉**。
3. ★ **这是「代码 vs 模型」分工的一个具体切片**：
   枚举是**确定性的活**，该由代码做；让模型去猜是把确定性的事变成了赌博。

### 【验证】

- **判别对照**：只改工具集，别的全不动 → 90s 卡死 vs 36s/16s 完成
- **剂量-反应**：verify 0→1→2，卡死率 1/9 → 3/9 → 7/9
- **全库扫描**：39 个 run、8,307 次 read，66.9% 是猜的；分界线与「谁是全新 agent」一致
- ⚠ 主要在 T-A + pipeline 上；`review`/`star` 只做了事后扫描，没做对照


## O1 观察：中心校验可能增加级联（未归因）

G3-3 的读数：`verify=0` → 2/3，`verify=1` → **3/4**（校验反而更差）。

**归因候选**（P5 已给了机制：下游 agent 读不到原文，就一直猜），
但当时**没做能分辨的对照**（未固定工具集）。
→ 保留为观察，归到 P5 里一起验。

## O2 线索：静默型错误比崩溃型难发现（很弱）

T-E 大规模那轮唯一漏掉的是 `src/retry.js`（D9）：
重试耗尽后隐式返回 `undefined` —— **不崩、不报错、不看注释看不出来**。
而缺陷库里**静默型占 8/20**。

⚠ 但只有 **1 个漏检数据点** → **只能算线索**。
要测这条：**固定缺陷总数，只改种类配比**（12 个缺陷里静默型占 2/6/10）。

**归因候选**：模型靠「看起来对不对」判断，而静默错误**看起来是对的**（同 P5 的本性 B1/B8）。

## 「价值提取」的元结论

重读这 109 轮，我发现自己当时**做实验的手艺是够的**（判据纯函数、对照、方差、
基础设施失败单列），**问题全在选题**：

| 当时的写法 | 现在应该写成 |
|---|---|
| 「反馈需要死区」 | 「**LLM 没有分阶段概念** → 所以护栏必须留收尾窗口」 |
| 「中心校验增加级联」 | 「**它看不见自己的代价** → 所以 O(n²) 校验会失控 → 要单点仲裁」 |
| 「委派稀疏」 | 「**它不会主动分工** → 所以分工要代码写死」 |
| 「代价不可复现」 | 「**它看不见自己的代价** → 所以管控挂结构边界，不挂资源」 |

★ **同一批数据，换框架读，就从「现象」变成了「做法」。**
区别不在数据，在**要不要把它归因到 LLM 的本性上**。

而这张「本性表」目前只有 **4 条有实验支撑**（无代价感 / 不主动分工 / 对齐抓力弱 / 采样随机），
**还有 4 条完全是空的**（无状态 / 上下文有限 / 会把局部当全局 / 会"看起来完成了"）。

**这 4 个空格，就是这门学科接下来最该填的地方。**

★ **而 G3-On2 顺手给了一个 B8 的活体样本**：在缺 `ls` 的环境里，模型几次
「声称已写入 answer.json」而**实际根本没写**，或「声称读完了 18 份」而用了 54 次读。
它的自报**不可信** —— 但那不是它撒谎，是它**只能拿"我以为"当"事实"**。
