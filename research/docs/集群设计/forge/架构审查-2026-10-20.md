## 3. 规则：什么时候动（骨架）

规则表在 `topology/rules.ts`。**触发不是"定时问"，是"集群自己的事件"**：

```
观察点①：agent_settled（员工停下）
观察点②：每 15 次工具调用        ← 微实验 A/B 实测得来
观察点③：每 5 分钟（时间节流）    ← 微实验 E：工具调用次数在长实验里是错的单位
        ↓
      tick()  ── 一个 tick 里按固定顺序跑七条规则
```

### 3.1 tick 的**执行顺序**（★ 这个顺序是被实测逼出来的）

```
onAudience()      ← 请观众评（不 fire 专家，快）
onConsensus()     ← 请缺席团队签字（不 fire）
onDispute()       ← 有僵局 ⇒ 送联合实验（不 fire）
onNewFinding()    ← 新产物 ⇒ 要同事挑战（不 fire）
onCapabilityGap() ← 报告能力缺口 ⇒ 起 libsmith
onPlateau()       ← 无进展 ⇒ 起 inspirer + archivist
onSettled()       ← ★★★ 必须最后：它 await fire("inspector")，等几分钟
```

依据：`rules.ts:302-311`。
★★ **为什么 `onSettled` 必须最后**：它 `await fire("inspector")`，专家要跑几分钟 ⇒ 排在它后面的规则**一个都轮不到**（实测：观众零表态）。

### 3.2 七条规则各自的判据（这是审查的重点）

| 规则 | 判据 | 触发后 | 依据 |
|---|---|---|---|
| `onSettled` | `outbox份数 > state.auditedOutputs` | fire `inspector`；解析 `VERDICT` | `rules.ts:318-335` |
| `onCapabilityGap` | outbox 文件名匹配 `/缺口\|提案\|撞墙\|做不到\|capability/i`，且距上次 ≥20min | fire `libsmith` | `rules.ts:337-350` |
| `onPlateau` | 连续 3 次 tick 既无新产物**且** `work/` 新增文件 < **10** | fire `inspirer` + `archivist` | `rules.ts:377-452` |
| `onNewFinding` | outbox 里有未被挑战过的产物 | 送 **2 位**同事挑战（一次一份）| `rules.ts:454-494` |
| `onAudience` | 有未被评过的产物（`rules.ts:503` 取 `filter(...)[0]`）| 送全体观众（一次一份）| `rules.ts:496-541` |
| `onConsensus` | 有产物**未全体签字**（`rules.ts:551` `find`）| 送缺席团队签字（一次一份）| `rules.ts:543-596` |
| `onDispute` | 有产物**门没开** 且 有团队非简单认同（`rules.ts:615`）| 送双方联合实验（一次一份，`rules.ts:641` break）| `rules.ts:598-643` |

### 3.3 参数（★ 全部来自微实验，不是拍的）

| 参数 | 值 | 依据/理由 |
|---|---|---|
| `THROTTLE_N` | 15 次工具调用 | 微实验 B：合格区内最省（5/10 太密，30 太晚）|
| `THROTTLE_MS` | 5 min | 微实验 E：长实验里一次工具调用 = 1~3 小时，次数是错的单位 |
| `PLATEAU_ROUNDS` | 3 | 一拍一审的节奏 |
| `FRESH_FILES_THRESHOLD` | 10 个文件 | 跑实验会落几十上百文件；改脚本只出 <5 个 |
| `COOLDOWN_MS` | 20 min | 防刷屏 |

依据：`rules.ts:47-99`（`THROTTLE_N` / `THROTTLE_MS` / `PLATEAU_ROUNDS` / `FRESH_FILES_THRESHOLD` / `COOLDOWN_MS`）。
★ `makeRules` 返回的七条规则在 `rules.ts:645`。

### 3.4 四本分开的账（★ 一个状态两个写者会毁掉判据）

| 账 | 谁写 | 判什么 |
|---|---|---|
| `state.auditedOutputs` | **只有** `onSettled` | 该审查吗 |
| `state.seenOutboxCount` | **只有** `onPlateau` | 有产出吗 |
| `state.challengedOutputs` | `onNewFinding` | 辩过了吗 |
| `state.audienceAsked` | `onAudience` | 评过了吗 |
| `state.signedAsked` | `onConsensus` | 请过签字吗 |
| `state.disputeAsked` | `onDispute` | 推过联合实验吗 |

依据：`rules.ts:160-200`（`State` 类型定义）。
★★ 这些**拆开**是血换来的：`auditedOutputs` 曾被 `tick()` 和 `onSettled()` 两处写 ⇒ 审查**从不触发**（`rules.ts:261-278`）。

### 3.5 收尾态（`closing`）

窗口 `--secs` 到点 ⇒ `closing = true` ⇒ 所有规则在 `ctx.closing?.()` 处 **early return**。
★ 目的：防「边收边产」的自激循环（实测超窗口 44 分钟）。
★ **已在跑的专家不打断**，等它们自己做完。

依据：`runner.ts:355-360`, `rules.ts` 各规则第一行。

## 4. 辩证三件套：怎么让他们吵起来

### 4.1 `challenge` —— 同事挑战

★★ **不是工具，是处境**：产物一出现，代码主动把「请挑战这份」送到 2 位同事面前（`rules.ts:454-494`）。
★ 投递用 `io.steer`（当场注入），不是 `queue`（会排在它自己的工具输出后面 —— 实测某席位整个窗口只收到 5 次）。

依据：`runner.ts:210-249`。

### 4.2 `sign_off` —— 共识门

**判据（纯函数 `gateVerdict`，可离线重判）**：

| 状态 | 判定 |
|---|---|
| 全体 `认同` | ✔ 放行 |
| 某队 `有保留` **且给了 ≥10 字的解除条件** | ✔ 放行（意见附文末）|
| 某队 `反对` | ⛔ 拦 |
| 某队**没表态** | ⛔ 拦（沉默不是认同）|
| 某队 `有保留` **但没给解除条件** | ⛔ 拦（★ 视为没表态）|

依据：`signoff.ts:62-84`（`gateVerdict`）。

★★★ 最后一行是 2026-10-19 夜间补的：原来 26 次签字里 **23 张"有保留"、0 张"反对"** ⇒ 门形同虚设（`有保留` 太廉价，成了免责声明）。

### 4.3 `joint_experiment` —— 分歧辩不出时一起设计实验

两段：`propose`（写清判什么/几个臂/判据纯函数源码）→ `sign`（认同 / 要求加臂 / 反对）→ `run`（取装置骨架真跑）。

依据：`tools/joint.ts`，`joint.jsonl`。

### 4.4 `judge` —— 观众表态

**收敛判据**：`resolveVotes(votes, question, threshold=0.9)` ⇒ 同一 question 下某方支持率 ≥90% ⇒ `decided`。

依据：`tools/judge.ts:53`（`resolveVotes`）、`:38-50`（`Vote` 接口）, `lines.ts:282`（`BOOK_THRESHOLD`）。

## 9. 我在代码里看到的疑点（★ 供你审查，不是结论）

> ★★ 这一节每条都只到「读代码/读日志得出」，**没有一条跑过微实验验证**。

### 9.1 `onConsensus` 的提前 return 会饿死后续产物

```ts
const target = outs.find((f) => { /* 有团队没签 */ });        // rules.ts:551
if (!target || state.signedAsked.includes(target)) return;     // rules.ts:555
```

★ `find` 取第一份没签全的；一旦这份被 `signedAsked` 记过，**下一次 `find` 还返回它** ⇒ `return` ⇒ **永久卡在第一份**。

★★ 与实测吻合：`onConsensus` 只被调用 8 次、只请了 8 份（outbox 24 份）。
★★ 疑点：`signedAsked.includes(target)` 之后应该是「跳过它找下一份」，不是整个返回。

### 9.2 `onDispute` 的判据覆盖了「没表态」，且一次 `break`

```ts
if (!rec) return true;        // 没表态 = 僵局     ← rules.ts:615
...
break;                        // 一次只推一份      ← rules.ts:641
```

★ 24 份产物里 13 份被拒（多数是「全体未表态」）⇒ 每份都算僵局 ⇒ **全挤进联合实验通道**，而 `break` 让每 tick 只推 1 份 ⇒ 实测只送 9 份。

### 9.3 `votes.jsonl` 缺 `artifact` 字段（见 §8.3）

★ 这是「量具记的字段，必须能回答你想问的问题」（纪律㉔）的直接违背。

### 9.4 `FRESH_FILES_THRESHOLD = 10` 不随席位数缩放

实测 detail：
```
新文件=521 → 在干活=true
新文件=101 → 在干活=true
新文件=9   → 在干活=false
```
★ 这个阈值在 hunt（单员工、一个实验目录）成立；forge 有 6 席，**任一方跑实验就产出上百文件** ⇒ `roundsSinceProgress` 几乎永远归零 ⇒ `inspirer`/`archivist` 只在**全员都闲**时才触发（实测各 2 次 / 5 小时）。

### 9.5 上一轮缺 `rule:done` 收尾行

`runner.ts:586-587` 会写 `★ 收尾：outbox N 份 …`，但 `_topology.log` **没有这一行**，最后一行是 `result archivist · 1753 字`（06:25）。
★ `_lib-rev.jsonl` 的「集群收尾」在 06:21 已写 ⇒ 说明走过了那一步，卡在后面的 `await Promise.allSettled(...)`（`runner.ts:571`，等 agent 收干净）。

### 9.6 `costUsd` 字段大面积缺失

窗口内 140 条带 `totalTokens` 的记录，`costUsd` 合计 **0.0000**；全 work 累计 0.12。
⇒ 成本只能按 token 事后推，不能按轮读。

### 9.7 实验目录没有 lib 版本标记

`_lib-rev.jsonl` 只有**集群级**的开工/收尾两条。`work/` 下 23 个实验目录（`reader3` 与 `reader4` 是同一问题的两版）**各自不记 lib 版本** ⇒ 无法判断哪份数据属于哪个修订（纪律⑩）。

### 9.8 门里的「有保留」占比 54/84

`有保留` 判据要求 `dislodge.trim().length >= 10`。实测 54 张有保留、33 张带解除条件 ⇒ 21 张被判「无效表态」。
★ 这个阈值（10 字符）是否够严，值得审查。

## 10. 一句话总结

★ forge 的形状是：**6 席 × 3 队立场对立 + 4 位观众评判 + 五类外部专家 + 七条事件规则 + 两道门（共识门/发布门）**。

★★ 实测里**争辩活了**（138 次全文可读）、**共识门活了**（84 条签字、13 份被真拒）、**发布门活了**（18 份进书）。

★★★ 但**观众这一环没活** —— 20 次请评只换来 3 张窗口内的票，且因为缺 `artifact` 字段，**"9 成支持就结束争辩"这件事在结构上不可能发生**。
