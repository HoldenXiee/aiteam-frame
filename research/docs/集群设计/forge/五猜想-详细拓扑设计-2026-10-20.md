## 0. 先定问题（否则五条都是拍脑袋）

### 0.1 forge 交出来的东西 vs hunt 交出来的东西

| | hunt（10-19 收尾）| forge（10-20 收尾）|
|---|---|---|
| 形态 | **一张 169 行状态表** | **10 份散文**（3362 行）|
| 状态标记 | ✅27 · ⚠24 · 📉4 · 🔁3 | ★ **无状态标记** |
| 被推翻的条目 | 有（7 条 🔁/📉）| ★ **0 条**（一条都没写进去）|
| 读者用它做判断 | ★ 一查就知道「这条还能不能信」 | 要读 583 行才可能知道 |

★★★ **这就是落差**：forge 干的活是「把表展开成散文」，不是「造一个更好的表」。

### 0.2 forge 的真实目标（引原文，不改写）

> 设计者：「**不强调一定要写新概念**，而是追求写的东西**描述的准确、有深度**，
> 可以**用作「工具」**来分析使用这新生产范式」

★★ 「工具」的定义：**能拿来跑一个判断动作**，不是**能拿来读一遍**。

### 0.3 一个读数（问"forge 现在像工具吗"）

| 读数 | 值 |
|---|---|
| 书的章数 | 10 |
| 其中真跑了新实验的 | **1 份** |
| 明写「0 次新 API」（纯重解释）| **3 份** |

| ★ 这些章号在书里有登记处吗 | ★ **没有**（第九章声明「替换第四章」，而第四章在归档区、从未进书）|
| `landing` 两席的产物数 | **0** |
| `theory-mapper` 一人的产物数 | **6** |

★★ 归因：**没有「书」这个对象**。只有「产物」和「拷贝进目录」。

# 猜想 A · 决策表

## A.1 论点

**forge 的第一产物应该是 `情况 → 判据 → 动作 → 代价 → 边界` 的表；「章」是注解，不是主体。**

★ 依据：书自己的 `前言` 就写了这个用法 ——「如果你**在踩坑**：第三部分按『什么情况 → 怎么做』组织」。
但实际第三部分是大章，读者踩坑时不会读 583 行。

## A.2 拓扑设计

**新增规则：`onTable`（唯一一条）**

```ts
/**
 * onTable —— 把新产物并入决策表（★ 只维护一张表，不新造文档）
 *
 * 判据：outbox 里有**未并入表**的产物，且累计 ≥ 2 份
 *       （★ 1 份不触发 —— 单条进不了表，只会变成加一列）
 * 动作：fire `archivist`，只问两件事：这张表该加哪行？哪两行冲突？
 */
async function onTable(): Promise<void> {
  if (ctx.closing?.()) return;
  const outs = listOutbox().filter((f) => f !== TABLE_NAME);
  const pending = outs.filter((f) => !state.tabledOutputs.includes(f));
  if (pending.length < 2) return;                    // ★ 阈值 2：单条不成表
  if (Date.now() - (state.firedAt["archivist"] ?? 0) < COOLDOWN_MS) return;

  state.firedAt["archivist"] = Date.now();
  state.tabledOutputs.push(...pending);
  ctx.trace("onTable", `${pending.length} 份待并入表，表现有 ${countTableRows()} 行`);

  await fire(
    "archivist",
    `有 ${pending.length} 份新产物还没进决策表：${pending.map((p) => `\`${p}\``).join("、")}。\n` +
      `★ 表在 \`outbox/${TABLE_NAME}\`（现有 ${countTableRows()} 行）。\n` +
      `★★ 你只做三件事，不要写新章：\n` +
      `  1. **加行**：每份产物给出「什么情况 → 判据 → 该做什么 → 代价 → 边界」五格\n` +
      `  2. **改行**：若它推翻了某行，把那行标 🔁 并指向新行（★ 不要删，读者要知道它错过）\n` +
      `  3. **报冲突**：若两行的「该做什么」在这种情况下矛盾，写进表末「未裁决」栏\n` +
      `★★★ 判死条件：若某份产物**填不满五格**（尤其说不出边界），不要硬填 —— ` +
      `把它列进「还进不了表」栏，并说清缺哪一格。`,
  );
}
```

**表的形态（★ 冻结，跑前写死）**

```markdown
| 情况（读者遇到什么） | 判据（怎么确认是这一类） | 动作 | 代价 | 边界 |
|---|---|---|---|---|
| 判据对，落地 0/4 | 判据 fp=0 但 matched<真数 | 先修「读得到」 | 2.8 份副本 | 仅 notes 单工人族 |
```

## A.3 判据（零成本实验可判）

| # | 判据 | 怎么量 |
|---|---|---|
| A-1 | 表存在且行数 ≥ 产物数 × 0.5 | `grep -c "^\| "` on 表文件 |
| A-2 | ★ **五格填充率** ≥ 80%（缺「边界」的行 ≤ 20%）| 数空格 |
| A-3 | ★★ 有 🔁 行 ≥ 1（说明它敢标推翻）| `grep -c "🔁"` |

★★ **A-3 是关键**：现在的书 **0 条被推翻**，而 hunt 有 7 条。
若表里也没有 🔁 ⇒ **forge 仍在美化，没在体系化**。

## A.4 判死条件

- 表行数 < 5：说明它写不出情况分类（那是**内容**问题，不是拓扑问题）
- 五格填充率 < 50%：说明这个形态对模型太硬，该改成自由文本
- ★ 出现「章」而不是「行」：说明 `archivist` 无视了指令 ⇒ `P13` 再现，要改成**代码生成表头**

# 猜想 B · landing 真的写产物

## B.1 论点

**`landing` 两席现在一份产物都不写（实测 0 份）—— 读者侧是哑的。**

★★★ 后果：你的裁定「观众最被说服哪个观点就写哪个观点」失效 ——
因为 `landing` **没有观点**，观众只能在 theory 造好的选项里挑。

## B.2 拓扑设计

**新增规则：`onSilentSeat`（唯一一条）**

```ts
/**
 * onSilentSeat —— 某个席位整段时间没有产物 ⇒ 把「你自己写」当处境送过去
 *
 * ★★★ 为什么不是「提醒它多写写」（那是提示词，没规则）：
 *   这是**结构性缺口**：landing 的定义里写着「你扮演读者」，
 *   而「扮演」在代码里**没有任何产物要求** ⇒ 它自然退化成审稿人（P13 变体）。
 *
 * 判据：某席位在窗口内产物数 = 0，且 outbox 已有 ≥ 5 份（有事可评了）
 * 动作：fire 该席位，明确要求**交一份产物**（不是意见）
 */
async function onSilentSeat(): Promise<void> {
  if (ctx.closing?.()) return;
  const outs = listOutbox();
  if (outs.length < 5) return;              // ★ 太早没东西可写

  for (const seat of ctx.peerKeys?.() ?? []) {
    if (!seat.startsWith("landing/")) continue;   // ★ 只管读者侧
    if (state.silentAsked.includes(seat)) continue;
    // ★ 判据：这个席位有没有以作者身份写过产物
    const mine = outs.filter((f) => isAuthoredBy(f, seat));
    if (mine.length > 0) continue;

    state.silentAsked.push(seat);
    ctx.trace("onSilentSeat", `${seat} 至今 0 份产物（outbox ${outs.length} 份）`);
    await fire(
      seat as ExpertName,
      `★ 你已经评了 ${outs.length} 份别人的产物，但**你自己一份都没写**。\n` +
        `★★ 这个集群不是审稿会 —— 你这一队的职责是**产出读者侧的东西**。\n` +
        `★★★ 现在请你交一份产物（不是意见、不是评审）：\n` +
        `  · \`reader\`：写**读者会在哪里卡住**的具体现场 —— 拿一章真去照做，卡在哪一步、缺哪句话\n` +
        `  · \`edge\`：写**这条在什么条件下不成立** —— 给你的边界一个反例或一个实测\n` +
        `★ 判据：你交的东西必须是**一种新的产物**，而不是对现有章末的补充。`,
    );
  }
}
```

**★ 为什么只管 `landing`，不管 `practice`**：
`practice` 有 2 份产物，虽少但**有**；`landing` 是 **0**，性质不同（完全退化）。

## B.3 判据

| # | 判据 | 怎么量 |
|---|---|---|
| B-1 | `landing/*` 产物数从 0 → **≥2** | `grep -l "forge / landing" outbox/*.md` |
| B-2 | ★ 该产物**不是**评审意见 | 人工读：有没有「建议」「应当补充」这类审稿腔 |
| B-3 | ★★ 它的产物被同事挑战过吗 | `grep "landing-" debate.jsonl` |

★★ **B-3 是真正的判据**：如果写出来没人辩，说明它只是形式产物。

## B.4 判死条件

- 产物数仍为 0：说明「fire 一次」不够（`P13`）⇒ 要改成每条 `onSettled` 都催
- 产物是评审意见：说明 `landing` 的立场定义（`lines.ts`）本身就有问题
  ⇒ ★★ **这时该回报设计者，不是我改**（硬规则①）

# 猜想 C · 推翻故事

## C.1 论点

**forge 最该产出的独有内容，是「这条我原来信，后来不信了，因为……」**

★ 依据：hunt 的 `CONVERGED` 有 7 条被推翻/降级（🔁4 + 📉3），
**书里 0 条**。而这恰恰**最有教育价值** —— 读者最该学的是**怎么发现自己错了**。

## C.2 拓扑设计

**新增规则：`onFalsify`（唯一一条）**

```ts
/**
 * onFalsify —— 出现「推翻/降级/替代」字样 ⇒ 要一份完整的推翻故事
 *
 * ★★★ 为什么这不能只靠提示词：
 *   现在的产物里**已经有**「v2 修订」「接受挑战」这类记录，
 *   但那都是**章内小节**，读者扫到了也记不住。
 *   ⇒ 必须是一个**独立产物**，才有资格进书。
 */
async function onFalsify(): Promise<void> {
  if (ctx.closing?.()) return;
  const outs = listOutbox();

  // ★ 判据：产物正文里出现「推翻/降级/被取代/原来的判据」
  //   ★★ 用文件名不够（推翻故事不一定写在标题里）⇒ 读内容
  for (const f of outs) {
    if (state.falsifyAsked.includes(f)) continue;
    if (!REVERSAL_RE.test(readArtifact(f))) continue;

    state.falsifyAsked.push(f);
    const id = reversalId(f);
    if (outs.some((g) => g.includes(id))) continue;      // ★ 已写过这个故事

    ctx.trace("onFalsify", `\`${f}\` 含推翻记录，要一份独立故事`);
    await fire(
      "archivist",
      `\`outbox/${f}\` 里写了某条原来成立、后来被推翻/降级。\n` +
        `★★★ 请把它写成**一份独立的产物**（不是章内小节），四段，缺一段不算完成：\n` +
        `  1. **原来的说法**（当时的判据是什么，日期）\n` +
        `  2. **什么让它漏了**（是判据、装置、还是语料？给出具体那一处）\n` +
        `  3. **新判据**（与旧的差在哪一句话上）\n` +
        `  4. **边界**（新判据在什么条件下也会漏）\n` +
        `★★ 为什么值得单独写：读者最该学的不是「这些结论都对」，是**怎么发现自己错了**。\n` +
        `★ 若你判断这条不构成推翻（只是措辞收紧），明说，并把它从「推翻」降级为「收窄」。`,
    );
  }
}
```

## C.3 判据

| # | 判据 | 怎么量 |
|---|---|---|
| C-1 | 独立推翻产物 ≥ 2 份 | `ls outbox/*推翻*` 或 grep 标题 |
| C-2 | ★ 四段齐全率 ≥ 75% | 数四段标题 |
| C-3 | ★★ 第 2 段「什么让它漏了」**指到了具体文件/行** | `grep -c "work/.*jsonl"` |
| C-4 | 原料是否够 | hunt `CONVERGED` 有多少 🔁/📉 |

★★ **C-3 是真正的判据**：说不出「什么让它漏了」= 没在反思，在叙事。
★★★ **C-4 先查**：如果可引用的推翻只有 7 条，可能撑不起一类章 ⇒ **C 的天花板是 7**。

## C.4 判死条件

- 四段中缺第 2 段：说明「归因到自己错了」这件事模型做不到 ⇒ 那 C 不成立
- 写出来的都在重复章内已有内容：说明它没有独立价值 ⇒ C 退化为格式

# 猜想 D · 活目录（章节登记）

## D.1 论点

**「第九章」在替换一个读者看不见的「第四章」—— 因为书没有统一登记处。**

★ 这是**bug 级**问题，不是设计问题。实测：

```
理论-第九章-…md: 「本章替换第四章的处方。第四章说「把答案表弄出来」
                   （outbox-r1/理论-把果写死-landing从0到2of4.md）」
```

而 `outbox-r1/` 是归档区，**从未进书**。

## D.2 拓扑设计

**新增规则：`onChapterIndex`（唯一一条）**

```ts
/**
 * onChapterIndex —— 章节号必须有唯一登记处，且引用必须能解析
 *
 * ★★ 与其它猜想的区别：这条是**一致性检查**，不是生成新内容。
 *   判据是纯函数，可以完全离线重判（纪律⑦）。
 */
async function onChapterIndex(): Promise<void> {
  if (ctx.closing?.()) return;
  const outs = listOutbox();
  const index = readChapterIndex();          // 读 outbox/_章节登记.md

  for (const f of outs) {
    if (state.indexChecked.includes(f)) continue;
    state.indexChecked.push(f);

    // ★ 纯函数：找出这份产物引用的章号
    const refs = extractChapterRefs(readArtifact(f));   // 第九章 / 替换第四章 / §4
    const unresolvable = refs.filter((r) => !index.has(r));

    if (!unresolvable.length) continue;
    ctx.trace("onChapterIndex", `\`${f}\` 引用了不存在的章：${unresolvable.join("、")}`);
    await fire(
      "archivist",
      `\`outbox/${f}\` 引用了**不在登记表里**的章：${unresolvable.join("、")}。\n` +
        `★★ 读者会去找它，但找不到（它可能在归档区，从没进书）。\n` +
        `第 1 步：更新 \`outbox/_章节登记.md\` —— 每章一行：章号 · 标题 · 一句话主张 · 来源产物\n` +
        `第 2 步：对每个无法解析的引用，二选一：\n` +
        `  · 把它**收进登记表**（若那份产物确实在 outbox 里且过了门）\n` +
        `  · 把它改成**自足的说法**（不要让读者去查一个不存在的东西）\n` +
        `★★★ 不许做的：把归档区的产物当成章来引用 —— 归档 = 没进书 = 读者看不到。`,
    );
  }
}
```

## D.3 判据

| # | 判据 | 怎么量 |
|---|---|---|
| D-1 | `_章节登记.md` 存在 | `ls` |
| D-2 | ★ **悬空引用数 = 0** | 纯函数离线重判（不需要模型）|
| D-3 | 登记表覆盖所有进书的章 | 比对 `book/src/05-集群产出/` |

★★ **D-2 是纯函数**，可以**离线跑到零成本** —— 这是五条里唯一能 100% 确定性验证的。

## D.4 判死条件

- 登记表建了但引用仍悬空：说明模型不查表 ⇒ 要改成 `publish.ts` 硬拦（代码拒绝写入）
- ★ 这种情况不算 D 失败，算 D **必须升级为硬门**

# 猜想 E · 可执行判据

## E.1 论点

**「工具」= 能拿来跑，不是能拿来读。每章该带一个 20 行能跑起来的判定脚本。**

★ 依据：10 份里只有 1 份真跑了新实验，3 份明写「0 次新 API」。
★★ 而设计者的原话是「可以用作**工具**」—— 工具得**能执行**。

## E.2 拓扑设计

**新增规则：`onUntested`（唯一一条）**

```ts
/**
 * onUntested —— 产物自称「0 次新 API」⇒ 问它能不能变成一个可执行判定
 *
 * ★★★ 注意这条与其它四条的区别：
 *   它**不产生产物**，它要求产物**带一个能跑的东西**。
 *   若确实做不到（例如那条是方法论而非断言），必须写明**为什么不能**。
 */
async function onUntested(): Promise<void> {
  if (ctx.closing?.()) return;
  const outs = listOutbox();

  for (const f of outs) {
    if (state.untestedAsked.includes(f)) continue;
    const body = readArtifact(f);
    // ★ 判据：产物自己声明"没有新读数"/"0 API"
    if (!/0 次新 API|0 API|全部是.*重新解释|不含新读数/.test(body)) continue;

    state.untestedAsked.push(f);
    ctx.trace("onUntested", `\`${f}\` 自称无新读数`);
    await fire(
      "archivist",
      `\`outbox/${f}\` 里写着「没有新读数」。\n` +
        `★★ 这不一定是缺点 —— 有些结论确实只能靠重新解释。\n` +
        `★ 但读者要拿它当**工具**用，就得能**跑一遍判断自己属不属于这个情况**。\n` +
        `第 1 步：问一句 —— **这一条能不能写成一个 20 行的判定脚本？**\n` +
        `  · 能 → 写出来，放进 \`work/checks/\`，并在章末给出跑法（一行命令）\n` +
        `  · 不能 → ★ 明写**为什么不能**（是缺数据？还是它不是断言而是定义？）\n` +
        `★★★ 不许做的：假装能跑（写一个永远返回 true 的脚本，比没有更坏）。`,
    );
  }
}
```

## E.3 判据

| # | 判据 | 怎么量 |
|---|---|---|
| E-1 | `work/checks/` 下的脚本数 | `ls` |
| E-2 | ★ 每个脚本能真跑且**输出非恒真** | 跑一遍，看不同输入给不同结果 |
| E-3 | ★★ 说不出「为什么不能」的比例 = 0 | 数「为什么不能」段落 |
