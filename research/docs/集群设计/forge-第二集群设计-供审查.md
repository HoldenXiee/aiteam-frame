## 一、设计者的裁定（逐字，本文的设计源）

**关于职责**：
> 「第二集群**主要职责是产出这个方向的最终产物** `research/book`。
> 而为实现这个职责，它就需要去**分析、总结、批判**地看第一集群的成果、归纳，
> 产出**体系化的成果**，然后**为了检验这个最终成果，就需要用实践来检验**，
> 而实践就是做**更复杂、更考验『把人的意图落地』**的实验。」

**关于「把人的意图落地」**：
> 「『把人的意图落地』是我对这个新生产范式的简单解释 ——
> 就是**人只需要设计集群**，设计**怎么完成人心中的目标、想法**。」

**★ DESIGN 第 64 行（设计者刚加的）**：
> 「以**结果**来生产 …… **先果后因**、**意图落地** ——
> 生产中只会去**设计目标**，而真正实现是**通过 ai 来逼近目标（想法）**」

**关于产出形态**：
> 「类似某专业的**教科书**，追求**深度**，讲透**为什么**有这个现象、**为什么**这么优化。
> 而又要求是**体系化**的，不能像现在的成果记录一样，**分散、且没有分析出定义或模型**。」

**关于两个集群为什么必须分开**：
> 「两个必须分开，**两个集群的职责不同，不可能同时优化，只能分开优化**，
> 只有分开优化，最终才都能实现好的结果。」

## 三、★★★ `forge` 的三条工作线（★ 不是"角度"）

### 3.1 ★★ 与 hunt 的"角度"本质不同

| | hunt 的角度 | **forge 的工作线** |
|---|---|---|
| 是什么 | **同一种活（探索）的三种偏好** | ★★ **三种不同的活** |
| 多员工买到 | 找盲区（同一问题的不同视角）| ★★★ **一条产不出教科书** |

★★★ **为什么 forge 必须多员工**：
教科书要求**同时**成立三件事 ——

```
① 讲透为什么          → 要【理论建构】
② 讲的东西是对的      → 要【实践检验】（设计者明确要求"用实践来检验"）
③ 读者能用            → 要【能落地】
```

★ **一个人做三件事 ⇒ 必然偏向自己最顺手的那件**
（实测倾向：写手会一直写、检验者会一直验、理论者会一直抽象）
⇒ **三条线各一人，最后必须合成一本。**

### 3.2 三条线（`prompts/lines.ts` 里的逐字定义）

| 线 | 干什么 | ★ 它的失败模式 |
|---|---|---|
| **`theorist`** | 建立**定义与模型**：说清一个词在这个领域里**到底是什么**；现象之间**怎么连起来**（谁是因、谁是果、什么条件下反转）| ★ 把 N 条成果**重新排个版**就当成"体系"。<br>★ 检查法：**你有没有引入一个原来的成果里没有的概念？** 一个都没有 = 你只是做了目录 |
| **`practitioner`** | ★★ **用实践检验** —— 拿体系去驱动一个 agent 集群干真事 | ★ 读一读就下结论；<br>★★ 只验"这条数字对不对"，不去验"**这套说法能不能办事**" |
| **`critic`** | **拆**：边界 / 替代解释 / "测不出来"≠"不成立" / **有没有两条不可能同时成立** | ★★ **一条都没批倒** ⇒ 你把「多」当成了「对」，那不是批判，是背书 |

### 3.3 ★★★ `practitioner` 那条线特别说清（我上一版完全漏掉的）

★★ **它验的不是"这条结论对不对"** —— 那叫复核，谁都能做。

★★★ **它验的是**：

```
人只给一句话的目标（果）
        ↓
一个 agent 集群自己逼近出来（因）
        ↓
★ 看它逼近得怎么样 —— 这才是在检验这套体系
```

★ 这正是 DESIGN 的「**先果后因**」：**只设计目标，实现由 ai 逼近**。

★ 已有先例可对照：`research/docs/实验/族B-意图落地结果.md`
> 人只说一句话（15.6k token）vs 人把要求列全（56.5k token）—— **质量几乎一样**。

## 五、★★★ `forge` 的产出形状（★ 这是核心设计）

★★ 它的 `outbox/` 写的**不是成果条目，是教科书章节的草稿**：

```markdown
# <这一章讲什么>（★ 是一个"主题"，不是一个"发现"）

## 这一个词是什么意思
<★ 定义 —— 说清它在这个领域里到底是什么>

## 为什么会有这个现象
<★ 机制 —— 因果链，不是"可能是因为">

## 所以该怎么做
<做法 —— 可操作>

## 为什么这么做有效
<★ 机制层面的解释 —— 不是"实测效果好">

## 边界
<★★ 什么条件下不成立 —— 这条最容易被跳过，别跳>

## 我们怎么知道的
<证据：谁跑的、哪个数据、你是不是复现过>
```

★★★ **两条硬判据**：

| 判据 | 不合格的后果 |
|---|---|
| **写不出「边界」** | ★★ 说明**还没检验它** —— 不许收进书 |
| **写不出「为什么」** | ★ 说明它**还是成果记录** —— 也不许收 |

## 六、★ 边界与权限（沿用，已实测）

| | |
|---|---|
| **可写** | ★ 只有 `research/labfirst/forge/` |
| **只读** | ★★ **`research/labfirst/hunt/`（被分析对象）** |
| **只读** | 仓库主体 |

★★★ **已实测堵上的洞**：守卫原来只知道自己的 `LAB` ⇒
`write hunt/outbox/xxx.md` 会被**放行**（而那是它正在分析的对象）。
★ 修法：**拦** + **给路**（`P12`）—— 「要推翻它 → 在**你自己空间里重做**」。
★ `outsideWrite` 已是纯函数 ⇒ 4 条回归测试 · **185/185**

★★ **一条 `forge` 特有的纪律**（手册里写明）：
> 你正在**检验别人的实验**。如果你改了量具，就分不清「它的结论错」还是「你改出来的错」。
> ⇒ **先在原样量具上复现，再改量具看差异。**
