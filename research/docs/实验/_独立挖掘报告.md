# 独立数据挖掘报告

只从 `research/demox/runs/*.jsonl` 原始数据出发，未读实验计划与成果清单。
口径：261 条记录全量；标注 `[clean]` 的统计剔除了 `hidden` 备份 / `partial` / `crashed` 文件（207 条）。
脚本在 `_dig/`（可删）。总样本：**11,709 次带参数的调用**（`agents[].callsDetailed`），
其中 read 12,696（含无参记录）/ ls 938 / write 451 / spawn_reviewer 13。

---

## 现象 1：多 agent 之间，28% 的 read 是重复劳动（同一个文件被 ≥2 个 agent 各读一遍）

`[clean]` 86 个多 agent run，8,036 次 read，6,328 个「(run, 文件)」对。

- 被 **多于一个角色** 读过的文件对：983 个 = **15.5%**
- 落在这些共享文件上的 read 调用：2,276 次 = **全部 read 的 28.3%**
- 方向高度单向（首次读者 → 后来的读者）：

| 方向 | 次数 |
|---|---|
| S1-摸底 → S2-去重 | 598 |
| copy1 → copy3 | 324 |
| S1-摸底 → S3-成文 | 309 |
| copy1 → copy2 | 303 |
| S2-去重 → S3-成文 | 146 |

单 run 最极端：`redundant-T-A rep1`（3 agent）有 82 次 read 落在共享文件上，
`corpus/m1..m6.md` 每一个都被 **3 个 agent 各读一遍**。

**为什么有意思**：委派省下的是「注意力」，没省下「读入」。上游读过的原文，
下游全部重新读一遍——而且方向永远是沿流水线向后。这意味着多 agent 的成本节约只发生在
「思考/输出」侧，输入侧完全没有去重机制。**备注：`injections.marker` 里
`narrow`（下游只拿结论）正是针对这一点的干预；下面现象 4 有它的读数。**

**强度**：n=86 run / 8,036 read，有对照（单 agent run 无此结构，比值天然为 0）。

## 现象 2：`idsFabricated > 0` 是 100% 准的失败预测器（8/8），且失败答案明显更短

`[clean]` 162 条有 readings 的记录：

- `idsFabricated > 0`：**8 条，其中 ok=true 的 0 条**
- `idsFabricated == 0`：154 条，其中失败 39 条

即「编造 ID」这个读数**一旦触发就是失败**（精确率 100%，召回 8/47）。触发者的答案长度也突变：

- fab>0 的 `answerChars` 中位数 **105**
- 全体 ok 的 `answerChars` 中位数 **166**；全体 fail 中位 **129**

触发者的共同形态：**输出很短（44–134 字符）但 token 消耗巨大**——
`G3-cascade-B rep1` 用 **1,687,798 token** 换来 134 字符答案，`G3-cascade-A rep1` 用 398,763 token 换 129 字符。

**机制猜测（这是猜测）**：ID 是模型无法现场编的「事实锚」。当上游传递链断掉、
下游拿不到真实文件名却在硬答时，它会生成看似合理但目录里不存在的 ID。
所以 `idsFabricated` 可能不只是评分项，而是**「交接信息丢失」的直接探针**。
`distractorsFound`（本应统计误报干扰项）在 **162 条里全部为 0**——这个判据目前是死的，
`idsFabricated` 反而在实际承担误报检测。

**强度**：n=162，有对照组（154 条 nofab），但 fab 组只有 8 例，是「全对」而非「高相关」。

## 现象 3：同一实验内时间呈**双峰**，慢的那个 rep 同时就是 token 最胖的那个（2/2）

`G0-3-flat`（同一 params `corpusPairs=4`，12 次）：

```
rep  secs   tok      calls  ok   groupsFound
1     61    10,786    21   t    4
2     85    20,224    20   t    4
3     71     9,848    14   t    4
4     59     7,833    14   f    0
5     79    13,085    12   t    4
6     45     4,956     4   f    0
1    121    30,100    22   t    4
2   552   393,041    43   t    4   <-- 13.1x 最长
3     42     9,689    12   t    4
4     77    16,916    14   t    4
5     74    16,070    13   t    4
6     76    17,269    14   t    4
```

- 时间跨度 `42s .. 552s` = **13.1x**；token 跨度 `4,956 .. 393,041` = **79x**
- `G0-3-variance-p8`（8 次）：`71s .. 568s` = **8.0x**，`13,905 .. 135,925 token`
- **「最慢的 rep」与「token 最胖的 rep」在两个组里都完全相同（2/2）**
- 慢的 rep 并不是做得更多：`393,041 token` 的 rep2 与 `9,848 token` 的 rep3
  **都产出 4 个组**，同样的正确答案，成本差 40 倍

**为什么有意思**：这不是「成本越高越努力」的连续曲线，而是一个**离散的坏模式**——
某一 rep 忽然把 40 倍 token 烧在一模一样的产出上。它们既没失败也没有额外收获，
所以现有判据（ok/失败）对它完全不敏感。

**强度**：n=12 与 n=8（同一 params 内），有同组对照。两组合计只有 2 个「胖 rep」样本，
所以「慢 rep == 胖 rep」是 2/2 的小样本一致性，不是统计显著。

## 现象 4：交接「变窄」比「保留全文」**更省一半 token 而且不掉分**

`F-variety`（18 run，`injections.marker` 三分组，每组 6）：

| marker | 含义 | n | ok | 平均 token | S1 calls | S3 calls | 下游 token 占比 |
|---|---|---|---|---|---|---|---|
| `narrow` | 下游只拿结论 | 6 | 100% | **81,788** | 19.2 | 14.5 | 77% |
| `attenuate` | 只要结构化摘要 | 6 | 83% | **40,907** | 20.3 | **4.0** | 45% |
| `amplify` | 下游拿全文并自己抽查 | 6 | 100% | 90,758 | 20.7 | **22.7** | 76% |

**为什么有意思**：`attenuate` 是三者里**最省（40,907，约为 amplify 的 45%）** 但也是
唯一掉分的（5/6）。它是靠让 S3-成文 几乎不动手（calls 4.0 vs 22.7）省下来的——
省的是下游的**验证动作**，不是读入量。所以「省 token」和「下游还会去查」是一对互斥项，
不是两个独立的旋钮。**“读入重复”（现象 1）与“验证动作”在数据里是两笔不同的账。**

**强度**：n=6/组，有三分组对照；attenuate 的那 1 次失败使 83% 与 100% 的差距不显著。

## 现象 5：`spawn_reviewer` 这个委派工具，13 次调用**参数全是空字符串**——委派内容是零信息

`[clean]` 全部 11,709 次调用里，空参数只出现在一个工具上：

- `spawn_reviewer`：13 次调用，**13 次 arg 均为 `""`**（其它 4 个工具 0 次空参）
- 出现在 `TE-big-smoke` / `TE-big` / `TE-diag` / `TE-threshold-big`

但被 spawn 出来的分身并非闲置——它们自己去找活干：

| run | spawn 次数 | reviewer 分身 | 各自 calls |
|---|---|---|---|
| TE-big rep2 | 2 | 2 | 37 / 18 |
| TE-diag rep2 | 3 | 3 | 12 / 12 / 13 |
| TE-threshold-big rep1 | 3 | 3 | 12 / 12 / 13 |

**为什么有意思**：这是唯一的显式「结构化委派」通道（`shape.edges`/`delegations` 只在这几个
run 里非零），而**入参携带的信息量为 0**。分身的任务完全由它们自己重新推导——
于是每个 reviewer 都独立做了 12–37 次调用，去重建 coordinator 早就知道的东西。
这解释了为什么 `TE` 系列 coordinatior 的 token 占比高达 69–87%（见下）却仍然没把信息传下去。
**这是猜测**：也许 spawn 时任务是通过 system prompt / 环境而非参数注入的，
那需要看 `TE-*.ts` 才能排除。

**强度**：n=13 次调用、5 个 run；同类工具对照（read/write/ls 零空参）成立。

---

### 附带：token 极度不均衡，且**不是**「越深越贵」

- 多 agent run（n=74）：**最深 agent 的 token 占比中位数仅 23%**（区间 1%–100%）
  ——成本并没有沿深度堆积。
- 但 `G3` 家族（n=36，3 agent 流水线）：**S1-摸底 一个 agent 吃掉中位 63% 的 token**
  （区间 18%–96%），调用数占比中位 **65%**。S1/S2/S3 平均 72.6 / 25.1 / 18.3 次调用。
- `TE` 家族反过来：hog 是 **coordinator**（5/5 全是它），占比 69–87%。

**为什么有意思**：这说明「谁是成本中心」由**分工形态**决定，而非深度：
3 段流水线的成本压在**第一段**，而星型（coordinator + reviewer）的成本压在**中间节点**。
两种形态的优化位置完全相反。

## 汇总：强度一览

| # | 现象 | n | 对照 | 强度 |
|---|---|---|---|---|
| 1 | 跨 agent 重复 read = 28.3% | 8,036 read / 86 run | 单 agent run | **强**（样本大、方向一致） |
| 2 | idsFabricated>0 ⇒ 失败 8/8 | 162 run | 154 条 nofab | 中（全对但仅 8 例） |
| 3 | 慢 rep == 胖 rep，同产出差 40 倍 | 12+8 run | 同 params 内 | 中（2/2 一致性，样本小） |
| 4 | narrow 省 55% token 不掉分 | 18 run | 三分组 | 中（每组仅 6） |
| 5 | spawn_reviewer 参数恒为空 | 13 次 / 5 run | 其它工具零空参 | 强（无一例外） |
| 附 | 成本中心位置随形态翻转 | 74 / 36 run | 两种形态互比 | 中 |

**未验证的机制**：现象 2、5 的因果解释都是猜测；现象 3 的成因（是上游慢还是模型重试）
光靠 jsonl 分不出来，需要 `work/` 里的中间产物或 `secs` 的更细切分。
