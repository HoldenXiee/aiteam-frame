> 这一轮发现了一个**让集群静默停摆 5 小时**的判据缺陷。

```

```

## 1. 日志里的病

```
rule:onSettled outbox=63 auditedOutputs=63      ← ★ 数量和已审相同 ⇒ 无事可做
rule:onPlateau outbox=63 新文件=373 产出=false 在干活=true roundsSinceProgress=0/3 约0分钟
rule:onPlateau outbox=63 新文件=211 产出=false 在干活=true roundsSinceProgress=0/3 约0分钟
```

★★★ **`work/` 里新出 373 / 211 个文件，而 `outbox` 一份没出**，
判据却说"在干活 ⇒ 健康" ⇒ **平台期计数永远被清零**。

★ 整轮统计：只有 **1 次**算到 `roundsSinceProgress >= 1`，**从未到 3**。

---

## 2. ★★ 前三次判据都没对（记下来，别走第四遍）

| 版本 | 判据 | 病 |
|---|---|---|
| v1 | 「有没有动作」| 跑同一条线的第 20 轮 = "健康的动" |
| v2 | 「只看产出」| 跑实验时被判卡住（★ 研究员自己抓到的）|
| v3 | 「产出 **or** 在干活」| ★★★ **在 `work/` 里无限写实验也算健康**（这一版要治的）|
| **v4** | 「`busy` **只延缓，不清零**」| — |

★ v2 的教训让 v3 矫枉过正：为了保护"跑实验不算卡住"，把"在忙"提升成了"有进展"。
★★ 但**写实验可以无限持续，产出可以为零** —— 保护变成纵容。

---

## 3. v4 判据

```ts
if (produced) {
  roundsSinceProgress = 0;      // 真进展
  busyStreak = 0;
} else if (busy) {
  busyStreak++;
  if (busyStreak % 2 === 0) roundsSinceProgress++;   // ★ 延缓一倍，不是清零
} else {
  busyStreak = 0;
  roundsSinceProgress++;        // 空转正常递增
}
```

★ 效果：
- **长期只写实验不出东西** ⇒ 会被判成平台期（正是病的样子）
- **跑完实验马上交产出** ⇒ 仍然不算卡住（v2 的病没回来）

## 4. ★★★ 判据是活的（纪律㉙：证明它在该失败时会失败）

我拿 v3 的判据跑了同一段数据：

```
v3 判据：8 轮「在忙但没产出」后 roundsSinceProgress=0（永远触发不了）
```

★ 而 v4 的测试断言 **8 轮后必须 ≥3**。
⇒ **这个测试在 v3 下会红，在 v4 下会绿** —— 不是"写了就过"的测试。
