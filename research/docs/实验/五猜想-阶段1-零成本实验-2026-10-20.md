## 2. 五条规则（默认全关）

| 开关 | 规则 | 判据 | fire |
|---|---|---|---|
| `table` | `onTable` | 未并入表的产物 ≥ **2** 份 | `archivist` |
| `silent` | `onSilentSeat` | `landing/*` 席位 0 产出 且 outbox ≥5 | 该席位自己 |
| `falsify` | `onFalsify` | 正文命中 `REVERSAL_RE` | `archivist` |
| `index` | `onChapterIndex` | 引用了登记表里没有的章号 | `archivist` |
| `untested` | `onUntested` | 正文命中 `UNTESTED_RE` | `archivist` |

**开法**：`CLUSTER_RULES=table,silent,falsify,index,untested` 或 `all`
**默认**：全关 ⇒ `tick()` 里五个 `?.()` 全是 `undefined` ⇒ **行为与拆分后完全一致**

### 2.1 为什么要有开关（★ 不是可选项）

纪律⑱ 单变量：一次只能开一条，否则「哪条起了作用」说不清。
★★ 而且不开开关就没法做**对照**（改前读数 = 全关那一轮）。

### 2.2 顺序：五条全部排在 `tick()` 尾部

```
onAudience → onConsensus → onDispute → onNewFinding → onCapabilityGap → onPlateau
  → onTable → onSilentSeat → onFalsify → onChapterIndex → onUntested
  → onSettled（★ 永远最后）
```

★★★ 理由（2026-10-19 的教训，这次提前避开了）：
`onTable` / `onFalsify` / `onChapterIndex` / `onUntested` **都会 `await fire("archivist")`**，
而 archivist 要跑几分钟 ⇒ 若排在前面，`onAudience`/`onConsensus` 会被**饿死**。

## 3. ★★★ 探针抓到的三个真实缺陷（这是本轮最重要的产出）

### 缺陷 ① `REVERSAL_RE` 判据写窄 ——「被 P26 取代」永远不命中

```ts
// 原来
/推翻|被取代|降级|.../
```
★ 真实文本是「**被 `P26` 取代**」（中间夹着证据编号）
⇒ `被取代` 要求两字紧挨 ⇒ **永不命中**。

**修法**：`被[^\n]{0,20}取代`（允许夹 20 字）

★★ 这与 `onDispute` 判据写窄（只认 `verdict === "反对"`）是**同一个病**：
「我想的是那个词，数据里是另一种写法」。

---

### 缺陷 ② `readChapterIndexRows` 表头格式一换就整表失效

```ts
// 原来：要求第一格就是章号
line.match(/^\s*\|\s*(?:第)?(...)\s*章?\s*\|/)
```
★ 只要表里多一列序号（`| 1 | 第4章 | … |`）或第一格是「章号」表头
⇒ **整张表解析不出来** ⇒ 返回空集 ⇒ **全部误报悬空**。

**修法**：扫描整行所有格子，任一格形如「第N章」即认。

---

### 缺陷 ③ ★★★ `readFileSync` **没有导入** —— 被 try/catch 静默吞掉

```ts
import { existsSync, readdirSync, statSync } from "node:fs";   // ★ 没有 readFileSync

export function readArtifactSafe(name, outboxDir = ...): string {
  try { return readFileSync(join(outboxDir, name), "utf8"); }
  catch { return ""; }        // ★★★ ReferenceError 被这里吞掉
}
```

★★★ 后果：**凡是要读产物正文的判据（C/D/E）全部恒 false**，且日志里**一声不响**。
★★ 而且 `npx tsc --noEmit` **不报错**（`readFileSync` 在别的作用域被降级引入）。

**修法**：补上导入。

★★★ **这是「机制写了 ≠ 接上了」的又一例**（AGENTS §二 的第 8 次）：
- 规则写了 ✔
- 规则被调用 ✔（探针能看到 calls=4）
- ★ **判据永远不命中** ✘
- ★★ **失败不响** ✘✘

**教训（值得单独记）**：
> `try { ... } catch { return "" }` 里包住的代码，**拼写/导入错误也会被当成"读不到"**。
> ⇒ 凡 `catch { return "" }`，必须先问：**这里会不会藏着一个真错误？**

## 6. 判据与指令必须同源（P11）—— 探针的一个已知局限

★★ 探针**直接用生产代码的判据函数**（`extractChapterNumbers` / `readChapterIndexRows` /
`REVERSAL_RE` / `UNTESTED_RE` / `countTableRows`），所以**判据 100% 同源**。

★ 但**规则函数体**（含 fire 文案）是各写一遍的 —— 探针只复刻了**判据分支**，没复刻文案。
★★ 影响：探针能证明「判据对不对」，**不能**证明「生产里那段的 if 顺序对」。

★ 缓解：五条规则里三条（C/D/E）用了 `return`（一次只推一份），
★ 这个行为在探针里**没有覆盖**。⇒ **阶段 2 真跑时必须核对 `_topology.log` 的 trace 次数**。
