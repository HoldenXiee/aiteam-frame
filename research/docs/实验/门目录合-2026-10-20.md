## 1. ① 目录：`syncSummary` 从「自动追加」改成「只报数」✔

### 1.1 第一版做的事是错的

第一版：书里有但目录没列的 ⇒ **自动追加到 `SUMMARY.md`**，没有那一节就**新建一节**。

**实测后果**：
```
原有那一节（手写、有分组）      11 条
## 05-集群产出（我自动新建的）   19 条  ← 平铺
⇒ 同一批内容出现在两个地方，目录分裂
```

★★★ **这正好撞在 AGENTS §三 说的 forge 的病上**：
「forge 失败时看起来像 —— **还在散记，只是写得更长**」。
我把散记从 10 份装成 29 份，**让病更重**。

### 1.2 为什么"自动补目录"本身是错的

**目录的结构就是书的组织方式**（先读什么、哪些是一组、哪些是附录）——
那是**内容判断**。

★ 按硬规则①：内容决定归集群。我能立的只是**要求**（"每一份都要能被读者找到"），
**不能替它决定放哪一节、和谁一组**。

### 1.3 改成

```ts
// 只算，一个字都不写
return { added, alreadyListed, total, danglingEntries };
```

★ 新增 `danglingEntries`：目录里指向**不存在的文件**（读者点了 404）——
这是第一版漏掉的一半。

**改后读数**：书 29 份 · 目录列出 29 · 读者点不到 **0** · 悬空条目 **0**。

### 1.4 过程中我自己的错

| 错 | 症状 | 怎么发现的 |
|---|---|---|
| `new RegExp` 拼模板串，反斜杠被吃 | 报「目录列出 **0** 份」| 打印才发现 |
| 改成逐行解析后，用 shell 处理 `\n` 把文件搞乱 | 语法错 | tsc |

★ 都属同一类：**不报错，只是算错**。已改成逐字符解析（`linkPathOf`），谁都吃不掉。

## 2. ② 解除条件的闭环 ✔

### 2.1 病（AGENTS §〇之三 原话）

> 「条件写在那儿，但**没人去执行**。」

**实测**：进书 29 份里 **25 份带解除条件，共 43 条**。
每条都写得**很可执行**：

```
[landing] §6.3 ② 的「改 schema 重跑 = K 轮 ≈ 0.7 份副本/轮」改成带任务族的区间…
[theory]  在 §2.2「数是停止条件」后补一句可判死的话：「它停在候选枚举上，不在报告凑数上…」
[practice] 在 §0.1 表下加 3 行，0 API：①「本章的『可自查』在后两章被拆细了…」
```

★★ 但**没有任何东西在事后检查它们有没有兑现**。
⇒ 「有保留」退化成**永久的免责声明**：门以为在把关，其实把责任推给了未来。

### 2.2 修法：算 + 递，不判

新增 `unresolvedDislodges(table, published)`：

| 做什么 | 为什么 |
|---|---|
| 只收**进书的**产物 | 门都没过，谈不上解除 |
| 只收 `verdict === "有保留"` 且条件 ≥10 字 | 太短的已在门上当"没表态" |
| ★ **不判断**某条是否已满足 | 那要读内容、要理解 ⇒ **是集群的活**（硬规则①）|

★ 接到**开工提示**里（AGENTS §〇之三 的要求：「每轮开工前把未兑现的列出来，送进集群」）：

```
## 📌 上一轮留下的待办（★ 有保留的解除条件，共 25 份 / 43 条）

★★ 这些是**你的同事上次说「可以发，但要做到这件事」**时留下的。
**到现在没人检查过它们有没有做到** —— 所以它们还挂着。

· outbox/理论-产物的三重身份… ← [landing] §6.3 ② 的「改 schema 重跑…」
· outbox/理论-第九章…          ← [theory]  在 §2.2「数是停止条件」后补一句…
…

★ 你怎么处理由你定：
· 已经做到的 → 在产物里写明「已按 X 解除」，让下一轮能核对
· 没做到的   → **做掉它**，这比再写一份新的更有价值
· 已经不该做的 → 说清为什么作废（不要默默留着）
★★★ 不许做的：装作看不见。挂在书里的未兑现条件，读者会当成"作者知道但没修"。
```

★★ 注意措辞：**"你怎么处理由你定"** —— 我递清单，它排优先级。

## 3. ③ 产物要有「合」的动作 ✘ **卡住，而且我差点做错**

### 3.1 我本来想做

29 份只有「写新的」，没有「把三份合成一份」⇒ 加一个合并机制。

### 3.2 ★★★ 但查代码时发现：前人试过了，被实测推翻

`tools/challenge.ts` 头注释原文：

```
★★ 为什么"辩证记录"是独立产物而不是合并产物：
   P46/P47 实测过「并集会被霰弹成员毒化」——
   把三份堆起来会更差；而记录辩论本身才是多员工的真产出。
```

⇒ **"把三份合并"这个方向本身被实验否过。**

★★★ 如果我按原计划加合并机制，就是**重复一个已知失败的实验**，
而且还不知道失败过。

### 3.3 所以这条要重新问

不是"加个合并工具"，而是：

| 问题 | 现状 |
|---|---|
| 29 份散记，`P46/P47` 说不能堆 | ✔ 已知 |
| 那**"收束"该长什么样**？ | ✘ **不知道** |

★ 可能的方向（**都还没验证**）：
- 不是"合并内容"，而是"合并**指称**"（一份索引页，告诉读者 A/B/C 三份该一起读）
- 或者"淘汰"（把被后续产物取代的标为废弃）—— 那反而是**减少**
- 或者接受它就是 29 份，改的是**入场顺序**（一本选集，不是一本教科书）

★★ 这是**集群设计决定**，而且前人已经证明简单合并不行。我不该自己拍。
