## 1. 实验 1 · 探针改成真正的单臂实验

### 1.1 改什么

`topology-probe.ts` v1 → v2：

| 项 | v1 | v2 |
|---|---|---|
| 跑法 | 无参数，一次跑五个 | ★ `--arm=X`，一次一个 |
| 沙箱 | 共用 `_sandbox/` | ★ `_sandbox/<arm>/`，每臂独立 `reset` |
| 对照 | 无 | ★ `--control` 跑"开关关/判据更窄"那一侧 |
| 读数 | `"✔ 接上了"`（形容词）| ★ `wrong`（判错条数），0 才算站得住 |
| 正负例 | 混杂 | ★ 每条标 `expectHit`，**负例比正例重要** |

### 1.2 读数：处理臂 vs 对照臂（★ 这才是有对照的实验）

| 臂 | 处理（wrong）| 对照（wrong）| 对照错在哪 |
|---|---|---|---|
| `table` | **0** / 4 条 | 1 / 4 | 阈值降到 1 ⇒ 「1 份未并入」也触发 |
| `silent` | **0** / 3 条 | 1 / 3 | 去掉 outbox≥5 门槛 ⇒ 太早就催 |
| `falsify` | **0** / 6 条 | 2 / 6 | 旧窄判据 ⇒ 「被 P26 取代」漏掉 |
| `index` | **0** / 3 条 | 2 / 3 | 假表 ⇒ 已登记的也报 |
| `untested` | **0** / 4 条 | 1 / 4 | 只认最窄写法 ⇒ 「不含新读数」漏掉 |

★★ **对照臂全部判错、处理臂全部判对** ⇒ 判据的写法是**有依据的**，不是随手写的。

### 1.3 边界（★ 这个实验**没有**证明的）

- ✘ **不能**证明生产 `tick()` 会调用这些规则 —— 那要真跑集群看 `_topology.log`
- ✘ **不能**证明产物质量（表填得满不满、故事写得实不实）
- ✔ 只证明：**判据在给定输入集上判得对**

## 2. 实验 2 · onConsensus 卡死 bug（★ 单变量，有对照）

### 2.1 病

```ts
// rules.ts onConsensus（改前）
const target = outs.find((f) => {
  const signs = ctx.signoffState!(f);
  return teams.some((t) => !signs?.has(t));
});
if (!target || state.signedAsked.includes(target)) return;   // ★ 卡死点
```

★ `find` 每次都返回**同一份**（第一份没签全的）；
★ 它一旦进了 `signedAsked`，`return` 就把它**永久挡住** ⇒ 后面的**永远轮不到**。

### 2.2 为什么这个实验能零成本确定性判定

★★ `onConsensus` 的**选取逻辑是纯函数**：

```
输入：outbox 文件名列表 + 签字表
输出：这一 tick 请谁签字
```

不需要模型、不需要事件序列。**真实数据就是输入。**
⇒ 拿上一轮真实的 24 份产物 + 真实签字表直接跑，得到确定数。

### 2.3 改前 / 改后读数（`micro/experiment-consensus.ts`，0 API）

```
═══ onConsensus 卡死 bug · 离线确定性实验（0 API）═══

输入：真实 outbox 24 份产物 · 真实签字表 15 份有记录

── 改前（旧逻辑） ──
   被请签字的产物：1 / 24 份
   ★ 其中 landing（读者）的：0 / 9 份
   顺序（前 5）：实验-换载体-可执行判据的可行性标定

── 改后（新逻辑） ──
   被请签字的产物：12 / 24 份
   ★ 其中 landing（读者）的：9 / 9 份

═══ 判定 ═══
被请签字：1 → 12 份（+11）
★ landing：0 → 9 份（共 9 份）
✔ 认定成立：漏请是因为 find/return，不是"没东西可签"
```

### 2.4 这个数为什么重要

★★★ **悬空的 4 个章号，正是 reader 写好的四章**：

```
reader 写的章：第六章、第七章、第八章、第十一章
书里存在的章：第五章、第九章、第十章
悬空的章号：  1,2,3,4,6,7,8,11
```

⇒ 读者侧的骨架（判/选/算/验、边界与价钱、没有真值时怎么判、改完怎么知道改对了）
**全部写完了，全部卡在门外**。

★ 而且 `theory-mapper` 5/5 全进书、`landing-reader` 0/7 全没进 ——
**这不是质量问题，是排队顺序问题**：谁先出现在 outbox，谁就进书。

### 2.5 改的是什么（★ 单变量，只动 2 行）

```ts
// 改后：把「已请过」放进 find 的条件里（继续往后找），而不是找到之后才判
const target = outs.find((f) => {
  const signs = ctx.signoffState!(f);
  return teams.some((t) => !signs?.has(t)) && !state.signedAsked.includes(f);
});
if (!target) return;
```

### 2.6 判死条件（跑前写死）

| 判据 | 阈值 | 实测 |
|---|---|---|
| 被请签字的产物数 | 应显著上升 | 1 → **12** ✔ |
| ★ landing 被请数 | ≥5 | **9 / 9** ✔ |
| 是否无限循环 | 全都签过后应停 | ✔ 停（有单测守） |
