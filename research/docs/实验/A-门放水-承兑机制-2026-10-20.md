## 1. 病（实测，第二次治同一个病）

### 1.1 第一次治的是什么

`2026-10-19` 已经修过一次：「有保留但**没给解除条件** = 没表态」。

```ts
if (!rec.dislodge || rec.dislodge.trim().length < 10) missing.push(...)
```

### 1.2 为什么没治好

★★ **团队学乖了** —— 每张保留都写一条条件，照样过。

**实测现状**（进书 29 份，签字 87 张）：
```
认同 44（51%）· 有保留 43（49%）· 反对 0
份数：全认同 4 · 含保留 25  ⇒  带保留率 86%
```

### 1.3 ★★★ 根因：两种表态的**代价不对等**

| 表态 | 代价 |
|---|---|
| **反对** | 要拿反例，**且卡住发布**（要说服别人）|
| **有保留** | 写一条条件，**照样进书** |

⇒ 结构上「有保留」是**通往发布的坦途**，「反对」是**堵路**。
⇒ 理性做法**永远是"有保留"**。

★ 这不是团队偷懒，是**设计缺陷**。

---

## 2. 我先试错的两个方案（都算过影响，都没采用）

### 2.1 「取消有条件地过」—— 太狠

干跑：29 份里只有 **4 份**全认同 ⇒ **挡掉 86%**，等于把书清空。

### 2.2 「保留份额上限」—— 是我拍的数

| 上限 | 挡掉 |
|---|---|
| 1 张 | 48% |
| 2 张 | 14% |

★ 现状分布 `{0张:4, 1张:11, 2张:10, 3张:4}` —— **没有天然分界**。
★★ 任何阈值都是**我拍的数**，不是设计出来的。

---

## 3. 最终采用：把「有保留」从**结论**降级成**提议**

### 3.1 机制

```
A 说「有保留 + 解除条件 X」   ⇒ 只是提议
需要 B 或 C 说「认可保留」     ⇒ 才生效
没人认可                       ⇒ A 算没表态 ⇒ 产物进不了书
```

### 3.2 为什么这个比阈值好

| | 阈值 | 承兑 |
|---|---|---|
| 依赖 | ★ 我拍的数 | ✔ 不依赖任何数 |
| 代价 | 人为设卡 | ★★ **自然代价**：要说服一个同事 |
| 与现有机制 | 新增 | ✔ 同构（`sign_off` 本来就是表态工具）|

### 3.3 实现

```ts
export type Verdict = "认同" | "有保留" | "认可保留" | "反对";

// 承兑人：除自己以外，有谁说了「认可保留」
const who = endorsers(t);
if (!who.length) {
  missing.push(`${t}（有保留，但**没有同事「认可保留」** ⇒ 这条保留不算表态）`);
  continue;
}
accepted.push(`${t}（由 ${who.join("、")} 承兑）：${rec.reason} —— ★解除条件：${rec.dislodge}`);
```

## 4. ★★★ 最关键的读数：机制真的被用了

**那张「认可保留」的原文**（practice 给 landing 背书）：

> 「我核过 landing 这条保留里的每个数，逐格成立，所以我给它背书
> （这是「认可保留」，不是我自己另有保留）：
> **(1)** 每落地价的 Wilson 区间 77–175k —— 用我自己的 32 行复算：S1Q1 合计 565,958 token、6/8 落地…
> **(3)** §0 把「判据」列拆成「可算量 / 0-API 程序」两列 —— 这是这张表最容易骗人的地方，我独立同意…
>
> ★ **我为什么给背书而不是自己也提一条**：这三条都是可执行、0 API、改完就能核的，
> 而按照这个门的实测（**87 张签字 43 张有保留、0 张反对**），
> **有保留不背书就等于把一份我核过是对的东西挡在书外**。」

★★★ **它读懂了新机制的设计意图** —— 而且引用了**我在测试里写的那组数**。

## 5. ★★★ 三次真跑才接通（第 6、7 次「写了没接上」）

| 轮 | 结果 | 原因 |
|---|---|---|
| 1 | 崩了（exit=1）| ★ `pendingTodo` 那段有坏字符串（`tsc` 过了但 **esbuild 不过**）|
| 2 | 带保留 **0 份** | ★★ 门生效了，但**「认可保留」一次都没用**（20 张签字里 0 张）|
| 3 | 带保留 **1 份** | ✔ 补了工具描述后接通 |

### 5.1 第 2 轮为什么"没接上"

★★★ 我加了新的 `verdict` 选项，但**工具描述里还写着「三选一」**：

```
★ 三选一：认同 / 有保留 / 反对
```

⇒ 它读到的描述里**根本没有第四个选项**。
⇒ 这和 `TOOLS_NOTE`「你有两个工具」是**同一个病**（第 5 次）：**定义里的错误陈述主动排除了正确选项**。

★ 而且提示词里**没有一处**告诉它"去认可同事的保留"。

### 5.2 修法

工具描述改成四选一 + 说清为什么，并明确邀请：

```
★★ 为什么要「认可保留」：实测 87 张签字里 43 张有保留、0 张反对（86%）。
   根因是代价不对等：反对要拿反例且卡住发布，有保留写条条件就照样进书。
★ 看到同事提了一条站得住的保留时，用「认可保留」给他背书。
```

### 5.3 ★★ 一条新的工程教训

★★★ **`tsc --noEmit` 通过 ≠ 跑得起来。**

第 1 轮 `tsc exit=0`，但 `tsx`（esbuild）报 `Unterminated string literal`。
⇒ 两个解析器对字符串字面量的容忍度不同。

**⇒ 以后改完必须跑一次 `--dry`**（它走 esbuild），不能只信 tsc。

## 6. 测试（新增 6 条）

| 守什么 |
|---|
| ★★★ 保留**没人承兑** ⇒ 不算表态 ⇒ 不许进 |
| ★★★ 有同事承兑 ⇒ 生效 ⇒ 可以进（带保留）|
| ★★ 自己认可自己 ⇒ 不算承兑（否则等于没升级门槛）|
| ★★ 「认可保留」本身不是对产物的结论 |
| ★★ 承兑谁都能给（不需要特定某人）|
| ★ 反对仍然直接挡（不受承兑影响）|

★ 同时更新了 2 条**旧测试**（它们测的是旧行为：有保留+条件就过）。
★★ 这是刻意的 —— 行为**故意变了**，旧断言必须跟着变，否则测试在骗人。

## 7. 边界（★ 没证明的）

| # | 没证明 |
