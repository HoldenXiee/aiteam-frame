## 3. ★★★ 三个发现

### ① B8 修正：「把做完了当做对了」**在有真判据时不存在**

**它跑了 14–26 次测试**，**每一次都验证到真绿了才收工**。

> ★★ **对照**：此前结论说「它对'找不到'诚实，只对'我做完了'不验证」（B8）。
> **现在看清楚了**：**不是它不愿意验证，是此前的任务**没什么可验证的**** ——
> 写个 JSON 说"我分好组了"，没有东西能跑。
>
> ★★★ **给了真判据，它自己就会反复验证。** 这条直接改写了 B8。

### ② `guided`（告诉它失败清单）**没有省任何事**

```
solo   跑测试 16 / 14 次
guided 跑测试 26 / 16 次     ← ★ 反而更多
```

★ **人的提示没有减少它的工作量** —— 与族 B 的「`spec` 花 3.6 倍只买到 3/3 vs 2/3」同型。

### ③ ★★ **成本结构：定位 90%，修改 10%**

```
edit 只用了 1–2 次；bash + read 占了 90% 以上
```

> ★★★ **「修 bug」这类活的成本几乎全在**定位**（读代码、跑测试、缩小范围）。
> **而"判断类"任务**根本没有定位阶段** —— 它一步就是结论。**
>
> ★ **所以我们此前的所有结论，都缺了"定位"这一整块劳动。**

---

## 4. 【做法】

| # | 做法 |
|---|---|
| 1 | ★★ **要它自己验证，就得给它能跑的东西** —— 真判据在场时它不需要被提醒（B8 修正） |
| 2 | ★★ **改造型活的成本在定位，不在修改** —— 优化要往"更快缩小范围"上使 |
| 3 | ★ **告诉它失败清单≈没告诉** —— 它自己跑一次就知道，而且人给的清单反而让它多跑 |
| 4 | ★ **注入 bug 必须实测验证"注入后测试真红"** —— 否则测的是空气（我第一轮就撞到过：类型错、片段不唯一） |

## 5.5 ★★ 三个 bug 逐个对照（装置修好后重跑）

**装置坑（已修）**：沙箱里的 `node_modules` 是 Windows junction，`rmSync` 会穿透去删**真仓库的** → `EPERM`；
另外整包复制 `dev/` 会把**克隆的 pi 源码**带进来，typecheck 报一堆无关错。

**修好后**：

| bug | 结果 | 轮数 | bash | token |
|---|---|---|---|---|
| `tools-noreload` | ✓✓（另一文件也 ✓✓） | 20–34 | 17–25 | 519k–993k |
| ★ **`ctx-refresh`** | ★ **✓✗（最难）** | 13–27 | ★ **15–41** | 202k–837k |
| `obs-syscount` | ✓✓ | 19–31 | 14–27 | 310k–662k |

> ★★ **`ctx-refresh` 最难**（1/2），失败那轮 **bash 41 次**（全场最多）——
> **它反复跑测试、缩小范围，但没找到那处 `refreshContext`。**
>
> ★★★ **成本量级对照**：**修一个 bug 要 20–40 万 token**，
> **而族 B 整个"意图落地"任务只要 15.6k** —— ★ **差 20 倍。**
>
> **⇒ 「改造型」和「判断型」是**两种完全不同量级的劳动**，混在一个实验体系里比较会得出荒谬结论。**
