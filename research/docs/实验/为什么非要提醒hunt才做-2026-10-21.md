# ★★★★★ 为什么非要你提醒，hunt 才去做（2026-10-21）

> 设计者原话（这一篇的全部依据）：
> 「按照道理来说，hunt 集群**应该可以自己发现**没用 skill，或重审目标，获取灵感时，
> **应该能发现比 skill 更适合 agent 集群的东西**。
> 因为 hunt 集群**本身就是探索**，而且还有**修改底层库的权限**，
> 但是**为什么运行这么多次 hunt 后，非要到我提醒，才做这件事**」

---

## 0. 结论先说

★★★ **不是它懒，不是它笨，也不是它没有权限 —— 是结构上从来没有一个时刻问过它。**

它每次都在**用**手段（跑实验、写脚本、改库），
但**从来没有一个时刻**被要求**退一步看这些手段本身**。

---

## 1. 根因：它的 4 条规则，一条都不问"手段"

| 规则 | 治什么 | 会不会问"你用的东西还好吗" |
|---|---|---|
| `onSettled` | 有新产物 ⇒ 审查 | ✘ 只看**产物**，不看**做法** |
| `onCapabilityGap` | 报了缺口 ⇒ 起改库者 | ✘ 只在**缺口已经写出来之后**才动 |
| `onPlateau` | 平台期 ⇒ 换路 | ✘ 问的是**研究内容**该不该换 |
| `onNewFinding` | 有新产物 ⇒ 要同事挑战 | ✘ 挑战的是**结论**，不是**手段** |

★★★★★ **四条规则全都在看「研究内容」，没有一条看「研究方法」。**

## 3. 修法：第 5 条规则 `onInstrumentReview`

### 3.1 判据（可判死，不靠感觉）

```
① 距上次审视 ≥ REVIEW_EVERY_MS（默认 90 分钟，一轮最多问一次）
② 而且这段时间**确实在干活**（有过新产物或新文件）
   —— ★ 没干活时该问的是"该不该退休"，那是 onPlateau 的事
③ 冷却（与 inspirer 共用，避免同时起两个长跑专家）
```

### 3.2 ★★★ 派活时问的问题（这是整条规则的灵魂）

不是"你想不想用 skill"——那还是我在替它想。

★★★ 我问的是：

> **你（和你的同事）反复在用的那件东西，还好用吗？有没有更好的？**

**具体怎么问（照着做）：**
```
① 挑一件你**这轮至少用过 3 次**的东西
② 说出它**为什么是这样**（当初为了治什么病）
③ 问：那个病**现在还在吗**？不在了 / 变了 ⇒ 它可能该换
④ 再问：**有没有一件东西，你一直在手工做，而它本该是结构？**
   （判据：这件事写成一条规则/工具/门，是不是就不用靠"记得"了）
```

### 3.3 ★★★ 直接点了它自己的盲区，但换成可回答的形式

```
★ 特别注意一个盲区（项目里早就写下过，但从没被当成规则）：
   「它判不了自己的盲区」（C7）
   ⇒ 所以别问"我有什么没想到"（答不出来），
     要问"**我反复做的哪件事，其实可以交给结构**"。
```

★ 「我有什么没想到」是**不可回答**的问题。
★★ 「我反复做的哪件事可以交给结构」是**可回答**的 —— 因为它有具体对象和次数。

### 3.4 产出要求（不给它开空头支票）

★ 必须带：
- 挑的是哪件东西、**用过几次**（给数）
- 它当初治什么病、**那个病现在还成不成立**（给证据）
- 更好的做法是什么、**为什么更好（可判死的判据）**

★ 不许写：
- 泛泛的「应该多反思」
- 直接改框架（规则表/门/席位）—— 只能**提议**

## 4. ★★★ 我自己的错：又一次「写了没接上」

### 4.1 第一次真跑：`rule:onInstrumentReview` **一次都没出现**

```
rule:tick          1
rule:onNewFinding  1
rule:onCapabilityGap 1
（没有 onInstrumentReview）
```

★★ 我加上了规则、加上了调用点、tsc 也过了 —— **但它没跑**。

### 4.2 根因：**顺序**

```ts
await rules.onNewFinding();
await rules.onCapabilityGap();      // ★ 这里 await fire("libsmith")（几分钟）
await rules.onInstrumentReview();   // ★ 被饿死
await rules.onPlateau();            // ★ 也被饿死
```

★★★★★ **`onCapabilityGap` 里有 `await fire("libsmith")`** —— 它等专家跑完，
整个 tick 卡在那里 ⇒ 后面的规则一个都轮不到。

★★ 这与 AGENTS §三 记的 `onSettled` 那个老坑**是同一个病**，只是换了一条规则。
★★★ 而那次教训写进文档了，我**却没有把"顺序"当成一条结构性约束**，
只是给 `onSettled` 加了注释。

### 4.3 修法：**顺序按"会不会阻塞 tick"排，不按重要性排**

```ts
await rules.onNewFinding();
await rules.onInstrumentReview();   // ★ 不 fire → 先跑，饿不死
await rules.onPlateau();            // ★ 同上
await rules.onCapabilityGap();      // ★ 会 await fire → 往后排
await rules.onSettled();            // ★ 一定最后
```

### 4.4 第二次真跑：接通了

```
rule:onInstrumentReview  距上次 29880077 分钟 / 阈值 2 分钟
fire        inspirer ← ★★★ 这一轮**不问研究内容**，问**你自己在用的手段**。
```

★★★ **规则触发 → 派活 → 专家起来。** 完整链路。

## 5. ★★ 还有一个没解决的：tick 频率

```
420 秒里 tick 只跑了 1 次
rule:skip ×4（tick 还在跑，新的被跳过）
```

★ 原因：`onInstrumentReview` 到期那次 `await fire("inspirer")` 会等专家几分钟。
★★ 这是**设计如此**（专家要跑），但它会拖慢整轮。

★ 这和 forge 修过的 `dispatcher`（队列 + 峰值并发 1）是同一个问题的两种解法：
- forge：**不 await**，排队给派活器
- hunt：**还是 await**

★★★ 要不要给 hunt 也上派活器？**这是下一步，不是现在。**

## 7. ★★★★★ 这件事对我最大的教训

### 7.1 我一直以为"给了权限它就会用"

★★ **错。** hunt 有改库权限、有实验能力、有探索使命 ——
**但它没有一次把"审视手段"当成一件事去做。**

★★★ 因为**能力不是处境**。这正是 `P13`：「允许它做 X」它不做。

### 7.2 更刺人的：**我加了工具就以为接上了**

★ `write_skill`（forge）上线两轮才被用 1 次；
★★ `onInstrumentReview` 上线第一次 **0 次触发**，因为顺序错。

★★★ **每次都是"写了没接上"**（AGENTS §二，现在是第 12 次）。

### 7.3 ★★★ 而这一次的教训比前 11 次更深

前 11 次都是「**忘了接线**」。
★★ 这次是「**接了线，但排在一条会阻塞的线后面**」——
★ 这更隐蔽：代码上完全正确，**只是永远轮不到**。

★★★ 所以纪律要加一条：

> **一个机制"没有出现"时，除了查"接线了吗"，
> 还要查"它在队列里排第几、前面有没有 await"。**
