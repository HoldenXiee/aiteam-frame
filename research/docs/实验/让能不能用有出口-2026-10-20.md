# 让「能不能用」有出口：五个连环 bug（2026-10-20）

> 从「forge 的病」到「机制真的在跑」。这一轮是**实验**，单变量、逐次读数。

---

## 0. 起点：病在哪

| 判据（改前） | 实测 |
|---|---|
| 含 ≥20 处 `work/` 实验路径 | **27/34 = 79%** |
| 观众达成 90% 共识 | **0 / 24** |
| newcomer 被问过 | **12/36 = 33%** |

★★★ 根因：`missions.ts` 写着「**没长出新概念的内容，不算这本教科书的内容**」，
而 `grep "概念|定义|模型" rules.ts` ⇒ **12 条规则里 0 条提到**。

**最重的禁令零出口**（纪律㉕）。

---

## 1. 第一步：把「能不能用」做成判据

新增 `usabilityGate`（`tools/judge.ts`，纯函数）：

| 规则 | 依据 |
|---|---|
| newcomer 说「都不够」⇒ 卡 | 他的定义就是「没有这本书背后的上下文的人」 |
| 其他观众 ≥2 人说不够 ⇒ 卡 | 单人异议归 `sign_off` 门 |
| **newcomer 沉默 ⇒ 不算通过** | 实测 62% 根本没被问过 |

★ **不动 `BOOK_THRESHOLD=0.9`**：它回答「该写哪一方」，不回答「能不能用」。
四观点并存时 90% **结构上永远达不到** —— 那正是观众机制 0/24 的原因。

**第一次读数**：
```
被评 24 份 · 可用 8 · 卡住 16（其中 ★ 没人问过 15）
```

★★★ **卡住的 94% 不是"内容不可用"，是"机制没问"。**

## 2. ★★★ 然后连续挖出五个 bug（每个都是「推了 ≠ 投了」的变体）

### bug ① `steer` 排进不存在的运行

```ts
void ag.io.steer(text)   // ★ 只排队
```

观众启动时被要求「读完**然后继续等**」⇒ 「等」= 它结束了 run
⇒ 之后 `steer` 排进的是**一次不存在的运行**。

★ 和 2026-10-19 那次修的是同一类（当时修的是「观众从没被 prompt 过」）。

### bug ② `prompt` 撞上正在跑的 run

改成 `steer().then(() => prompt())` ⇒ 实测**报错 95 次**：
```
agent 正在运行：请用 io.queue() 投递，或用 io.waitIdle() 等它跑完
```

★ 库自己告诉我正解了。

### bug ③ 题目字符串不同源（纪律⑪）

```
规则算的：`x.md` 这份东西该不该进书…   ← 带反引号
观众存的：x.md 这份东西该不该进书…     ← 没反引号
```

⇒ `voteCoverage` **永远算出 0** ⇒ **同一批 3 份被无限重推**。

★ 修法：加 `normQuestion()`，两边都归一化再比。

### bug ④ 一次推 3 份，观众只评 1–2 份

实测去重后 49 题 / 120 票：
```
4 票齐全 16 题（33%）· 2-3 票 4 题 · 1 票 29 题（59%）
```

★ 又是"推了 3 份 ≠ 评了 3 份"（同一个坑第 N 次）。改成一次推 1 份。

### bug ⑤ ★★★ 观众 prompt 让它「自己 `ls outbox/` 挑」

启动 prompt 第 1 条原文：
```
1. 先看 `outbox/` 里有什么（`ls outbox/`），挑最近的读。
```

⇒ **观众按自己的口味挑，根本不听我推的那份。**
这就是"每份产物只有一个人评过"的真根因。

★ 修法：改成「**等**着，会有明确的『请评判 X』消息送过来」。

## 3. 修完的读数

### 3.1 逐次对比

| 阶段 | newcomer 覆盖率 | 4 票齐全 |
|---|---|---|
| 起点 | 33%（12/36） | — |
| `steer`+`prompt`（95 次报错） | 38% | — |
| `steer`→`queue`（0 报错） | 48%（22/46） | 15/46 = 33% |
| 推 1 份/tick | — | 19/56 = 34% |
| **prompt 改成"等着"** | ★ **4 人都在投** | **21/61 = 34%** |

### 3.2 ★★★ 关键证据：修好后，推的 3 份真的被评了

```
本轮 6 票 → 正好对应那 3 份推送的产物（每份 2 票）
近 10 分钟 9 票: {"newcomer":2,"operator":2,"skeptic":2,"builder":3}
```

★★ **改前**：推了 3 份，一份都没被评，观众在评别的。
★★★ **改后**：推什么评什么，4 个观众都参与。

### 3.3 但「4 票齐全」只从 33% 涨到 34%

★ 因为每份要 4 个观众**各自评一次**，而观众有 run 的时间差。
★★ 量具显示：`忙→排进当前 run` **8 次** / `闲→起新 run` **4 次** ——
多数消息要等它当前那轮跑完。

## 8. ★★★ 我违反了纪律⑩，然后修了它

### 8.1 违了什么

★★ 纪律⑩：「**改语料/判据/机制后，旧数据不与新数据混用**」。

而 `votes.jsonl` 是**跨轮累积**的，里面混了：
- 旧机制（没有 `usabilityGate`、没有背书通道、观众自己挑产物）下的票
- 新机制下的票

⇒ **§3.1 那张表的"起点 33%"和"现在 34%"不是同一个口径。**

### 8.2 怎么修的（结构性，不是靠自觉）

`runner.ts` 里加 `runStartedAt`，收尾读数**同时报两个口径**：

```
★ 本轮（18:15 之后）：观众评过 4 份 · **可用 4** · 卡住 0（没人问过 0）
（全库累积）观众评过 74 份 · 可用 33 · 卡住 41（其中 ★ 没人问过 32）
```

### 8.3 ★★★ 这就是本轮的结论

| 口径 | 结果 |
|---|---|
| **本轮**（新机制）| **4 份全可用 · 0 卡住 · 0 没人问过** |
| 全库累积（混了旧机制）| 74 份 · 可用 33 · **没人问过 32** |

★★★ **累积里那 32 份"没人问过"全是旧机制留下的历史包袱。**
**新机制下 0 份。**

★★ 换句话说：**我之前用来判断"病很重"的那些读数，全都是旧机制的产物。**
这是纪律⑩存在的理由 —— **不切时间窗，我会把历史包袱当成现在的病。**

### 8.4 ★ 但只有 4 份样本

★★ **4 份太少，不能下"机制已修好"的结论。**
只能说：**在新机制下，被推送的产物，4 个观众都评了，没有一份漏掉。**

要更有信心，需要一轮长窗口（观众能评到几十份），拿本轮的 `neverAsked` 是不是仍是 0。
