# 拆分两集群代码 —— 改前基线（纪律②：改动当实验做）

> 2026-10-20 · 拆分 `research/clusters/hunt/`（一份代码两用）→ `clusters/hunt/` + `clusters/forge/`
> ★ **这是纯机械搬移**。设计改动不在本轮（见 §6 边界）。

---

## 1. 为什么改（问题的定性）

★★★ 设计者指出：
> 「为什么代码还是放在同一个文件夹中，还是用环境变量来区分，这样**非常不便于优化**。
> 你先把这两个集群的代码分开，然后再重新写架构（**forge 单独是要单独设计的**）」

**现状的病**（不是美观问题，是可维护性问题）：

| 病 | 证据 |
|---|---|
| 一份 `runner.ts` 里 `isForge` 分支 **7 处** | `runner.ts:160/166/186/194/291/328/465` |
| 改 forge 的席位 ⇒ 必须读 hunt 的分支 | 同文件两个语义混在一起 |
| `paths.ts` 用 `process.env.CLUSTER` 决定一切 | 一个环境变量决定 5701 行代码走哪条路 |
| forge 的设计边界**没有落在代码边界上** | 改 forge 容易误伤 hunt |

★★ 结果：**forge 无法单独设计** —— 它的每个决定都要先穿过「hunt 会不会受影响」。

## 3. 拆分方案（已由设计者裁定）

| 决定 | 裁定 |
|---|---|
| 共用件怎么办 | ★ **各自完全独立复制一份**（不抽 `_shared/`）|
| 老路径 `clusters/hunt/` | ★ **保留，作为 hunt 的真目录** |
| 本轮做到哪 | ★ **只拆目录 + 机械搬移 + 跑通测试，不动设计** |

### 3.1 目标形状

```
research/clusters/
├── hunt/          ← 第一集群（广探索/冗余/创新）· 自包含
│   ├── paths.ts   CLUSTER 常量 = "hunt"
│   ├── runner.ts  无 isForge 分支
│   ├── topology/rules.ts
│   ├── prompts/{angles,researcher,missions,index}.ts
│   ├── tools/{challenge,consult,spawn-line}.ts
│   ├── micro/  pre/    （微实验装置，hunt 自己的）
│   └── （无 judge / signoff / joint / publish / lines / audience）
│
└── forge/         ← 第二集群（沉淀成书）· 自包含
    ├── paths.ts   CLUSTER 常量 = "forge"
    ├── runner.ts  无分支，直接就是团队×观众
    ├── topology/rules.ts
    ├── prompts/{lines,researcher,missions,index}.ts
    ├── tools/{challenge,consult,spawn-line,judge,signoff,joint,publish}.ts
    └── （无 angles；无 micro/pre 的 hunt 语料）
```

★★ **`env.ts`、`guard.ts`、`lock.ts`、`lib-state.ts`、`topology/progress.ts`、`feedback.ts`、`snapshot.ts` 两边各一份**（按裁定）。

### 3.2 为什么独立复制是合理选择（★ 我认同这个裁定）

| 支持 | 理由 |
|---|---|
| ✔ 真的能单独设计 | forge 改规则表不会「穿透」到 hunt |
| ✔ 单变量对照成立 | 想比较两集群，代码各自独立才分得清 |
| ✔ 符合设计者原话 | 「两个集群**职责不同，不可能同时优化，只能分开优化**」|

| 代价（★ 必须记下） | |
|---|---|
| ⚠ 守卫改一处要改两处 | 将来若 guard 有安全修复，**两边都要改** —— 这是迟早要处理的技术债 |
| ⚠ 体量翻倍 | 5701 → 约 4600 × 2 |

★ 缓解：**不合并代码，但把"两份应该一致"的件列成清单**，将来用测试守住（同一测试 import 两份，断言行为一致）。本轮不做。
