## 2. 派活器搬到 hunt（治 tick 被卡住）

### 2.1 病

```
600 秒窗口 · tick 只跑 1 次
rule:skip 工具节流 被跳过（上一次 tick 还在跑——它在等专家）  ×4
```

★ 根因：规则里 `await fire(...)` 等专家跑完（3–6 分钟）⇒ 整个 tick 停住。
★★ 与 forge 2026-10-20 记的**是同一个病**，只是换了个集群。

### 2.2 修法（沿用 forge 的做法）

```
规则里 fire(...)  = 「记下该派谁」，几微秒返回
drainer           = 按「同一时刻只跑一位」的节奏真派
需要专家原话的     = fireWait(..., onDone)  ← 只有 onSettled 要 VERDICT
```

### 2.3 ★★★★★ 途中抓到一个**死锁**（两个集群都中）

```ts
const drain = () => {
  if (running) return;
  if (opts.closing()) return;   // ★★★ 这里
  ...
}
// 以及
.finally(() => { ...; if (queue.length && !opts.closing()) drain(); })  // ★★★ 还有这里
```

★★★ 和「收尾时等队列跑空」**互成死锁**：
- 收尾后 `drain` 永远立刻返回 ⇒ 队列永不清空
- 收尾循环又在等队列清空 ⇒ 永远等

**实测症状**（hunt）：
```
flow  等派活器收干净（队列 2 · 在跑 1）
result inspirer · 1336 字
（然后那两位永远没跑，被 dispose() 直接关掉）
```

**修法**（正确语义与 AGENTS §三之二一致：**收尾后不再 fire 新的，已 fire 的会跑完**）：
| 位置 | 改成 |
|---|---|
| `enqueue` | 收尾后**拒绝新活**（并记日志）|
| `drain` | **不再检查 closing** —— 已排的照跑 |
| `.finally` | `if (queue.length) drain();`（去掉 closing 判断）|

★★ 两个集群**同时修**（forge 也有同一个 bug）。

## 3. PREREG 断链：做成读数 + 立要求

```

### 3.2 ★★★★★ 我**故意删掉了 STALE 这个数**

- 集群报：STALE **32/101**（它用 **git 历史**判「盘上那份 driver 不是跑过的那份」）
- 我第一版用 **mtime** 判：**9/101**
- **差 23 个**

★★★ 而 mtime 回答「现在」，不回答「当时」——**正是纪律㉛禁掉的用法**。

**⇒ 结果：这个读数只报「有没有」，不报「是不是过期」。**
★ 宁可少报一个数，**也不报一个我知道量错的数**。

（测试里专门有一条守这个：`读数里**不出现 STALE**`。）

### 3.3 递进开卷段：三选一，都算回答

```
(a) 这是病 ⇒ 说清最便宜的修法，并**用一次实验**证明有效
(b) 不算病 ⇒ 说清为什么不需要
(c) 只对新数据要求 ⇒ 说清旧数据怎么处理

★★ 允许答 (b)/(c) —— 但**不许不答**

★ 不许做的：
  · 事后补 hash 到旧行里 —— 那不是恢复链接，是**伪造链接**
  · 说「以后注意」—— 那没有判据，下一轮会一样

## 4. ★★★★★ 它答了，而且已经自证

产物：`手段IV-判据冻结0of1750可反查-最便宜修法是一个包装器seal-前向实验篡改必红孤儿必红.md`

### 4.1 它先否掉了 (b)，用三个可数的理由

> 「(b) 的说法会是「判据住在 driver 里，driver 在 git 里，所以有 hash」。(b) 被这三条打死：
>  1. **28/101 批跑的时候 driver 还没提交**
>  2. **36/101 批连 `t` 都没有** ⇒ 连「跑的那一刻」都定不出来
>  3. **4/101 批有 diff**
>  ⇒ (b) 只在 **7/101** 上成立。这不是「不需要」，是「**只在 7% 的数据上需要得起**」。」

### 4.2 修法：包装器 + append-only seal（0 行 driver 改动）

```
SEAL {"batch":"seal-e3b","seq":7,"preregSha":"2fb4da1401103e25","driverSha":"54f7f8e1…","window":[0,224)}
VERIFY seal-e3b
  rows=2 resolved=2 orphan=0 seals=1 voided=0 mixed=false
  PASS
```

**E4v2（孤儿行）**：往已封口的批追加 1 行 ⇒ `orphan=1` ⇒ **FAIL**；截回 ⇒ **PASS**
**E3v2（篡改对照）** ⇒ PASS

### 4.3 ★★★ 而且它把「可恢复」的三个口径对齐了

> 「它们差 **7.6 倍**：行内判据字段 **0/1750**（窗口层）· 名字层 **54/101**」

★ 这说明我给的「53/101」和它的「43/101」**量的不是同一件事** —— 它把这个差别写清了。

### 4.4 ★ 它还顺手指出了分母问题

> 「连「有没有时间戳」都有三个分母：**52 批 / 47 批 / …**
>  ⇒ 「无时间轴」这件事本身的分母没对齐。
>  **任何用「62 批 maxT=null」当分母的结论都要重算。**」
