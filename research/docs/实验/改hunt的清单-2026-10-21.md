# 改 hunt 的清单（2026-10-21 · 基于"被我的启动参数绑住"那次分析）

---

## 0. 一句话

★★★★ **根因不是"它不会"，是结构上的三处不对称** —— 全在框架层，全是我能改的：

| # | 不对称 | 后果（实测） |
|---|---|---|
| 1 | **选角度按序号**，而建设性的那个排在最后 | `slice(0,2)` ⇒ `hands-on` **0 次** |
| 2 | **默认 `--employees=1`** | 不传参数 ⇒ 只有「先证伪」，**探索无从谈起** |
| 3 | **「回头看」可无限触发，没有配额** | 自审 **63%**（34/54），探索被挤掉 |
| 4 | 「该变成什么接口」派给**借框架的**而不是**做实现的** | 答案要的是能跑的接口 |

## 1. 已经改完的四处

### 1.1 ★★★★★ `pickAnglesN`：按角色选，不按序号

```ts
// 原来
const seats = ANGLES.slice(0, employees);
//   ANGLES = [falsifier(先证伪), instrument-skeptic(先怀疑量具), hands-on(先动手做)]
//   ⇒ 任何截断都先切掉唯一建设性的那个

// 现在
export function pickAnglesN(n, angles) {
  const constructive = angles.filter(a => a.key === "hands-on");
  const others = angles.filter(a => a.key !== "hands-on");
  return [...constructive, ...others].slice(0, n);
}
```

| 要几个 | 改前 | 改后 |
|---|---|---|
| 1 | falsifier | ★ **hands-on** |
| 2 | falsifier + instrument-skeptic（**两个都是对抗**）| **hands-on + falsifier** |
| 3 | 三个 | 三个 |

★ 9 条测试，含两条「老写法会怎么错」的回归对照。

### 1.2 ★★★ 默认值 `1 → 3`

```ts
const employees = Number(arg("employees") ?? 3);   // 原来 ?? 1
```

★ 理由：hunt 的使命是**广探索**，一个角度不叫广探索。想省钱可以显式传 `--employees=1`，
**但默认必须是广的那个**。

### 1.3 ★★★★★ 广探索度必须是**可见读数**

```
seat  ★ 广探索度：起 3 个角度 = hands-on + falsifier + instrument-skeptic · ✔ 三种角度齐全
seat  ★ 广探索度：起 2 个角度 = hands-on + falsifier · ★★ 未起：instrument-skeptic（3 个才是广探索）
```

★ 这个错之所以静默很久，是因为**"起了几个角度"从来没进日志**（纪律㉖：没有名字 = 没发生）。

### 1.4 ★★★★★ 座位派活账（纯函数 + 5 条测试）

```
flow  ★ 座位派活账：hands-on=4 · falsifier=2 · instrument-skeptic=0 · inspector=1 · … · ★★ 0 次：instrument-skeptic/watchdog
```

★★ 与 `git log` 数前缀的区别：
- 那个数的是**提交** —— 0 次提交 ≠ 没干活（它可能只是没提交）
- **这个是派活** —— 0 次派活才是真的没被叫过

### 1.5 配额改成「占比 ≥ 50% 就停」

```ts
// 第一版（错）：自审数 ≥ 研究结论数（只数 P<数字>）
//   ★ 把 `面-denom` 这类真研究漏掉了（纪律㉞：口径太窄）
// 现在：自审占比 ≥ 50% 就停
if (share >= 0.5) return { allowed: false, ... };
```

实测：生病时 **34/54 = 63% ⇒ 停**；三角度正常 ≈ 1/3 ⇒ 放行。

### 1.6 `onGeneralize` 改派给**做实现的**那一位

```ts
const hasHandsOn = (ctx.peerKeys?.() ?? []).includes("hands-on");
if (hasHandsOn && ctx.challenge) { ctx.challenge("hands-on", prompt); return; }
await fire("inspirer", prompt);
```

★ 为什么不能 `fire("hands-on")`：`fire` 的 `ExpertName` 只含专家
（inspector/archivist/inspirer/watchdog/libsmith），角度座位不在其中。
★★ **这是好事** —— 它把"派给了不存在的座位"挡在编译期（同族：`spawn_seat` 那两个路由到空气的座位）。

实测日志：
```
rule:onGeneralize 新增研究结论 58 份 ≥ 节拍 1 份 ⇒ 该提炼了
rule:onGeneralize → hands-on（steer，问题当场注入）
```

## 3. ★★★ 还没改的（按优先级）

| # | 待改 | 为什么还没改 |
|---|---|---|
| 1 | **`hands-on` 的产出没人挑战** | `challenge` 的触发在 `onNewFinding`，而它看的是"新产物"；实测 `hands-on` 收到挑战 5 次 vs 另两位 24/25 —— ★ 怀疑是**它从不空闲**导致 steer 排不进（已改 steer，但没有读数证明）|
| 2 | **`onSettled` 之后谁接** | 现在辩证只发生在"产物被审定"时；建设性产物（接口/脚本）算不算"产物"未定 |
| 3 | **forge 也有 `libsmith`** | 出书集群在改库 —— 这条**不是我加的**，但同样是错配（要单独算一次实验）|
| 4 | 配额上限 50% 是我定的 | **没有对照实验**证明 50% 比 40%/60% 好（单变量，要单独跑）|
| 5 | 收尾时的派活账 | 真跑 `--secs=300` 时收尾在等一个 3–6 分钟的专家，**超时被 kill ⇒ 这一行没打出来**；只有单元测试证明它正确 |
