# 观察与派活分开 —— tick 结构的根本修复（2026-10-20）

> 设计者：「这还有什么需要决定的吗，你都可以改集群了，**肯定是哪个好，就怎么做啊**」

---

## 0. ★★★ 先纠正我一个错误认知

设计者澄清（逐字）：
> 「**你（研究助手）是可以改框架的**，只是**研究员集群不能自己改自己的框架**」

★ 我上一轮说「按你的裁定『框架不能变』，我不擅自改规则表」——
**那是把对集群的约束错当成对我的约束。**

| 谁 | 能不能改框架 | 为什么 |
|---|---|---|
| 集群 | ✘ 不能 | 它只能在框架里长 agent |
| **研究助手（我）** | ✔ **能** | ★★ 这**正是**我的活：「研究怎么设计集群」|

★ 而 AGENTS.md 的判据本来就写着「这是关于『**集群该怎么设计**』的决定，还是『研究内容』的决定？」
⇒ 改集群设计 = 我的活。我读反了。

**这个错读的代价**：我因此把「改规则结构」整条路排除，说「tick 被卡住是无解的，只能减轻」。

## 1. 病：tick 被自己的下一句话堵死

### 1.1 机制

```
tick()  每 5 分钟一次，**串行** await 每条规则
   ├─ onSettled   ── await fire("inspector")   ← 专家跑 3–6 分钟
   ├─ onPlateau   ── await fire("inspirer") + fire("archivist")
   └─ …其余
```

**观察频率（5 分钟）和干活时长（3–6 分钟）是同一个量级** ⇒ 一次 tick 被占满。

### 1.2 实测

| 窗口 | tick 实际 | 该有 | 差距 |
|---|---|---|---|
| 180s | **1** | ~6 | 1/6 |
| 600s | **3** | ~20 | **1/7** |

★ 后果不是"慢"，是**后面规则全死**：`onChapterIndex` 从上线起 **0 次触发**。

### 1.3 它是怎么来的（历史）

`tick` **不是设计出来的，是被 bug 逼出来的**：

```
原始设计：规则挂在 agent_settled 事件上（agent 停了才检查）
    ↓
★★ 前提破了：研究员一口气跑长实验（一次 bash = 1~3 小时）
   ⇒ settle 几小时才来一次 ⇒ 规则连被调用的机会都没有
    ↓
tick 诞生（5a15de2 · 2026-10-19）
   ★ 加了 tick，但**规则里还是"等专家说完"**
   ⇒ 把一个原本无害的写法变成了致命
```

★ 先人的补救是**调整规则顺序**（不 fire 的在前，fire 的在尾）——
那是**绕过**，不是解决：前几条能跑，后面的永久饿死。

## 2. 我走过两条错路（都记下来）

| | 做法 | 结果 |
|---|---|---|
| ① | `await fire(...)`（原状）| tick 被卡 3–6 分钟 |
| ② | `void fire(...)`（第一版修复）| ★★ **tick 快了，但一个 tick 里能同时 fire 好几个**<br>实测：一个 tick 里 `archivist` + `inspector` 同时开工<br>⇒ 成本不可控、日志交错、9 处返回值全变 `""` |

★★★ ② 是我自己在实测里发现的 —— 这就是为什么"跑起来"不等于"对了"。

## 3. 现在这条（③）：**观察快、派活慢，两件事分开**

### 3.1 设计

```
规则里 `await fire(...)`  = 「记下这个专家该被派」（几微秒）
                            ↓
                     [ 队列 ]
                            ↓
        drainer：**同一时刻只跑一位**，跑完取下一个
```

### 3.2 三个保证

| 保证 | 怎么做到 | 读数 |
|---|---|---|
| tick 永不被专家卡 | `fire` 只入队，立刻返回 | tick 5 次 / 420s |
| **一次只有一位专家** | `running` 旗标 + `finally` 里取下一个 | **峰值并发 = 1** |
| 同一专家不重复排 | `runningRole` + 队列双重检查 | 实测日志：`archivist 已在队列里，不重复排` |

### 3.3 `onSettled` 要读 `VERDICT` 怎么办

★ 走 `onDone` 回调（`drainer.enqueue({ …, onDone })`）。
语义与 `await` 一致 —— **只是不占住 tick**。

### 3.4 收尾必须等队列跑空

```ts
const disp = rules.dispatcher;
if (disp.busy() || disp.queued() > 0) {
  // 最多等 6 分钟
  while ((disp.busy() || disp.queued() > 0) && Date.now() < deadline) await sleep(2000);
  log("fire", `派活器已收干净 · 本轮共派 ${disp.fired()} 位 · 峰值并发 ${disp.peakConcurrent()}`);
}
```

★★ 为什么必需：`fire` 现在只是"排队"，专家在后台跑。
若不管队列直接 `dispose()` ⇒ **把正跑着的专家截断**，它写的 `work/audits/` 和回流意见全丢。
★ 这个风险是**改成排队制才有的**（以前 `await` 天然跑完才继续）。

## 4. 实测读数

### 4.1 完整证据链（真跑 420s，日志原文）

```
rule:fire   ▶ archivist 开始（排队 0s）← 有 40 份新产物还没进决策表…
rule:fire   … inspector 排队（队列 1）← 研究员刚产出新东西…
rule:fire   … inspirer  排队（队列 2）← 研究员已经约 15 分钟既没交新成果…
rule:fire   … archivist 已在队列里，不重复排
…
fire        等派活器收干净（队列 2 · 在跑 1）
```

★★★ **三个专家同时"该派"，但在跑的只有 1 位，其余 2 位在队列里。**

★ 若还是旧版 `void fire`，这 3 位会**同时跑** —— 成本直接翻三倍。

### 4.2 对比表

| | 原状 `await` | ② `void` | ③ 派活器 |
|---|---|---|---|
| 180s 的 tick 次数 | 1 | 3 | 2–3 |
| 420s 的 tick 次数 | — | — | **5** |
| **峰值并发专家数** | 1（但卡 tick）| **3（失控）** | **1** ✔ |
| 9 处 `fire` 返回值 | 专家原话 | `""` | `""`（★ 需原话的用 `onDone`）|
| 专家挂掉 | 抛给调用方 | 记 ⛔ | 记 ⛔ + `onDone("")` |
| 同专家去重 | 天然（串行）| ✘ 无 | ✔ |

## 5. 测试（新增 6 条）

`dev/test/dispatch.test.ts`：

| 守什么 |
|---|
| ★★★ **一口气排 3 位 ⇒ 峰值并发仍是 1**（这就是设计）|
| ★★ 同一专家重复排队 ⇒ 去重 |
| ★★ `onDone` 拿到原话（`onSettled` 要读 VERDICT）|
| ★★★ 专家挂掉 ⇒ `onDone("")`，调用方不会永远等 |
| ★★ 收尾态 ⇒ 不再排、不再跑 |
| ★★ 队列排空后 idle（收尾才能安全 dispose）|

### 5.1 ★★★ 测试抓到的实现 bug

第一版我去重只查 `queue`，**漏了"正在跑的那一位"**（它已经 `shift` 走了）
⇒ 连排 3 次 `archivist` 会真的派 3 次。

★ 测试「同一专家重复排队 ⇒ 去重」当场红了。
⇒ 修法：把 `runningRole` 也算进去。

### 5.2 为什么必须有 `peakConcurrent()` 这个读数

★★ 纪律㉔：量具记的字段必须能回答你想问的问题。

这个设计**唯一**要保证的就是"一次只跑一位"。
没有这个数，测试只能证明"tick 快了"，**看不出并发失控** —— 而那正是 ② 的病。

## 8. 边界（★ 没证明的）

| # | 没证明 |
|---|---|
| 1 | **长窗口**（1–2 小时）tick 频率是否稳定 —— 只测到 420s |
| 2 | 队列积压很深时（如 5 位）会不会饿死后面的 —— 只见到队列 2 |
| 3 | 收尾「最多等 6 分钟」够不够 —— 专家可能跑更久 |
| 4 | `dispose()` 时若还有专家在跑，会不会污染 `work/` |
| 5 | ★★ **省下的时间有没有让书变好** —— tick 从 1 变 5 是手段，不是目的 |
