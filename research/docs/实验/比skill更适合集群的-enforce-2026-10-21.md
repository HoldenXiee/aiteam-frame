# ★★★★★ 比 skill 更适合集群的东西：`enforce`（2026-10-21）

> 设计者原话（这一篇的起点）：
> 「skill 可能会有弊端，你可以尝试看看有没有更好的方式实现 ai 发挥更好的作用，
> 这个底层库开放了很多 api（甚至有需求可以自己改底层库造 api），完全可以去实验创新，
> 创新出更符合我们目标的东西。
> （比如：**skill 在单 agent 上有用**，能让 agent 快速学会，避免犯错，**但是也有弊端**。
> 然后我们这个是 **agent 集群**，按照 skill 的作用，**会不会有更好的东西，更适合 agent 集群**）」

---

## 0. ★★★ 你这句话点破了我一直在犯的错

我上一轮做的 `write_skill`，**本质是把「单 agent 的学习方式」照搬到集群上**。

★ skill 是干什么的：**让一个 agent 学会一件事，以后不犯**。
★ 而集群里要解决的不是「它不会」，是「**这一位成员，在这件事上，反复做错**」。

**这两件事的解法不一样。**

---

## 1. ★★★ skill 的四个弊端（你说了「有弊端」，我把它们逐条落到集群场景）

| skill 的性质 | 在**单 agent** 上 | 在**集群**上变成问题 |
|---|---|---|
| **静态文本** | ✔ 学会了就一直会 | ✘ **情况变了它还在** —— 过时的规矩比没规矩更坏 |
| **一律生效** | ✔ 就一个 agent | ✘ **守规矩的人也在付 token** |
| **不追踪谁犯** | ✔ 就是自己 | ✘ **改了谁都不知道该改谁** |
| **不撤销** | ✔ 有助于稳定 | ✘ **错误修好之后它还在占地方** |

★★★ 核心一句话：

```
skill  治的是「这个 agent 不会做」        ⇒ 需要 文档
集群要治「这一位成员在这件事上反复做错」  ⇒ 需要 干预
```

---

## 2. ★★★★★ `enforce`：一次**有对象的干预**

| | `write_skill` | **`enforce`** |
|---|---|---|
| 作用范围 | 全体（进所有人上下文）| ★ **一位成员**（`target`）|
| 形态 | 文档 | ★ **装在对方身上的门** |
| 治谁 | 谁读到算谁 | ★ **只治它自己** |
| 撤销 | 删文件（靠人记得）| ★★ **`until` 条件满足就自动失效** |
| 记账 | 一条 md | ★★★ **每次被拦都落盘** ⇒ 能问"这条起效了吗" |

### 2.1 ★★★ 为什么「装在对方身上」是真事，不是比喻

库给了 `agent.permissions.gate(fn)`（单槽位，每次工具调用前过一遍）。

```ts
target.permissions.gate(async (call) => {
  for (const r of chain) if (r.tools.includes(call.name))
    return { block: true, reason: `⛔ 集群对你下了一道约束：「${r.rule}」…` };
  return undefined;
});
```

★★★ 这和 skill 的差别是**结构性的**：

| | 进哪里 | 结果 |
|---|---|---|
| skill | 进它的**上下文** | 它读了，**可能照做，可能不照做** |
| **enforce** | 进它的**执行回路** | **不满足就真的过不去** |

★★★ 这正是**纪律㉕**：「**规则必须落在结构上，不能落在提示词里**」。
skill 在提示词层，enforce 在结构层。

### 2.2 ★★★ 一个陷阱：`gate` 是**单槽位**

```ts
gate(fn)   // 后一次覆盖前一次
```

★★ 如果直接调，**下第二条约束会把第一条冲掉** —— 那是静默失效。

★ 修：`enforce` 在 runner 里维护一条 `chain`，每次装门时**把所有约束串起来**。

★ 实测验证：

```
chain 长度 = 2（应为 2）
read  → 约束A：不许 read
write → 约束B：不许 write
ls    → 放行
★★★ 两条都在（没被单槽位覆盖）✔
```

---

## 3. ★★★ 两道硬要求（都是针对「过时规矩」的）

### 3.1 `until`：**什么条件下自动失效**

★ 没有退出条件的干预，就变成了「过时的规矩」。

★ 拒绝的报错要点出原因：

```
until 必填：**什么条件下这条约束自动失效**
—— 没有退出条件的干预会变成过时规矩
```

### 3.2 `evidence`：**现在确实在犯**

★ 没有实测依据的干预 = 拍脑袋 = 不许（纪律②）。

### 3.3 ★★ 还有一个：`target` 指不出人 ⇒ **拒绝，并告诉它该用什么**

```
target「全体」不存在。现有成员：theory#1、practice#1、landing#1
（★ skill 是给全体的，enforce 是给**一个人**的 —— 指不出人，就别用 enforce）
```

★★ 这条最重要的不是"拒绝"，是**报错里教它怎么选**。
★ 否则它会一直拿"全体"去试。

## 4. 测试：14/14

| 组 | 守什么 |
|---|---|
| ① 有对象 | ★★★★ 指不出具体的人 ⇒ 拒，**并告诉它该用 skill** |
| ② 有退出条件 | ★★★★ 没有 `until` ⇒ 拒；`until` 满足 ⇒ 自动撤销 + 记时间 |
| ③ 能判死 | 口号 ⇒ 拒 |
| ④ 有证据 | 空 ⇒ 拒 |
| ⑤ 不碰框架 | 规则表 / 门 / 席位 三种都拒 |
| ⑥ 落到盘上 | ★★★ 真装进去了（不是写文档）；真记账；收尾态不许下 |

★ 其中一条是我自己写错被测试抓出来的：
「必须接受**新加的团队**」没被 `/加一个团队/` 匹配 ⇒ **放宽到 `/加.{0,2}团队/`**。
★★ 这是测试比实现更严的一次。

## 4.5 ★★★★★ 真跑：集群**自己写了一条规矩**

```
skill   ★★ 集群写了一条新规矩：「projection-named」
        → .../agent/skills/projection-named/SKILL.md
```

★ **这是第一次**：`write_skill` 上线两轮，前一轮 0 次调用，这一轮 1 次。

### 它写的是什么（★ 质量超出我预期）

**它抓到一个会让结论反过来的病：**

> 「同一批数据同一判据，`num vs gap2` 的 p **从 0.0014 变 1.0**」

**原因是「读法没写」**：

| 读法 | num | gap2 | 判决 |
|---|---|---|---|
| 交付口径（整份产物喂 judge）| 1/8 | 8/8 | ★ p=0.0014 ⇒ **解除** |
| 内容口径（只喂主表）| 7/8 | 8/8 | ★ p=1.0 ⇒ **不解除** |

★★★ **两种都真，结论相反。**

### 它给的反例是**带文件名和行号的**

> 「`理论-成员边界与基数` v8 §① 写『num vs gap2：p = 0.0014 ⇒ (b) 解除』——这是**交付口径**；
> 同一批**内容口径**是 num 7/8 vs gap2 8/8、p=1.0、差 0。」

★★ 而且它还发现**同一份文件里 v8「解除」与 §7「未解除」相隔 239 行并存** ——
★★★ **读者无论读到哪个，都以为自己读完了。**

### ★★★ 为什么这条东西有意义

| 判据 | 结果 |
|---|---|
| 判据能判死吗 | ✔ 「一律写出读法与源集；禁止 p=… 不带读法」|
| 有具体反例吗 | ✔ 带文件名 + 行号 + 两个口径的数 |
| 有实测证据吗 | ✔ 「本轮复算：verify.out.txt 逐行打出两个口径」|
| 它是不是日记 | ✘ **不是** —— 有自查步骤（跑前 0 token）|

★★★★★ **这已经是真正的知识沉淀。**

★ 而且它选了 `skill`（全体）而不是 `enforce`（个人）—— **选对了**：
这个病是**全员**的（谁写判决都可能不写读法），不是某一个成员的毛病。

★★★ 把它和我设计的 `enforce` 放在一起看，分工就清楚了：

| | 治什么 | 这次该用哪个 |
|---|---|---|
| `write_skill` | **全员**都有的盲点 | ✔ **它用了这个** |
| `enforce` | **某一位**反复做错 | 这次不适用 |

## 5. 边界（★★★★★ 这一节最重要）

### 5.1 ★★★★★ 我还没证明它有用

| 已证明 | 没证明 |
|---|---|
| ✔ 门能装进去（`chain` 成立）| ✘★ **`enforce` 会不会被用**（本轮 0 次；`write_skill` 已经 1 次）|
| ✔ 单槽位陷阱被绕过 | ✘ **它会滥用吗**（对每个人下一堆约束？）|
| ✔ 输入校验能挡住口号/框架 | ✘ **拦错了怎么办**（约束装错，那一轮它就干不了活）|
| ✔ 记账落盘 | ✘ **"被拦"真的是因为违反了吗**（现在的门只看工具名，**不看内容**）|

### 5.2 ★★★★★ 已补：门现在能**看参数**（约束 vs 禁用的分界线）

★ 我第一版的门只看工具名 ⇒ **「拦 write」= 禁用 write**，不叫约束。

★★ 补了 `requireInInput`：**这些字串必须出现在参数里，否则拦**。

| 写法 | 含义 |
|---|---|
| 只给 `tools: ["write"]` | ★ **禁用** write |
| `tools: ["write"]` + `requireInInput: ["依据："]` | ★★★ **约束**：可以写，但**必须带着依据** |

★ 实测（测试 19/19）：

```
内容合格（含「依据：」） ⇒ 放行        ← ★ 这是约束
内容不合格             ⇒ 拦，并说清缺什么
不管的工具             ⇒ 一律放行
多个要求               ⇒ 必须全部满足
```

★★★ **这才是「落在结构上」**：不是"读到了就照做"，是"**不合格就真的写不出去**"。

## 6. 我这一轮的最大收获（不是代码）

★★★ **你说的那句话改变了我的做法。**

★ 我之前所有的工作都是「**改 prompt / 加工具 / 立要求**」——
★★ **全都是在「让单个 agent 更懂」，而不是「让集群更会治理」。**

| 我之前做的 | 本质 |
|---|---|
| 立要求（术语未定义 51%→0）| 更好的提示词 |
| `write_skill` | 更好的文档 |
| **`enforce`** | ★ **第一次落在结构上** |

★ 而库其实早就给了四个面（`tools` / `context` / `model` / `skills`），
★★ 我只用了最弱的一个（`skills`）。

### 6.1 还没用上的三个面

| 面 | 能做什么 | 对集群的意义 |
|---|---|---|
| `context.erase/replace/compact` | **清空/改写另一个 agent 的记忆** | ★★★★ 治「死守错误结论」|
| `model.set/setThinking` | 换型号、换思考档 | ★★★ 按需分配成本 |
| `tools.add/remove` | **给另一个 agent 加/删工具** | ★★★★ 能力随情况变 |

★★★ 尤其第三个：**集群可以给某位成员临时加一把工具**（而不是出厂固定）。
★ 这和 `spawn_seat` 是同一件事的两个方向：一个长**人**，一个长**能力**。
