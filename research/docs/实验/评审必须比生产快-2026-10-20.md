# 评审必须比生产快（2026-10-20）

> 这一轮只有一个改动：**观众的 prompt 从「等推送」改成「自己循环评」**。
> ★ 结果：**评过份数 6 → 57（9.5 倍）**。

---

## 0. 发现的病：评审速度 < 生产速度

### 0.1 症状（按主题切，最讽刺的那一类）

```
读者产物 20 份 · 有票 6 份（30%）
```

★★★ **8 份 `读者-*` 产物从没被观众评过。**

> 给读者写的东西，**读者从没被叫去评**。

### 0.2 根因是算术，不是态度

| 项 | 数 |
|---|---|
| outbox 产物 | ~50–58 份 |
| `onAudience` 推送 | **1 份 / tick** |
| 实测 tick | ~5–8 次 / 10 分钟 |

⇒ **推完全部需要 50+ tick**，而一轮只跑 5–8 tick ⇒ **永远积压**。

#### 为什么不能"每 tick 多推几份"（试过，失败）

| 尝试 | 结果 |
|---|---|
| 每 tick 推 3 份 | 实测 `4 票齐全` 33% → 34%，**几乎没变** |
| 每 tick 推 1 份 | 33% → 34% |

★ 原因：**"推了 3 份"和"评了 3 份"不是一回事** —— 观众收到 3 个题目，它评 1–2 个就结束这一轮。
★★ 这是我这一整轮反复栽的同一个坑（**推了 ≠ 做了**）。

---

## 1. 改法：把"被推送"从主循环降级为优先级提示

### 1.1 改前（prompt 第 1 条）

```
1. ★★★ **等**着 —— 会有明确的「请评判 X」消息送过来。
   ★★ 不要自己 ls outbox/ 挑着读：...
```

★ 这是我上一轮改的 —— 治了"观众自己乱挑"，但**引入了"评审速度受推送速度限制"**。

### 1.2 改后

```
1. ★★★ **自己循环评** —— 这是你的主循环，别等别人叫你：
     ls outbox/ 列出全部产物 → 挑**你还没评过**的一份 → 读 → 用 judge 表态 → 再挑下一份。
   ★★ 为什么要自己循环：实测产物约 50 份，而「请评判」推送每 tick 只发 1 份
     ⇒ 8 份「读者-*」产物从没被评过（最讽刺的一类）。评审必须比生产快，否则永远积压。
2. 收到「请评判 X」的消息时，**优先评那一份**（那是规则按票数排序挑出的最缺票的）。
3. 按**你的身份**看。question 参数原样用。
4. ★★ 全部评完了再停下来。**不要只评一两份就结束** —— 积压就是这么来的。
```

### 1.3 ★ 关键设计：推送没有取消，只是降级

- **主循环** = 自己挑（不受 tick 限制）
- **推送** = 优先级提示（规则按票数最少排序，告诉它"这份最缺票"）

★★ 两者是**互补**，不是替代 —— 因为规则知道全局票数，观众不知道自己缺哪份。

## 3. 本轮同时修的两个 bug

### 3.1 `inspector` 失联导致审查停摆

**实测**：inspector 跑了 900s+ 没回来，期间 `onSettled` 反复打
`上一位 inspector 还在跑（已 601s），不重复叫` ⇒ **审查停摆 15 分钟**。

★★ 根因：`inspectorInFlight` 只在 `onDone` 里清零。
**如果那次 run 永不回调**（崩了 / dispose 截断 / 网络挂住），标志**永久为 true**
⇒ `onSettled` **永久失效**。

★ 修法：加 1800s 超时兜底（= 实测最长 900s 的 2 倍，只兜"永不回来"，不误杀长任务）。
★ 测试 6 条（`inspector-stale.test.ts`），含「900s 仍别叫」和「1800s+ 强制清零」。

### 3.2 沙箱并发测试 flaky

**实测**：`沙箱执行：并发真的并行` 偶发失败（398 / 523ms，判据 340ms）。

★★ 根因：**我在同一台机器上跑真集群**，测试进程被抢 CPU。
★ 这是**装置缺陷，不是能力缺陷**（纪律⑧）。

★ 修法：三次取最短（并发路径的最短值不受偶发抢占影响）。3 次连跑全绿。

## 5. 新增的两个离线读数器

| 命令 | 算什么 |
|---|---|
| `npm run readout -- --since=<ISO>` | 票 / 可用性 / 签字，**可按时间窗切**（纪律⑩）|
| `npm run book` | 书结构量（可达 / 引用 / 聚类 / 痕迹）|

★ 两者都调**同一个纯函数**（`usabilityGate` / `bookReport`），
所以离线看到的数与集群收尾时报的**必然一致**（纪律⑦的用处）。

## 6. ★★★ 边界（没证明的）

| # | 没证明 |
|---|---|
| 1 | ★★★ **内容到底改没改** —— 我量的是"谁被问了"，不是"它写得更能用了" |
| 2 | "可用 44/60" 里，**newcomer 说够用是否可信** —— 他是唯一硬门槛 |
| 3 | 4 票齐全 15 题 / 35 题（43%）—— 仍有 13 题只有 2 票 |
| 4 | 观众"自己循环"会不会**挑好读的**（这是它自己挑的固有风险）|
| 5 | ★★ 「没长出新概念」**仍然零出口** —— 判它要懂内容，我不能碰 |

| 7 | `usabilityGate` **仍然只报数、不拦截** |

★★★ 第 4 条是我这轮改法引入的**新风险**：
从"我指定它评什么"变成"它自己挑"，可能回到最初的病（**83% 的份只有一个人评过**）。

★ 数据现在还看不出来 —— 票数分布 `{2:13}` 有 13 题只有 2 票，可能与这个有关。

## 8. ★★★ 验证了新风险：它确实偏向挑短的（但只差 20%）

§6 第 4 条我担心"观众自己挑会挑好读的"。实测：

```
评过 34 份 · 中位字数 12864
没评 24 份 · 中位字数 15426
```

★★ **评过的比没评的短 20%** —— 偏差**存在**。

★★★ 但**只有 20%**，不是数量级差异 ⇒ 不构成"只评好读的"那种严重偏差。

★ 这个数现在成了**基线**：以后若偏差拉到 50%+，说明"自己挑"这条路走坏了。
★★ 也说明 `onAudience` 推送（按票数排序、不看长度）**仍然是必要的纠偏** ——
   它把"最缺票的"直接指出来，抵消观众的挑短倾向。

**⇒ 两者必须都在，缺一个都会偏。**
