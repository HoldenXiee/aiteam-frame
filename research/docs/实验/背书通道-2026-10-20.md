> 上一轮 A 的边界问题：「带保留 86%→1/8 有没有代价？多少是"真该改"、多少是"懒得背书"」
> 这一轮量了，答案是后者 —— **但根因不是"懒"，是机制没给机会**。

## 2. 根因：通道根本不存在

### 2.1 发现过程

我先量了「为什么没人背书」，得到：

```
有保留的产物 29 份
其中「其他团队全都已签过（没法再签认可）」 28 份 = 97%
```

### 2.2 读代码验证

```ts
// onConsensus（改前）
const missing = teams.filter((t) => !signs?.has(t));
// ★ 只发给「还没签过的团队」
```

★★★ **「认可保留」需要已经签过的团队再表一次态 —— 他们收不到任何消息。**

⇒ **机制上不存在背书通道。** 团队不是不愿，是**根本没有被问到**。

---

## 3. 修法：加一条专门的「请背书」路径

```ts
// 先找「有保留但没人承兑」的
const resvTarget = outs.find((f) => {
  const sig = ctx.signoffState!(f);
  const resv = teams.filter((t) => sig.get(t)?.verdict === "有保留");
  if (!resv.length) return false;
  const endo = teams.filter((t) => t !== resv[0] && sig.get(t)?.verdict === "认可保留");
  return endo.length === 0;      // ★ 没人承兑
});
```

发给**已经签过、但不是保留者**的团队，并说清：

```
★★★ 机制说明（这是新加的一步）：
「有保留」现在**只是提议** —— 必须有**另一个团队说「认可保留」**才生效。
没人认可的保留不算表态 ⇒ 这份产物进不了书。

★ 所以请你二选一（用 sign_off）：
· **认可保留** —— 你核过它的解除条件，认为它站得住（给同事背书）
· **认同**（改判为认同）—— 你认为这条保留根本不必要

★★ 不要因为「不想卡住发布」就随便认可 —— 背书意味着那条解除条件真的成立。
★ 但也不要因为「已经签过了」就不回 —— 你这一次的态度决定它能不能进书。
```

★ 最后两句是**防两个方向的滥用**：既不许随便背书，也不许装看不见。

---

## 4. 为什么只涨到 14%（★ 还是不够）

### 4.1 速率算得出来

| 项 | 值 |
|---|---|
| 带保留的产物 | 29 份 |
| `onConsensus` 每 tick 只推 **1 份** | （这是原有节奏）|
| 420s 跑了几 tick | **5** |
| 处理完 29 份需要 | **≈ 29 tick ≈ 40 分钟** |

★★★ **背书请求和签字请求共用同一条规则、同一个"一次一份"的节奏。**
⇒ 短期跑（7 分钟）只能处理 4 份。

### 4.2 这不是机制错，是节奏没配

可能的方向（**都还没试**）：
- 背书请求**批量发**（一次发 3 份），因为它只是"请人看"，不像签字需要聚焦
- 或者把「背书」从 `onConsensus` 拆出来，给它自己的节奏
- 或者承认：**需要更长的窗口**（40 分钟才能处理完一轮）
