# 让集群自己长规则（2026-10-20）

> 设计者（逐字）：
> 「我的建议是这个集群的架构是**自己长出来的**，这样更有适应力，能完成更复杂的任务。
> 也就是一个**内容比较简单但是拓展性高的框架**，然后随着对任务的推进，
> 逐渐丰富这个框架，使得这个集群慢慢变得越来越有能力胜任这个任务」

---

## 0. 结论

**做了。端到端验证通过。**

```
rules           ★ 集群自己长了 1 条规则：onTocDrift
rule:onTocDrift ★ 触发：书里有 26 份，目录只列了 10 份 —— 差 16 份读者看不到
fire            archivist ← 书里有 26 份，目录只列了 10 份 —— 差 16 份读者看不到
```

★ 规则**不是我硬编码的** —— 是运行时从集群可写目录加载的。

## 1. 先诊断：为什么现在「长不出来」

### 1.1 实测的能力边界

| 它能做什么 | 证据 |
|---|---|
| ✔ 改库 | `lib/aiteam/` 可写，`PATCHES.md` **292 行 9 处改动**，质量很高 |
| ✔ 写实验代码 | `work/` 下 **318 个 .ts** |
| ✘ **改自己的规则表** | `clusters/forge/topology/rules.ts`（1043 行）**在 lab 之外** |

★ 它唯一的路径是 `guard.ts` 里的那句：

```
「想要仓库里别的东西变 → 写进 outbox/，研究助手去做」
```

### 1.2 这就是「架构越来越复杂」的根因

```
每次架构变化 → 必须经过研究助手 → 研究助手的方式是"看读数→加一条规则"
```

★★★ 结果：**12 条规则里 8 条同形状**（检测到某情况 → fire 一个专家），
其中 4 条是**我加的**，而我自己的设计文档写着「每条猜想最多新增 1 条规则」。

⇒ **问题不是规则多，是「修改权在外部，不在集群里」。**

## 2. 设计：把「框架」和「判据」分开

```
代码（人维护，集群不可改）        集群可写
──────────────────────────       ──────────────────
① 什么时候看（三个观察点）        ③ 看什么（判据）
② 怎么 fire（fire 机制）          ④ 该问谁（角色）
⑤ 门与发布（判定权）
```

★ **集群写的是 ③④**：「在什么条件下，问谁、问什么」。
★★ 它**不能**碰 ①②⑤ —— 那是框架，框架要简单且稳定。

### 2.1 为什么规则文件放在 `LAB` 之内

```ts
USER_RULES_FILE = "topology/rules.user.ts"   // 相对 <LAB>/
```

★★★ **`LAB` 之内 ⇒ guard 天然放行，守卫一行没改。**

★ 对比：若把 `clusters/forge/` 放开，集群就能改框架本身 —— 那等于没有边界。

### 2.2 规则的形状（刻意很窄）

```ts
{
  name: "onTocDrift",              // 进 _topology.log 的 rule:<名字>
  why: "治什么病",                  // ★ 必填，不填不加载
  when: (ctx) => string | null,     // null=不动 / 字符串=动，字符串是给专家看的理由
  then: (ctx, reason) => ({ fire: "archivist", why: reason })
                        | ({ tell: "theory/mapper", text: "…" }),
  cooldownMs?: number,              // 默认 20 分钟
}
```

★★ **只有两种动作**（fire / tell）—— 这是「简单但可扩展」的具体含义：
动作种类少 ⇒ 框架简单；判据自由 ⇒ 可扩展。

### 2.3 `ctx` 给什么（全只读）

| 字段 | 是什么 |
|---|---|
| `outbox` | 产物名列表 |
| `read(name)` | 读一份产物 |
| **`readAt(relPath)`** | ★ 读 LAB 里任意文件（含 `../../book/...`）|
| `seats()` | 现存席位 |
| `audiences()` | 现存观众 |
| `signsOf(artifact)` | 签字表 |
| `published()` | 已进书的产物 |
| `lastFiredAt()` | 这条规则上次动的时间 |

★★★ `readAt` 是被**实测逼出来的**：第一版只给 `read(name)`（只读 outbox），
结果规则被调用了、但判据**恒返回 null**（读不到书 → 空串）。

## 3. 安全：失败必须响（不许静默）

| 情况 | 行为 |
|---|---|
| 文件不存在 | 正常，0 规则（大多数轮次） |
| 语法错 | ★★ 整份跳过，**在 `_topology.log` 报错** |
| 没导出 `rules` 数组 | 报问题 |
| 某条缺 `name`/`why`/`when`/`then` | ★ 只丢那一条，报第几条 |
| `when` 抛错 | 记 `⛔ when 抛错`，不影响其它规则 |
| `then` 抛错 | 记 `⛔ then 抛错` |
| 收尾态 | 不动 |

★★ 为什么这么严：本项目已经栽过**三次**「写了但没接上、而且不响」
（`writeVerdicts` / `readFileSync` 未导入 / `publishAndReport`）。

## 5. 新增测试 `dev/test/user-rules.test.ts`（16 条）

| 组 | 守什么 |
|---|---|
| 框架边界 | ★★★ 能写规则、**不能写框架**（`rules.ts` / `runner.ts`） |
| 加载 | 文件不存在 / 语法错 / 没导出 / 缺字段 —— 各自响亮 |
| 执行 | null 不动 / 命中 fire / 冷却 / when 抛错 / then 抛错 / 收尾态 / tell |

★★ 其中「语法错必须报出问题」这条，是因为**静默丢弃最危险**
（会被当成「我写的规则没用」）。

### 5.1 测试踩到的坑（★ 记下来）

★★ 第一版测试用**同一个目录**反复写 `rules.user.ts` ⇒ 断言随机失败。
根因：**ESM 会缓存同一路径的模块**，第二次 `import()` 拿到的还是第一次的内容。
⇒ 修法：每个测试用独立目录（`d1/`、`d2/`…）。

### 6.1 关于第 3 条（★ 我认为最重要）

★★★ 现在**没有任何机制阻止它像我一样不断加规则**。

我在 `README.md` 里写了要求：

> 「加规则之前先回答三件事：① 治什么病 ② 和已有的重复吗 ③ 怎么知道它有用」

★ 但那只是**文档** —— 按纪律㉕「写在文档里的规则 = 没有规则」。

⇒ **下一步该做的可能是**：给「规则数量」或「规则重复度」一个判据。
但**这件事应该问设计者**：是让人定期看，还是让它自己有个上限？
