# 判据的两种错法（v3 太松、v5 太严）2026-10-20

> 我想验证「孤立清单」有没有效，结果发现**验证用的判据本身是错的**。

---

## 0. 出发点

上一轮的两个未验证项：
1. 「孤立产物清单」递了，它改了吗？
2. 「平台期 v4」触发了，集群换路了吗？

⇒ 跑 20 分钟长窗口，比前后孤立数。

---

## 1. 第一眼看起来像"停滞"

| 时间点 | outbox | 零引用 |
|---|---|---|
| 跑之前 | 64 份 | 25 份（40%）|
| 20 分钟后 | 65 份 | 26 份（41%）|

**只多 1 份，零引用率还涨了 1 个点。**

★ 再加上 `onPlateau` 到 **2/3** 没到 3/3（`inspirer` 没触发），
看起来就是「清单无效 + 集群停滞」。

---

## 2. ★★★ 但 `git diff` 说的是另一回事

```bash
git -C research/labfirst/forge diff --stat HEAD -- outbox/
# 15 files changed, 592 insertions(+), 195 deletions(-)
```

★★★ **集群这一轮改了 15 份产物（净 +397 行）。**

它**不是停滞，是在改稿**。

★ 而且新写的那 1 份是 `读者-列义要证不要猜-接手一批别人读数的三查.md`
—— **一个新的读者章**，不是重复。

---

## 3. ★★★ 根因：`产出` 只数**文件个数**

```ts
// v4 的写法
const produced = outs > state.seenOutboxCount || convM > state.lastConvergedMtime;
//                      ↑ 只比个数
```

⇒ **改了 15 份、加了 592 行，判据说"没有产出"**。

### 3.1 这和 v3 是同一类错误的两个方向

| 版本 | 错法 | 病 |
|---|---|---|
| **v3** | 「产出 **or** 在干活」| ★ **太松**：在 `work/` 里无限写实验也算健康 |
| **v4** | 「产出 = 个数变多」| ★ **太严**：改已有产物不算产出 |
| **v5** | 「产出 = 集合变 **或 内容变**」| — |

★★★ 两版都在**同一个地方**犯错：**没有想清楚"产出"到底指什么。**

---

## 4. v5 的实现

```ts
export function outboxFingerprint(): { count: number; hash: string } {
  // 名字 + 字节数 + mtime（秒级）当指纹
  parts.push(`${f}:${st.size}:${Math.floor(st.mtimeMs / 1000)}`);
}

const fp = outboxFingerprint();
const contentChanged = state.outboxHash !== undefined && state.outboxHash !== fp.hash;
const produced = outs > state.seenOutboxCount || contentChanged || convM > state.lastConvergedMtime;
```

★ 首次（`outboxHash === undefined`）**不算**内容变化 —— 否则第一 tick 就误报。

## 5. 真跑读数

```
rule:onPlateau outbox=65 新文件=10  产出=false 在干活=true roundsSinceProgress=1/3
rule:onPlateau outbox=65 新文件=344 产出=false 在干活=true roundsSinceProgress=1/3
rule:onPlateau outbox=65 新文件=26  产出=true  在干活=true roundsSinceProgress=0/3   ← ★ v5 检出内容变化
```

★★ 最后那行 `产出=true` 是 v5 的功劳 —— **同一个份数（65），它检出了内容变了。**

## 6. 测试（新增 5 条）

| 守什么 |
|---|
| ★★★ 实测的病：份数没变但内容改了 ⇒ **必须算产出** |
| ★★ 份数变多 ⇒ 算产出（老行为不能丢）|
| ★★ `CONVERGED.md` 更新 ⇒ 算产出 |
| ★★★ 什么都没变 ⇒ 不算（否则平台期永不触发）|
| ★ 首次不算内容变化（否则第一 tick 误报）|

```
npx tsc --noEmit  → exit 0
npm test          → 355/355（新增 5 条）
```

## 7. ★★★ 「孤立清单」有效性：有初步证据，但不干净

那一轮被改的 15 份里，新写的 5 份中：

```
实操-设计一个集群…  1 次引用（光秃秃 0）
实践-一个数有三种读数…  ★ 5 次引用（光秃秃 0）
实践-主表全对判据判0…   0 次引用
理论-数与延…            0 次引用
读者-列义要证不要猜…    0 次引用
```

★ **有的写 5 次引用，有的写 0 次** —— 清单没有让全体改变，但也不是全无效。

★★ 但**这份证据不干净**：我不知道那 5 次引用是「清单让它加的」，
还是「它本来就要引用那几份」。**没有对照。**

## 8. ★★★ 边界（没证明的）

| # | 没证明 |
|---|---|
| 1 | ★★★ **清单是否有效** —— 改动里有引用，但没有对照，分不清因果 |
| 2 | ★★ **`inspirer` 触发后是否有用** —— 这轮又没到 3/3（v5 把计数清零了）|
| 3 | `THROTTLE_MS = 5 分钟` ⇒ 20 分钟只有 4 个 tick —— 长窗口要 30 分钟以上 |
| 4 | 零引用率 40% → 41% —— **基本没动** |
| 5 | 反对票仍然 **0 张** |

★★★ 我这一轮最大的收获不是"修了 v5"，而是发现：

**「验证一个机制有没有效」这件事，本身需要正确的量具。**
我这轮两次差点得出错误结论（"集群停滞"、"清单无效"），
都是因为**判据只看文件个数**。

---

## 9. ★★★ 补：用 git 历史做零成本对照（我上一节说"没对照"，这里补上）

★ 方法：`git show` 每个提交时候的 outbox，用**同一个纯函数**重算孤立率。
⇒ **零模型成本**，而且每一轮都是独立快照（纪律⑦：可离线重判）。

### 9.1 完整趋势

| 提交时份数 | 零引用 | 零引用% | 平均引用 |
|---|---|---|---|
| 25 | 13 | 52% | **0.68** |
| 26 | 13 | 50% | 0.69 |
| 27 | 14 | 52% | 0.67 |
| 28 | 15 | 54% | 0.64 |
| … | … | … | … |
| 54 | 23 | 43% | 1.59 |
| 57 | 24 | 42% | 1.56 |
| 60 | 24 | 40% | 1.63 |
| 62 | 24 | 39% | **1.65** |

### 9.2 ★★★ 结论（诚实版）

**趋势确实在改善**：平均引用 **0.68 → 1.65（2.4 倍）**，零引用 **52% → 39%**。

★★★ **但这**不能**归因于「孤立清单」** —— 清单是**今天**上线的，
而这条趋势从 25 份的时候（很早就）就开始了。

★ 可能的真实原因（都没验证）：
- 产物越写越多，可引用的对象变多（**分母效应**）
- 集群自己逐渐形成了"要指回别人的"习惯
- 早期产物短，没东西可引

★★ **所以「孤立清单」到现在仍然是未验证的。**
要验证它，需要**有/无清单的两轮对照**（成本约 $6），或者
**清单上线后新写的产物** 的引用率 vs 之前的基线。

★ 后者更便宜：现在基线是 **39% 零引用 / 1.65 均引**，
下一轮若新产物明显好于此 ⇒ 有信号；否则无。
