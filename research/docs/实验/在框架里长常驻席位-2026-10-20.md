## 2. 框架 vs 里面长的东西（这条分开是关键）

```
框架（固定，集群不可改）              里面长（可变）
──────────────────────────           ────────────────────────
· 观察点 / tick 节流                  · 起几个常驻座位
· 规则表（12 条）                     · 每个座位的职责
· fire / tell 机制                    · 座位与谁是什么关系（能挑战谁）
· 共识门 / 发布门
· 状态账本
```

★★ 判据：**「长出来的东西能不能反过来改变框架？」**
若能 ⇒ 那不是「长」，是改框架。

## 3. 实现：`spawn_seat`

### 3.1 与 `spawn_line` 的区别（★ 别混淆）

| | `spawn_line`（原有）| `spawn_seat`（新增）|
|---|---|---|
| 生命周期 | 一次，await 完 dispose | **常驻**，本轮一直活着 |
| 产物 | 返回一段结论 | 它自己写入 outbox |
| **拓扑** | **不变** | ★ **多一个节点** |

### 3.2 框架约束（★ 在工具里是硬的，不给商量）

| # | 约束 | 为什么 |
|---|---|---|
| ① | 新座位**只读**（`READONLY_TOOLS`，5/7 个工具）| ★★★ 长出来的东西**不能改框架** |
| ② | 新座位**没有 `spawn_seat`** | 不许递归长成树把成本烧光 |
| ③ | 团队名必须是**现有的** | 长的是座位，不是新开团队 |
| ④ | 重名拒绝 | 已经在做的活不该再长一个 |
| ⑤ | 本轮上限 4 | 座位多了就变成"大家都在说、没人真看" |
| ⑥ | 收尾态不长 | 与其它规则同一条纪律 |

★ 实测验证：
```
新座位工具数: 5 （全套: 7）
含 spawn_seat? ✔ 不能递归
含 write?      ✔ 只读
```

### 3.3 只在内存里（设计者裁定）

```ts
const grownSeats: GrownSeat[] = [];   // ★ 只在内存，不写盘
```

★★ 为什么不写盘：若写盘并下轮读回，**盘上的结构会变成事实上的框架**，只是没写在代码里 ——
那比写死更难管。

★★★ 本轮有效的**好处**：每轮从同一个固定框架出发 ⇒ **不同轮的拓扑可比**
⇒ 「它长出了什么」本身成为**可观测的现象**，而不是累积的既成事实。

### 3.4 接线（★ 这一步是重点，本项目栽过 3 次）

长出来的座位必须同时接进：

| 接线点 | 为什么 |
|---|---|
| `researcherByKey.set(key, a)` | ★ 能被 `deliverTo` 投递 |
| `grownSeats.push(seat)` | ★ 能被**别人挑战**（在 `peers` 里）|
| **立刻 `io.prompt()`** | ★★★ 「建出来」≠「它在跑」——不 prompt 的话 `steer` 会排在"不存在的运行"后（本项目踩过）|
| `grownRuns.push(...)` | ★ 收尾要等它们做完，否则 dispose 会截断 |
| `work/grown.jsonl` | ★ **量具与机制同批上线** —— 否则无法分辨"没发生"和"发生了我没看见" |

## 6. 我自己判断的两件事（设计者说"你自己判断"）

### ① `spawn_line` 是同步的，要不要改成异步？

**判断：不改。**

- 改它 = 改**框架**（工具的行为语义），而设计者说框架不能变
- 而且它现在的语义是**对的**：`consult` / `spawn_line` 都是"我问一句，等个答案"
- ★ 真要长驻的东西，现在有 `spawn_seat` 了 —— **不需要动 `spawn_line`**

### ② 我加的 5 条猜想规则，要不要撤？

**判断：撤。**

理由：
- ★ 它们是**我加的**，且 4 条同形状（检测→fire archivist）—— 是「框架变复杂」的直接证据
- ★★ 它们默认全关（`CLUSTER_RULES` 不设就不加载），所以撤掉**不改变任何已有读数**（单变量安全）
- ★★★ 按设计者「框架不能变」的裁定：**加规则才是改框架**，我加 5 条本身就违反了这条

⇒ 具体撤法见下节，**但要等设计者确认**（因为撤框架组件也是改框架）。
