# 族 A 首跑：「异常路由 + 人工队列」—— ★ 人第一次真的在流程里

> 2026-10-17 · 系统 [`bench/routing.ts`](bench/routing.ts) · 任务 [`bench/tasks-voucher.ts`](bench/tasks-voucher.ts) · 数据 `runs/routing-T-G.jsonl`（9 轮）
> **设计依据**：[`任务设计重做.md`](任务设计重做.md) 族 A —— 研究员指出「这个项目不只用于编程，而是服务于整个人类的劳动」

---

## 0. 一句话

**第一条"人真在里面干活"的任务。** 多工具真的用上了（`bash` 用了 8–21 次，此前**所有系统 0 次**）；
**而且抓到一个可命名的现象：★ 硬规则的显眼信号会把软问题的暗信号盖住。**

---

## 1. 为什么这条族是分水岭

| | 此前所有任务 | ★ 族 A |
|---|---|---|
| 领域 | 编程（读文档找重复） | ★ **业务单据审核**（不是代码） |
| 工具 | `read/write/ls` | ★ **`bash`×8~21、`read`、`write`、`grep`** |
| **人的位置** | ★ **只在最后看判据** | ★★ **人是流程的一环**（异常处理者） |
| ★ 人的工作量 | **不可测** | ★★ **人工队列长度 = 可测** |

★ **"让人的意图/想法落地"的第一条正面实现。**

## 3. ★★ 工具真的多样了

```
queue  rep1: read×5  bash×13  write×1
queue  rep3: bash×11 read×4   write×3
budgeted rep1: bash×21 read×2 write×1
```

> ★★ **`bash` 8–21 次** —— 而**此前所有系统的 `bash` 都是 0 次**。
> **它用 `bash` 写代码去算硬规则**（金额上限、日期合法性）—— 这正是「**通过代码使用智力**」。

---

## 4. ★★★ 核心发现：**硬规则的显眼信号盖住了软问题的暗信号**

### 现象：漏推的**总是同一张单的副本**

```
该推给人的：V4、V8、V12、V16、V20、V24
漏推的：    ★ V8、V12、V24  —— 三轮**完全相同**

V8 = V12 = V24：  "咨询费 8000 元，2026-03-10，按上次说的办"
                     ↑ 金额超硬规则上限(3000)   ↑ 事由引用了不存在的上下文
推对了的：V4("出差"含糊) / V16,V20("见备注") —— 金额都没超限
```

### ★★ 它自己把机制说出来了（rep2 的理由，逐字）

> 「咨询费8000元＞咨询费上限3000元，金额超限。
>  **事由虽含糊（"按上次说的办"），但已被硬规则直接拦下，无需转人。**」

> ★★★ **它不是没看见那句"按上次说的办"——它**看见了**，
> 然后**主动决定**「既然硬规则已经拦下，就不用推给人了」。**
>
> **这是一个**判断策略**：「硬规则命中 → 短路 → 不再看后面的理由」。**

### ★ 而且策略**不稳定**

- **rep1**：同一张单**推对了**（理由："引用了审核方看不到的上下文，无法核实。需人判。"）
- **rep2/rep3**：短路掉了

> ★★ **所以这不是能力缺失，是**策略在两种做法之间摇摆**（B4 采样随机的一个具体形态）。**

---

## 5. 【做法】

| # | 做法 |
|---|---|
| 1 | ★★ **"硬规则命中"不该短路掉"软问题"** —— 两件事独立，一个是"能不能批"，一个是"谁来判" |
| 2 | ★★ **把两者在流程上分开**：先过全部检查项，再决定路由，别边查边路由 |
| 3 | ★ **人的工作量要单独计量**（队列长度）—— 它和"判得对不对"是两个目标 |
| 4 | ★ ★ **多工具（bash/grep）能让它自己写代码算规则** —— 比让它"心算"可靠得多 |
| 5 | ⚠ **给它"人的工时额度"没有让它更省**（`budgeted` 队列＝3，与 `queue` 一样）—— 又一次"方向盘"没起作用，待查 |

| ★ 同张单 rep1 推对、rep2 短路 —— 策略摇摆 | **强** |

| ★ `bash` 8–21 次（此前 0 次） | **强** |
| ⚠ 每档 3 轮；`none` 档判据有漏洞 | 中 |

## 6.5 ★★ 单变量对照：机制方向对了，但**不稳定**

**设计了一个精确对照**：让两条单据的**事由完全相同**（都是"按上次说的办"），
**唯一差别是金额**是否超硬规则上限。

```
V12:  咨询费 8000 元，2026-03-10，按上次说的办    ← ★ 超限（>3000）
V16:  咨询费 2800 元，2026-03-10，按上次说的办    ← ★ 不超限
      softIssues 完全相同：[引用了不存在的上下文]
```

**预测**：若「硬规则短路软问题」成立 → V12 会被漏推，V16 不会。

**结果（4 轮）**：

| rep | **V12（超限）** | **V16（不超限）** |
|---|---|---|
| 1 | ★ **自己判(不通过)** ✗ | 推给人 ✓ |
| 2 | 推给人 ✓ | 推给人 ✓ |
| 3 | 推给人 ✓ | 推给人 ✓ |
| 4 | 推给人 ✓ | 推给人 ✓ |

### ★★ 结论：机制方向对，但它是**一个概率，不是一条规则**

- **V16（不超限）四次全推对** —— ★ **句子里那句"按上次说的办"它每次都看见并处理了**
- **V12（超限）四次漏一次** —— ★ **超限的单子有一定比例会被短路**

> ★★ **这比"它总是短路"更有意思**：
> **它是一个**随机失效**（B4 采样随机的具体形态），而不是系统性缺陷。**
>
> ★ **所以"治"它不能靠"教它一条规则"** —— 要靠**流程上把两件事分开**（做法 1/2）。
