## 二、★★★ ② `onDispute` 活了 —— `joint` 从 0 到 11


## 五、★★ ⑤ flaky 测试：量具缺陷，不是能力缺陷

```ts
// 原来（绝对墙钟）
assert.ok(ms < 250, ...)        // ★ 并发跑测试时抖动 254~388ms

// 现在（相对判据）
const SERIAL = 5 * 80;          // 串行下界 400ms
assert.ok(ms < SERIAL * 0.85);  // 明显低于串行 ⇒ 证明真的并发
```

★★ **纪律⑧**：机器忙不代表沙箱串行。用绝对墙钟测并发，测到的是**机器负载**。
★ 修后**连跑 3 遍全绿**。

## 七、★★★ 今夜的方法论收获（比产出更重要）

★★ **我做的每一个"机制"，第一次接上去时都是空转的。共 7 次：**

| # | 机制 | 空转原因（每一层都能静默失败）|
|---|---|---|
| 1 | `onAudience` 规则 | 调用**没插进代码**（replace 静默失败）|
| 2 | `sign_off` 工具 | 只是工具，没人用（`P13`）|
| 3 | 投递 | 团队名 → 座位名**映射落空**，失败被丢弃 |
| 4 | 规则顺序 | `onSettled` 会 `await` 专家**饿死后面所有规则** |
| 5 | 观众 | **从未被 `io.prompt` 启动** ⇒ steer 排在"不存在的运行"后 |
| 6 | 门本身 | "有保留"**太廉价** ⇒ 门形同虚设 |
| 7 | `onDispute` | 判据**写窄了**（只认反对票）⇒ 永远匹配不到 |

★★★ **规律**：

> 规则写了 ≠ 规则被调用 ≠ 消息送达 ≠ 目标在运行 ≠ 对方会响应 ≠ 判据匹配得上

★ **每一层都能静默失败，而只有日志里真的出现它，才算接上。**

★★ **推论（给设计者的建议）**：新机制上线，第一件事不是"看它设计得对不对"，
是**核对"它到底有没有发生"** —— 而且**量具必须与它同批上线**。
