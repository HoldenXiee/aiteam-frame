# 实验 II 结果：形态扫描 —— 单 agent 完胜所有多 agent 形态

> 2026-10-16 · 数据 `runs/{flat,pipeline,star,carry,redundant}-T-A.jsonl`
> **同一任务（T-A, pairs=12）、同一难度、同一模型、同一工具集** —— 只换形态
> ★ 这是 `DESIGN.md` ① 类（"具体类型，应该怎么去设计"）的**正面入口**

---

## 0. 一句话

**在 pairs=12 这个规模上，四种多 agent 形态没有一个在「质量 × 成本」上胜过单 agent。**

| 形态 | 通过 | 过度合并 | **token 中位** | 秒（中位） |
|---|---|---|---|---|
| ★ **flat 单 agent** | **4/4** | 0 | **139,860** | **99** |
| **carry** 流水线 + 完整交接 | 3/4 | 1 | ★ **66,609** | **94** |
| redundant 冗余（3 份独立） | **1/3** | 0 | 165,792 | 263 |
| pipeline 静态流水线 | 3/4 | 1 | 212,121 | 154 |
| star 星形（1 + scouts） | 4/4 | 0 | **233,987** | 167 |

> ★★ **单 agent 4/4 全对，成本还最低之一。**
> ★ **多 agent 里唯一"划算"的是 `carry`**（完整交接，66k）—— 但它仍是 3/4。

---

## 1. ★ 单 agent 的最优解就是理论最优

**看 `flat` 最省的那一轮（25,227 token，12/12 全对）**：

```
ls corpus                  ← 1 次
read M1.md  … read M26.md  ← 26 次，每份**恰好读一遍**
write answer.json          ← 1 次
```

> ★★ **1 + 26 + 1 = 28 次调用，零重复，零浪费。**
> **这就是这个任务的理论最优** —— 它一次性做到了。

### 而多 agent 做不到这件事，因为：

| 形态 | 为什么做不到 |
|---|---|
| **pipeline** | 3 个 agent 各自要理解任务，**上游读过的下游要重读**（N1） |
| **star** | coordinator 起 scout，但 scout 的产出要**回到 coordinator 再过一遍** |
| **redundant** | 3 份独立解答，**3 倍读入**，而且交集会投掉少数派的正确答案（P7） |

---

## 2. ★ carry 是唯一的例外，而且原因正是 P9

`carry`（完整交接）**比 `pipeline`（默认交接）便宜 3.2 倍**（66k vs 212k），质量一样（3/4）。

**这直接验证了 P9**：**交接物完整 → 下游不需要重新推断 → 既省又准。**

★ **这是"多 agent 该怎么设计"的第一条具体答案**：
> **如果非要用多 agent，交接物必须完整** —— 否则成本涨 3 倍，质量还不升。

---

## 3. ★ 成本中心随形态翻转（N7 得到确认）

| 形态 | 成本分布 |
|---|---|
| flat | 单点 **100%** |
| **pipeline** | 第一棒 **22%** / 其余 39% |
| **star** | ★ **其余（scout）100%** |
| carry | 第一棒 30% / 其余 35% |
| redundant | 其余 33% |

> ★ **流水线的成本压在**第一棒**（S1 独立占 63%，见 N3），星形压在**中间节点**（coordinator/scout）。**
> **⇒ 优化位置完全相反** —— 想省流水线的钱要去改 S1，想省星形的钱要去改协调层。

---

## 4. 【做法】

| # | 做法 |
|---|---|
| 1 | ★★ **先问"这个规模需不需要多 agent"** —— 实测 pairs=12（26 份材料）上**单 agent 全胜** |
| 2 | ★ **非要多 agent，就用完整交接**（carry 比默认 pipeline 便宜 3.2 倍） |
| 3 | ★ **别用冗余做"质量保险"** —— 它在这里 1/3 通过，且 3 倍读入（P7 已解释） |
| 4 | ★ **优化位置看形态**：流水线改第一棒，星形改协调层 |
| 5 | ★ **"1 ls + N read + 1 write"是单 agent 的理论最优** —— 跑一次看它离最优多远 |

---

## 5. 【验证】

| 证据 | 强度 |
|---|---|
| 五形态同条件对照（4 轮/形态） | **强**（同任务同难度同模型） |
| flat 最优解 = 理论最优（25k，12/12） | ★ **强**（可肉眼验证调用序列） |
| carry vs pipeline 3.2 倍成本差 | **强** |
| 与 N2/N3/N7 一致（多 agent 过度合并、S1 吃成本、成本中心随形态翻转） | ★ **强**（三条独立吻合） |
| ⚠ **每形态只有 3–4 轮** | 中 |
| ⚠ **只有一个任务、一个规模（pairs=12）** | ★ **中** —— **不能推广到更大规模** |

### ⚠ 重要的限定（已部分验证）

**这个结论只在 pairs=12 上成立。** 我去验了更大的规模：

#### pairs=16（36 份材料）—— ★ **它们打平了**

| 形态 | 通过 | token 中位 | 秒 |
|---|---|---|---|
| flat 单agent | **3/3** | **256,822** | 132 |
| pipeline 流水线 | **3/3** | 249,993 | 196 |

> ★ **单 agent 在 36 份材料上没有输**（B6 上下文有限**还没发作**）。

#### ★ 但看到了 B6 的**前兆**

```
pairs=12（26份）: flat 用 1 ls + 26 read + 1 write  ← 理论最优
pairs=16（36份）: flat 用了 60–72 次 read  ← ★ 只该用 36 次
   重复读了：notes-rev-C-final2.md / a.txt / misc1.txt
             misc15.txt / 已做实验的价值提取.md  ← ★ 翻到我的项目文档去了
```

> ★ **读到"该读的"之后，它开始到处翻** —— 这是上下文压力下
> 「找不到就多找找」的行为，**但还没到出错的程度**。
>
> ⚠ **pairs 的上限是 16**（话题池容量）—— **要做更大的规模，得换任务**（如 T-E 的 35–50 文件）。

★ **这是下一步最该验的事**：**单 agent 到底在哪一个规模开始输？**（B6 的第一次实测）
