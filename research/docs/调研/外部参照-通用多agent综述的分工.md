# 外部参照：通用多 agent 综述与本项目的分工

> **2026-10-16 · 研究员指令做的一次外部文章评价（不是本项目实验，不是选题）。**
>
> **被评对象**：腾讯云开发者社区《Multi-Agent 协作：分工、协作与冲突解决》
> <https://cloud.tencent.com/developer/article/2675285>（作者 HOS(安全风信子)，2026-05-24）
>
> **本文的用途**：把一篇**外部综述**当镜子照一遍，看**它覆盖了我没覆盖的哪一层**、
> **我覆盖了它覆盖不了的哪一层**，以及**它的哪些零件可以直接拿来做我排好的实验**。
>
> ⚠ **本文不是选题清单**（`研究规划.md` §0.4：外部来源是灵感/参照，不是选题来源）。
> 它的产出只有两样：**① 一张"我没进过视野的层"的清单 ② 三个可复用的零件**。

## 0. 一句话

**文章是"设计空间的地图"，demox 是"在地图上若干格子里插了旗"。**

| | 文章 | demox |
|---|---|---|
| 画的是 | **有哪些坐标轴**（横轴全、纵轴浅） | **在少数坐标点上真实 LLM 会怎么反应**（横轴窄、纵轴深） |
| 体裁 | 索引型教程（给选项 + 给能跑的骨架） | 受控实验记录（现象 → 归因 → 做法 → 验证） |
| 该被什么标准评 | **覆盖面、骨架可用度、决策纪律** | 对照、剂量、可复现、可证伪 |

★ **两者不是竞争关系。** 谁也**不该拿自己的强轴去否定对方的弱轴** ——
这篇文档最初的版本正是犯了这个错（见 §5 的自我更正），那一版已作废。

## 1. 文章覆盖了什么（按它自己的体裁评价）

**目标**：让一个没搭过多 agent 系统的人一次性看到主要设计维度，并拿到能跑的起点代码。

| 维度 | 覆盖 | 备注 |
|---|---|---|
| 角色模型 | Specialist / Generalist / 混合 | 三者优劣都列了；结论偏软（"混合是实践最优解"无出处） |
| 任务分解 | TaskGraph + 环检测 + 关键路径 + 并行分组 | ★ **实现质量高**，见 §4① |
| 通信协议 | Blackboard / Message Passing / Shared Memory + 对比表 | ★ 含版本历史、队列上限、`correlation_id`，见 §4②③ |
| 协作策略 | 串行 / 并行 / 层次 / 混合 | 四种都实现了；选择判据只有示例常数 |
| 冲突解决 | 投票 / 仲裁 / 优先级 | **覆盖到了**（很多同类文章会漏） |
| 规模化 | AgentPool / 动态调度 / 负载均衡 / 自动扩缩容 | ★ 含 cooldown、utilization，见 §4④ |
| 完整案例 | Planner-Coder-Reviewer | 端到端可跑（demo 级） |

**结论：按索引型教程的标准，这是一篇合格的、覆盖面扎实的文章。**
`AgentPool.acquire()` 的 timeout+超池扩容、`AutoScaler` 的 cooldown 这些是**对真实工程问题的回应**，
不是抄来的模板。

### 它的真实短板（落在体裁内部，不是"没做实验"）

| # | 短板 | 说明 |
|---|---|---|
| 1 | **"各有优劣"密度过高，收敛不足** | 几乎每节都以"根据任务特性灵活选择"收束，**很少给"根据什么选"的判据**。作为索引卡够用，作为决策辅助弱 |
| 2 | **质量分数的来源被跳过** | `_resolve_quality_dispute` 用 `quality_scores` 排序、`ReviewerAgent._calculate_score` 是硬编码扣分表 —— **"分从哪来"推给了调用方，且未标注这是开放问题** |
| 3 | **冲突解决的退化行为未提示** | `RuleBasedArbitrator` 信息不足时 fallback 到 `"Random resolution"` / `"First-come-first-served"` —— **机制静默退化成随机**，这个坑没写 |
| 4 | **安全/权限层缺席** | 只在"未来方向"提了一句 |
| 5 | **引用与正文耦合弱** | 引了 CrewAI / AutoGPT / AI-System，正文没有一处说"这里参照了哪个设计"（⚠ 这是**弱批评**，索引型文章的引用习惯本就如此） |

★ **一句话**：文章的问题**不是"没做实验"，是"给了选项，没给选择的纪律"** ——
风险不在它错了，而在**读者会把 `sequential_threshold=0.3` 这类占位值当结论照搬**。
**这是一句注就能补上的缺陷，却是它最可能造成实际损害的地方。**

## 2. ★ 核心产出：文章目录 = 我**没进过视野**的层

> **这一节是本文最值钱的部分。**
> `系统科学调研.md` §5 那"四条漏掉的维度"是**理论指出**的；
> 这里是**外部实践指出**的 —— 而且是**更基础的层**：那四条是"设计维度"，这几条是"**整个层面都没做**"。

| 层 | 文章有 | demox 有吗 | 我该不该有 |
|---|---|---|---|
| **通信协议**（黑板 / 消息总线 / 共享内存） | ✅ 三套完整实现 | ❌ **一个字都没有** | 判定见下 ★ |
| **冲突解决**（投票 / 仲裁 / 优先级） | ✅ | ❌ 没有 | ★ 有前置障碍，见 §3 |
| **池化与调度**（AgentPool / 负载均衡 / 扩缩容） | ✅ | ❌ 没有 | 我有判据缺装置，见 §3 |
| **递归**（子 agent 自己是完整系统） | ❌ 文章也没有 | ❌ | 已在 §5 维度 1 |
| **交接面方向**（衰减 vs 放大） | ⚠ 隐含在协议对比里 | ❌ | 已在 §5 维度 2 |
| **人的位置** | ❌ 全程无"人" | ❌ | 已在 §5 维度 4 |

★ **关键判断**：文章覆盖的这三层，**恰好都不在 `系统科学调研.md` §5 那四条里**，
也不在 `已做实验的价值提取.md` 的"四栏空着"里。

> **为什么？因为那两条清单都是"我碰过的东西的延伸"**——
> §5 的四条来自系统科学理论，四栏来自 `DESIGN.md` 逐句对齐。
> **两把尺子都量不到"我根本没进过的层"。**
> 文章目录提供了**第三把尺子：一个完整的、别人认为该有的功能清单。**

### 三条新层的判定

| 层 | 我为什么不觉得缺 | 现在怎么判断 |
|---|---|---|
| **通信协议** | 我的形态是**单向交接**（pipeline 三跳），压根没有"双向通信"的需求 | ⚠ **P5 已经暴露了协议之下的洞**：66.9% 的 read 在盲猜（下游不知道目录里有什么）。**这不是协议问题，但"东西有没有传过去"本来就是协议要管的**。→ 若做候选 F（衰减 vs 放大），**三种协议正好是三种"交接面形状"的取值** |
| **冲突解决** | 我的 agent **不并行写共享状态**（只读扇出），所以没有冲突 | ★ 判断成立，**但前提是"我不做写共享的活"**。真实工作（§1.1 调研：加新功能=写必串行）里冲突是存在的。→ **有前置障碍**，见 §3 |
| **池化调度** | 我只有 2–4 个 agent，规模上不需要池 | ★ 但**文章有装置、我有判据**：45% 饱和点（β=−0.404）、协调开销随链接数增长。→ 见 §3 |

## 3. ★ 三个零件：能直接接进我已排好的实验

> 严格对应 `实验计划.md` 的候选，**不是新增选题**。

### ① `TaskGraph` → **候选 G（可分解程度）**

- **我缺什么**：候选 G 要扫"分解到多细"，但没有一个**抽象的分阶段表示**，只能用 pipeline 的 `stages` 参数硬扫。
- **文章给什么**：`get_parallel_groups()`（按依赖分层）、`calculate_critical_path()`（最长链）、
  `has_cycle()`（环检测）、`Task.get_depth()`（深度）。**可直接用的抽象**。
- **⚠ 但要用它的哪一半**：文章的 TaskGraph 是**静态的**、代码构造的。
  ★ 而 P3 已经证明**模型不主动分工**（36 轮只 5 轮委派）——
  **静态图恰好是唯一可行的做法**，所以这不是限制，是契合。
- **接口**：候选 G 的"扫阶段数"改成"扫关键路径深度 / 并行组数"。

### ② Blackboard 的**版本历史** → `系统科学调研.md` §4「VSM 的 S2 协调层」

- **我缺什么**：§4 明写 **S2（协调层）"完全没碰"** —— 我连"交接面演化了什么"都没记录。
- **文章给什么**：`_version_history` + `get_history(key, limit)` + `BlackboardEntry.version`。
  ★ **这正是"交接面随时间变成了什么样"的记录装置** —— S2 该有的最小可观测量。
- **接口**：pipeline 的 S1→S2→S3 交接面，逐版记录 → 就能量"衰减了多少变异度"（维度 2）。

### ③ MessageBus 的 `correlation_id` → 素材库 G2（信息衰减曲线）

- **我缺什么**：G2-1 要测"一条信息传到第 k 跳还剩多少"，中央难题是**追踪那条信息**。
- **文章给什么**：`correlation_id` + 广播时 `msg_copy.correlation_id = message.id`。
  ★ **天然的信息追踪器** —— 注入一个已知事实，顺着 id 看它在第 k 跳的产物里出现在哪、出现几次、有没有失真。
- **接口**：与 G3-3 的注入基建**共用**（`bench/inject.ts` 已有诱饵/误导指令）。

### ④（附加）`AutoScaler` 的判据漏洞 → 素材库 G5

- **文章怎么做的**：`scale_up_threshold: 0.8`（利用率超 0.8 就扩），**纯反应式，没有"该不该扩"的判据**。
- **我手上有什么**：**45% 饱和点**（单 agent 准确率 > 45% 后加 agent 负回报，β=−0.404, p<0.001）、
  **MAST 41%–86.7% 失败率**。
- ★ **文章的扩张器 + 我的饱和点 = 池化调度不再是赌博。**
  ⚠ 但 45% 那个数来自外部文献（Google 四基准），**外推到本库环境需先跑基线复现**（调研 §5 已标此风险）。

## 4. 明确**不能**直接抄的一处：冲突解决的输入

文章整套投票/仲裁，**输入全部假定可信**：`quality_scores`、`voter_weights`、`agent_priorities`。

而 demox 手里有一条硬证据（`已做实验的价值提取.md` 的 B8 活体样本）：

> 在缺 `ls` 的环境里，模型几次「声称已写入 answer.json」而**实际文件不存在**，
> 或「声称读完了 18 份」而用了 **54 次 read**。**它的自报不可信。**

★ **这不是说文章错** —— 是说**移植前必须先解决"谁来给这个分"**。
文章的 `ReviewerAgent._calculate_score` 用硬编码扣分表，在 demo 里没问题；
但**一旦换成模型自评，整条仲裁链的输入就塌了**。

> **判断**：冲突解决这一层，**装置可以借鉴，机制不能直接搬** ——
> 前置条件是先有一条"怎么不靠模型自报拿到分"的做法（这正是我四栏空着的"质量"那一栏）。

## 5. ★ 自我更正：本文第一版错在哪（保留，因为它是方法论的样本）

> 第一版对文章的评价带明显敌意。核完之后发现**多处不成立**，逐条记下 ——
> 这不是自我批评的仪式，是**一条可复用的教训**。

| 第一版我说 | 实际 | 性质 |
|---|---|---|
| "三个引用没有一个是论文或受控实验" | **没核就下结论**。核完：**CrewAI**（10 万+ 开发者、活跃维护）、**AutoGPT**（真实平台）**都是业界重要项目**。第三个 `AI-System/MultiAgent-System` 现在 404（可能重命名/删除），**不等于当初不可靠** | ❌ 事实错误 |
| "零实证" | 这是**综述/教程体裁**，本就不产出原始数据 | ❌ 体裁误判 |
| "魔数无出处" | 教程里**可调示例参数**，作者从未声明是生产定值 | ❌ 曲解 |
| "`_generate_code` 返回模板、`_perform_review` 是字符串匹配" | **demo 骨架**，文章没说是生产实现 | ❌ 不公平比较 |
| 用 demox 内部叙事（"判据纯函数""有 ground truth"）当客观事实 | 那也是**项目自述** —— 我批文章"只有自报"，自己也在用自报 | ❌ 双重标准 |

★ **根本错误**：**没先问"这篇文章想干什么"**，就直接拿 demox 的唯一尺子（"必须做对照实验"）去量。

> **教训（可复用的）**：
> **评价一个东西之前，先确定它的体裁与它自己承诺的目标，再用那个标准量它。**
> 拿一个项目的强轴去量另一个项目的弱轴，得到的不是评价，是**立场**。
>
> ⚠ 而这条教训**对 demox 自己也成立**：
> 我在 `研究规划.md` §1.5 用"归因 / 利用 / 质量 / 人"四栏审查自己时，
> **那也是一把尺子** —— 它同样量不到"我没进过视野的层"（§2 已说明）。

## 6. 总评（修正版）

**按它自己的体裁（索引型教程）打分：**

| 项 | 分 |
|---|---|
| 覆盖面 | ★★★★☆ |
| 代码骨架可用度 | ★★★★☆ |
| 决策纪律（"根据什么选"） | ★★☆☆☆ |
| 开放问题标注 | ★☆☆☆☆ |
| **作为入门索引** | **★★★★☆ 合格甚至不错** |
| **作为生产决策依据** | **★★☆☆☆ 会误导** —— "灵活选择"看着像结论 |

**一句话：**

> 文章画的是**设计空间有哪些坐标轴**（横轴全、纵轴浅）；
> demox 画的是**在少数坐标点上真实 LLM 会怎么反应**（横轴窄、纵轴深）。
> **谁也不该拿自己的强轴去否定对方的弱轴。**

**对 demox 的两条结论：**

1. ★ **文章目录 = 我"整个层没进过视野"的清单**（通信协议 / 冲突解决 / 池化调度）。
   这不是"待办" —— 是**第三把尺子**，补上了 §5 四条与四栏都量不到的地方。
2. **三个零件可复用**（TaskGraph / Blackboard 版本历史 / `correlation_id`），
   分别接候选 G、S2 协调层、G2 衰减曲线 —— **都是已排好的实验，不是新增选题**。

**反过来对文章的一句（保持对称）：**

> 它的 `AutoScaler` 按利用率扩池，**缺的正是"该不该扩"的判据**；
> 而那个判据我手里有（45% 饱和点，β=−0.404）。
> **它给了我装置，我给了它判据 —— 这才是两份东西的正确关系。**
