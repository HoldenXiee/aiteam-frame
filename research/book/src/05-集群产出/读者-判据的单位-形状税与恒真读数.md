## 1. 定义：claim 的单位是「关系」，判据的单位是「容器」

一条「n03 与 n22 打架」可以写成很多种容器：

```jsonc
// A. 关系容器：一个对象 = 一条关系
{"pair":["n03","n22"],"kind":"conflict","quoteA":"…","quoteB":"…"}

// B. 带着「我查过、不是」的候选容器
{"candidates":[
  {"pair":["n03","n22"],"verdict":"conflict", …},
  {"pair":["n01","n15"],"verdict":"none","why":"整体不是同一件事"}]}

// C. 每篇笔记的台账
{"notes":[{"note":"n01","lineCount":5,"pairedLines":[5],"singletonLines":[1,2,3,4]}, …]}

// D. 把真对 + 一条相关笔记写在一起
{"relation":"n03|n22|n37","kind":"conflict","why":"n37 是按模型分的限定，三者合起来才完整"}
```

**定义（本章用的三个量）：**

| 量 | 定义 | 怎么算 | 要不要真值 |
|---|---|---|---|
| `fp_容器` | 冻结判据的 `fp`：**每个**非「恰好 2 份笔记」的条目 +1；每个 2 元表外对（含干扰对）+1 | `notesTask.judge().fp` | 要（答案表） |
| `fp_关系` | 产物里**被断言为关系**的、不在答案表里的**不同配对**数（3 元以上条目里的对不算断言） | `pairread.items()` 里 `asserted ∧ notes.length==2` 的去重 off-truth 对 | 要 |
| **形状税** | `fp_容器 / max(1, fp_关系)` | 上两行相除 | 要 |

★★ **形状税不是「模型多报了」，是「判据把不承载断言的东西也读成了断言」。** 它由四类成分构成，四类之和**恒等于** `fp_容器`（逐条核对过，残差 ≤2/轮，来自两个 walker 的分组差异）：

```
fp_容器 = ①一元条目（台账/元数据/未配对清单）
        + ②三元以上条目（真对 + 一条相关笔记，或主题归组）
        + ③二元表外·被报告自己否定的（"我查过、不是"）
        + ④二元表外·被断言的（含冻结干扰对）
```

★ **只有 ④ 是「它判错了」。** ①②③ 是形状/透明度，不是内容错误。这一章的全部读数就是把 ④ 从 `fp` 里挖出来，看它有多大。

依据：`work/practice/notesTask.ts:453-500`、`work/practice/pairread.ts:1-95`、`work/practice/_fp-tax2.ts`

## 2. 实测（一）：三个干净的病例

★ 用 r0/r1 的格子做病例（r2/r3 有续跑碰撞，见 §6.5；这三例都在干净格上）。

### 2.1 一条真关系写成「真对 + 一条相关笔记」= 一漏 + 一假

`s-selfcount r1` 的产物里有三条**三元条目**：

| 产物写的（3 元） | 判据读到 | 关系级读到 |
|---|---|---|
| `n03\|n22\|n37` | 不是 2 元 → **fp+1**；`n03\|n22` 没被记 → **漏** | n03\|n22 打架（真），n37 是限定 |
| `n12\|n38\|n34` | 同上 | n12\|n38 重复（真） |
| `n16\|n40\|n34` | 同上 | n16\|n40 重复（真） |

结果：`matched 9/12`、`fp 3`、`missing` 恰好是这三对。**三条正确的关系，被判据记成 6 个错（3 漏 + 3 假）。**

★ 这不是模型写错：三条 3 元条目里都**包含**真对，第三份笔记是它给的限定/证据。判据的单位是「条目必须恰好 2 元」，于是多写一份笔记 = 把一条对的判成两条错的。

### 2.2 「我查过、不是」被读成「是」

`two-selfcount r1` 的产物：12/12 真对、`pin 12/12`、`fp 6`、`landing=false`。它的 6 条 `fp` 是：

| 判据记的 fp | 产物里的位置 | 产物在说什么 |
|---|---|---|
| `n03\|n07` | `verification.near_miss_examples_not_counted[0]` | ★ **明确写着「不计入」** |
| `n08\|n10` | 同上 `[1]` | 同上 |
| `n11\|n19` | 同上 `[2]` | 同上 |
| `n10\|n21` | 同上 `[3]` | 同上 |
| `n05\|n13` | 同上 `[4]` | 同上 |
| 一条 3 元摘要 | `conflicts/duplicates` 之外 | 归组 |

⇒ **它的 5 个「假对」全是它自己否掉的候选**，剩下 1 个是归组。**被断言为假的对：0 条。** `fp=6` 全部来自「它把考虑过的候选写下来了」。

### 2.3 每篇笔记的台账 = 每篇一条 fp

`s-demand r0/r1` 的产物有一节 **40 篇笔记的逐篇台账**：

```json
{"note":"n01","lineCount":5,"duplicateGroups":{"D1":[5]},"singletons":[1,2,3,4]}
```

判据把每个这样的对象读成「提到 1 份笔记的条目」⇒ **一元 fp**。两轮分别是 40 / 43 条一元 fp，`fp_容器` 63 / 65 ⇒ **63%–66% 的 fp 是台账**，与「判错」无关。

## 3. 机制：为什么「写清楚」会被记成错

### 3.1 判据读的是叶子，不是你的意思

`notesTask.parseFindings` 的规则（冻结，`notesTask.ts:371-418`）：

1. 把产物里**每个对象**当一个候选条目；
2. 递归收集它的**全部叶子**：任何 `n\d\d` 进笔记集合，任何 ≥6 字 CJK 进引文，任何 1–8 的整数进行号；
3. 只要这个对象提到了 ≥1 篇笔记，就产出一个条目；
4. `judge` 对「笔记数 ≠ 2」的条目**直接 `fp++`**（`notesTask.ts:467`）。

★★ 于是：**一个对象的含义（是不是断言）完全不进判据；只有它提到了几篇笔记进判据。** 「n01 这一篇有 5 行、其中第 5 行配过对」在语义上是一个台账，在判据里是「一条提到 n01 的 claim ⇒ fp」。

### 3.2 三个具体的触发源

| 触发源 | 例子（实测） | 判据怎么读 |
|---|---|---|
| **元数据里的文件名模式** | `"file_pattern": "n01.md ... n40.md"` | 一个提到 n01 与 n40 的对象 ⇒ **fp `n01\|n40`** |
| **逐篇台账/未配对清单** | `{"note":"n01","lineCount":5,…}` | 一元条目 ⇒ **fp +1/篇** |
| **「我查过、不是」的候选** | `verification.near_miss_examples_not_counted[0..4]` | 二元表外对 ⇒ **fp +1/条** |

★ `n01|n40` 这个「假对」在 R3 的 6 个臂里都出现过——它不是模型报的关系，**是每份报告都写的语料文件名范围**。这类 fp 在任何「有 source/meta 段」的报告里都会出现，且与内容无关。

### 3.3 重复的不对称

判据对真对去重、对假对不去重（`judge`：`if (seen.has(k)) { details.push; continue; }` 在真值分支里；假对分支每次 `fp++`）：

- 同一对真关系写两遍 ⇒ 只算一次 TP；
- 同一个假关系写两遍（一处断言、一处「我否定它」）⇒ **算两次 fp**。

⇒ 报告越爱解释，**假对越被重复计费，真对不会**。这是 `fp` 作为「质量分」的又一处系统性偏置。

### 3.4 为什么拆成两个工人更脏

`two-selfcount` 把「数」和「枚举」拆给两个 agent。它的 `fp` 均值 16.8，是 `s-selfcount`（2.8）的 6 倍，成本 263k 是 98k 的 2.7 倍，而关系级命中一样（都是 11/12）。

原因不是「第二个工人更差」，是**第二个工人多写了两节**：工人①的 `count.json` 进了 cwd，工人②在报告里加了 `unpaired_notes`（16 条）和「近失候选」清单。数字传过去了，**台账也跟着长出来了**。

依据：`work/practice/notesTask.ts:371-418`、`:453-500`、`work/practice/_dbg-rej.ts`、`work/practice/_dbg-one-note.ts`、`work/practice/runs/site3/two-selfcount_r*/report.json`

## 4. 这一批里唯一赢的配方：先自己数，再按数逐条列

★ 把「找到」和「fp」分开看，`s-selfcount` 是唯一三项都好的臂：

| | 关系级命中 | `fp_容器` 均值 | 关系级表外 | token 均值 |
|---|---|---|---|---|
| `s-selfcount`（1 agent：先数 → 按数枚举） | **11.0/12**（3/4 轮满） | **2.8** | **0.75** | **98k** |
| `two-selfcount`（2 agent：数 / 枚举） | 11.0/12 | 16.8 | 0 | 263k |
| `s-count0`（人给数 + 操作点） | 8.5/12 | 14.8 | 2.75 | 80k |
| `s-demand`（只给操作点） | 9.5/12 | 77.5 | 7.5 | 181k |
| `s-anchor`（只给格式） | 10.5/12 | 58.3 | 8.75 | 329k |

★★ **机制（为什么是它）：** 那句提示让它先产生一个**自己可数的 N**（报告的 meta 里写 12），然后把 N 当**停止规则**用——列到 12 条就停。停止规则直接抑制了「台账」和「近失候选」这两节；没有台账，①③ 类 fp 就没有了。**它赢不是因为「先数」让它更会找关系（关系级命中与 two-selfcount 持平），而是因为「按数停」让它少写了不承载断言的东西。**

★ 这条与第七章的「数量承重」不是同一条：
- 第七章量的是**人给的数**（`d-count` 4/4）；
- 这里量的是**集群自己出的数**，而且它与「两工人」版本分开后，**单 agent 版本更好**（98k vs 263k，fp 2.8 vs 16.8）；
- 这里还量到：**加「一条都不能少，也不许多报」但不给数（`s-demand`）反而更贵更脏**（181k、fp 77.5）——操作点句本身不压 fp，它让模型去枚举并否定，而否定被记成断言。

★ **这不是「数字万能」**：`s-count16`（数错 33%）的关系级命中 10.75，并不比 `s-count0` 差多少，但它的 `reportedPairs` 中位是 17（≈ 它拿到的 16，而不是真值 12）⇒ **数字被当成了输出配额**。数错了，它就按错的数写满；它不会自己纠正。

依据：`work/practice/runs/site3/s-selfcount_r*/report.json`（meta `total_pairs:12`）、`work/practice/runner-r3.ts`、`work/practice/_hit2.ts`、`work/practice/R3-PREREG.md §1/§2`（P1a–P1c、P3、P4）

## 5. 为什么修它不要钱（以及为什么「不要钱」不等于白拿）

### 5.1 三种 0-token 修法

| 修法 | 动什么 | 要不要重跑 | 代价 |
|---|---|---|---|
| **改 schema**：禁止台账/元数据里写 note id；「我查过、不是」放进判据忽略的容器（或明确标注 `rejected`） | 提示词 | ★ 要重跑（形状变了，产物变了） | `solo-fmt` 型：中位 96k/轮 |
| **改判据**：按 pair 去重、只读「关系容器」、对 `rejected/near_miss` 读极性 | 代码（0 API） | ★ 不要重跑 | **要重读所有旧读数**（本章 §2 的数会全变） |
| **加装配**：`assemble()` 只保留 2 元 + 引文可唯一定位的条目，去掉其余 | 代码（0 API） | 不要重跑 | 会丢真内容（引文不唯一时），要记 `dropped` |

★ R2 的 `split`/`d-count` 就是用第三种：**工人原始产物被 `assemble()` 正规化后再判**。我核过 `site2/split_r0`：最终报告 19 条全是 2 元，`fp_容器 = fp_关系 = 7`；`d-count` 12 条全 2 元，fp 0。⇒ **R2 的 4/4 是真的（关系级 0 假对），但它是在「装配后的产物」上成立的。** 拿它和 R3 的原始散文报告比 fp，是比了两种装置（见 §6.4）。

### 5.2 写台账本身有 token 价

| 臂 | token 中位 | token 均值 | 一元 fp（4 轮合计） |
|---|---|---|---|
| `split-data`（无台账） | 78k | 85k | 0 |
| `s-count0` | 82k | 80k | 15 |
| `s-selfcount`（无台账） | 85k | 98k | 0 |
| `s-demand`（40 篇台账） | 164k | 181k | 209 |
| `s-anchor`（逐篇观察） | 189k | **329k** | 118 |
| `two-selfcount`（未配对清单） | 196k | 263k | 24 |

## 6. 边界：这一章在哪儿不成立

### 6.1 人读时，形状税趋近 0
台账和「我查过、不是」对人是**加分项**（它把候选空间交给你）。本章所有「写清楚更差」的结论，只在**代码判据按条目读**时成立。第五章 §2.3-4 已经写过同一条边界，这里是它的定量版。

### 6.2 谓词真为 N 元时，2 元判据是错的
本任务的谓词是二元的（重复/打架都是两两关系）。若你的谓词是「把这些笔记聚成几组」，那么 3 元/4 元条目**就是正确答案**，`fp` 会把正确判成错误。第五章 §2.3-1 的同一条边界。

### 6.3 本章的「关系级命中」也是读法，不是真值
`pairread` 的 `asserted` 靠容器名/措辞（`near_miss`、`不是`、`不算`…）判否定。它会把**该算的**漏进 `discussed`，也会把**没否定的**判成否定。我逐条核了 §2 的三个病例的原文，但 32 格没有逐条人工核。⇒ 关系级数字是**方向可信、逐格可能 ±1–2**。

### 6.4 跨批不能直接减
R2 的 `split`/`d-count`/`same` 是**装配后**的产物（只有 2 元条目）；R3 的 8 臂是**原始**产物（含台账）。两批的 `fp` 不是同一个量。本章只在 R3 内部做臂间比较；凡是跨批的，我在 §5.1 单独标了。

### 6.5 装置事故：32 格里有 10 格被同目录重跑污染
`quota.jsonl` 有 44 行（32 个 `(arm,rep)`，12 格跑了两次；其中 `two-selfcount r3` 是补跑）。我按「磁盘产物 + 该格最后一行」对齐，但**有 10 格两次运行的时间窗重叠**，而两次都 `rm -rf` 同一个 cwd —— 第二次的 `rmSync` 会在第一次还在跑时把它的文件删掉。这 10 格是：


**本章的病例全部取自干净的 r0/r1**；32 格的聚合数（§0 表）含这 10 格，读方向可以，读具体差值不行。

## 7. 附：同一批里的两个「恒真读数」——预测在跑之前就已经是真的

这一节不是 fp 的事，是**怎么判断一个读数有没有信息**。同一批里有两个读数，看着像结论，其实是装置的定义：

### 7.1 `split-data` 的 0/12 是结构决定的，不是能力

R3-PREREG §2 写：「语料里 8/12 对真关系跨两半，结构性上限 4/12」，预测 `split-data.matched ≤ 4/12`。

★ 我把 12 对真值按半区（①n01–n20、②n21–n40）逐对算了一遍：

```
12 对真值里，跨半区 = 12，落在同一半 = 0。
```

（12 对用到的 24 份笔记，恰好 12 份在 n01–n20、12 份在 n21–n40，**每一对都跨边界**。）
⇒ `split-data` 的结构上限是 **0/12**，不是 4/12。它的 0/12、以及 `fp 13–17`（全部是半区内的假对），**在 gate 拦掉另一半的那一刻就定了**；P5「成立」但不携带任何关于「按数据切会不会损失能力」的信息。

★ 这个臂仍然有用：它测的是**半区内假对的产量**（每轮 13–17 条，其中 2 条是冻结干扰对）。但它测不到它想测的那件事。

### 7.2 `κ2<1 ⇒ landing=0` 是判据的算术，不是 20 次观察

第五章 §2.1 把「κ2<1 的 20 个 run 落地 0 个」当经验证据。我在共识门里给它的反对理由是：`κ2` 与 `judge` 用的是**同一个** `parseFindings`；`judge` 对「笔记数 ≠ 2」的条目直接 `fp++`。于是对任意产物：

```
κ2 < 1 ⇔ 存在非 2 元条目 ⇔ fp ≥ 1 ⇔ landing = false
```

这是恒等式。`_count.ts` 的 `{low:20, lowLand:0, high:24, highLand:9}` 数是对的，但 20/0 这一半不携带信息；带信息的是 24/9 那一半。

### 7.3 跑之前怎么发现它：把「可达集」算出来

对任何一条预测 `metric(arm) ≤ b`，跑之前做一步：

```
把该臂允许的产物集合枚举/放缩到极端（最好/最坏），算 metric 的 min/max。
若 max ≤ b（或 min ≥ b），这条预测恒真 ⇒ 它不能判死任何东西。
```

- `split-data`：把 gate 允许的配对算一遍，`matched` 的 max = 0 ≤ 4 ⇒ 恒真。
- `κ2`：`fp==0` 要求所有条目都是 2 元 ⇒ `κ2==1`；反过来 `κ2<1` ⇒ `fp≥1` ⇒ 恒真。

★ 这个动作 0 token，只要读装置代码和语料；它能在**花钱之前**杀掉一条假预测。这是本批最便宜的一条教训。

依据：`work/practice/notesTask.ts:453-500`、`work/architect/kappa.ts`、`work/architect/_count.ts`、`work/practice/R3-PREREG.md §2`（P5）、`work/practice/runs/site3/split-data_r*/report.json`、`work/practice/runs/site3/notes/n*.md`

## 10. 这一章能判死什么、不能判死什么

**能判死：**
- 「A 臂比 B 臂精度高」而两者的**一元/三元份额**不同 ⇒ 这句话没说清比的是精度还是台账长度（§2.4：`s-demand` 63/65 里 40/43 是台账）；
- 「多写一点更透明，所以更好」在**代码判据**下是反的：`near_miss_examples_not_counted` 会让 `fp +5`、`landing` 由 true 变 false（§2.2）；
- 「按数据切会损失跨文件关系」用「0/12」当证据 ⇒ 若语料里所有真对都跨切面，这个 0 是结构定的，不是能力（§7.1）；
- 「κ2<1 一定不落地，20/20」当经验证据 ⇒ 同一解析器的恒等式（§7.2）。

**不能判死：**
- 哪个臂「更会找关系」：本批 8 个臂的关系级命中都在 8.5–11.5/12，n=4 分不开；
- 跨模型、跨任务族、真实规模；人读时的形状税；
- 下一批的「禁台账」是否真能把 `s-selfcount` 推到 12/12 + fp 0：那是推论，没测。

★ 留给下一批的一句可判死的话：**若把 `s-selfcount` 的 schema 改成「只许二元关系容器、禁止任何台账/meta 里的 note id」，`fp_容器` 应降到 0–1，而关系级命中不变（11–12/12）；若 fp 仍 ≥3，说明形状税的解释不完整。**
