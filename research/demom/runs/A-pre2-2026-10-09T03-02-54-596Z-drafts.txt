## scout 结论：T2 工具白名单

### 各材料核心结论（每条带编号）

- **M5**：白名单越宽，任务完成率越高——同一环境下把白名单从 3 个工具扩到 6 个，完成率从 40% 提到 90%。
- **M6**：环境自动发现的扩展，其注册的工具名**不会**并入 permissions.only（R41）；只有**显式声明**的扩展注册的工具会自动并入。
- **M9**：白名单越宽，任务完成率越低——同一任务上从 3 个工具扩到 6 个，完成率从 80% 掉到 55%（工具越多，模型越容易挑错路）。
- **M17**：permissions.only 是裁剪不是沙箱——名单外的工具连注册表都进不去，模型看都看不到；但被点名的高危工具照样能造成真破坏。「能看不能看」才是名单的活。
- **M18**：白名单是硬过滤，不是「提醒模型别用」——名单外的东西不会出现在模型的工具声明里，是「压根看不见」而非「知道但被拦」。
- **M26**：不写 permissions.only 意味着拿到 pi 的默认集（read / bash / edit / write），不是「没有工具」；要真的零工具，必须显式写 `only: []`。
- **M32**：三档语义同名不同义——创建期只有 only（精确）与 deny；运行期的 allow 才是**并集**（在这些之外再启用这些）。三档都 async、都要求空闲（要碰声明面走 reload）。
- **M33**：有报告称环境自动发现的扩展注册的工具**会**并入 permissions.only，并称实测通过——与 M6 的说法相反，记录备查。
- **M37**：白名单让工具**不可见**（硬过滤），门让调用**被拒绝**（看得见但被拦）；要防「它乱试」用前者，要教「为什么不行」用后者。

### 矛盾（成对写明）

1. **M5 vs M9**：M5 说「白名单越宽，任务完成率越高」（3→6 工具，40%→90%）；M9 说不——「白名单越宽，任务完成率越低」（3→6 工具，80%→55%）。同一类实验，结论直接相反。
2. **M6 vs M33**：M6 说环境自动发现的扩展**不并入**白名单（只有显式声明的扩展才并入）；M33 说有报告实测证明环境自动发现的扩展**会并入**白名单。两者直接对立。

### 重复（同一件事在多份材料里说过）

1. **M17 / M18 / M37** 三份都在说同一件事：名单外的工具对模型**不可见**（硬过滤），而不是「看得见但被拦」。M17：「连注册表都进不去，模型看都看不到」；M18：「不会出现在模型的工具声明里……压根看不见」；M37：「白名单让工具不可见」。
2. **M18 与 M37** 还重复了「硬过滤 ≠ 被拦」这一区分：M18「不是知道但被拦，而是压根看不见」；M37「不可见 vs 被拒绝……要防乱试用前者，要教为什么不行用后者」。
3. **M5 与 M9** 是同一实验主题（白名单宽度对任务完成率的影响）的两份材料，但结论相反（见矛盾 1）。

### 与 T1–T5 五个主题的关系

派活人已说明这 9 份全部围绕 T2；逐份核对后确认均与 T2（工具白名单的边界）相关，没有与 T1–T5 都无关的材料。

## scout 结论：T4 技能与扩展

### 各材料核心结论

**M10-技能是软约束，扩展是硬接线**
1. 技能是软约束：靠模型读了照做，不是代码强制；删掉技能文件脚本照样 exit 0，判据是模型行为变了。
2. 扩展是硬接线：在函数体里 registerTool / on 事件，删掉它注册的工具与钩子就真的消失了。
3. 两者在 spec 里都是精确白名单：不写=环境里的全给，写了=集合就是这些，[]=一个都没有。

**M22-技能按路径注入，按名注册没有意义**
1. skills.add 只接受路径或 Skill 对象；技能是被环境发现的，按名注册没有意义。
2. 运行期加的技能不经过白名单——白名单只裁环境自动发现的那部分。

**M23-技能与扩展共用一个环境目录**
1. skills/ 与 extensions/ 走 pi 的自动发现：目录里放着就生效，不需要写进 createAgent 的 spec。
2. 想核对实际加载到了什么，用 lab.inspectEnv()，别靠猜。

**M27-技能是可靠的约束手段**
1. 技能是可靠的约束手段：写好一份 SKILL.md，模型会照着做，行为可复现。
2. 对需要稳定输出格式的任务，用技能就够了，不必上代码强制。

**M36-扩展加载失败必须可读**
1. 扩展加载失败在 v1 里是零信号的静默失败点之一，所以 extensions.errors() 必须可读。
2. 两种错误不同：加载失败是 {path, error}，运行期钩子异常是 {extensionPath, event, error}。

**M39-技能基本不起作用**
1. 技能经常不起作用：模型有时候读有时候不读，同一个 SKILL.md 在不同轮次效果不一致。
2. 删掉它脚本照样 exit 0（软约束），所以它不构成任何保证。

### 矛盾（成对）

1. **M27 vs M39（直接对立，核心矛盾）**：M27 说「技能是可靠的约束手段，模型会照着做，行为可复现」；M39 说「技能基本不起作用，同一个 SKILL.md 在不同轮次效果不一致，不构成任何保证」。对「技能是否可靠」给出相反结论。
2. **M10 vs M27（定性张力）**：M10 把技能定性为「软约束」（靠模型照做、非代码强制）；M27 称其为「可靠的约束手段」。两者都同意「不必上代码强制」，但对技能可靠性的定性不同。
3. **M10 vs M22（白名单范围张力）**：M10 说 spec 白名单是「精确白名单」（写了=集合就是这些）；M22 说白名单只裁环境自动发现的那部分，运行期加的技能不经过白名单——即白名单并不能完全决定最终环境。

### 重复

1. **M10 与 M39** 都提到「删掉技能文件，脚本照样 exit 0」这一事实（用法不同：M10 用它定义软约束，M39 用它论证技能不构成保证）。
2. **M22 与 M23** 都讲「技能/扩展由环境自动发现」：M22 说技能被环境发现、按名注册无意义；M23 说 skills/ 与 extensions/ 走 pi 自动发现、目录里放着就生效。
3. **M10、M22、M23** 三份都涉及白名单/加载机制，但角度不同（M10 讲 spec 白名单语义，M22 讲白名单只裁自动发现部分，M23 讲自动发现本身），并非简单重复。

### 与 T1–T5 的关系

六份材料都围绕 T4（技能与扩展的区别），没有与五个主题都无关的材料。M36 虽讲扩展加载失败，但仍属 T4 范畴（扩展的加载与错误处理）。

## scout 结论：T3 审批门

### 各材料核心结论（每条带材料编号）

**M8（审批门拦的是动作不是人）**
1. 审批门拦的是动作（某一次调用），不是人。
2. permissions.gate 是同步单槽位：后设的覆盖先设的，没有读回来的机会，所以判定逻辑要一次写清。
3. 返回 {block: true, reason} 挡下这次调用，reason 会作为工具结果回到模型面前——写清「为什么」远比单纯拒绝有用；门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里。

**M16（门应该拦得尽可能严）**
1. 门判定逻辑应尽量保守，宁可拦错不可放过。
2. 凡是看不懂的调用一律挡下，让模型换一种写法，以最大程度避免破坏性操作。

**M20（门是单槽位，没有读回来的机会）**
1. permissions.gate 只写不读：后一次调用覆盖前一次。
2. 判定逻辑要一次写清，不能指望「先设一个粗糙的、之后再读回来细化」。
3. 这个限制逼着你把规则想清楚。

**M25（被拦下的调用不会出现在监听器里）**
1. 门排在 on("tool_call") 之前。
2. 被门挡下的调用不会出现在监听记录里。
3. 审计时要注意：监听记录里没有的调用，可能不是没发生，而是被门拦了。

**M28（门拦得太严会误事）**
1. 门判定逻辑设得太保守时，agent 大量正确的调用被误拦。
2. agent 反复重试、上下文被拒绝理由填满，任务完成率反而下降。
3. 过度保守的门是伪安全——拦的是自己的效率。

**M29（门的 reason 要写给模型看）**
1. block 返回的 reason 不是日志，它会作为工具结果回到模型面前。
2. 写「为什么不行」比写「不允许」有用得多——模型能根据理由换一条路。
3. 给不出理由的拒绝，等于让模型原地打转。

**M35（裁剪与拦截的分工）**
1. 问「能不能做」要靠门，问「能看不能看」才是名单的活。
2. 这两件事经常被混为一谈，但实现上完全不同：名单改的是工具集，门拦的是某一次调用。

**M37（硬过滤与「看得见但被拦」是两回事）**
1. 白名单让工具不可见，门让调用被拒绝——两者是两回事。
2. 前者模型连想的余地都没有，后者模型会看到一条明确的拒绝理由。
3. 要防「它乱试」用前者（白名单），要教「为什么不行」用后者（门）。

**M38（门不能读回来，所以要一次写清）**
1. 门是同步单槽位，不能读回来。
2. 实践中通常把判定写成一个纯函数：输入 {name, input}，输出 undefined 或 block。
3. 这样它可测、可读，不依赖任何累积状态。

### 矛盾（成对写明）

- **M16 vs M28（直接对立）**：M16 说门应该拦得尽可能严——判定逻辑尽量保守、宁可拦错不可放过、看不懂的一律挡下；M28 说门拦得太严会误事——大量正确调用被误拦、任务完成率反而下降，过度保守的门是伪安全。一个主张「越严越好」，一个主张「太严会误事」。
- **次要张力（非直接对立，但值得注意）**：M29 强调 reason 要写给模型看、给不出理由的拒绝会让模型原地打转；M28 指出拒绝理由填满上下文会拖垮效率。两者不矛盾但构成张力：reason 要写清楚，但拒绝本身不能太多。

### 重复（同一件事在多份材料里说过）

- 「门是单槽位、只写不读、没有读回来的机会、判定逻辑要一次写清」：**M8、M20、M38** 三份都在说。
- 「门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里」：**M8、M25**。
- 「reason 会作为工具结果回到模型面前，写清『为什么』比单纯拒绝有用」：**M8、M29**。
- 「门与名单/白名单的分工：门拦调用，名单改工具集/让工具不可见」：**M35、M37**。

### 与 T1–T5 五个主题都无关的材料

- 本批 9 份材料全部围绕 T3（审批门），没有与五个主题都无关的材料。

依据：M8、M16、M20、M25、M28、M29、M35、M37、M38

## scout 结论：T1 上下文预算

### 逐份核心结论（每条带材料编号）

- **M1**：① context.override 只改这一轮发到模型面前的消息，会话历史一条不动，可逐轮收紧而不丢证据；② override 比压缩便宜且更可预测，因为裁剪规则由设计者写死、不需要模型参与；③ 要按整轮裁——只删 toolResult 却留下带工具调用的 assistant，pi 会把工具结果补回来。
- **M2**：① context.usage 读当前上下文占用；② history 与 RunResult.messages 是同一视角，都不含 system（system 是会话级、每轮由 pi 重建）；③ 要看会话原样得走 context.raw.session.messages。
- **M3**：① 压缩（compact）会真的动历史，且首行就是 abort()，运行中调用会静默打断在飞那轮；② 逐轮裁剪成本低得多——什么历史都不改，只是这一轮少发几条。
- **M4**：① 裁历史分三层：override 改本轮（一次性、下一轮消失、历史分毫未动）／replace、erase 改历史（append-only、永久生效）／reset() 整段重置；② reset() 逐条抹除、仍是同一个 agent，不可编辑条目（system／压缩摘要）进返回值的 skipped。
- **M7**：① 逐轮裁剪不改任何历史、只在发出去那一刻少带几条，比压缩便宜且不需要模型参与决策；② 压缩是不可逆的历史改写。
- **M15**：① context.autoCompact 默认开着，上下文快满时自动压缩，短会话看不出区别、长会话才触发；② 关掉它意味着自己管预算，适合「上下文由 override 精确控制」的 agent。
- **M19**：① 想知道占了多少读 context.usage；② 想看清楚发了什么读 history，但它和 RunResult.messages 一样都不含 system，别拿它数总长度，会少算。
- **M30**：① 设计文档明确：上下文是本研究方向比较关注的东西，功能必须提供足够的操控能力；② 操控能力简单分为读（获取当前 agent 的上下文）和改写（直接赋予 agent 上下文）两类。
- **M34**：① 子 agent 也会拿到派活工具，递归是真实可能的；② 兜底手段通常是计数器：深度到顶就拒绝并回一句拒绝理由，而不是抛错——抛错会打断整轮。
- **M40**：① extensions 白名单里永远有一个例外：库自己的桥接扩展（工具表／事件接线／审批门都靠它），任何白名单都裁不掉；② inspectEnv 输出里的 `<inline:1>` 就是它。

### 矛盾

**未发现矛盾。** 逐份核对后，各材料对同一件事的表述方向一致，没有「A 说 X、B 说不 X」的对立：

- 「裁剪 vs 压缩谁更省」：M1、M3、M7 三份一致说逐轮裁剪更便宜／压缩更贵，无相反结论。
- 「history 是否含 system」：M2、M19 一致说不含，无相反结论。
- 「override 是否只改本轮」：M1、M4 一致，无相反结论。
- M15（autoCompact 默认开）、M34（递归兜底用计数器）、M40（桥接扩展裁不掉）均为独有信息，与其他材料无冲突。

### 重复

1. **「逐轮裁剪比压缩便宜／划算，因为不改历史、不需要模型参与」**——M1、M3、M7 三份重复；其中 M1 与 M7 措辞几乎相同（「比压缩便宜」「不需要模型参与」）。
2. **「history 与 RunResult.messages 是同一视角、都不含 system」**——M2、M19 重复；M19 额外加了「别拿它数总长度会少算」的推论。
3. **「override 只改本轮、历史不动」**——M1、M4 重复；M4 更完整（给出 override／replace／reset 三层）。
4. **「裁剪规则由设计者写死／不需要模型参与决策」**——M1、M7 重复。

依据：M1、M2、M3、M4、M7、M15、M19、M30、M34、M40

## scout 结论：T5 多 agent 分工

### 一、各材料核心结论

**M12-分工：花名册 vs 无花名册**
- 给 agent 花名册（成员表），它只能从中挑人；不给花名册，它按 role 任意字符串起人。
- 花名册约束强但可能不够用；无花名册灵活但可能起出重复的、职责重叠的分身。
- 这是使用者代码的选择，库里没有花名册概念。

**M13-分工：委派的深度护栏**
- 子 agent 也能拿到派遣工具，递归真的可能发生。
- 深度计数器是使用者代码，库里没有 maxDepth 这种东西。
- 没有护栏的集群会一直派活；护栏加在哪一层（深度 / 人数 / 预算）会直接改变结果，是个设计决定不是实现细节。

**M14-把控权留在使用者手里**
- 库提供机制，使用者提供政策：花名册、委派、红线都是使用者代码。
- 想让 agent 拥有哪种集群形态，是设计者代码的事，不是库的字段——因为这些假设必须可被替换、可被度量，不能焊死在库里。

**M24-最多几层只能自己数**
- 库不给护栏，「最多几层」只能自己数。
- 一个 MAX_DEPTH 常量加一次比较就能拦住无限递归。
- 但要记住拦在哪一层，结果就不一样。

**M31-成员表能约束行为**
- 预定义成员（一张名单）能约束 agent 的行为——agent 只能从名单里挑人，挑不到就拒绝。
- 检验方式：删掉名单、让 role 接受任意字符串，跑同一个任务对比结果。
- 材料自述是「同一件事的另一处论述」（即与 M12 同题）。

**M34-递归的风险与兜底**
- 子 agent 也会拿到派活工具，递归是真实可能的。
- 兜底手段通常是一个计数器：深度到顶就拒绝并回一句拒绝理由，而不是抛错——抛错会打断整轮。

**M42-群必须告诉成员「为什么要成群」**
- 如果集群的协调者不知道「不分工的后果」，它倾向于自己干完——尤其任务看起来不大的时候。
- 要让它真的分工，得让它看见约束：上下文有上限、时间有预算、或者活本身大到一个人做不完。
- 光给一个 spawn 工具，不等于它会用。

**M43-集群与工作流是两种形态，不是一个连续谱**
- 集群 = 运行时决定谁做什么；工作流 = 设计时就把边画好。
- 两者的差别不在自由度大小上，而在「图是什么时候产生的」：一个运行时长出来，一个设计时就画好。
- 所以两者的成本与失败模式也不同。

**M44-工作流的代价是预判**
- 固定流程的代价是它必须预判任务需要几步。
- 预判准了就高效，预判错了就浪费——浪费的形式是：要么人手不够（阶段太少），要么空转（阶段太多）。
- 集群没有这个问题，但它要付出协调成本。

### 二、矛盾分析

- **未发现针锋相对的硬矛盾**：9 份材料对同一件事的结论方向一致，没有「A 说 X、B 说不 X」的直接冲突。
- **最接近的一对张力（侧重不同，非相反结论）**：M13 说护栏加在哪一层（深度/人数/预算）「是个设计决定不是实现细节」，M24 说「一个 MAX_DEPTH 常量加一次比较就能拦住无限递归」，语气上把实现说轻了；但 M24 自己也承认「拦在哪一层，结果就不一样」，两者核心结论一致，只是 M13 强调设计选择、M24 强调实现简单。
- 另一处侧重差异：M12 指出花名册「约束强但可能不够用」，M31 只讲约束行为的正面效果——但 M31 自述是 M12「同一件事的另一处论述」，属重复而非矛盾。

### 三、重复分析

- **M12 ≈ M31**：花名册/成员表能约束 agent 挑人行为（M31 明确自称是 M12 同一件事的另一处论述；M12 侧重「不够用」的代价，M31 给出检验方式）。
- **M13 ≈ M34**：子 agent 拿到派遣工具 → 递归真实可能 → 需要计数器兜底（M34 补充「拒绝并回理由，而不是抛错，抛错会打断整轮」）。
- **M13 ≈ M24**：库没有护栏，深度计数器要使用者自己加（M24 具体化为 MAX_DEPTH 常量 + 一次比较）。
- **M12 ≈ M14**：花名册是使用者代码/政策，库里没有花名册概念（M14 把它泛化为「库提供机制、使用者提供政策」的一般原则）。
- **M43 ≈ M44**：集群与工作流的成本/失败模式不同（M43 给「图何时产生」的判据，M44 是它的具体化：工作流代价=预判，预判错的浪费形式是人手不够或空转；集群代价=协调成本）。

### 四、补充观察（与 T5 相关但非重复）

- M42 与 M13/M34 描述的是两种不同方向的失败模式：M42 是「不分工」（协调者自己干完），M13/M34 是「过度分工/无限递归」——两者互补，不矛盾。
