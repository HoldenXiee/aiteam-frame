# 实验室 A：agent 自由集群

> **状态：设计草稿，等你审。** 一行代码还没写。
> 这份要回答一个问题：**为了完成任务 T，我为什么把它设计成一个「自由集群」这个形状？**
> 审这份的目的不是看它写得对不对，是确认**它是这个形态下为 T 专门设计的好解法**——
> 不然跑出来的差异归因不到形态上（主设计 §6 风险 1）。

---

## 0. 一句话

**没有一个 agent 知道全局有几步。** 每个 agent 手里有三样东西：派活的口、交片段的筐、一张花名册。
谁派给谁、派几次、要不要并行、什么时候停 —— 全部由模型在运行时决定。代码里**没有任何一步叫「第 1 步」**。

对照实验室 B（固定流程）：B 的每一步跑之前就在纸上画得出来，A 的画不出来。

---

## 1. 为什么「自由」不是为了自由而自由

任务 T 里有**两处事先不知道要分几步**的地方，这就是自由存在的理由：

1. **有几处矛盾、分别在哪** —— 不读完材料不知道。B 只能在流程里插一个「查矛盾」阶段，A 可以读着读着觉得「这块有蹊跷，我派个人专门去核」。
2. **去重有多难** —— 材料里重复是明写的还是绕着说的，决定要多细的比对。B 的「去重」阶段是固定一次，A 可以决定要不要再派一轮。

**如果任务里没有这两处，自由集群就没有存在理由**，那 A 会退化成一个更贵更乱的 B。这句话是 A 的设计前提，也是 §6 风险 2 的来源——如果预跑发现「5 个主题各自独立、去重一眼可见」，那要改的是**任务**，不是 A 的设计。

---

## 2. 花名册：有哪些角色可选

**设计决定**：给 4 个角色。**不是**「每个主题一个 agent」（那是 B 的切法，等于把流程偷偷塞进花名册）。

| 角色 | 干什么 | 工具集 | 为什么需要它 |
|---|---|---|---|
| `scout` | 读材料，报告「哪几份在讲同一件事 / 哪几份对不上 / 哪几份与主题无关」 | `read` + 花名册材料清单 | 对应 T 的 ②③（去重、矛盾）——**这是必须先做完才知道要做什么的一步** |
| `analyst` | 针对**一个**主题，从被指认的材料里提炼依据 | `read` + `note` | 对应 ①④（覆盖、标 id）。**按主题派，派几个由模型定** |
| `checker` | 拿成品逐条核：id 编没编、重复有没有漏、矛盾有没有成对 | `read`（**只读**） | 对应产物判据本身。**给它只读权**，它没法「顺手改一下」 |
| `writer` | 把上游片段拼成 `report.md` | `read` + `write` + `note` | 只有它能落盘 |

**关键设计**：`scout` 和 `checker` 的存在，就是任务 T 里那两处「不知道要分几步」的兑现。
模型如果够聪明，它自己会发现「我得先摸清楚再分配」；发现不了，就会直接派 analyst 硬写 —— **那正是我们要观测的自由度的代价**，不是 bug。

**花名册本身是使用者代码**（`Map`，见 `examples/09-roster.ts`），库里没有这个概念。

---

## 3. `spawn`：派活的口

一个工具，`spawn(role, task)`：

- `role` **必须在花名册里**，不在 → 拒绝并回一份可选清单（这是 `examples/09-roster.ts` 那一行查表）；
- 起一个真 agent（`lab.createAgent`），`await io.prompt(task)`，把子 agent 的**文本**当工具结果返回；
- 子 agent 也拿到 `spawn` → **递归真的可能发生**，所以护栏不是摆设。

**设计决定：允不允许并行？**
`spawn` 是同步 `await` 的，所以模型连发三次 `spawn` 看起来是串行的。**这是故意的**——并行要模型自己用「一次 spawn 派多个 analyst」来换（task 里写「同时分析主题 1、2、3」），
要不要这么干是它的判断。**这个决定会让 A 慢**，如实记录，不替它优化。

---

## 4. 终止条件：护栏（A 唯一的硬骨头）

**问题**：没有终止条件的集群会一直派活。

**设计决定（需要你点头）**：**按 token 预算，超限后允许已派出的活收尾。**

- 预算记在闭包里，每次 `spawn` 前检查 `累计 tokens`；
- 超限 → **拒绝新的 spawn**，理由回给模型（「预算用完了，就现有材料收尾」）；
- 已经派出去的 agent **跑完**，不打断。

**为什么是这三个选项里的这个**：

| 方案 | 为什么没选 |
|---|---|
| 数深度（`MAX_DEPTH`，如 `10-spawn.ts`） | 深度跟「花多少钱」没关系。一个 agent 可以很浅但很贵 |
| 数 agent 总数 | 同上，而且 5 个 scout 和 5 个 analyst 代价完全不同 |
| **数钱** | ✅ 这才是真实约束。人管团队就是按预算管的 |
| 硬停在半路 | 会把 A 的成绩压低成「产物残缺」，而那反映的是**我的打断**，不是它的能力。允许收尾更干净 |

**这条直接决定 A 的成绩，所以必须你点头。** 换个选法 A 的数字会变，实验结论跟着变。

---

## 5. 工具集为什么是「给多少」的问题

花名册每个角色都有明确的工具集（§2 的表）。这里有个陷阱要挑明：

**给大了 = 自由是假的**（模型想干什么都行，谈不上委派）；
**给小了 = 变相流程**（每个角色能做的事窄到只有一种，等于写死了边）。

我的落点是：**只有 `writer` 能 `write`，`checker` 只读**，其余靠 `note`（把片段记进一个共享的中间文件）。
这样「谁干活、干到哪一步」是模型排的，但「谁能落盘」是设计者卡的 —— 这是**有意的偏置**，写进 README 认账。

---

## 6. 中间产物怎么传（与 B 必须一致）

**走文件**：`work/draft/<角色>-<序号>.md`，`note` 工具往里追加。

理由：可查、可复核、能进 `runs/` 当证据、更接近真工作流。
**代价**：两边都多一层读写成本 —— B 也必须同样走文件，不然又是一条没被控制的变量。

## 8. 这个设计可能的毛病（先认账）

1. **`scout` 是半个流程。** 我把它放进花名册，等于已经告诉模型「你得先摸底」。这是设计者的手伸进了它的决策。**要检验**：把 `scout` 从花名册拿掉再跑一次——模型会不会自己派一个「摸底」的活？（拿掉算 A′，属可选实验）
2. **预算是硬的，B 没有对应约束。** B 阶段数写死，天然不会失控。严格说这是**形态自带的差别**，不算不公平 —— 但要在结论里写明「A 的成绩含预算闸的影响」。
3. **4 个角色是我拍的**，没有依据。预跑后可能要调。

## 10. 两轮预跑后的修订（措施 1 + 2）

**第一轮预跑（14 份材料）的结果推翻了 A 的前提**：root 起了 **1 个 agent、delegations=0** ——
它选择一个人干完。这不是模型偷懒，是**任务对它太小**：14 份材料一个 agent 完全 hold 得住。
按主设计 §6 风险 2，这属于「任务没分辨力」，所以做了两处修订：

**措施 1 —— 语料从 14 份扩到 44 份**（`bench/corpus.ts`）。
重复组 1→5、矛盾组 1→4、干扰 1→3。理由：单 agent 的上下文预算是硬的 ——
44 份全读一遍接近窗口上限，它**必须**开始取舍，而取舍正是派活的动机。

**措施 2 —— root 的 role 加一句硬约束**（`run.ts`）：「材料很多，单靠自己读完会超出上下文上限，
所以你必须用 spawn 把材料分给不同角色」。它只说**不分工的后果**，不给步骤 —— 怎么分仍是它自己定。

> ⚠️ **这条只说给 A，B 没有**（B 本来就分工，不需要劝）。这是**没被控制的变量**，
> 必须在结论里认账：A 的 role 比 B 多了一句。辩护理由：集群形态**固有地**需要告诉成员「为什么要成群」——
> 光给一个 spawn 工具不等于它会用（语料里的 M42 就是这个观察）。但这是辩护，不是等价。

**预跑验证的判据**（达不到就不进入正式跑）：A 的 `delegations >= 1` 且 `agentCount >= 2`。
