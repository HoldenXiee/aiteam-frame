# 侦察报告：T1「上下文预算怎么裁」

## 一、核心结论（逐份）

- **M1**：context.override 只改「这一轮发出去的消息」，会话历史一条不动，因此可逐轮收紧而不丢证据；比压缩便宜且可预测（规则由设计者写死，不需模型参与）。注意要按整轮裁——只删 toolResult 却留下带工具调用的 assistant，pi 会把工具结果补回来。
- **M2**：context.usage 给出当前上下文占用；history 与 RunResult.messages 是同一视角，都不含 system（system 是会话级、每轮由 pi 重建）；要看会话原样得走 context.raw.session.messages。
- **M3**：压缩（compact）会真的动历史，且首行就是 abort()，运行中调用会静默打断在飞那轮；逐轮裁剪不改历史、只是这一轮少发几条，成本低得多。
- **M4**：裁历史的三层——override 改本轮（一次性，下一轮消失，历史分毫未动）；replace/erase 改历史（append-only，永久生效）；整段重置用 reset()（逐条抹除、仍是同一个 agent，不可编辑条目如 system/压缩摘要进返回值的 skipped）。
- **M7**：逐轮裁剪不改任何历史、只在发出那一刻少带几条，比压缩便宜且不需模型参与决策；压缩是不可逆的历史改写。
- **M15**：context.autoCompact 默认开着，上下文快满时自动压缩；短会话看不出区别，长会话才触发。关掉它意味着自己管预算，适合「上下文由 override 精确控制」的 agent。
- **M19**：读占用用 context.usage；看发了什么用 history——但它和 RunResult.messages 一样不含 system，别拿它数总长度，会少算。
- **M30**：设计文档明确「上下文是本研究方向比较关注的一个东西」，功能必须提供足够操控能力；简单分就是「获取当前 agent 的上下文」（读）与「直接赋予 agent 的上下文」（改写）。
- **M34**：子 agent 也会拿到派活工具，递归是真实可能的；兜底手段通常是计数器——深度到顶就拒绝并回一句拒绝理由，而不是抛错（抛错会打断整轮）。
- **M35**：问「能不能做」靠门，问「能看不能看」才是名单的活；两者常被混为一谈，但实现完全不同——名单改的是工具集，门拦的是某一次调用。
- **M40**：extensions 白名单永远有一个例外：库自己的桥接扩展（工具表/事件接线/审批门都靠它），任何白名单都裁不掉它；inspectEnv 输出里的 `<inline:1>` 就是它。

## 三、矛盾对（对同一件事给出相反结论）

## 核心结论

**M8 - 审批门拦的是动作不是人**
- permissions.gate 是同步单槽位，后设覆盖先设，没有读回来的机会，判定逻辑要一次写清
- 返回 {block: true, reason} 挡下调用，reason 会作为工具结果回到模型面前，写清「为什么」比单纯拒绝有用
- 门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里

**M16 - 门应该拦得尽可能严**
- 安全第一：门判定逻辑尽量保守，宁可拦错不可放过
- 看不懂的调用一律挡下，让模型换一种写法
- 最大程度避免破坏性操作

**M20 - 门是单槽位，没有读回来的机会**
- permissions.gate 只写不读，后一次调用覆盖前一次
- 判定逻辑要一次写清，不能指望先设粗糙的再读回来细化
- 这个限制逼着你把规则想清楚

**M25 - 被拦下的调用不会出现在监听器里**
- 门排在 on("tool_call") 之前
- 被门挡下的调用不会出现在监听记录里
- 审计时注意：监听记录里没有的调用，可能不是没发生，而是被门拦了

**M28 - 门拦得太严会误事**
- 实测教训：门判定逻辑设得太保守时，agent 大量正确的调用被误拦
- 反复重试、上下文被拒绝理由填满，任务完成率反而下降
- 过度保守的门是伪安全 —— 拦的是自己的效率

**M29 - 门的 reason 要写给模型看**
- block 返回的 reason 不是日志，会作为工具结果回到模型面前
- 写「为什么不行」比写「不允许」有用得多，模型能根据理由换一条路
- 给不出理由的拒绝，等于让模型原地打转

**M38 - 门不能读回来，所以要一次写清**
- 由于门是同步单槽位，实践中通常把判定写成一个纯函数：输入 {name, input}，输出 undefined 或 block
- 这样它可测、可读，不依赖任何累积状态

## 去重线索

1. **单槽位/一次写清**：M8、M20、M38 三份材料都提到 permissions.gate 是同步单槽位、只写不读、后设覆盖先设、判定逻辑要一次写清。M20 和 M38 都强调「不能读回来」这个限制，M8 和 M20 都提到「后设覆盖先设」。

2. **reason 要写给模型看**：M8 和 M29 都提到 reason 会作为工具结果回到模型面前，写清「为什么」比单纯拒绝有用。

3. **被拦下的调用不会出现在监听器里**：M8 和 M25 都提到门排在监听器之前，被拦下的调用不会出现在监听记录里。

## 矛盾对

**M16 vs M28**：M16 说门应该拦得尽可能严（宁可拦错不可放过），M28 说门拦得太严会误事（过度保守的门是伪安全，拦的是自己的效率）。

# scout 摸底结论 —— T2：工具白名单的边界（M5、M6、M9、M17、M18、M26、M32、M33、M37）

## 核心结论（逐份）

- **M5**：白名单越宽，任务完成率越高——同一环境下把白名单从 3 个工具扩到 6 个，完成率从 40% 提到 90%。
- **M6**：环境自动发现的扩展，其注册的工具名不会并入 permissions.only（R41）；白名单是「精确就是这些」的硬过滤。但显式声明的扩展注册的工具会自动并入。
- **M9**：白名单越宽，任务完成率越低——同一任务上从 3 个工具扩到 6 个，完成率从 80% 掉到 55%；工具越多模型越容易挑错路。
- **M17**：白名单是裁剪不是沙箱：名单外的工具连注册表都进不去，模型看都看不到；但 pi 没有内置沙箱，被点名的高危工具照样能造成真破坏。「能看不能看」才是名单的活。
- **M18**：白名单是硬过滤，不是「提醒模型别用」——名单外的工具不会出现在模型的工具声明里，是「压根看不见」而非「知道但被拦」，看不见的东西它不会去想。
- **M26**：不写 permissions.only 意味着拿到 pi 的默认集（read / bash / edit / write），不是「没有工具」；要真的零工具必须显式写 only: []。容易踩的坑：以为不写就是不给。
- **M32**：三档语义同名不同义：创建期只有 only（精确）与 deny；运行期的 allow 才是并集（在这些之外再启用这些）。三档都 async、都要求空闲（要碰声明面走 reload）。
- **M33**：有报告称环境自动发现的扩展注册的工具会被并入 permissions.only，并称实测通过；这与另一处说法相反，记录备查（即 M6 的反例）。
- **M37**：白名单让工具**不可见**，门让调用**被拒绝**——前者模型连想的余地都没有，后者模型会看到一条明确的拒绝理由；要防「它乱试」用前者，要教「为什么不行」用后者。

依据：M5、M6、M9、M17、M18、M26、M32、M33、M37

## 去重线索（同一件事多处重复）

1. 「名单外工具是『看不见』而非『被拦』」在 **M17、M18、M37** 三处重复：M17 说名单外工具连注册表都进不去；M18 强调「压根看不见、不会去想」；M37 把两者总结为「不可见 vs 被拒绝」的分工。三者可合并为一条。
2. 「白名单从 3 个工具扩到 6 个的覆盖率实测」在 **M5 与 M9** 重复：同一实验范式、同一扩法，但两组数据方向相反（详见矛盾对）。
3. 「环境扩展是否并入 permissions.only」在 **M6 与 M33** 重复：同一主题，两种相反说法（详见矛盾对）。

依据：M17、M18、M37、M5、M9、M6、M33

## 矛盾对（对同一件事给出相反结论）

1. **M5 vs M9 —— 白名单越宽是否提高任务完成率**：M5 说从 3 扩到 6 个工具，完成率 40%→90%（越宽越高）；M9 说同口径下完成率 80%→55%（越宽越低）。两组实测结论完全相反。

依据：M5、M9、M6、M33

# T4 侦察结论：技能与扩展的区别（M10、M22、M23、M27、M36、M39）

## 核心结论（逐份）

**M10-技能是软约束，扩展是硬接线**
- 技能靠模型读了照做，非代码强制；删掉技能文件脚本照样 exit 0，判据是模型行为变了 → 软约束。
- 扩展在函数体里 registerTool / on 事件，删掉则工具与钩子真的消失 → 硬接线。
- 两者在 spec 里都是精确白名单：不写=全给，写了=集合就是这些，[]=一个都没有。

**M22-技能按路径注入，按名注册没有意义**
- skills.add 只接受路径或 Skill 对象；技能被环境按路径发现，按名注册无意义。
- 运行期加的技能不经过白名单——白名单只裁环境自动发现的那部分。

**M23-技能与扩展共用一个环境目录**
- skills/ 与 extensions/ 走 pi 自动发现：目录里放着就生效，无需写进 createAgent 的 spec。
- 核对实际加载内容用 lab.inspectEnv()，别靠猜。

**M27-技能是可靠的约束手段**
- 技能是可靠约束手段：写好 SKILL.md，模型照着做，行为可复现。
- 需要稳定输出格式的任务，用技能就够，不必上代码强制。

**M36-扩展加载失败必须可读**
- 扩展加载失败是 v1 里零信号的静默失败点之一，extensions.errors() 必须可读。
- 两种错误不同：加载失败 {path, error}；运行期钩子异常 {extensionPath, event, error}。

**M39-技能基本不起作用**
- 技能经常不起作用：模型有时读有时不读，同一 SKILL.md 不同轮次效果不一致。
- 删掉它脚本照样 exit 0（软约束）→ 不构成任何保证。

依据：M10、M22、M23、M27、M36、M39

## 去重线索（同一件事在多份材料里重复说）

1. **「删掉技能文件，脚本照样 exit 0」**：M10 与 M39 重复出现。M10 用它论证"软约束"，M39 用它论证"不构成保证"——同一现象被两份材料分别引用。
2. **技能的自动发现机制**：M22（按路径发现、按名注册无意义）与 M23（目录放着就生效、无需写进 spec）都在讲技能/扩展靠目录自动发现、按路径生效。
3. **白名单作用范围**：M10（spec 里精确白名单：不写=全给/写了=就是这些/[]=都没有）与 M22（白名单只裁环境自动发现的部分）在白名单语义上有重叠。
4. **「技能不可靠 vs 扩展可靠」的对比框架**：M10（软约束 vs 硬接线）与 M39（技能无保证）从技能侧、M36（扩展加载失败要可读）从扩展侧，都围绕"技能靠不住、扩展靠代码"这一对比展开。

依据：M10、M22、M23、M36、M39

## 矛盾对（两份材料对同一件事给出相反结论）

1. **M27 vs M39（核心矛盾）**：M27 说技能是可靠约束手段、行为可复现、用技能就够；M39 说技能基本不起作用、不同轮次效果不一致、不构成任何保证。对"技能是否可靠"给出相反结论。
2. **M27 vs M10（次要张力）**：M27 主张技能可靠到"不必上代码强制"；M10 定性技能只是"软约束"（非代码强制）。对"软约束是否等于可靠"存在张力——若软约束即无保证，则 M27 的"就够了"站不住。
3. 其余材料间为补充关系，无直接矛盾。

依据：M10、M27、M39
