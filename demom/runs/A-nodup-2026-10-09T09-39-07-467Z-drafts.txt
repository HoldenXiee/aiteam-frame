## T2 工具白名单 — 逐条核心主张 + 重复/矛盾标注

### 逐条核心主张
- **M5**：实测白名单从 3 个工具扩到 6 个，任务完成率从 40% 提到 90% —— 白名单越宽，完成率越高。
- **M6**：环境自动发现的扩展注册的工具名**不会**并入 permissions.only（R41）；但**显式声明**的扩展会自动并入。白名单是「精确就是这些」的硬过滤，不该被环境里碰巧存在的扩展悄悄撑开。
- **M9**：实测白名单从 3 个工具扩到 6 个，任务完成率从 80% 掉到 55% —— 白名单越宽，完成率越低，工具越多模型越容易挑错路。
- **M17**：permissions.only 是裁剪不是沙箱：名单外工具连注册表都进不去、模型看不到；但被点名的高危工具照样能造成真破坏，「能看不能看」才是名单的活。
- **M18**：白名单是硬过滤而非「提醒模型别用」：名单外工具不出现在模型的工具声明里，是「压根看不见」而非「知道但被拦」，看不见的东西它不会去想。
- **M26**：不写 permissions.only 会得到 pi 默认集（read / bash / edit / write），不是「没有工具」；真零工具必须显式写 `only: []`。
- **M32**：三档语义同名不同义：创建期只有 only（精确）与 deny；运行期的 allow 才是并集（在这些之外再启用这些）。三档都 async、都要求空闲（碰声明面走 reload）。
- **M33**：有报告称环境自动发现的扩展注册的工具**会**并入 permissions.only（实测通过），与另一处说法相反，记录备查。
- **M37**：白名单让工具**不可见**（模型连想的余地都没有），门让调用**被拒绝**（模型看到明确拒绝理由）；防「它乱试」用前者，教「为什么不行」用后者。
- **M40**：extensions 白名单永远裁不掉库自己的桥接扩展（工具表 / 事件接线 / 审批门都靠它），inspectEnv 输出里的 `<inline:1>` 就是它。

### 重复（同一主张的不同表述）
- **M17 ≈ M18**：都主张「白名单是硬过滤，名单外工具模型看不见」（M17「连注册表都进不去，模型看都看不到」；M18「压根看不见」）。
- **M18 ≈ M37**：都主张「硬过滤（不可见）」与「被拒绝（看得见但被拦）」是两回事，M37 是 M18 的再强调。
- （M17 的「能看不能看」与 M37 的「不可见」也部分重叠。）

### 矛盾（同一问题相反结论，成对指出）
- **M5 vs M9**：同一实验设计（白名单 3→6 个工具），M5 说完成率上升（40%→90%），M9 说完成率下降（80%→55%）—— 白名单宽度与完成率的关系结论相反。
- **M6 vs M33**：M6 说环境自动发现的扩展**不并入** permissions.only（R41），M33 说**会并入**（实测反例）—— 标题对立，内容确实对立。注意 M6 区分了「自动发现不并入 / 显式声明并入」，M33 未作此区分，矛盾点集中在「自动发现的扩展是否并入」。

### 例外（非严格矛盾，补充关系）
- **M17 vs M40**：M17 说白名单把工具裁到设计者点名的几个，M40 指出库自己的桥接扩展任何白名单都裁不掉 —— M40 是 M17 的例外。

依据：M5、M6、M9、M17、M18、M26、M32、M33、M37、M40

## T1 上下文预算（补）+ 无关材料核实

### 逐条核心主张
- **M15**（自动压缩的开关）：`context.autoCompact` 默认开着，上下文快满时自动压缩；短会话无感、长会话才触发。关掉它意味着自己管预算，适合「上下文由 override 精确控制」的 agent。
- **M19**（读上下文占用的两个视角）：想知道占了多少，读 `context.usage`；想看清发了什么，读 `history`——但 `history` 和 `RunResult.messages` 一样都不含 system，别拿它数总长度，会少算。
- **M30**（上下文是本研究方向最该操控的东西）：设计文档写明上下文是本研究方向最该操控的东西，其功能必须提供足够操控能力，简单分为「读」（获取当前 agent 上下文）与「改写」（直接赋予 agent 上下文）两类。
- **M34**（递归的风险与兜底）：子 agent 也会拿到派活工具，递归真实可能；兜底手段通常是计数器——深度到顶就拒绝并回一句拒绝理由，而不是抛错（抛错会打断整轮）。
- **M35**（裁剪与拦截的分工）：问「能不能做」要靠门，问「能看不能看」才是名单的活；两者常被混为一谈，但实现完全不同：名单改的是工具集，门拦的是某一次调用。

### 无关材料核实
- **M11**（本季度食堂菜单与轮值安排）：**无关**。内容为一周菜品表与楼层轮值安排，纯行政后勤事务。
- **M21**（办公楼消防演练通知）：**无关**。内容为消防演练时间、撤离路线与电梯停用安排，纯安全演练通知。
- **M41**（打印机耗材领用流程的更新）：**无关**。内容为硒鼓/纸张统一申领流程更新，纯行政采购流程。

### 重复标注
- **M19 ↔ M30**：同说「读上下文」这一操控入口。M30 把操控能力概括为「读 / 改写」两分，M19 具体给出「读」的两个视角（`context.usage` 看占用、`history` 看内容且不含 system），后者是前者的具体化，主张方向一致。
- **M15 ↔ M30**：同主张「上下文须可被主动管理」。M30 从设计目标讲上下文必须提供足够操控能力（读+改写），M15 从预算管理讲关掉自动压缩后就要自己管预算（override 精确控制），互为印证。

### 矛盾标注
- 在 M15、M19、M30、M34、M35 这 5 份相关材料中，**未发现对同一件事给出相反结论的成对材料**；各条主张方向一致、相互互补（例：M34 的「到顶拒绝并回理由、而非抛错」恰是 M35 门拦截某次调用的行为风格）。
- 3 份无关材料（M11、M21、M41）与主题材料之间也无矛盾——它们讨论的根本不是同一件事。

依据：M15、M19、M30、M34、M35、M11、M21、M41

## T3 审批门 — 逐条核心主张 + 重复/矛盾标注

### 逐条核心主张

- **M8**：审批门拦的是动作（调用）而不是人（用户/模型身份）。门是同步单槽位，后设覆盖先设，没有读回来的机会，所以判定逻辑要一次写清。返回 {block: true, reason} 挡下调用，reason 会作为工具结果回到模型面前。门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里。

- **M16**：门应该拦得尽可能严。安全第一的做法是门判定逻辑尽量保守，宁可拦错不可放过。凡是看不懂的调用一律挡下，让模型换一种写法。这样能最大程度避免破坏性操作。

- **M20**：门是单槽位，没有读回来的机会。permissions.gate 只写不读：后一次调用覆盖前一次。所以判定逻辑要一次写清，不能指望「先设一个粗糙的、之后再读回来细化」。这个限制逼着你把规则想清楚。

- **M25**：被拦下的调用不会出现在监听器里。门排在 on("tool_call") 之前。所以如果你既装了门又装了监听器，被门挡下的调用不会出现在监听记录里 —— 做审计时要注意这一点：监听记录里没有的调用，可能不是没发生，而是被门拦了。

- **M28**：门拦得太严会误事。实测教训：门判定逻辑设得太保守时，agent 大量正确的调用被误拦，它反复重试、上下文被拒绝理由填满，任务完成率反而下降。过度保守的门是伪安全 —— 拦的是自己的效率。

- **M29**：门的 reason 要写给模型看。block 返回的 reason 不是日志，它会作为工具结果回到模型面前。所以写「为什么不行」比写「不允许」有用得多 —— 模型能根据理由换一条路。给不出理由的拒绝，等于让模型原地打转。

- **M38**：门不能读回来，所以要一次写清。由于门是同步单槽位，实践中通常把判定写成一个纯函数：输入 {name, input}，输出 undefined 或 block。这样它可测、可读，不依赖任何累积状态。

### 重复标注

- **M8 与 M20**：都提到「门是同步单槽位，后设覆盖先设，没有读回来的机会，所以判定逻辑要一次写清」。

- **M8 与 M25**：都提到「门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里」。

- **M8 与 M29**：都提到「reason 会作为工具结果回到模型面前」。

- **M8 与 M38**：都提到「门不能读回来，所以要一次写清」。

- **M20 与 M38**：都提到「门是单槽位，没有读回来的机会，所以要一次写清」。

### 矛盾标注

- **M16 与 M28**：M16 说「门应该拦得尽可能严」「宁可拦错不可放过」「凡是看不懂的调用一律挡下」。M28 说「门拦得太严会误事」「门判定逻辑设得太保守时，agent 大量正确的调用被误拦」「过度保守的门是伪安全 —— 拦的是自己的效率」。

  **核实结论**：这两份材料看似对立，但**可以调和**。M16 强调的是安全原则（宁可拦错不可放过），M28 强调的是过度保守的负面后果（误拦导致效率下降）。关键在于「尽可能严」和「太严」的界限：M16 的「尽可能严」可理解为「在合理安全范围内的严格」，而 M28 的「太严」指的是「超出合理范围的过度保守」。两者在「门应该严，但不能太严；应该在安全和效率之间找到平衡」这一调和立场上是一致的。严格来说，M16 的「宁可拦错不可放过」与 M28 的「过度保守的门是伪安全」存在张力，但并非不可调和的矛盾。

## T1 上下文预算

**逐条核心主张：**

- **M1**（上下文预算：裁的是「这一轮发出去的」）：context.override 只改这一轮送到模型面前的消息，会话历史一条不动，可逐轮收紧而不丢证据；它比压缩便宜且更可预测，因为裁剪规则由设计者写死、不需要模型参与。附带提醒：要按整轮裁，只删 toolResult 会留下带工具调用的 assistant，pi 会把工具结果补回来。
- **M2**（上下文占用怎么读）：context.usage 给出当前上下文占用；history 与 RunResult.messages 是同一视角，都不含 system（system 是会话级的，每轮由 pi 重建）；要看会话原样得走 context.raw.session.messages。
- **M3**（压缩不如裁剪省）：压缩（compact）会真的动历史，且其首行就是 abort()，运行中调用会静默打断在飞的那一轮；逐轮裁剪成本低得多，因为它什么历史都不改，只是这一轮少发几条。
- **M4**（裁历史的三层：override / replace / reset）：override 改本轮（一次性，下一轮就消失，历史分毫未动）；replace、erase 改历史（append-only，永久生效）；整段重置用 reset()——逐条抹除、仍是同一个 agent，不可编辑条目（system / 压缩摘要）进返回值的 skipped。
- **M7**（为什么逐轮裁剪比压缩划算）：逐轮裁剪不改任何历史，只在发出去的那一刻少带几条，所以比压缩便宜、也不需要模型参与决策；压缩则是不可逆的历史改写。

**重复标注：**

- **M1 ≈ M7**：核心主张几乎同义——逐轮裁剪不改历史、比压缩便宜、不需要模型参与（M1 的「比压缩便宜……不需要模型参与」与 M7 的「比压缩便宜、也不需要模型参与决策」是同一取舍的两种说法，M7 标题即「换个说法」）。
- **M3 ≈ M7**：M3 的「逐轮裁剪……什么历史都不改，只是这一轮少发几条」与 M7 的「不改任何历史，只在发出去的那一刻少带几条」重复。
- **M1 ≈ M3**：两者都基于「裁剪不改历史 vs 压缩动历史」的同一对比展开（M1 说 override「会话历史一条不动」，M3 说压缩「会真的动历史」）。
- **M1 ≈ M4**：对 override 语义的描述重复——M1 的「只改这一轮……会话历史一条不动」与 M4 的「override 改本轮（一次性，下一轮就消失，历史分毫未动）」一致，M4 更详细（补充了 replace/erase/reset 层）。
- 综合：M1、M3、M7 三者在「逐轮裁剪优于压缩」这一论点上高度重复；M4 与 M1 在 override 语义上重复。M2 独立（讲 context.usage 的读法），与其余四份既不重复也不矛盾。

**矛盾标注：**

- 本组（M1、M2、M3、M4、M7）内部**未发现相反结论**。五份材料对「override 只改本轮、历史不动」「裁剪比压缩便宜且不需模型参与」的表述方向一致，M2 与 M4 为补充性内容，不与其他材料冲突。

## T5 多 agent 分工 — 逐条核心主张

- **M12**：给 agent 一张花名册（成员表），它只能从中挑人；不给则按 role 任意字符串起人。前者约束强但可能不够用，后者灵活但可能起出重复、职责重叠的分身。花名册是使用者代码的选择，库里没有花名册概念。
- **M13**：子 agent 也能拿到派遣工具，递归真的可能发生；深度计数器是使用者代码，库里没有 maxDepth。没有护栏的集群会一直派活；护栏加在哪一层（深度/人数/预算）会直接改变结果，是设计决定不是实现细节。
- **M14**：库提供机制，使用者提供政策：花名册、委派、红线都是使用者代码。想让 agent 拥有哪种集群形态是设计者代码的事，不是库的字段——因为这些假设必须可被替换、可被度量，不能焊死在库里。
- **M24**：库不给护栏，「最多几层」只能自己数。一个 MAX_DEPTH 常量加一次比较就能拦住无限递归——但要记住拦在哪一层，结果就不一样。
- **M31**：预定义成员（一张名单）能约束 agent 的行为——agent 只能从名单里挑人，挑不到就拒绝。检验方式：删掉名单、让 role 接受任意字符串，跑同一个任务对比结果。（材料自注：「同一件事的另一处论述」）
- **M42**：如果集群的协调者不知道「不分工的后果」，它倾向于自己干完——尤其任务看起来不大的时候。要让它真的分工，得让它看见约束：上下文有上限、时间有预算、或活本身大到一个人做不完。光给 spawn 工具不等于它会用。
- **M43**：集群 = 运行时决定谁做什么；工作流 = 设计时就把边画好。两者差别不在自由度大小，而在「图什么时候产生」：一个运行时长出来，一个设计时就画好。所以成本与失败模式也不同。
- **M44**：固定流程（工作流）的代价是必须预判任务需要几步。预判准了高效，预判错了浪费——浪费形式：人手不够（阶段太少）或空转（阶段太多）。集群没有这个问题，但要付出协调成本。

依据：M12、M13、M14、M24、M31、M42、M43、M44

## 重复标注

1. **M12 ≈ M31**：同一论点——「花名册/成员表能约束 agent 的分工行为，agent 只能从名单里挑人」。M31 自注是「同一件事的另一处论述」，并补充了检验方法（删名单、role 接受任意字符串、跑同一任务对比）。
2. **M13 ≈ M24**：同一论点——「库不提供递归深度护栏，深度计数器/MAX_DEPTH 是使用者代码，要自己数」。M24 是 M13 的具体化（给出 MAX_DEPTH 常量 + 一次比较的实现），两者共同承认「拦在哪一层，结果不一样」。
3. **M12 ⊂ M14（部分重复/泛化）**：M14 把 M12 的「花名册是使用者代码」泛化为一般原则「库提供机制、使用者提供政策，花名册/委派/红线都是使用者代码，不能焊死在库里」。M12 是 M14 的一个具体实例。

依据：M12、M13、M14、M24、M31

## 矛盾标注

- **M43 与 M44 不矛盾**（按要求核实）：M43 断言集群与工作流是两种形态（图产生时机不同），因此「成本与失败模式也不同」；M44 正是展开这一句——工作流的代价是预判（预判错则人手不够或空转），集群的代价是协调成本。两者是「总—分」互补关系，M44 为 M43 的「成本与失败模式不同」提供具体内容，方向一致，无相反结论。
- 本批 8 份材料内部**未发现其他成对矛盾**：M12 说花名册「约束强但可能不够用」与 M31 只说「能约束行为」是详略差异而非相反结论；M13 说护栏位置「是设计决定」与 M24 说「一个常量比较就能拦住」语气轻重不同，但两者都承认「拦在哪一层结果不一样」，不构成矛盾。

依据：M12、M13、M24、M31、M43、M44

## T4 技能与扩展 — 逐条核心主张 + 重复/矛盾标注

### 逐条核心主张
- **M10**：技能是软约束（靠模型读了照做，删掉文件脚本照样 exit 0），扩展是硬接线（在函数体里 registerTool/on 事件，删掉就真消失）；两者在 spec 里都是精确白名单（不写=全给，写了=集合就是这些，[]=一个都没有）。
- **M22**：skills.add 只接受路径或 Skill 对象，技能由环境**发现**，按名注册无意义；运行期加的技能不经过白名单，白名单只裁环境自动发现的那部分。
- **M23**：skills/ 与 extensions/ 共用 pi 的自动发现机制，目录里放着就生效，无需写进 createAgent 的 spec；用 lab.inspectEnv() 核对实际加载。
- **M27**：技能是可靠的约束手段——写好 SKILL.md 模型会照着做，行为可复现，稳定格式任务用技能就够，不必上代码强制。
- **M36**：扩展加载失败是 v1 的零信号静默失败点，extensions.errors() 必须可读；加载失败={path,error}，运行期钩子异常={extensionPath,event,error}。
- **M39**：技能基本不起作用——模型有时读有时不读，同一 SKILL.md 不同轮次效果不一致，删掉脚本照样 exit 0（软约束），不构成任何保证。

### 重复
- **M10 与 M39** 共用同一判据「删掉技能文件脚本照样 exit 0」：M10 用它把技能定性为软约束，M39 用它推出技能不构成保证——事实判断一致，结论一中性一负面。
- **M22 与 M23** 都讲「环境自动发现」：M22 讲技能按路径被环境发现，M23 把同一机制推广到 extensions/，并给出 lab.inspectEnv() 核对手段。
- **M10 与 M22** 都涉及白名单语义：M10 讲 spec 声明的精确白名单，M22 补充运行期 skills.add 不受白名单约束——互补。

### 矛盾（成对）
- **M27 vs M39（重点核实，直接矛盾）**：M27 说「技能是可靠的约束手段，行为可复现」；M39 说「技能基本不起作用，同一 SKILL.md 在不同轮次效果不一致，不构成任何保证」。两者对「技能是否可靠/可复现」给出相反结论。M10 的软约束判据（删掉脚本照样 exit 0）在事实上支持 M39 的立场；M27 虽也承认「不必上代码强制」，却仍断言可靠可复现，与 M39 直接冲突。
- **M10 vs M27（程度张力）**：M10 强调技能是软约束（无代码强制力），M27 强调技能可靠可复现、不必上代码强制——对技能约束力的评价一弱一强，M27 的「可靠」断言超出 M10 的「软约束」定性。
- **M10 vs M22（潜在张力）**：M10 说「两者在 spec 里都是精确白名单」，若理解为所有技能都受白名单约束，则与 M22「运行期加的技能不经过白名单」冲突；按 M22 的限定（白名单只裁环境自动发现的部分）两者可调和。
