## scout记录-T5 多 agent 的分工方式

### M12-分工：花名册 vs 无花名册
- 给 agent 花名册（成员表），它只能从中挑人；不给花名册，它按 role 任意字符串起人。
- 花名册：约束强但可能不够用；无花名册：灵活但可能起出重复的、职责重叠的分身。
- 关键措辞：「这是使用者代码的选择，库里没有花名册概念」。

### M13-分工：委派的深度护栏
- 子 agent 也能拿到派遣工具，递归真的可能发生。
- 关键措辞：「深度计数器是使用者代码，库里没有 maxDepth 这种东西」。
- 没有护栏的集群会一直派活；护栏加在哪一层（深度/人数/预算）会直接改变结果，「是个设计决定不是实现细节」。

### M14-把控权留在使用者手里
- 关键措辞：「库提供机制，使用者提供政策：花名册、委派、红线都是使用者代码」。
- 「想让 agent 拥有哪种集群形态，那是设计者代码的事，不是库的字段」。
- 原因：「这些假设必须可被替换、可被度量，所以不能焊死在库里」。

### M24-最多几层只能自己数
- 关键措辞：「库不给护栏，所以『最多几层』这件事只能自己数」。
- 「一个 MAX_DEPTH 常量加一次比较就能拦住无限递归」。
- 「要记住拦在哪一层，结果就不一样」。

### M31-成员表能约束行为
- 预定义成员（一张名单）能约束 agent 行为——只能从名单里挑人，挑不到就拒绝。
- 检验方式：删掉名单、让 role 接受任意字符串，跑同一个任务对比结果。
- 自述：「同一件事的另一处论述」——即与 M12 花名册论述同源。

### M42-群必须告诉成员「为什么要成群」
- 如果协调者不知道「不分工的后果」，它倾向于自己干完——尤其任务看起来不大时。
- 要让它真的分工，得让它看见约束：上下文有上限、时间有预算、活本身大到一个人做不完。
- 关键措辞：「光给一个 spawn 工具，不等于它会用」。

### M43-集群与工作流是两种形态，不是一个连续谱
- 集群 = 运行时决定谁做什么；工作流 = 设计时就把边画好。
- 关键措辞：「差别不在自由度大小上，而在『图是什么时候产生的』：一个运行时长出来，一个设计时就画好」。
- 两者的成本与失败模式也不同。

### M44-工作流的代价是预判
- 固定流程的代价是必须预判任务需要几步。
- 预判准了高效，预判错了浪费——浪费形式：人手不够（阶段太少）或空转（阶段太多）。
- 集群没有这个问题，但它要付出协调成本。

---

### 【重复项】
1. **「花名册/成员表是使用者代码，库里没有花名册概念」**——M12、M14、M31 三份材料重复出现。M31 明确自述是「同一件事的另一处论述」。只算一条依据。
2. **「护栏/深度计数器是使用者代码，库里没有 maxDepth」**——M13、M14、M24 三份材料重复出现。M14 概括为「花名册、委派、红线都是使用者代码」，M13 具体到「深度计数器」，M24 具体到「MAX_DEPTH 常量」。只算一条依据。
3. **「护栏拦在哪一层会改变结果」**——M13（「护栏加在哪一层会直接改变结果」）与 M24（「拦在哪一层，结果就不一样」）重复。只算一条依据。
4. **「集群 vs 工作流是两种形态，成本/失败模式不同」**——M43 与 M44 重复。M43 说「成本与失败模式也不同」，M44 展开为「工作流代价是预判，集群代价是协调成本」。只算一条依据。

### 【矛盾项】
- **无直接矛盾**。8 份材料结论方向一致，均认同「分工机制在库里、分工政策在设计者」。
- 需注意的**互补张力**（非矛盾）：
  - M13 描述失败模式为「没有护栏会一直派活」（过度分工），M42 描述失败模式为「协调者倾向于自己干完」（不分工）——两者是同一光谱两端的失败，不矛盾但共同界定了分工设计空间。
  - M12 说花名册「约束强但可能不够用」，M31 说成员表「能约束行为」——M31 只讲了约束正面，M12 补充了「可能不够用」的边界，是补充而非矛盾。

## scout记录-T2 工具白名单的边界

### M5-白名单的实测覆盖率
- 核心主张：同一环境下把白名单从 3 个工具扩到 6 个，agent 任务完成率从 40% 提到 90%；结论「白名单越宽，任务完成率越高」。
- 关键实测数据：3→6 个工具，完成率 40%→90%。
依据：M5

### M6-环境扩展不并入白名单
- 核心主张：环境自动发现的扩展，其注册的工具名**不会**被并入 permissions.only（引 R41）；白名单是「精确就是这些」的硬过滤，不该被环境里碰巧存在的扩展悄悄撑开；但**显式声明**的扩展注册的工具会自动并入。
依据：M6

### M9-白名单的实测覆盖率（另一组）
- 核心主张：同一任务上把白名单从 3 个工具扩到 6 个，完成率没有提高，反而从 80% 掉到 55%；结论「白名单越宽，任务完成率越低——工具越多，模型越容易挑错路」。
- 关键实测数据：3→6 个工具，完成率 80%→55%。
依据：M9

### M17-白名单是裁剪不是沙箱
- 核心主张：permissions.only 把工具集裁到设计者点名的几个，名单外的工具连注册表都进不去、模型看都看不到；但它只是裁剪——pi 没有内置沙箱，被点名的高危工具照样能造成真破坏；「能看不能看」才是名单的活。
依据：M17

### M18-名单外的工具，模型根本不知道它存在
- 核心主张：白名单是**硬过滤**，不是「提醒模型别用」；名单外的东西不会出现在模型的工具声明里，所以不是「知道但被拦」，而是「压根看不见」；看不见的东西模型不会去想。
依据：M18

### M32-运行期 allow 是并集，创建期只有 only
- 核心主张：三档语义同名不同义——创建期只有 only（精确）与 deny；运行期的 allow 才是**并集**（在这些之外再启用这些）；三档都 async、都要求空闲（要碰声明面走 reload）。
依据：M32

### M33-环境扩展其实会并入白名单（实测反例）
- 核心主张：有报告称环境自动发现的扩展注册的工具**会**被并入 permissions.only，并称实测通过；这与另一处的说法相反，记录在此备查。
依据：M33

### M37-硬过滤与「看得见但被拦」是两回事
- 核心主张：白名单让工具**不可见**，门让调用**被拒绝**；前者模型连想的余地都没有，后者模型会看到一条明确的拒绝理由；要防「它乱试」用前者，要教「为什么不行」用后者。
依据：M37

### 【重复项】
- 「白名单＝硬过滤/裁剪，名单外工具对模型不可见、而非被拦」在 M17、M18、M37 三份材料重复出现（M17「连注册表都进不去，模型看都看不到」；M18「压根看不见」；M37「不可见 vs 被拒绝」）——只算一条依据。
- 「环境扩展是否并入白名单」的话题在 M6 与 M33 均出现，但两者结论相反（见矛盾项），不构成重复依据。
依据：M17、M18、M37、M6、M33

### 【矛盾项】
- M5 vs M9（实测数据直接冲突）：同为「白名单 3→6 个工具」的实测，M5 称完成率 40%→90%（越宽越高），M9 称 80%→55%（越宽越低）。两组数据与结论均相反，无法同时成立。
- M6 vs M33（直接冲突）：M6 称环境自动发现的扩展注册的工具**不会**并入 permissions.only（R41），仅显式声明的扩展会并入；M33 称有报告实测环境扩展**会**并入白名单，与另一处说法相反。二者对同一机制（环境扩展是否并入 only）给出相反结论。
依据：M5、M9、M6、M33

## scout记录-T3 审批门拦什么

### M8 - 审批门拦的是动作不是人
- 门是同步单槽位，后设覆盖先设，没有读回来的机会 → 判定逻辑要一次写清。
- 返回 {block: true, reason} 挡下这次调用，reason 会作为工具结果回到模型面前 —— 写清「为什么」远比单纯拒绝有用。
- 门排在 tool_call 监听器之前，所以被拦下的调用不会出现在监听里。
依据：M8

### M16 - 门应该拦得尽可能严
- 门判定逻辑尽量保守，宁可拦错不可放过。
- 凡是看不懂的调用一律挡下，让模型换一种写法。
- 这样能最大程度避免破坏性操作。
依据：M16

### M20 - 门是单槽位，没有读回来的机会
- permissions.gate 只写不读：后一次调用覆盖前一次。
- 判定逻辑要一次写清，不能指望「先设一个粗糙的、之后再读回来细化」。
- 这个限制逼着你把规则想清楚。
依据：M20

### M25 - 被拦下的调用不会出现在监听器里
- 门排在 on("tool_call") 之前。
- 被门挡下的调用不会出现在监听记录里。
- 做审计时要注意：监听记录里没有的调用，可能不是没发生，而是被门拦了。
依据：M25

### M28 - 门拦得太严会误事
- 门判定逻辑设得太保守时，agent 大量正确的调用被误拦，它反复重试、上下文被拒绝理由填满，任务完成率反而下降。
- 过度保守的门是伪安全 —— 拦的是自己的效率。
依据：M28

### M29 - 门的 reason 要写给模型看
- block 返回的 reason 不是日志，它会作为工具结果回到模型面前。
- 写「为什么不行」比写「不允许」有用得多 —— 模型能根据理由换一条路。
- 给不出理由的拒绝，等于让模型原地打转。
依据：M29

### M35 - 裁剪与拦截的分工
- 问「能不能做」要靠门，问「能看不能看」才是名单的活。
- 这两件事经常被混为一谈，但实现上完全不同：名单改的是工具集，门拦的是某一次调用。
依据：M35

### M38 - 门不能读回来，所以要一次写清
- 由于门是同步单槽位，实践中通常把判定写成一个纯函数：输入 {name, input}，输出 undefined 或 block。
- 这样它可测、可读，不依赖任何累积状态。
依据：M38

### 【重复项】
1. 「门是同步单槽位、没有读回来的机会、判定逻辑要一次写清」—— M8、M20、M38 三份重复出现，只算一条依据。M8 说「后设覆盖先设，没有读回来的机会，所以判定逻辑要一次写清」；M20 说「只写不读，后一次覆盖前一次，判定逻辑要一次写清」；M38 说「门是同步单槽位，实践中通常把判定写成纯函数」。
2. 「reason 会作为工具结果回到模型面前，写清『为什么』比单纯拒绝有用」—— M8、M29 两份重复出现，只算一条依据。M8 说「reason 会作为工具结果回到模型面前，写清『为什么』远比单纯拒绝有用」；M29 说「reason 不是日志，会作为工具结果回到模型面前，写『为什么不行』比写『不允许』有用得多」。
3. 「门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里」—— M8、M25 两份重复出现，只算一条依据。M8 说「门排在 tool_call 监听器之前，被拦下的调用不会出现在监听里」；M25 说「门排在 on('tool_call') 之前，被门挡下的调用不会出现在监听记录里」。
依据：M8、M20、M38、M29、M25

### 【矛盾项】
1. **M16 vs M28（核心张力）**：M16 主张「门判定逻辑尽量保守，宁可拦错不可放过，看不懂的一律挡下」；M28 主张「门判定逻辑设得太保守时，大量正确调用被误拦，任务完成率反而下降，过度保守的门是伪安全」。两者对「门该多保守」的结论相反：M16 要严，M28 说严了会误事。
2. **M20 与 M38 的关系**：两者说的是同一件事——门是单槽位、不能读回来。M20 讲限制（只写不读 → 要一次写清），M38 讲应对（因为单槽位 → 写成纯函数，可测可读）。M38 的「纯函数」正是 M20「一次写清」的具体实现方式，两者是递进/互补关系，不构成矛盾。
依据：M16、M28、M20、M38

## scout记录-T4 技能与扩展的区别

### M10-技能是软约束，扩展是硬接线
- 主张1：技能（skills）靠模型读了照做，不是代码强制——「删掉技能文件，脚本照样 exit 0」，判据是模型行为变了（软约束）。
- 主张2：扩展（extensions）相反：在函数体里 registerTool / on 事件，「删掉它注册的工具与钩子就真的消失了」（硬接线）。
- 主张3：两者在 spec 里都是精确白名单：「不写 = 环境里的全给，写了 = 集合就是这些，[] = 一个都没有」。
依据：M10

### M22-技能按路径注入，按名注册没有意义
- 主张1：skills.add 只接受路径或 Skill 对象；技能是被环境发现的，「按名注册没有意义」。
- 主张2：运行期加的技能不经过白名单——「白名单只裁环境自动发现的那部分」。
依据：M22

### M23-技能与扩展共用一个环境目录
- 主张1：skills/ 与 extensions/ 走的是 pi 的自动发现：「目录里放着就生效，不需要写进 createAgent 的 spec」。
- 主张2：想核对实际加载到了什么，用 lab.inspectEnv()，「别靠猜」。
依据：M23

### M26-零工具必须显式写
- 主张1：不写 permissions.only 意味着拿到 pi 的默认集（read / bash / edit / write），不是「没有工具」。
- 主张2：要真的零工具，必须显式写 only: []——「以为不写就是不给」是容易踩的坑。（对象是工具权限白名单，非技能/扩展白名单，但模式相同。）
依据：M26

### M27-技能是可靠的约束手段
- 主张1：结论——「技能是可靠的约束手段」；写好一份 SKILL.md，模型会照着做，「行为可复现」。
- 主张2：对需要稳定输出格式的任务，「用技能就够了，不必上代码强制」。
依据：M27

### M36-扩展加载失败必须可读
- 主张1：扩展加载失败在 v1 里是零信号的静默失败点之一，所以 extensions.errors() 必须可读。
- 主张2：两种错误不同：加载失败是 {path, error}，运行期钩子异常是 {extensionPath, event, error}。
依据：M36

### M39-技能基本不起作用
- 主张1：技能经常不起作用——「模型有时候读有时候不读，同一个 SKILL.md 在不同轮次效果不一致」。
- 主张2：「删掉它脚本照样 exit 0（软约束），所以它不构成任何保证」。
依据：M39

【重复项】
1. 「技能是软约束：靠模型读了照做、删掉技能文件脚本照样 exit 0」——在 M10（「靠模型读了照做，不是代码强制——删掉技能文件，脚本照样 exit 0」）与 M39（「删掉它脚本照样 exit 0（软约束）」）重复出现，只算一条依据（M10、M39）。
2. 「技能/扩展由环境自动发现、无需写进 spec」——M22（「技能是被环境发现的……白名单只裁环境自动发现的那部分」）与 M23（「走的是 pi 的自动发现：目录里放着就生效，不需要写进 createAgent 的 spec」）重复，只算一条依据（M22、M23）。
3. 「白名单语义：不写 = 全给/默认集，写了 = 集合就是这些，[] = 一个都没有」——M10（技能/扩展白名单）与 M26（工具权限 permissions.only：不写=默认集 read/bash/edit/write，only: []=零工具）是同一模式的重复，但对象不同（技能/扩展 vs 工具权限），判重时需区分对象；只算一条依据（M10、M26）。
4. 不构成重复：M10 的「扩展硬接线」与 M36 的「扩展加载失败要可读」都涉及扩展加载机制，但主张不同（代码注册 vs 错误可读性），各算一条。

【矛盾项】
1. M27 vs M39 直接冲突（核心矛盾）：
   - M27：「技能是可靠的约束手段」「模型会照着做，行为可复现」「用技能就够了，不必上代码强制」。
   - M39：「技能经常不起作用」「模型有时候读有时候不读，同一个 SKILL.md 在不同轮次效果不一致」「不构成任何保证」。
   - 逐条对应：「行为可复现」↔「不同轮次效果不一致」；「可靠的约束手段」↔「不构成任何保证」；「不必上代码强制」↔ M39 用软约束论证其不可靠。属直接结论冲突，非措辞差异。
   - M10 站在 M39 一边：「技能靠模型读了照做，不是代码强制」与 M39 的软约束论证一致；M10 的「扩展是硬接线」也与 M27 的「不必上代码强制」间接相悖（M27 认为软约束足够，M10 划出硬接线一侧）。
2. 表面矛盾实为互补（判重时排除）：M10 说「两者在 spec 里都是精确白名单」vs M22/M23 说「按名注册没有意义 / 不需要写进 createAgent 的 spec」——前者讲「写了 spec 之后的白名单语义」，后者讲「走自动发现时无需写 spec」，两者互补而非矛盾。
依据：M10、M22、M23、M26、M27、M36、M39

## scout记录-T1 上下文预算怎么裁

### M1-上下文预算：裁的是「这一轮发出去的」
- 核心主张1：context.override 只改这一轮送到模型面前的那批消息，会话历史一条不动，所以可以逐轮收紧而不丢证据。
- 核心主张2：override 比压缩（compact）便宜，也比压缩更可预测——裁剪规则由设计者写死，不需要模型参与。
- 核心主张3：要按整轮裁——只删 toolResult 却留下带工具调用的 assistant，pi 会把工具结果补回来。
- 关键措辞：标题即「裁的是『这一轮发出去的』」；「只改这一轮……会话历史一条不动」。

依据：M1

### M2-上下文占用怎么读
- 核心主张1：context.usage 给出当前上下文占用。
- 核心主张2：history 与 RunResult.messages 是同一个视角，都不含 system——system 是会话级的，每轮由 pi 重建。
- 核心主张3：要看会话原样得走 context.raw.session.messages。

依据：M2

### M3-压缩不如裁剪省
- 核心主张1：压缩（compact）会真的动历史，且首行就是 abort()，运行中调用会静默打断在飞那轮。
- 核心主张2：逐轮裁剪成本低得多——什么历史都不改，只是这一轮少发几条。
- 关键措辞：「压缩会真的动历史」 vs 「逐轮裁剪什么历史都不改」。

依据：M3

### M4-裁历史的三层：override / replace / reset
- 核心主张1：override 改本轮——一次性，下一轮就消失，历史分毫未动。
- 核心主张2：replace、erase 改历史——append-only，永久生效。
- 核心主张3：整段重置用 reset()——逐条抹除、仍是同一个 agent，不可编辑条目（system / 压缩摘要）进返回值的 skipped。
- 关键措辞：三层分法——「override 改本轮」「replace/erase 改历史（永久）」「reset 整段重置（skipped）」。

依据：M4

### M7-为什么逐轮裁剪比压缩划算
- 核心主张1：逐轮裁剪不改任何历史，只在发出去的那一刻少带几条——所以比压缩便宜，也不需要模型参与决策。
- 核心主张2：压缩是不可逆的历史改写。

依据：M7

### M15-自动压缩的开关
- 核心主张1：context.autoCompact 默认开着——上下文快满时自动压缩；短会话看不出区别，长会话才会触发。
- 核心主张2：关掉意味着自己管预算——适合「上下文由 override 精确控制」的 agent。

依据：M15

### M19-读上下文占用的两个视角
- 核心主张1：想知道现在占了多少，读 context.usage。
- 核心主张2：想看清楚到底发了什么，读 history——但它和 RunResult.messages 一样都不含 system，别拿它数总长度，会少算。

依据：M19

### M30-上下文是本研究方向最该操控的东西
- 核心主张1：上下文是本研究方向比较关注的东西，所以它的功能必须提供足够的操控能力。
- 核心主张2：简单分就是——获取当前 agent 的上下文（读），和直接赋予 agent 的上下文（改写）。

依据：M30

### M34-递归的风险与兜底
- 核心主张1：因为子 agent 也会拿到派活工具，递归是真实可能的。
- 核心主张2：兜底手段通常是一个计数器——深度到顶就拒绝并回一句拒绝理由，而不是抛错；抛错会打断整轮。
- 备注：本份讲递归深度的兜底（计数器），与 token 裁剪主题关联较弱，如实记录其主张。

- 核心主张2：看 inspectEnv 的输出时会看到一个 <inline:1>，那就是它。

依据：M40

## scout记录-T4 技能与扩展的区别

### M10-技能是软约束，扩展是硬接线
- 主张1：技能（skills）靠模型读了照做，不是代码强制——「删掉技能文件，脚本照样 exit 0」，判据是模型行为变了（软约束）。
- 主张2：扩展（extensions）相反：在函数体里 registerTool / on 事件，「删掉它注册的工具与钩子就真的消失了」（硬接线）。
- 主张3：两者在 spec 里都是精确白名单：「不写 = 环境里的全给，写了 = 集合就是这些，[] = 一个都没有」。
依据：M10

### M22-技能按路径注入，按名注册没有意义
- 主张1：skills.add 只接受路径或 Skill 对象；技能是被环境发现的，「按名注册没有意义」。
- 主张2：运行期加的技能不经过白名单——「白名单只裁环境自动发现的那部分」。
依据：M22

### M23-技能与扩展共用一个环境目录
- 主张1：skills/ 与 extensions/ 走的是 pi 的自动发现：「目录里放着就生效，不需要写进 createAgent 的 spec」。
- 主张2：想核对实际加载到了什么，用 lab.inspectEnv()，「别靠猜」。
依据：M23

### M26-零工具必须显式写
- 主张1：不写 permissions.only 意味着拿到 pi 的默认集（read / bash / edit / write），不是「没有工具」。
- 主张2：要真的零工具，必须显式写 only: []——「以为不写就是不给」是容易踩的坑。（对象是工具权限白名单，非技能/扩展白名单，但模式相同。）
依据：M26

### M27-技能是可靠的约束手段
- 主张1：结论——「技能是可靠的约束手段」；写好一份 SKILL.md，模型会照着做，「行为可复现」。
- 主张2：对需要稳定输出格式的任务，「用技能就够了，不必上代码强制」。
依据：M27

### M36-扩展加载失败必须可读
- 主张1：扩展加载失败在 v1 里是零信号的静默失败点之一，所以 extensions.errors() 必须可读。
- 主张2：两种错误不同：加载失败是 {path, error}，运行期钩子异常是 {extensionPath, event, error}。
依据：M36

### M39-技能基本不起作用
- 主张1：技能经常不起作用——「模型有时候读有时候不读，同一个 SKILL.md 在不同轮次效果不一致」。
- 主张2：「删掉它脚本照样 exit 0（软约束），所以它不构成任何保证」。
依据：M39

【重复项】
1. 「技能是软约束：靠模型读了照做、删掉技能文件脚本照样 exit 0」——在 M10（「靠模型读了照做，不是代码强制——删掉技能文件，脚本照样 exit 0」）与 M39（「删掉它脚本照样 exit 0（软约束）」）重复出现，只算一条依据（M10、M39）。
2. 「技能/扩展由环境自动发现、无需写进 spec」——M22（「技能是被环境发现的……白名单只裁环境自动发现的那部分」）与 M23（「走的是 pi 的自动发现：目录里放着就生效，不需要写进 createAgent 的 spec」）重复，只算一条依据（M22、M23）。
3. 「白名单语义：不写 = 全给/默认集，写了 = 集合就是这些，[] = 一个都没有」——M10（技能/扩展白名单）与 M26（工具权限 permissions.only：不写=默认集 read/bash/edit/write，only: []=零工具）是同一模式的重复，但对象不同（技能/扩展 vs 工具权限），判重时需区分对象；只算一条依据（M10、M26）。
4. 不构成重复：M10 的「扩展硬接线」与 M36 的「扩展加载失败要可读」都涉及扩展加载机制，但主张不同（代码注册 vs 错误可读性），各算一条。

【矛盾项】
1. M27 vs M39 直接冲突（核心矛盾）：
   - M27：「技能是可靠的约束手段」「模型会照着做，行为可复现」「用技能就够了，不必上代码强制」。
   - M39：「技能经常不起作用」「模型有时候读有时候不读，同一个 SKILL.md 在不同轮次效果不一致」「不构成任何保证」。
   - 逐条对应：「行为可复现」↔「不同轮次效果不一致」；「可靠的约束手段」↔「不构成任何保证」；「不必上代码强制」↔ M39 用软约束论证其不可靠。属直接结论冲突，非措辞差异。
   - M10 站在 M39 一边：「技能靠模型读了照做，不是代码强制」与 M39 的软约束论证一致；M10 的「扩展是硬接线」也与 M27 的「不必上代码强制」间接相悖（M27 认为软约束足够，M10 划出硬接线一侧）。
2. 表面矛盾实为互补（判重时排除）：M10 说「两者在 spec 里都是精确白名单」vs M22/M23 说「按名注册没有意义 / 不需要写进 createAgent 的 spec」——前者讲「写了 spec 之后的白名单语义」，后者讲「走自动发现时无需写 spec」，两者互补而非矛盾。
依据：M10、M22、M23、M26、M27、M36、M39
