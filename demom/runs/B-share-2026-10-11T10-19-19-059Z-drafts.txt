## [S1-摸底]
## corpus 摸底结果（全 44 份，M1–M44）

先约定 T1–T5 主题：T1 上下文管理（裁剪/压缩/预算）、T2 白名单/工具裁剪、T3 技能 vs 扩展、T4 审批门（permissions.gate）、T5 分工/集群/递归。

### ① 重复候选（讲同一件事）

- **M3 与 M7**：逐轮裁剪比压缩划算——不改历史、成本低、不需模型参与；压缩会动历史、不可逆。M7 自述「同一个取舍换个说法」。
- **M8、M20、M38**：门是单槽位、只写不读、判定逻辑要一次写清（建议写成纯函数）。
- **M18 与 M37**：白名单是硬过滤（不可见）≠ 门是被拒绝（看得见但被拦）。M37 自述「再强调一次」。
- **M12 与 M31**：花名册/成员表能约束 agent 行为——给名单只能从名单挑人，不给则任意字符串。M31 自述「同一件事的另一处论述」。
- **M13 与 M34**：递归风险与深度兜底——子 agent 也能派活，需计数器/深度护栏，到顶拒绝而非抛错。
- **M2 与 M19**：context.usage 读占用；history / RunResult.messages 都不含 system，别拿它数总长度。

### ② 矛盾候选（对同一件事结论相反）

- **M5 vs M9**：白名单宽度与任务完成率——M5 说 3→6 完成率 40%→90%（越宽越高）；M9 说 3→6 完成率 80%→55%（越宽越低）。结论相反。
- **M6 vs M33**：环境扩展注册的工具是否并入 permissions.only——M6 说不并入（R41）；M33 说会并入（实测反例），自述与另一处相反。
- **M16 vs M28**：门该多严——M16 说越严越好、宁可拦错；M28 说太严会误事、误拦致完成率下降。
- **M27 vs M39**：技能是否可靠——M27 说技能是可靠约束手段；M39 说技能基本不起作用、不构成保证。

### ③ 与 T1–T5 都无关的材料

- **M11**：本季度食堂菜单与轮值安排（食堂后勤）
- **M21**：办公楼消防演练通知（消防演练）

## [S2-去重] 重复候选核对结论

### 核对方法
用 list_corpus 列出 corpus/ 全部 44 份材料，用 read 逐份重读原文，对 S1 的 6 组重复候选逐一核对，并检查是否有遗漏。

### S1 的 6 组重复候选——全部确认正确

**组 1：M3、M7（T1 上下文管理）**
- M3："压缩会真的动历史……逐轮裁剪的成本低得多，因为它什么历史都不改，只是这一轮少发几条。"
- M7："同一个取舍换个说法：逐轮裁剪不改任何历史，只在发出去的那一刻少带几条，所以它比压缩便宜、也不需要模型参与决策。压缩则是不可逆的历史改写。"
- **判定：确认重复。** 核心论点完全一致——裁剪不改历史、成本低；压缩改历史、不可逆。M7 自述"同一个取舍换个说法"。

**组 2：M8、M20、M38（T4 门/审批）**
- M8："permissions.gate 是同步单槽位：后设的覆盖先设的，没有读回来的机会，所以判定逻辑要一次写清。"
- M20："permissions.gate 只写不读：后一次调用覆盖前一次。所以判定逻辑要一次写清，不能指望「先设一个粗糙的、之后再读回来细化」。"
- M38："由于门是同步单槽位，实践中通常把判定写成一个纯函数：输入 {name, input}，输出 undefined 或 block。"
- **判定：确认重复。** 三者核心都是"门是单槽位、只写不读、判定逻辑要一次写清"。M8 额外讲了 reason 和监听器，M38 额外讲了纯函数写法，但核心论点一致。

**组 3：M18、M37（T2 白名单）**
- M18："白名单是**硬过滤**，不是「提醒模型别用」。名单外的东西不会出现在模型的工具声明里，所以它不是「知道但被拦」，而是「压根看不见」。"
- M37："再强调一次那个差别：白名单让工具**不可见**，门让调用**被拒绝**。"
- **判定：确认重复。** 两者都在讲"白名单是硬过滤（不可见）vs 门是被拒绝（看得见但被拦）"的区别。M37 自述"再强调一次"。

**组 4：M12、M31（T5 分工/集群）**
- M12："给 agent 一张花名册（成员表），它只能从中挑人；不给花名册，它按 role 任意字符串起人。"
- M31："同一件事的另一处论述：预定义成员（一张名单）能约束 agent 的行为 —— agent 只能从名单里挑人，挑不到就拒绝。"
- **判定：确认重复。** 两者都在讲"花名册/成员表能约束 agent 行为"。M31 自述"同一件事的另一处论述"。

**组 5：M13、M34（T5 分工/集群）**
- M13："子 agent 也能拿到派遣工具，所以递归真的可能发生 —— 深度计数器是使用者代码，库里没有 maxDepth 这种东西。"
- M34："因为子 agent 也会拿到派活工具，递归是真实可能的。兜底手段通常是一个计数器：深度到顶就拒绝并回一句拒绝理由，而不是抛错。"
- **判定：确认重复。** 两者都在讲"递归风险与深度兜底"——子 agent 能派活、需要计数器、到顶拒绝。

**组 6：M2、M19（T1 上下文管理）**
- M2："context.usage 给出当前上下文占用。history 与 RunResult.messages 是同一个视角，都不含 system。"
- M19："想知道现在占了多少，读 context.usage。想看清楚到底发了什么，读 history —— 但它和 RunResult.messages 一样都不含 system。"
- **判定：确认重复。** 两者都在讲"context.usage 读占用；history/RunResult.messages 不含 system"。

## [S3-查矛盾]
## S2-矛盾核对（拿原文逐组核对 S1 的矛盾候选）

核对方式：用 list_corpus 确认文件名，再 read 读 corpus/ 原文，逐组比对。

### 第 1 组：白名单宽度 vs 任务完成率 —— M5 vs M9 ✅ 成立
- **M5 说**：同一个环境里白名单从 3 扩到 6，完成率 40%→90%，结论「白名单越宽，任务完成率越高」。
- **M9 说**：同一个任务上白名单从 3 扩到 6，完成率 80%→55%，结论「白名单越宽，任务完成率越低——工具越多，模型越容易挑错路」。
- 同一件事（白名单宽度与完成率的关系），结论相反，配对正确。

### 第 2 组：环境扩展是否并入 permissions.only —— M6 vs M33 ✅ 成立
- **M6 说**：环境自动发现的扩展，其工具名**不会**被并入 permissions.only（R41），白名单是硬过滤。
- **M33 说**：环境自动发现的扩展注册的工具**会**被并入 permissions.only（实测反例），并自述「这与另一处的说法相反」。
- 同一件事（环境扩展是否并入白名单），结论相反，配对正确。

### 第 3 组：门该多严 —— M16 vs M28 ✅ 成立
- **M16 说**：门判定逻辑尽量保守，宁可拦错不可放过，看不懂的调用一律挡下。
- **M28 说**：门判定逻辑设得太保守时，大量正确调用被误拦，完成率反而下降，过度保守是伪安全。
- 同一件事（门应多严），结论相反，配对正确。

### 第 4 组：技能是否可靠 —— M27 vs M39 ✅ 成立
- **M27 说**：技能是可靠的约束手段，写好 SKILL.md 模型会照着做，行为可复现。
- **M39 说**：技能基本不起作用，模型有时读有时不读、效果不一致，不构成任何保证。
- 同一件事（技能是否可靠），结论相反，配对正确。

### 核对结论
S1 列出的 4 组矛盾候选全部配对正确，无配错、无遗漏。可进入下游的矛盾清单直接采用。

依据：M5、M9、M6、M33、M16、M28、M27、M39
