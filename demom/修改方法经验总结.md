# 修改方法经验总结：流程与集群的根本剖析

> 这是 [`研究记录.md`](研究记录.md) 的**分析篇**。那边是数据，这边是从数据里抽出来的东西。
> 所有结论都能在那边的表里对上号；对不上的地方我标了「反例」。
>
> 📊 图文版（含 7 张图 + 动图）见 [`report/报告.md`](report/报告.md)。

### 变体名对照（本文一律用**中文名**，括号里是代码里的代号）

| 中文名 | 代号 | 一句话 |
|---|---|---|
| **A 基线** | `base` | 自由集群基线。协调者可自己读全部材料，也可派活 |
| **A 断视野** | `nodup` | 把协调者的 `read` 拿掉，它只能看子 agent 交回的文字 |
| **A 可互问** | `talk` | 给 agent 装 `peers`/`ask` 双向通信工具 |
| **A 已读清单** | `ledger` | 给协调者一份外部已读备忘录，每轮注入 |
| **B 基线** | `base` | 固定流程基线。阶段之间靠 `draft/` 的自由文本交接 |
| **B 指令保真** | `preserve` | 提示词要求写手保留 S2 判定的合并分组 |
| **B 代码保真** | `mechanical` | 分组落成 JSON + 插一个纯代码阶段强制合并 |
| **B 核对原文** | `verify` | 让 S2/S3 拿原始材料逐组核对，而非只看摘要 |
| **B 轨迹共享** | `share` | 用 `context.override` 把上游上下文轨迹注进下游 |
| **B 中途纠正** | `steer` | 超量时不中止，用 `io.steer` 插一句话拉回来 |
| **B 共享工作台** | `board` | 自造构件：结构化黑板 + 读后即消化 |

> 固定流程（B）的骨架始终是：`S1 摸底 → S2 去重 ‖ S3 查矛盾 → S4 成文 → S5 校验`。

## 0. 一句话的根因

**「流程 vs 集群」不是根本变量，「判断与执行之间有没有一个有损交接」才是。**

而交接有三种做法，本质是两种：

| 做法 | 谁在用 | 去重 |
|---|---|---|
| **合流**（判断与执行共享同一份上下文） | A/base（不分离）· **B/share（轨迹共享）** | 4/6 · **6/8** |
| **重建**（下游重读原文，把上游的结论重推一遍） | B/verify | 8/11 |
| **断流**（只传自由文本） | A/nodup · B/base | 0/2 · 2/4 |

**「重建」能用，但它是在用重复劳动买信息 —— 而「合流」可以不用重读就把信息传过去。**
实测：`share` 的 S4 的 read 次数降到 **0**，总成本比 `verify` **便宜 1.8 倍、快 1.9 倍**。

> ⚠️ **这段结论是我在被质疑后重做的。**
> 前四轮实验我只用了库的 `io.prompt` / `usage` / `on` / `permissions.only`，
> **从没碰过 `context.override`（轨迹共享）和 `permissions.gate`（审批门）**。
> 而它们一个直接给出了更好的交接机制，一个直接拦住了失控。
> 教训写在 §6.4：**在说「形态不行」之前，先确认自己把工具用完了。**

看这张表（每格是「判断者在哪做判断 → 执行者怎么拿到它」）：

| 系统 | 判断 | 执行 | 交接 | 去重成绩 |
|---|---|---|---|---|
| **A/base** | root（自己读，**1–49 份**，其中 3 次读了 42–49） | root 自己写 | **无交接**（同一上下文） | 4/6 |
| **A/nodup** | root（**0 份**，看不见材料） | root 写 | 有损（只能靠 scout 的自由文本 note） | **0/2** |
| **B/base** | S2（**只读 S1 摘要**） | S4 写 | 有损（自由文本 draft） | 2/4 |
| **B/mechanical** | S2（**只读摘要**） | S4 写 | **无损**（结构化 JSON + 代码强制） | **0/2** |
| **B/verify** | S2（**读了 45–47 份**） | S4 写 | **无损**（结构化 JSON + 代码强制） | **8/11** |

读出来的两件事：

1. **A/nodup 和 B/base 是同一种失败** —— 都是「判断者看不见原始材料，且靠自由文本交接」。
   一个在集群里，一个在流程里，**失败机制一模一样**。这直接说明形态不是根因。
2. **A/base 和 B/verify 是同一种成功的两种实现** ——
   A 靠**取消交接**（判断和执行在同一上下文里，压根不传），
   B 靠**消灭交接的损耗**（传，但用代码保证无损）。

> ⚠️ **一个必须说清的地方**：A/base 的 root 读了多少份，**和它成不成并不严格相关**
> （read=49 那次失败了，read=1 那次反而成了）。原因是 **A 的「视野」是分散的** ——
> root 可以自己读，也可以靠 scout 读完后写下的 note。所以「root 读了几份」**不能**
> 当作 A 的视野指标。
> **B 里可以** —— S2 是唯一做去重判断的人，它读了几份就是它的全部视野。
> §3 原语 1 里那条「1–2 份 → 45–47 份」的对照，**只在 B 内部成立**。

### 把库的工具用完之后，又撞到两件更根本的事（详见 §10）

1. **能力给了，模型不会自己用。** 我给集群每个 agent 都挂了 `peers`（看有谁）和
   `ask`（直接问它）—— **一次都没被调用过**，加了角色提示也没用。
   工具是好的、模型也看得见（我写了最小实验验证），**它就是不选**。
   与最初的 `spawn` 完全同一个模式 —— 不给“你一个人读不完”它就不分工。
2. **A 的最优形状是「1 个 agent」。** root 自己把 45 份材料全读完的那些次都过了；
   大量委派（deleg 6–7）的那四次（ledger）**全挂**。
   **集群在这个任务上收敛到了单 agent** —— 因为去重需要全局视野，而全局视野只能靠一个人看完。

## 1. 两个形态的修改方法清单（具体做了什么）

### 1.1 对**集群 A** 的修改

| 修改 | 干预对象 | 手段 | 可离线验证 | 结果 |
|---|---|---|---|---|
| root 加硬约束「你一个人读不完，必须用 spawn」 | 结构（强制分工） | 提示词 | ✗ | 委派 0 → 5 |
| `nodup`：把 `read` 从 root 白名单拿掉 | **视野** | 工具裁剪 | ✗ | ❌ 4/6 → **0/2**，token −43% |

**两次都是"全局旋钮"**：动的是 root 的提示词或 root 的工具集。
而 root 在运行时要做多少个判断、每个判断依赖什么信息 —— **设计者事前不知道**。
所以改动的影响范围**不可预测**：拿掉 `read` 本来是想省重复劳动，结果把全局综合能力一起拿掉了。

### 1.2 对**流程 B** 的修改

| 修改 | 干预对象 | 手段 | 可离线验证 | 结果 |
|---|---|---|---|---|
| `preserve`：S4 任务加「保留 S2 的合并分组」 | 交接保真 | 提示词 | ✗ | 2/3（有效但不可靠） |
| `mechanical`：S2 加 `record_groups` 工具 + 插 **S6 纯代码阶段** | 交接保真 | **代码** | **✓** | 机制✓，但整体 0/2 |
| `verify`：S2/S3 拿到 `list_corpus` + `read` + 明确要求核对原文 | **视野** | 工具 + 提示词 | ✗ | **8/11** |
| 每阶段 `maxCalls` 上限 | **边界** | **代码** | **✓** | 掐掉 572 万 token 的失控 |
| 任务文本 `work/report.md` → `report.md` | **测量** | 文本 | ✓ | 消除假失败 |

**五次都是"定点手术"**：改的是**具名阶段**（S2 的工具、S4 的任务、S4 与 S5 之间插一段）。
设计者事前就知道这个位置在干什么、它的输入输出是什么，所以改动的影响范围**可预测**。

## 2. 根本剖析之一：为什么 A 的改动是钝的、B 的改动是准的

### 2.1 结构性差异：**可寻址的干预点**

这是我认为最本质的一条：

> **流程的优势不是"阶段固定"，而是设计者在设计期就拥有「可寻址的干预点」。**
> 集群的每一步都由模型在运行期决定 —— **设计者手里没有地址**。

具体到这次：

- B 里我想修「合并丢失」，我能说：**在 S2 和 S4 之间，把 S2 的输出变成结构化的，然后在 S4 之后插一段代码**。
  这是一个**坐标**（S4 之后、S5 之前），跑一百次都在同一个位置。
- A 里我想修同一个问题，我能说什么？「让 root 在写之前先检查一遍」？
  —— 但 root 什么时候写、写完还改不改、检查是它自己做还是派个 checker —— **全是运行期决定的**。
  我只能改 root 的提示词，然后祈祷它在某个时刻想起来。

**同一个修复意图，在 B 里是一个坐标，在 A 里是一句祈祷。**

### 2.2 推论：集群的改动为什么容易"误伤"

A/nodup 是这条的完美例证。我想砍掉「root 自己读全部材料」这个重复劳动 ——
这个判断在**设计期**看起来完全合理（明明有 5 个 scout 在读）。

但运行期的真相是：**root 读材料不是为了"读"，是为了"在同一上下文里做跨材料综合"。**
它读完之后做的判断（哪些是同一件事）和执行（怎么写进报告）**共享同一份上下文**，
所以不存在交接损耗。

拿掉 `read` 之后，root 被迫依赖 scout 的自由文本 note —— **它从「无交接」掉进了「有损交接」**。
这就是为什么 A/nodup 的去重是 **0/2**，和 B/base 是同一种病。

**集群的"重复劳动"里，有一部分其实是"上下文共享"，而上下文共享是集群唯一的保真手段。**
把它当浪费砍掉，等于把保真机制一起砍掉。

## 3. 根本剖析之二：三个修改原语

把所有改动按"它在修什么"归类，只有三个原语（加一个测量层的）：

### 原语 1：视野修复 —— 让判断者看得见原始材料

| 证据 | 数字 |
|---|---|
| B 的判断者（S2）读的材料数 | base **1–2 份** → verify **45–47 份** |
| B 的 S2 token | base **~18k** → verify **~132k**（7×） |
| 去重成绩 | base **2/4** → verify **8/11** |

**原理**：判断质量 ≤ 该判断点可见的信息。**全局判断必须有全局视野** —— 这是信息论上的硬约束，
不是"提示词写得好不好"的问题。

**代价**：7 倍的判断成本。而这个代价是**必须付的**，不是浪费。

> ⚠️ **反例**：vision 是必要不充分条件。verify 里仍有 3/11 失败，虽然都读了 45+ 份。
> 所以「给视野」不是万能药 —— 它还取决于材料本身有没有唯一正确答案（见 §7 的语料瑕疵）。

### 原语 2：保真修复 —— 把判断无损地送到执行

这里有一条**手段的阶梯**，从弱到强：

| 手段 | 机制 | 可靠性 | 证据 |
|---|---|---|---|
| **轨迹共享** | 把上游的**真实上下文**注进下游（`context.override`） | **最高** | share **6/8**，S4 的 read 降到 **0–2** |
| **不分离** | 判断与执行在同一个 context 里 | **最高** | A/base 4/6 |
| 靠**代码**强制 | 结构化数据 + 确定性变换 | **高** | 离线验证：24 份报告**修好 8 份、弄坏 0 份** |
| 靠**指令**要求 | 请模型记得保留 | **中** | preserve 2/3 |
| 什么都不做 | 自由文本转述 | **低** | B/base 2/4 |

**核心区分：提示词是「请求」，代码是「保证」，而轨迹共享是「不用传」—— 因为下游直接拿到了上游看到的东西。**

#### ★ 这一格是我一开始漏掉的（重要修正）★

前四轮实验里，我一直用**文件**做交接 —— 那是 Anthropic 的 artifact systems 那一派。
**我从没试过库原生的轨迹共享（`context.override`），而它比我自己搭的那套更好。**

| | 走文件（verify） | 轨迹共享（share） |
|---|---|---|
| ok | 8/11（73%） | **6/8（75%）** |
| token | 1,004k | **559k（1.8× 便宜）** |
| 秒 | 1964 | **1032（1.9× 快）** |
| **S4 的 read 次数** | 1–60 | **0–2** |

最硬的那个读数：**S4 的 read 次数降到 0** —— 它根本不需要再去读文件，
因为上游**读过什么、怎么想的**已经在它的上下文里了。

这与 Cognition 的 Principle 1 完全对上（“share context, and share full agent traces,
**not just individual messages**”）—— 而我之前是把它归到「厂商自报、没数字」那一类里轻处理的。

#### 为什么它反而**更便宜**（反直觉）

轨迹共享让每一环的上下文变大（注了 ~100k 字符），但**总成本降了**。原因是它**消灭了重复读**：

| 阶段 | verify 的 read | share 的 read |
|---|---|---|
| S2-去重 | 45–47 次 | 19–32 次（因为 S1 的轨迹里已经有 44 份材料） |
| S4-成文 | 1–60 次 | **0–2 次** |

**所以「重复读」不是浪费，而是「用重新推导来替代信息传递」。**
把它换成真正的传递，总成本就下来了。

（这直接修正了我在 A/nodup 里的判断 —— 当时我把 root 重读材料当「重复劳动」想砍掉，
其实那正是集群**唯一的信息传递方式**。见 §2.2。）

`preserve` 和 `mechanical` 想修的是**同一个东西**（S2 的合并决定在 S4 处丢失），
差别只在手段：一个是"请你记得"，一个是"我来保证"。结果 2/3 vs 结构性不可能失败。

### 原语 3：边界修复 —— 给每一步一个上限

**证据**：B 的 S5 校验阶段单次 **423 次工具调用、572 万 token**（占该次总用量 96%），**无人拦**。

**原理**：**模型没有内生的"够了"感。** 它不知道自己已经读了 423 遍同一份文件。
边界必须由外部给定。

**关键设计细节**（这条是踩出来的）：护栏要**按阶段**设，不能用一个全局值。

| 看工具调用次数 | 正常阶段 | 失控阶段 |
|---|---|---|
| 实测范围 | 3–99 次 | 119 / 135 / 423 次 |

**99 和 119 分不开**。但按阶段就分得开 —— 因为设计者知道每个位置该有多重：
S1 要读 ~44 份材料（上限 60 合理），S5 只是校一份报告（上限 30 就够）。

> 这是固定流程**能干、集群干不了**的事：**每个位置的上限由设计者写死**，不需要模型自我克制。

### （原语 0：测量修复 —— 这一层是给研究者的，不是给系统的）

这次一共修了 **6 次判据** + 1 个路径 bug。它们的共同点：**把假失败从真失败里摘出来。**

| 假失败 | 伪装成什么 | 真相 |
|---|---|---|
| 判据把「合并成一行」判成「没去重」 | 模型都不行（0/20） | 判据语义反了 |
| `"M37".includes("M3")` 为 true | 模型没去干净 | **子串碰撞** |
| 报告用粗体段落而非 bullet → 退回旧逻辑 | 模型没去干净 | 判据的 fallback 分支里藏着同一个 bug |
| 产物写到 `work/work/report.md` | **产物不存在**（能力失败） | 我的任务文本路径歧义 |

**「0% 通过率」和「产物不存在」这两类信号，先怀疑测量，再怀疑模型。**
第 3 个判据 bug 让 A 从 1/6 变 4/6 —— 一个字符，结论翻三倍。

## 4. 根本剖析之三：交接的三种实现 —— **合流 vs 重建**

把五个变体排在一起看，会出现一个我没预料到的统一：

| 变体 | 下游怎么拿到上游的信息 | 本质 | 去重 |
|---|---|---|---|
| A/base | 不分离 —— 判断和执行本来就在同一个 agent 里 | **合流（天然）** | 4/6 |
| **B/share** | 把上游的上下文轨迹**注进**下游（`context.override`） | **合流（显式）** | **6/8** |
| A/nodup | 不传，只能看 scout 的自由文本 note | **断流** | 0/2 |
| B/base | 不传，下游看上游写的自由文本 draft | **断流** | 2/4 |
| B/verify | 下游**自己重读原始材料**，把上游的结论重推一遍 | **重建** | 8/11 |
| B/mechanical | 传了，但传的是**错的分组** | 传对了也没用 | 0/2 |

### 4.0 先搞清楚这三个词到底在说什么

它们回答的是**同一个问题**：

> **当「做判断的人」和「写产物的人」不是同一个 agent 时，写的人怎么知道判断的人知道的事？**

| | 写的人手上有什么 | 怎么到手的 |
|---|---|---|
| **合流** | **和判断者一样的东西** | **传过去的** —— 或者压根就是同一个人 |
| **重建** | **和判断者一样的东西** | **自己重新拿了一遍** |
| **断流** | **只有一段文字结论** | ——（过程全丢） |

**关键：合流和重建最终的信息状态是一样的**（都知道全部），区别只在**信息是怎么到手的**。
断流是**信息量本身就不够**。所以这是**两条轴**，不是三选一：

- **轴 1（信息够不够）**：断流 **不够** ｜ 合流 / 重建 **够**
- **轴 2（怎么拿到）**：合流 = **传递** ｜ 重建 = **重算**

**判断任意变体属于哪类，问两句：**

> **Q1：写产物的人手上有原始材料（或判断者的推理）吗？** 没有 → **断流**；有 → Q2
> **Q2：它是怎么有的？** 别人搬过来的 / 它自己就是判断者 → **合流**；自己重读了一遍 → **重建**

**类比：你没参加那场会，要写纪要**

| 你手上有什么 | 信息完整吗 | 对应 |
|---|---|---|
| 会是你自己开的 | 完整（脑子里全有） | **合流 · 不分离** |
| 拿到了全程录音 | 完整（听录音就能写） | **合流 · 送过去** |
| 把参会人重新叫来问一遍 | 完整（但开了第二次会） | **重建** |
| 只拿到同事的一页纸摘要 | **残缺**（漏了什么你不知道） | **断流** |

这个类比能一次说清两组容易混的关系：

- **重建 vs 断流**：重建的信息**是完整的**（你重新问全了）；断流的信息**是残缺的**（你只有那一页纸）。
  证据：重建 **8/11**，断流 **0/2 · 2/4**。差别不是「做得好不好」，是「有没有」。
- **合流 vs 重建**：信息完整度**一样**，但合流是**别人给你**，重建是**你自己再跑一遍**。

**三个最常见的误解：**

1. ❌「合流 = 一定要传东西」—— **A 基线是合流，但它什么都没传**，因为它压根不分离。
   合流说的是**信息状态**（执行者和判断者知道的一样多），不是**动作**。
2. ❌「重建 = 断流的一种（只是做得好）」—— 不对，见上。
3. ❌「断流 = 完全没信息」—— **B 基线传了完整的一段摘要，2/4**。断流是**有损**，不是**零**。
   它的病不是「没有信息」，是「信息只剩一段文字，**中间过程全丢**」。

> 图文版见 [`report/fig7_handoff_detail.png`](report/fig7_handoff_detail.png)（四条信息流并排）。

### 4.1 关键认识：`verify` 的「读原文」= 用**重复劳动**换信息

这一格把我之前的一个判断掀了。

`verify` 为什么能到 8/11？因为我让 S2 **重读 45–47 份原始材料**。
但严格说，S2 读的那些材料，**S1 刚刚读过**。这是重复劳动。

而我最早在 A 里把同样的东西叫「重复劳动」，还想把它砍掉（`nodup`）—— 结果 **0/2**。

**两件事是同一件事：**

> **当信息没有别的传递渠道时，「重新读一遍」就是信息传递本身。**
> 它不是浪费，它是**用算力买信息**。

所以 `verify` 的 7 倍判断成本（S2：18k → 132k token）不是低效，是**在付费买视野**。
而 `share` 的贡献是：**同样的信息，可以不用重读就传过去** —— 于是成本从 1004k 降到 559k。

### 4.2 所以「集群 vs 流程」的争辩，很可能是**问错了问题**

- A/base 和 B/share **做的是同一件事**：让判断和执行共享同一份上下文。
  只是一个靠「不分开」，一个靠「把上下文送过去」。
- A/nodup 和 B/base **失败的是同一件事**：信息传递断了。
  一个断在协调者看不见材料，一个断在写手只看到摘要。

**两者真正的差别只有一个：信息怎么流动。**

这解释了为什么我在 `研究记录.md` §6 里找不到「形态」的干净结论 ——
因为形态不是自变量，**交接机制才是**。形态只是决定了**默认的交接机制**：

- 集群默认 **合流**（协调者自己读，判断与执行不分家）→ 所以它的「重复劳动」其实是保真机制
- 流程默认 **断流**（阶段之间只传自由文本）→ 所以它天生容易丢信息

> **流程不是“天生比集群差”，而是“默认交接方式更差”。而默认是可以改的 —— `share` 就是改法。**

## 5. 统一框架：视野 × 交接保真

把三个原语里的两个（视野、保真）交叉，就是这次全部数据的形状：

| | **交接有损**（自由文本转述） | **交接无损**（代码 / 无交接） |
|---|---|---|
| **判断者看得见原文** | B/preserve 2/3 ⚠️ | **A/base 4/6** · **B/verify 8/11** · **B/share 6/8** ✅ |
| **判断者看不见原文** | B/base 2/4 · **A/nodup 0/2** ❌ | B/mechanical 0/2 ❌ |

读法：

- **右下角（看不见 + 无损）= 白干**。B/mechanical 把交接修得完美，但送过去的是**错的分组**。
  代码能保证"你说的我照做"，**保证不了"你说的对"**。
- **左上角（看得见 + 有损）= 打折扣**。B/preserve 的判断者只有摘要，靠指令硬撑到 2/3。
- **右上角（看得见 + 无损）= 两个条件都满足** —— 这是唯一的稳定区，A/base 和 B/verify 都在这里。
- **左下角（看不见 + 有损）= 双重损失**，A/nodup 和 B/base 都在这里。

**两个条件必须同时满足，且它们修的是不同的东西**：
视野修的是「判断的输入」，保真修的是「判断的输出」。**只修一个都不够。**

> ⚠️ **诚实声明**：这个 2×2 是**组织框架**，不是拟合出来的定律。
> 每格 n 只有 2–3，`preserve` 那一格（2/3）本身就在噪声里。
> 我信的是"两条轴都存在且互相独立"这个结构，不是具体格子里的数字。

## 6. 修改方法的元经验：**代码优先，离线验证**

这是我认为对**实践**最有价值的一条，而且它是被这次经历逼出来的：

### 5.1 代码干预可以离线验证，提示词干预不能

| | S6 强制合并（代码） | preserve（提示词） |
|---|---|---|
| 怎么验证 | 拿 **24 份历史报告**跑一遍 | 只能**真跑** |
| 花多久 | **几毫秒** | **3 次 × ~30 分钟 ≈ 1.5 小时** |
| 得到什么结论 | 「修好 8 份、弄坏 0 份」（确定） | 「有效但不可靠」（概率） |
| 能不能防回归 | 能（每次改动重跑那 14 份） | 不能 |

**这一个差别决定了迭代速度。** 代码改动是**可证伪**的；提示词改动只能靠采样，而采样有噪声 ——
`preserve` 我一开始 n=1 时以为「一行指令就修好了」，补到 n=3 才发现是 2/3。

### 5.2 推论：想用代码，就得先有"结构化交接面"

这条推下去，会得到一个**反直觉但很重要**的结论：

> **`mechanical` 那次 0/2 不是白跑的 —— 它造出了 S6 能挂上去的那个面。**

顺序是这样的：

```
想让保真可离线验证        →  必须用代码
代码要能接住              →  必须有一个结构化接口（而不是自由文本）
所以第一步必须先造接口     →  record_groups（mechanical）
接口造好之后，代码才有地方挂 →  S6（mechanical）
接口 + 代码都就位，再修视野 →  verify 8/11
```

如果我只做 `verify`（给 S2 原文）而不做 `mechanical`（造接口 + 代码），
那 S2 判断对了，S4 照样会把合并拆开 —— **还是 2/3 那一档。**

**所以"把自然语言交接改成结构化交接"本身就是一个独立的、有价值的改造目标**，
哪怕它单跑一次成绩是 0/2。

### 5.3 对集群的推论（可操作）

集群想享受"代码保真"，**必须先在运行期造出一个结构化交接面** ——
因为设计者不知道判断会在哪里发生，只能让 agent 自己把判断**落成数据**。

具体到 A：让 scout 的 `note` 从自由文本变成结构化（比如"我发现的重复组：[[M12,M31]]"），
然后 root 写报告前，用一个**代码钩子**（A 已经有 `draftsExtension` 可以挂）做强制合并。

**这条 A 还没测。** 但它正是 B 的成功路径在 A 上的镜像。

## 7. 为什么"流程比集群好"这个说法会流传

现在数据够了，可以给出比上一版更根本的解释：

### 7.1 因为「流程的失败更局部、更好修」

B 的失败可以定位到**一个阶段**（S4 丢了合并），修法是**一个坐标上的手术**。
A 的失败弥散在运行期（协调者视野、上下文保真、终止条件…），修法是**全局旋钮**。

实践中流程迭代更快、更快见效 → 人们得出「流程更好」。
**我的数据直接支持这条**：B 四轮 2/4 → 8/11；A 一轮就撞了负结果。

### 7.2 但更根本的是：**流程的干预点是设计者造的，所以"能改"这件事本身被误读成了"更好"**

这是这次最微妙的一层。回想 §2.1：

> 流程允许设计者在**已知坐标**上干预。

这句话有个副作用：**凡是能在一个坐标上被修好的问题，看起来都像是"流程更擅长"，
其实只是"流程更容易被修"。**

反过来，集群的问题往往**看起来不可修**（"我该改哪儿？"），
但它的不可修**不是因为问题更难，而是因为设计者没有地址**。

**所以"流程比集群好"这个印象，有很大一部分是"可寻址性"造成的错觉，
而不是能力差异。** 这次我把 A 也按同样的方法改（给它造交接面、给它代码钩子），
大概率也能涨 —— 那就证明形态不是根本变量。

### 7.3 ★ 元经验之一：先确认工具用完了 ★

这条是这次最尴尬、也最该记住的教训。

前四轮实验，我用的库 API 只有：`io.prompt` / `usage` / `on` / `permissions.only`。
我据此写下了「交接保真要靠文件 + 代码」的结论 —— **而库原生的 `context.override`（轨迹共享）
比我自己搭的那套便宜 1.8 倍、快 1.9 倍，我却从来没试过。**

这不是「没想到」，而是**在没穷尽工具的情况下就下了结论**。
一个**操控库**的价值恰恰在于它提供了哪些**干预手段**；
而我在总结「怎么修改 agent 系统」时，只用了其中两种手段，却写了普遍性的结论。

**规则：写「某类系统不行 / 只能这样做」之前，先把手上工具清单过一遍，把没用过的用一次。**

### 7.4 还有一层：集群的失败"有界"，流程的失败"无界"
这是补样本时才发现的转折：

- 集群有预算闸（虽然只在 `spawn` 前拦），失败**有天花板**
- 流程因为"阶段数固定"而**让人以为不会失控** —— 但**阶段内部可以失控**（572 万 token / 423 次调用）

**「结构固定」不等于「代价有界」。** 这是一个很容易被忽略的盲区，
而且它偏向流程 —— 因为流程的失控**在图上完全看不出来**。

## 8. 什么时候选哪个形态（决策表）

| 你的任务… | 倾向 | 理由 |
|---|---|---|
| 全局性质靠**一次综合**就能得出（如去重） | **集群** | 判断与执行同上下文 → 天然无交接损耗 |
| 阶段边界**天然存在**（如"先摸清→再写→再校验"） | **流程** | 有坐标可干预，且每个坐标都能加代码护栏 |
| 需要**可离线验证**的保证 | **流程** | 代码只能挂在具名阶段上 |
| 任务形状**事前说不清** | **集群** | 不需要预见 —— 模型在运行期决定结构 |
| 要**封顶成本** | 两者都要，但**流程更需要** | 流程的失控在结构上看不出来 |
| 判断者需要**全局视野** | 两者都要 | **这是硬约束，与形态无关** |

**最实用的那条**：如果你的流程里有「判断完就是机械操作」的环节 ——
**把它从模型手里拿走，交给代码。** 这一步几乎免费，而且能离线验证。

## 9. 反例与边界（必须一起看）

1. **A 从头到尾没被认真改过。** 8/11 vs 4/6 是「改过的 vs 没改的」，
   不是「流程 vs 集群」。§5.3 列了 A 的镜像改法，还没测。
2. **视野是必要不充分。** verify 读了 45+ 份仍有 3/11 失败。
3. **2×2 每格 n=2~3**，是组织框架不是定律。
4. **判据改过 6 次**，存在研究者自由度风险（辩护见 `研究记录.md` §3）。
5. **语料有瑕疵**：M1 的正文意外地与 M3≡M7 组重叠，让「正确答案」不唯一 ——
   这可能是 M3≡M7 始终最难的原因，也提醒「视野够了但材料有歧义」时仍会失败。
6. **模型只有一个**（`longcat-2.5-preview-free`）。文献普遍发现模型越强、MAS 优势越小。
7. **任务只有一个**（读多写少 + 全局综合）。按 Scaling 论文，顺序规划类任务结论可能反转。

## 10. 能力实验：把库的其余高级功能用一遍

被质疑之后，我把库剩下的高级功能逐个试了。结果分三类：**有效的 / 无效的 / 根本没被用上的**。

### 10.1 ★ 最重要的发现：**能力给了，模型不会自己用** ★

`talk` 变体给每个 agent 都挂了 `peers`（看有谁）+ `ask`（直接问它）。

**结果：`asks` 始终是 `undefined` —— 一次都没被调用过。**

我先怀疑工具没挂上，专门写了个最小实验验证：

```
【只有 ping】    回答：ping 工具返回了 "pong"，工作正常。
【只有 peers/ask】回答：我可用的工具有：1. peers  2. ask
```

**工具是好的、模型也看得见它们 —— 它就是不选。**

加了角色提示（“需要确认某件事时用它去问”）之后，**仍然一次都没用**。

> **与最初的 `spawn` 完全同一个模式**：不给“你一个人读不完”它就不分工（delegations=0）；
> 给了才分工。现在 `ask` 又重演了一次。

**所以「给 agent 一个能力」与「让 agent 用上这个能力」是两件事。**
库给的是**机制**；用不用是**策略层（role 文本 + 任务形状）**的事 ——
这正是 `AGENTS.md` 里那条「库不含任何策略」的实测例证。

### 10.2 `ask` 为什么用不上：因为最优策略不需要它

更根本的原因在数据里：

```
talk run2:  1 个 agent，0 次委派，read 45 次，83k tokens，✓ ok
talk run1:  2 个 agent，1 次委派，root read 45 次，✓ ok
```

**root 自己把 45 份材料全读了。** 它读完之后不需要问任何人 ——
它比任何子 agent 知道的都多。

而 `spawn` 交回的轨迹（`talk` 里开了 traceShare）它也不需要看 —— 它自己有原文。

> **所以「agent 直接通信」在这个任务上没有生态位：因为获胜策略是“根本不分工”。**

### 10.3 ★ A 的最优形状是「1 个 agent」★

把 A 的六次 base 加两次 talk 排开看：

| 形状 | 去重 |
|---|---|
| root 自己读完（read 42–49） | ✓（大多） |
| root 大量委派（deleg 6–7） | ✗（ledger 4/4 全挂） |

**集群（cluster）在这个任务上收敛到了“单 agent”。**
这不是 bug，是它自己选出来的最优解：既然去重需要全局视野，而全局视野只能靠“一个人看完”，
那分派出去就是错的。

这与 Cognition 那篇的结论完全一致（“单线程 agent + 完整上下文”），
也是我在 §4 里说的「合流」：**A 靠不分工实现了合流。**

### 10.4 `ledger`（外部工作台）：无效，甚至可能有害

动机是好的：root 要读 45 份材料，跨材料去重需要记得住前面读过什么。
我用 `on("tool_call")` 实时收集它读了哪几份，再用 `context.override` 把「已读清单」
注进每一轮 —— 一个不占大脑的外部工作台。

**结果：0/4，而 base 是 4/6。** 而且委派反而更多了（平均 6 vs base 的 5）。

两个可能的解释，我没能分辨：
1. **`override` 在消息数组**最前面**插一条合成的 user 消息，本身就干扰了模型** ——
   这是个值得单独查的技术问题（override 的注入位置）；
2. 工作台让 root 觉得自己“已经掌握全局”，反而更放心地分派出去。

⚠️ **n=4，也可能是噪声。但至少可以确定：没有证据表明它有帮助。**
这也是一次诚实记录的负结果 —— **不是每个高级功能都有用。**

### 10.5 ★ `io.steer`（中途纠正）：收益最大的一个护栏 ★

#### 动机：现有护栏全是**事后**的

之前所有护栏都是：撞上限 → `abort` → 这一轮白跑。
而 pi 的 `steer` 是**实时**的（源码注释原话）：

> “Delivered **after the current assistant turn finishes executing its tool calls, before the next LLM call**.”

—— **不打断运行**，只在下一次请求前插一句话。于是可以「把它拉回来」而不是「把它打死」。

#### ★ 踩过的两个坑（这两个坑本身就是结论）★

**坑 1：触发点选错了 → steer 帮了倒忙。**

第一版触发是「连续 20 次调用没有 note/write」。结果 **0/2**：

```
steered=["S1-摸底（第 1 次，已 20 次调用）", ...]
S1-摸底 calls=31   ← 正常要 46 次
失败：重复没去干净：M18、M37
```

**因为「读材料」本来就是 S1 的活，不是空转。** 它在第 20 次就被叫停，只读了 31 份。

> **教训：`abort` 的门槛可以设得很高（它是最后手段），
> 但 corrective steer 会插进正常工作里，触发必须精确。**

**坑 2：拉完不给余地 → steer 等于白拉。**

改成「就在本来要 abort 的那个点上 steer」之后，仍然只有 2/3：

```
steered=["S4-成文（第 1 次，已 71 次调用）","S4-成文（第 2 次，已 72 次调用）"]
guarded=["S4-成文（73 次调用 > 上限 70，拉过 2 次）"]   ← 拉完两次就 abort，只多给了 2 次调用
```

模型还没来得及按你说的收尾就被打死了。**所以 steer 之后必须抬高上限（`GRACE=30`）。**

#### 结果

| 配置 | n | ok | tokens |
|---|---|---|---|
| steer（触发点错） | 2 | **0/2** | — |
| steer（触发点对、无余地） | 3 | 2/3 | — |
| **steer（触发点对 + 余地）** | **3** | **3/3** | **330k** |
| 合计 | 6 | **5/6（83%）** | 457k |

加余地之后的效果在数据里看得很清楚：

```
S5-校验（第 1 次，已 31 次调用，上限抬到 60）   → 没 abort，正常收尾，✓ ok
```

**一个本来会被 abort 的阶段，被拉回来了。**

#### 与其它变体的对比

| 变体 | n | ok | tokens | 秒 |
|---|---|---|---|---|
| B/verify（文件交接） | 11 | 8/11（73%） | 1004k | 1964 |
| B/share（轨迹交接） | 8 | 6/8（75%） | 559k | 1032 |
| **B/steer（share + 中途纠正）** | **6** | **5/6（83%）** | **457k** | 1469 |

**目前最好的一档：成功率最高、成本最低。**

#### 更深的一层：这是「干预位置」的第三种可能

回顾 §2.1 —— 我说过流程的优势是「设计者拥有**可寻址的干预点**」。
但那时我脑子里的干预点只有两种：**事前**（写进提示词/工具白名单）和**事后**（看产物判分）。

`io.steer` 给了第三种：**事中**。

| 时机 | 手段 | 能做什么 |
|---|---|---|
| 事前 | role 文本 / 工具白名单 / 预算闸 | 只能**预设**，不知道会发生什么 |
| **事中** | **`io.steer`** | **看着它干，跑偏了就拉回来** |
| 事后 | 判据 / 机械验证（S6） | 只能发现，已经晚了 |

而且注意：`steer` 的**触发条件也是设计者写的代码**（`calls > cap`）——

## 11. 构造：工作台（Workbench）—— 用原语造的一个构件

前面十节都是「试库的功能」。这一节是**反过来**：从分析结论出发，用底层原语造一个东西。

代码在 [`bench/workbench.ts`](bench/workbench.ts)，接线在 `labB-workflow/` 的 `board` 变体。

### 11.1 它要解决的两个问题（都来自实测，不是想象）

| 问题 | 证据 |
|---|---|
| **交接有损** | A/nodup（集群）与 B/base（流程）**是同一种失败**（0/2 与 2/4）；而合流有效（A/base 4/6、B/share 6/8） |
| **合流很贵** | B/share 注入 ~100k 字符；B/verify 让 S2 重读 45 份原文 → 1004k token |

两者的交集：**原始材料被反复搬运** —— 读一遍、传一遍、再读一遍。

### 11.2 做法：把「原始材料」换成「结构化结论」，并让它全局可见

```
① 黑板      所有 agent 共享一份结构化状态（notes / dupGroups / contradictions / entries）
② 合流      每轮通过 context.override 注进**每一个** agent —— 但注的是提炼过的结论，不是原文
③ 读后即消化 用 post 把要点写进黑板之后，代码把那条**原始 read 的条目 erase 掉**
④ 代码守不变量 写入时就校验：编号必须真实、重复组≥2 个成员、矛盾必须两个编号
```

**④ 是刻意与 B 的 S6 同一条分工**：模型负责判断，代码负责保真。

### 11.3 用了哪些库原语（每一个都是必需的）

| 原语 | 在这件东西里的作用 |
|---|---|
| `context.override` | 每轮注入黑板（不改历史） |
| `context.entries()` | 拿到可寻址的条目（为了 erase） |
| `context.erase` | **读后即消化**：把原始 read 移出上下文 |
| 自定义工具 `post` | agent 往黑板写结构化结论 |
| `on("tool_call")` / `on("tool_result")` | 知道它读了哪份、什么时候读完的 |

### 11.4 造的过程中踩的两个坑（都是**实测**发现的，不是设计时想到的）

**坑 1：每轮重注整个黑板 → 成本爆炸。**

```
第一版：总注入量 887k 字符（黑板本身才几 k，但每个 agent 每轮都重注）
→ board 跑出 1.09M–1.56M token
```

修法：黑板改成**只追加的事件日志**，每个 agent 只收**自己没看过的增量**（`renderFor(selfId)`）。

**结果：887k → 7–25k 字符（最高 37× 降低）。**

> **这是「合流」真正的成本所在**：不是信息量，是**重复注入**。
> 任何共享上下文的做法（包括 B/share）都会撞到它。

**坑 2：靠 preview 定位要消化的条目 → 基本匹配不上。**

```
第一版：拿 entries() 的 preview 找含 "M3" 的 toolResult 条目
→ 44 份材料只消化了 3 份
原因：**preview 是那条消息的正文（即文件内容）**，而文件内容不会以它自己的编号开头
```

修法：`tool_call` 时记下「要读谁」，`tool_result` **之后**取一次 `entries()` 拿**最新的** toolResult 条目，
两步接起来。

**结果：消化数 3 → 35–90 份。**

### 11.5 数据

| 变体 | n | ok | tokens | 秒 | 说明 |
|---|---|---|---|---|---|
| B/share（轨迹共享） | 8 | 6/8（75%） | 559k | 1032 | 注入原始轨迹 |
| B/steer（+中途纠正） | 6 | 5/6（83%） | 457k | 1469 | 目前最便宜 |
| **B/board（工作台）** | **7** | **6/7（86%）** | 963k | 2319 | **准确率最高** |

**修完两个坑之后的最后 3 次：3/3，平均 653k token。**

机制生效的直接读数：

```
黑板 notes=41  → S4 只 read 了 3 次   ← 黑板真的替代了重读
黑板 notes=0   → S4 read 了 35 次     ← S1 没往黑板上写，就退化成「重读」
```

> **一个诚实的话**：board 的**准确率最高（86%）但不是最便宜**（653k vs steer 457k）。
> 它的价值在于**把「共享上下文」从自由文本/原始轨迹变成了结构化、可校验、可增量的状态** ——
> 这是一条能继续优化的路（见 11.6），而不是一个已经赢了的方案。

### 11.6 还没做完的部分

1. **S1 的护栏太紧**：有了黑板，每份材料要 read + post **两次调用**，
   而 `maxCalls=60` 是按「只读」定的 —— 实测 S1 撞了 61 次上限。
   应当按「材料数 × 2 + 余量」重新定。
2. **黑板注进去的内容仍是自由文本**。真正的一致性还没做到 ——
   理想情况是结构化的，模型直接照抄。
3. **没做「黑板冲突检测」**：两个 agent 对同一组给出不同判定时，
   代码应该能发现并标出来（现在只是追加）。
4. **没把 board 接给 A** —— 集群那边同样能用（它的 root 本来就在做「合流」）。
