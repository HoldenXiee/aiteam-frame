## 0. 一句话

**最终的答案不是「流程好还是集群好」，而是「交接机制」：合流 > 重建 > 断流。**

| 做法 | 谁在用 | 去重 |
|---|---|---|
| **合流**（判断与执行共享同一份上下文） | A/base（不分离）· **B/share（轨迹共享）** | 4/6 · **6/8** |
| **重建**（下游重读原文自己推） | B/verify | 8/11 |
| **断流**（只传自由文本） | A/nodup · B/base | 0/2 · 2/4 |

`share` 用库原生的 `context.override` 把上游的**真实轨迹**注进下游 ——
**S4 的 read 次数降到 0**，而且比 `verify` **便宜 1.8 倍、快 1.9 倍**。

### 两个必须说的前提

1. **A 到最后也没被公平地改过。** 前四轮里 B 改了四次、A 只改过一次（还是负结果）。
   后来的 `talk` / `ledger` 是对 A 的补救，但样本只有 2 和 4。
2. **能力给了，模型不会自己用**（§10.2）：给集群挂上双向通信工具 `peers`/`ask`，
   **一次都没被调用过**。而 **A 的最优形状其实是「1 个 agent」** ——
   root 自己读完全部材料时胜率最高；大量委派时全挂。

**所以完整的故事是**：形态不是自变量，**交接机制**才是；而交接机制好不好，
取决于**判断者有没有全局视野** + **信息能不能无损地传下去**。

## 0.1 早期版本的一句话（保留，看认识怎么变的）

**把固定流程认真改进之后，它超过了自由集群：B/verify 8/11（73%）vs A 4/6（67%）。**

但要把话说全 —— **A 从头到尾没改过，B 改了四轮**。所以严格说这不是「流程天生比集群好」，
而是「**被认真改进的那一边更好**」。真正值钱的是**改进路线本身**（§2）：

1. 用**指令**要求保真 → 有效但不可靠（2/3）
2. 换成**代码**强制保真 → 结构上不可能失败（但暴露了下一个瓶颈）
3. 给做判断的人**全局视野** → 瓶颈解除（8/11）

第 3 条和 A 的 nodup 实验是**同一个教训**（§2.1）：**把做全局判断的那个人的眼睛蒙上，它就做不了全局判断。**

## 2. B 的四轮改进（这才是本文的主体）

### 2.1 A / nodup —— 先确立那条教训

**假设**：A base 里 root 每轮自己读 42–49 份材料，而 5 个 scout 又各读一遍 → 重复劳动，砍掉能省钱。
**做法**：把 `read` 从 root 的白名单里拿掉。

**结果：省了 43% 的 token（472k → 268k），但 ok 从 4/6 掉到 0/2，去重全崩。**

那份「重复」在干真活：**跨材料的去重需要有人同时看见所有材料**，而 scout 每人只看见一片。

### 2.2 B / preserve —— 用指令要求保真（有效但不可靠）

**发现**：B 的 S2-去重 **做对了**（草稿写着「M12 与 M31…合并」），但 S4-成文把每份材料又展开成独立 bullet，
**把上游的合并决定弄丢了**（base 里 27/31 条是「- M数字：…」逐份列举）。

**做法**：只加一条指令 —— 要求 S4 保留 S2 的合并分组。

**结果（n=3）**：**2/3**。去重从 0/4 → 2/3，最难两组（M3≡M7、M13≡M24≡M34）0/4 → 3/3。
但**没修到可靠** —— 因为「模型是否遵守指令」本身是变量。

### 2.3 B / mechanical —— 用代码强制保真（结构上不可能失败）

**思路**：固定流程真正的优势不是「阶段固定」，而是**设计者能在已知位置插一个确定性步骤**。
集群里没有这个位置 —— 每一步都由模型决定，所以只能「请模型记得做对」。

**做法（只改两处）**：
1. S2 多一个 `record_groups` 工具，把分组落成**结构化 JSON**（不只是自由文本）
2. S4 之后插一个**纯代码阶段 S6-强制合并**：读 JSON，把散在多个 bullet 里的同组材料**机械地并回去**

**先离线验证机制**（拿 14 份历史报告跑）：**修好 6 份，弄坏 0 份**。机制没问题。

**真跑（n=2）：0/2。** 但失败原因**不是**强制合并 —— 代码阶段跑通了。
**是 S2 给的分组本身错了**：它写的是「M1、M7 是同一件事」，真值是「M3、M7」。

**而 S2 自己交代了原因**：

> 「原始材料 M1–M44 **不在可访问路径**，判定依据为 S1-摸底」

查下来是个**设计缺口**：S2 的工具是 `[read, note]`，而语料文件名是 `M3-压缩不如裁剪省.md`
—— 它既没有 `list_corpus` 去看文件名，任务也没叫它读原文。**它只能看着 S1 的摘要做判定。**

### 2.4 B / verify —— 给做判断的人全局视野（瓶颈解除）

**做法**：S2 和 S3 都拿到 `list_corpus` + `read`，并被明确要求**拿原始材料逐组核对**，
发现 S1 的候选错了就改、漏了就补。

**结果：8/11（73%）**，去重逐组 9/11、9/11、9/11、9/11、8/11。

**注意这条与 §2.1 的对称性**：

| | 谁被蒙上了眼 | 后果 |
|---|---|---|
| A / nodup | 集群的**协调者**（root 没有 read） | 4/6 → 0/2 |
| B / mechanical | 流程的**判断者**（S2 只能看摘要） | 0/2 |

**同一个教训，两个形态各撞一次**：全局判断需要全局视野，这不是「集群 vs 流程」的差别。

### 2.5 一个反直觉的发现：S1 的「错误」其实是语料的锅

S1 把重复组配成了 **M1+M7**，真值是 **M3+M7**。看起来是模型读错了 —— 但查语料发现：

- **M3**：「压缩（compact）会真的动历史……相比之下逐轮裁剪的成本低得多」
- **M7**：「同一个取舍换个说法：逐轮裁剪不改任何历史……所以它比压缩便宜」
- **M1**：「context.override 只改这一轮……**它比压缩（compact）便宜**，也比压缩更可预测」

**M1 的正文里也写了「它比压缩便宜」** —— 所以 S1 配 M1+M7 **是有依据的**，
它只是**没发现 M3 也在说同一件事**。

这是我**自己语料的设计瑕疵**：M1 意外地与 M3≡M7 组重叠，让这一组变得有歧义。
它**对两个实验室同样不利**（A 的 M3≡M7 也是 5/6，唯一没满分的一组），所以不构成偏袒，
但它是「为什么 M3≡M7 始终最难」的真正原因。**判据本身没错**（M3 确实该合并），只是难度被无意抬高了。

## 3. 方法发现：判据错了六次（这段可能比结果更值钱）

每一次都是**先看到不可能的通过率或不可能的错误**，才发现判据本身有问题：

| # | 症状 | 真因 | 修法 |
|---|---|---|---|
| 1 | 去重 **0/20**（所有组、两边全灭） | 判据写的是「同组 id 不许出现在**同一行**」，把**正确做法**（合并成一行）判成了错误 | 改成「不许散在**多个条目**里」 |
| 2 | 干扰材料「被盗用」，但模型明明处理对了 | 判据把「提到 M11 说它无关」也算成采信 | 只在**依据行**上抠 id |
| 3 | 一个**合并得完美**的报告被判「M3、M7 没去干净」 | **子串匹配**：`"M37".includes("M3")` 为 true，`"M27".includes("M7")` 为 true | 全部改用词边界 `\bM3\b` |
| 4 | 一份**正确处理了干扰项**的报告被判越界 | 它在附录里写「M11/M21/M41 无关，已排除」并带了一行「依据：…」 | 越界只在**主题节内部**统计采信 |
| 5 | 一份**合并得很好的**报告又被判没去重 | 报告用**粗体段落**而非 bullet 写事实 → `entries` 为空 → **退回第 1 次修掉的旧逻辑** | 「事实单元」= bullet **或**一段连续正文 |
| 6 | 又一份排除声明被判越界 | 排除声明**直接附在最后一个主题节末尾**，没另起一节 | 依据行**紧邻的正文**里有「无关/未纳入」→ 不算采信 |

**第 3 个 bug 让 A 从 1/6 变成 4/6**（判据的一个字符，结论翻三倍）。
**第 5 个 bug 让 B base 从 0/4 变成 2/4**（同一个语义错误的残留，藏在 fallback 分支里）。

> ⚠️ **必须自己警惕的地方**：判据改了 6 次，每次都是「让结果更合理」。
> 这是研究者自由度（researcher degrees of freedom）的典型风险 —— **调判据直到它说出我想听的话**。
> 我的辩护：六次修正都指向**同一族语义错误**（把「提到」当成「采信」、把「合并」当成「重复」、
> 把「节级依据行」当成「事实单元」），而不是为了抬高某个变体；
> 且六次修正对 A 和 B 是**对称施加**的（改完都重判了全部 28 条记录）。
> 但这个风险必须写在台面上，不能藏着。

## 4. 另一类 bug：不是判据错，是**任务文本错**

### 4.1 路径歧义（一个静默的测量假象）

B 的 S4 任务原文是「写出 **work/report.md**」，而 `cwd` **就是** `work/`。
于是模型有时写到 `work/work/report.md` —— 判据读 `cwd/report.md` 读不到，
整次跑被记成「**产物不存在**」，看起来像**能力失败**，实际是**路径歧义**。

实测确认：`demom/work/work/report.md` 真的存在（4462 字节）。
**A 的写手角色里也有同一句话** —— 所以这是个**两边共有的**测量假象。

**修法**：文本统一改成 `report.md`；并在 runner 里加诊断 ——
产物写到了嵌套路径就在记录里明说「这是路径歧义，不是能力失败」，**不许它继续伪装**。

### 4.2 `agent.usage` 不是实时读数（库层缺口）

我想给 B 加一个「单个 agent 烧超过 100 万 token 就中止」的护栏，**结果它从来没触发过**。
查库源码：`agent.usage` 是在 **prompt 结算之后**才累加的
（`src/surfaces/io.ts` 里 `deps.accumulate` 跑在 settle 的 `all` 循环里）。

**所以拿它做实时闸，是拿了一个不会动的读数。** 一个 agent 在**单轮内**失控（423 次工具调用）
对 `agent.usage` 完全不可见 —— 直到它跑完才一次性计入。

**这是本实验发现的库层缺口**（记录，不改库）：实时护栏只能挂在 `tool_call` 事件上。

### 4.3 护栏要按**阶段**设，不是一个全局值

按工具调用次数看，正常阶段 3–99 次、失控的 119/135/423 次 —— **分不开**（99 和 119 差不多）。
但**按阶段就能分开**，因为设计者知道每个位置该有多重：S1 要读 ~44 份材料（60 合理），
S5 只是校一份报告（30 就够）。于是 `Stage.maxCalls` 逐阶段写死。

**这是固定流程能干、集群干不了的事**：每个位置的上限由设计者写死，不需要模型自己克制。

（踩过的坑：S4 一开始设 40，结果它正常干活要 41–62 次 → **我自己的护栏把一次通过的运行掐死了**。
教训：护栏的阈值必须从**实测分布**里取，不能拍脑袋。）

## 5. 文献：为什么会有「流程比集群好」的说法

三个来源，性质不同（**注意：多数是厂商自报，未经第三方复现**）：

### 5.1 Cognition《Don't Build Multi-Agents》(Walden Yan, 2025-06)
<https://cognition.ai/blog/dont-build-multi-agents>

- 核心论点：可靠性由**上下文工程**决定，不是 agent 数量。两条原则：
  > "Share context, and share full agent traces, not just individual messages"
  > "Actions carry implicit decisions, and conflicting decisions carry bad results"
- 例子是**定性**的：两个并行子 agent 写同一个游戏，各按自己的假设写，结果对不上。
- 结论：**单线程线性 agent + 完整上下文**；非并行不可时，子任务要是**只读**的。
- **没有任何 benchmark 数字** —— 是生产经验论证（Devin）。

**后续（关键）**：Cognition 后来发了《Multi-Agents: What's Actually Working》：
> "Our original observations still hold today for **parallel-writer swarms**"

—— 他们反对的是**并行写**，不是集群本身。

### 5.2 Anthropic《How we built our multi-agent research system》(2025-06)
<https://www.anthropic.com/engineering/multi-agent-research-system>

- 自报：多 agent 比单 agent 强 **90.2%**；成本约 **15×** token。
- **最诚实的一句**：
  > "token usage by itself explains 80% of the variance" … "Multi-agent systems work mainly because they help spend enough tokens to solve the problem."
- 他们自己的**不适用场景**：
  > "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit"

### 5.3 Anthropic《Building Effective Agents》(2024-12)
<https://www.anthropic.com/engineering/building-effective-agents>

- **workflow = 预定义代码路径**；**agent = 模型自己决定流程**。
- 立场：「先找最简单的方案」；agent 的代价是「更高成本 + 误差累积」。

### 5.4 实证研究（这些是第三方、有数字）

| 研究 | 关键数字 | URL |
|---|---|---|
| **Towards a Science of Scaling Agent Systems** (2025-12) | **260 组配置**、6 个基准、5 种架构。相对单 agent：**+80.8%（可分解的金融推理）→ −70.0%（顺序规划）**；**没有集中式验证的架构误差传播更严重** | <https://arxiv.org/abs/2512.08296> |
| **The Illusion of Multi-Agent Advantage** | 自动搜索出的 MAS「持续不如 CoT-SC，成本高达 10×」；**专家手工设计的** MAS 在适合分解的任务上：GPT-5 **49.1% → 96.7%** | <https://multi-agent-eval.github.io/> |
| **Single-agent or Multi-agent? Why Not Both?** (UIUC) | **约 80% 的案例是平局**；模型越强，MAS 优势越小；混合路由省 **88.1%** 成本 | <https://arxiv.org/html/2505.18286v1> |
| **Why Do Multi-Agent LLM Systems Fail? (MAST)** NeurIPS 2025 | 1600+ 条轨迹、7 个框架，**14 种失败模式 / 3 大类**：系统设计、**agent 间错位**、任务验证 | <https://arxiv.org/abs/2503.13657> |
| **AgentAsk** | 交接处的**边级错误分类**：**Data Gap / Signal Corruption / Referential Drift / Capability Gap** | <https://arxiv.org/abs/2510.07593> |

## 6. 把文献和数据对起来

| 文献说 | 我的数据 |
|---|---|
| Cognition：并行**写**会让各 agent 的隐含决定互相冲突 | ✅ **复现两次**：A/nodup（协调者失去全局视野）去重全崩；B/mechanical（判断者只看摘要）分组判错 |
| Cognition：子任务应是**只读**的 | ✅ **A 的最优集群正是这个形状**：root 保持全局视野并负责写，scout **只读+记笔记** |
| Anthropic：多 agent 靠「花更多 token」赢 | ❌ **我的数据不支持**：A 473k vs B/verify 470k（剔除失控后）持平，赢的不是钱 |
| Anthropic：需要共享上下文/强依赖的任务不适合多 agent | ⚠️ **任务符合这条，但集群仍赢了 base 流程** —— 因为它的协调者保住了全局上下文 |
| Scaling 论文：无集中式验证的架构误差传播更严重 | ✅ B/base 正是「无验证保真」：S2 对、S4 丢，没人拦 |
| AgentAsk：交接处 Signal Corruption | ✅ **精确命中** B/base 的失败：S2 的合并决定在 S4 处失真 |
| Anthropic：**artifact systems**（子 agent 写持久存储，只回传轻量引用） | ✅ **直接有效**：把 S2 的分组从自由文本改成结构化 JSON，才让代码强制合并成为可能 |
| Scaling 论文：**集中式验证**降低误差传播 | ✅ **最有效的一招**：S6 是纯代码验证 + 修复，不依赖模型自觉 |

**「流程比集群好」这个说法是怎么来的**——我的综合（推断，非定论）：

1. **比错了任务**。文献里的负结果集中在「顺序规划」（−70%）和「并行写」。
2. **自动搜索的集群 = 集成（ensembling）**，不是真分工；手设计的结构才有效。
3. **成本叙事**：Anthropic 的 15× 常被引用，但那是**研究型**任务；我这里是持平的。
4. ★ **最可能的原因：流程的失败更局部、更好修。**
   流程的失败是**局部**的（一个阶段的指令写漏了，改一行就好）；集群的失败是**弥散**的。
   实践中流程迭代更快、更快见效 → 人们得出「流程更好」的结论。
   **我的数据直接支持这条**：B 四轮改进 2/4 → 8/11；而 A 想再提升，得动的是协调者的视野与保真机制，牵一发动全身。
5. ★ **但流程的失败「无界」，集群的失败「有界」**（补样本时才发现的转折）：
   B 的校验阶段能单次烧掉 572 万 tokens（423 次调用）而**无人拦** ——
   因为「阶段数固定」让人误以为它不会失控，**但阶段内部可以失控**。
   集群的预算闸虽然只拦在 spawn 之前，但它至少有个闸。

**所以更准确的说法不是「谁更好」，而是**：

> **流程的错误更早暴露、更好定位；集群的错误更弥散、但更可控。**
> 两者适合的运维方式是**反的**：**流程需要加护栏，集群需要加验证。**

## 7. 怎么让 agent 系统更好（已测结论）

### 对**流程**（B 的四轮，按收益排序）

| 改动 | 效果 | 判据 |
|---|---|---|
| **给做判断的人全局视野**（S2/S3 读原文） | mechanical 0/2 → verify 8/11 | ✅ **收益最大** |
| **结构化交接 + 代码强制保真**（S6） | 离线验证：14 份修好 6 份、弄坏 0 份 | ✅ 结构性有效 |
| **每阶段护栏**（`maxCalls`） | 掐掉 572 万 token 的失控 | ✅ 成本可控 |
| 用**指令**要求保真（preserve） | 2/3，不可靠 | ⚠️ 有用但不如代码 |

### 对**集群**（A 的一条，以及从 B 迁移的假设）

| 改动 | 效果 | 判据 |
|---|---|---|
| **协调者保留全局视野**（root 能读全部材料） | 4/6（去掉后 0/2） | ✅ 有效 |
| 去掉协调者的 read（省 token） | token −43%，ok 0/2 | ❌ **得不偿失** |

**从 B 的成功可以直接迁移到 A 的**（还没测）：
1. **把 scout 的自由文本 note 改成结构化**（对应 artifact systems）
2. **给 A 加一个机械验证器**（对应 S6）—— 现在 A 的 checker 是**软检查**，
   它自称「五项全部通过」而判据说没有，说明**软验证不可靠**
3. **给 A 的每个角色加上限**（对应 `maxCalls`）

> ⚠️ 注意：这 3 条 A 都还没测。所以现在的 73% vs 67% **不代表形态的优劣**，
> 只代表「B 被改过、A 没有」。这是本文最重要的免责声明。

## 8. 局限（分析时必须带上）

1. **A 没被改进过** —— 头号局限。B 改了四轮，A 只改过一轮（nodup，还是个负结果）。
   所以 73% vs 67% 是「改过的 vs 没改的」，不是「流程 vs 集群」。
2. **样本仍然小且不对称**：A 6、B/verify 11、preserve 3、mechanical 2、nodup 2。
   73% vs 67% 的差距**在噪声内**（8/11 vs 4/6）。
3. **判据被调过 6 次**（见 §3）：存在研究者自由度风险，已用「对称施加 + 全量重判」作辩护。
4. **判据只能判结构**：查 id 在不在、组有没有散开，**判不了「说得对不对」**。没引 LLM-as-judge。
5. **A 多了一句提示词**（root 的「你一个人读不完」），B 没有 —— 未控制的变量。
6. **模型只有一个**：文献普遍发现「模型越强，MAS 优势越小」（UIUC 那篇），换强模型结论可能变。
7. **任务只有一个**：读多写少 + 全局综合。按 Scaling 论文，换顺序规划类任务结论可能反转。
8. **语料有个瑕疵**（§2.5）：M1 意外地与 M3≡M7 组重叠，抬高了该组难度。
9. **A 的预算闸从未触发**（`budgetHit 0/6`），集群的护栏未被检验。

## 9. 怎么重跑 / 重判

node demom/bench/prep.ts                                       # 铺现场
